# 上游的导入与升级

GeoCode 把两个上游的源码放在本仓库里,并能持续合并它们的新版本:

| 目录 | 上游 | 原味分支 | 圈选清单 |
|---|---|---|---|
| `kernel/` | [OpenCode](https://github.com/anomalyco/opencode) | `kernel-upstream` | `scripts/kernel-manifest.txt` |
| `desktop/` | [OpenChamber](https://github.com/openchamber/openchamber) | `chamber-upstream` | `scripts/chamber-manifest.txt` |

当前使用的版本见两个目录下 `package.json` 的 `version`。

## 1. 机制

原味分支上只有上游某个版本按清单圈选出来的文件,每导入一个版本就是一个新的提交,没有上游的提交历史。不直接合并上游的历史,是因为清单排除的文件在原味分支上不存在:合并上游历史时,git 会把它们当成上游新增的文件带回来。

`main` 通过 subtree 合并持有两个原味分支。合并基准就在原味分支上:上游没动、GeoCode 改过的地方自动保留,只有两边都改了的地方才会冲突。

- 原味分支只由 `scripts/vendor.sh` 写入。不要在原味分支上,或 `main` 的 `kernel/`、`desktop/` 里手动增删上游文件。
- 原味分支要推到远端。没有它,别的 clone 做不了三方合并。

## 2. 圈选清单

清单每行一项:

| 写法 | 含义 |
|---|---|
| `<路径>` | 取这一项。目录整个取,文件单独取 |
| `!<路径>` | 上游的这一项有意不取 |
| `-<文件名>` | 圈选范围内任何位置叫这个名字的文件都不取 |

`#` 开头的行是注释。不取的理由写在清单里,就近放在对应的行旁边。

`vendor.sh` 按清单从上游下载指定版本、替换原味分支上的文件,然后核对暂存的文件与清单算出的文件是否完全一致。它还会检查两件事:上游有、而清单既没取也没声明不取的条目,会被报出来,由人决定取不取;清单里写的路径在这个版本中不存在,它会拒绝。

清单的每一行都决定下次合并时 `main` 上多出或少掉哪些文件,而且这类增删不会产生冲突,不会有任何提示。所以:

- 默认全取,只排除确认过不需要的。
- 排除之前,确认构建、运行与测试都不读它。
- 圈选错了,改清单、重新导入、再合并一次原味分支;不要在 `main` 上手动补删。

## 3. 首次导入

原味分支与 `main` 没有共同祖先,第一次导入分两步,之后的升级才是普通的 subtree 合并:

```bash
git merge -s ours --no-commit --allow-unrelated-histories <原味分支>   # 只记录合并关系,不改动文件
git read-tree --prefix=<目录>/ -u <原味分支>                           # 把内容读进子目录
git commit
```

导入后 `git diff <原味分支> main:<目录>` 应为空。

## 4. 升级一个上游

一次只升级一个上游。同时升级两个,API 变化、上游的问题与补丁的失效会混在一起,分不清原因。

1. 确认版本。最新版本以上游的发布为准(OpenCode 看 git tag 与 npm 的 `latest`,OpenChamber 看 GitHub Release),不看本地某个旧 clone。
2. 记下现在的补丁面,供第 8 步对比:

   ```bash
   surface() {   # 每行:改动块数、新增行数、文件
     git diff -U0 <原味分支> main:<目录> -- . ':!bun.lock' |
       awk '/^diff --git/{f=substr($3,3)} /^@@/{h[f]++} /^\+[^+]/{a[f]++} END{for(k in h) print h[k]"\t"a[k]+0"\t"k}' |
       LC_ALL=C sort -t$'\t' -k3
   }
   surface > before.tsv
   ```

3. 在临时 worktree 里导入新版本,不动主工作树:

   ```bash
   git worktree add <临时目录> <原味分支>
   (cd <临时目录> && <仓库>/scripts/vendor.sh <kernel|chamber> <上游 tag>)
   ```

   有未归类的新条目时,先改清单再重跑。这一步先不提交。
4. 试合并,不改动任何分支。在临时 worktree 里把暂存的内容做成一个不挂在分支上的提交,拿它试合并:

   ```bash
   probe=$(git commit-tree "$(git write-tree)" -p <原味分支> -m probe)
   git merge-tree --write-tree -X subtree=<目录> main "$probe"
   ```

   退出码 0 表示没有冲突;有冲突时,它会列出冲突的文件。
5. 读上游这一版的改动。合并只在两边改了同一处时才报冲突:上游改了块注释里或提前返回之后的代码、把逻辑挪到别处、给接口或设置页改了名,都会干净地合进来,补丁看上去仍在原处,实际已被绕过。所以合并之前,先读上游在两个版本之间的改动:

   ```bash
   git diff --name-only --diff-filter=M <原味分支> main:<目录> -- . ':!bun.lock' > patched.txt   # 打过补丁的上游文件
   git diff --stat <原味分支> "$probe"                                                       # 上游这一版改了哪些文件
   tr '\n' '\0' < patched.txt | xargs -0 git diff <原味分支> "$probe" --                      # 这些文件里,上游改了什么
   ```

   打过补丁的文件,逐个读上游的改动,对照 GeoCode 在同一处的补丁:补丁是否仍然挡得住,被包住的代码里有没有该保留的新行为。其余文件,找新增或改名的入口(接口路由、IPC 命令、设置页、读取配置与加载插件的地方),它们是第 9 步核对的对象。据第 4、5 步决定升不升,决定升级再在临时 worktree 里提交快照。
6. 合并:`git merge -X subtree=<目录> <原味分支>`。冲突逐处手解,不要整个文件取某一方,那会丢掉同一文件里的其他补丁。
7. 锁文件与依赖:见 §5。
8. 核对补丁:

   ```bash
   git diff --name-status <原味分支> main:<目录>      # 对上游的全部改动
   surface > after.tsv && LC_ALL=C diff before.tsv after.tsv
   ```

   上游删除或改名了打过补丁的文件时,git 不报冲突,补丁随文件一起消失。所以对比前后两份补丁面,少了的行、块数或行数变少的文件,逐个说出原因。
9. 跑检查与真实会话:补丁在不在,由第 8 步回答;补丁还起不起作用,只有运行时的测试与真实会话能回答。升级 OpenChamber 时,还要重新核对 GeoCode 的关闭与访问控制:关闭的接口、IPC 命令与隐藏的设置这几份手写清单是否漏了第 5 步找出的入口,关闭所依托的唯一入口是否仍然唯一,访问控制依赖的上游行为是否变了。升级 OpenCode 时,核对内核仍然只读两处配置:上游有没有新增读取配置的目录、往上级目录查找、加载插件或技能的地方,GeoCode 替换掉的两个内核服务(插件来源与远程配置)接口有没有变。
10. 把这个目录上的全部改动逐项审阅一遍,清单取第 8 步 `git diff --name-status` 的结果,逐个读合并后的文件,不只看 diff。

第 2、5、8、10 步的清单一律取自 git,不靠搜索标记。核对与审阅的结果列成表(文件、合并前后的改动块、变化的原因、审阅结论),逐项确认后,这次升级才算完成。

## 5. 锁文件与依赖

合并后,锁文件先取上游那一份,再用 `bun install` 调和,不要删掉重新生成:

```bash
git show <原味分支>:bun.lock > <目录>/bun.lock
rm -rf <目录>/node_modules && (cd <目录> && bun install)
```

- 删掉重新生成,bun 会把大量间接依赖解析到范围内的最新版本,引入与这次升级无关的变化。
- `node_modules` 要清掉重装。增量安装不会清掉不再使用的旧版本,同一个包的两个版本并存,会引出大量看似补丁失效的类型错误。

`kernel/` 的锁文件与上游那份不同是正常的:上游的锁文件覆盖着没有圈选的包,安装时会被剪掉。调和之后核对两件事:

- 锁文件里解析出的每个版本,都在上游的锁文件里出现过。GeoCode 自己新加的依赖及其间接依赖除外,新加了哪些依赖,看 `git diff <原味分支> main:<目录> -- '*package.json'`;
- 上游为某个包声明了依赖补丁、而这个包仍在使用时,补丁要落在锁文件解析出的那个版本上。版本对不上时,bun 会静默跳过这个补丁。
