# 环境变量

本文档说明 GeoCode 怎样对待环境变量:从哪里取得、交给谁、哪些不认。最关键的决定是:GeoCode 自己的行为不受环境变量控制,环境变量为用户的工具服务;环境在应用启动时定下,各部分只在它的基础上收窄,或加上自己专属的变量。

## 1. 定位

GeoAgent 调用用户装的 conda、GDAL、git 这些工具,要拿到用户在终端里的那份环境:`PATH` 决定找到哪个程序,工具链各自的变量决定它们怎样工作,代理与证书决定能否联网。从访达或开始菜单启动的桌面应用只有系统给的最小环境,所以 GeoCode 要自己找回用户的环境,再交给需要它的部分。

环境变量同时也是一条控制应用的通道。内核与壳所基于的项目,用大量环境变量改配置的位置、换程序、打开调试与遥测,以适应服务器部署与远程使用。GeoCode 是本机一个用户的桌面应用,它的行为只由界面里的设置与配置文件决定,这条通道要关上。仍由环境变量决定的只有几类用户为通用工具与服务准备的:网络的代理与证书(第 2.5 节)、模型与网页搜索服务的密钥(第 2.6 节)、用户在配置文件里以 `{env:名字}` 写明要读的变量,以及找到 git、shell 这类程序的变量。

## 2. 核心设计

### 2.1 源头

应用启动时定下环境,之后启动的进程都从它继承:

- 继承启动环境。macOS 上再以交互的登录 shell 读一次环境,补上启动环境里没有的变量,并合并 `PATH`;Windows 上从注册表读用户与系统的 `PATH`。启动文件改了,要重启应用,agent 执行的命令与 GeoEngine 才拿得到。
- 去掉应用的开关:以 `OPENCODE_`、`OPENCHAMBER_`、`OTEL_`、`BUN_`、`ELECTRON_` 开头的变量,不论来自启动环境还是登录 shell。只在打包出的应用里去掉,开发时的启动脚本正是用这些变量传参数。

开关按前缀去掉,不逐个列名。前两类是上游两个项目自己的,每个版本都可能加新的开关,逐个列名时漏掉的一个会悄悄生效;后三类由 Bun 运行时、OpenTelemetry 库与 Electron 自己读取,名字列不全。其中 `OTEL_` 开头的变量能让内核把运行数据发往别处。代价是用户自己的工具用到的同前缀变量(如 `BUN_INSTALL`)也到不了 agent 执行的命令;终端以登录 shell 启动,会自己读回它们。

### 2.2 应用的目录

GeoCode 的配置、数据、缓存与状态目录固定在主目录下(`PATHS.md` 第 1 节),不认 `XDG_*`。壳的数据目录在启动的第一刻就要定下,那时登录 shell 的环境还没读到;目录若随 `XDG_*` 变,只在 `.zshrc` 里设了它的用户从访达启动时,壳与内核会各用一个目录。`XDG_*` 本身照常交给用户的工具。

### 2.3 三类去处

| 去处 | 拿到的环境 |
|---|---|
| 用户的地盘:agent 执行的命令(经内核)、终端、git、项目动作 | 源头的环境,只去掉 git 与终端为保护自己去掉的几项 |
| GeoEngine 的任务进程:内置的 Python 环境、QGIS 与安装时解包的程序 | 源头环境里网络、账户、临时目录与系统自身的变量,加上任务自己的 |
| 应用自身:主进程、壳服务端、内核 | 源头的环境;应用的开关已经去掉 |

用户的地盘要与用户自己的终端一样。GeoCode 不知道用户的工具需要哪些变量,原样交过去最稳妥。例外是上游原有的保护:git 命令不接受改变仓库位置、弹出密码提示的变量;经应用推送、拉取与克隆时,git 用一份干净的环境,不带代理、证书、凭据与设置里的变量;终端去掉让 shell 执行别的文件的变量。内核进程也带着这份环境,因为 agent 执行的命令继承它;内核另带 GeoCode 交给它的变量:托管的配置、口令、地理工具回调的地址与令牌(`DESKTOP.md` 第 2.3 节)。

GeoEngine 的任务进程运行的是 GeoCode 负责的软件:内置的 Python 环境,与 GeoCode 找到并验证过的 QGIS。用户为自己的工具设的 `PATH`、`PYTHONPATH`、`GDAL_*`、`PROJ_*` 与 conda 的变量,对它们只会指错地方,比如另一套 PROJ 的投影数据库会让坐标变换出错。所以任务进程只保留网络(代理与证书的位置)、账户与临时目录,以及系统自身要的变量,`PATH` 只含系统目录。语言变量也不给:它们不决定无界面运行的 QGIS 用什么语言,界面要的中文由 GeoCode 另行读取。代价是写在环境变量里的云存储凭据(如 `AWS_*`)与 GDAL 的网络选项也到不了 QGIS,读取云上的数据只能靠主目录里的凭据文件。各任务再加上自己的变量(`QGIS.md`、`PYTHON.md` 第 2.5 节)。

### 2.4 设置与项目的变量

这一部分沿用 OpenChamber 的机制,不另起一套:设置的「环境变量」页存下用户的变量,各去处在启动进程时把它们叠加上去。

- 设置页的变量交给内核、GeoEngine、git、终端与项目动作。交给内核与 GeoEngine 时同样去掉应用的开关。GeoEngine 的任务进程只取其中白名单里的几项。
- 设置页上改主目录与临时目录的变量不交给任何去处:它们会挪走内核与 GeoEngine 的文件,而壳不从设置页取变量,仍在原处。
- 项目的变量,与 direnv 这类导出变量的命令,只交给这个项目的 git、终端与项目动作,不交给内核:一个内核服务所有项目。这条命令只取自用户的设置,不取自仓库,只在用户操作时执行。

内核与 GeoEngine 只在启动时读变量。用户分不清哪个功能属于哪一部分,所以设置页保存之后只提示重启 GeoCode,它的按钮重启整个应用,所有去处一次都用上。

### 2.5 代理

代理以 `HTTP_PROXY`、`HTTPS_PROXY` 与 `NO_PROXY` 为准,大小写皆可,本机的回环地址总是直连,不读系统设置里的代理。内核的模型请求、壳服务端与内置的 Python 环境都照这一条:用户给 GeoCode 设一次代理,模型请求、地理工具与 GeoAgent 的脚本都跟着走(`PYTHON.md` 第 2.5 节)。设置页里的代理交给内核、GeoEngine、终端与本地的 git 命令;经应用推送、拉取与克隆时 git 不带代理(第 2.3 节);壳服务端自己的请求只用启动时的环境。窗口与浏览器面板经 Chromium 联网,跟随系统的代理设置。

### 2.6 服务的密钥

模型服务商与网页搜索服务照内核的做法,也能由环境变量接入:环境里有某个服务的密钥变量(如 `OPENAI_API_KEY`),这个服务就显示为已连接,选用时以它为密钥;环境里有 Google Cloud 的项目或 AWS 的配置时,Vertex 与 Bedrock 直接可用。界面里接入的与它们并存,同一个服务两边都有时,界面里存的密钥优先。

## 3. 边界与约束

- 不接受以环境变量给出的应用配置,只能靠这些变量调整的功能不再可用。开发版仍接受它们,外部内核、远程服务器这类只能用环境变量打开的机制在开发版里仍能打开。
- 不替用户改环境:不写用户的 shell 启动文件,不设系统的环境变量。
- agent 执行的命令看得到整份环境,包括其中的密钥与地理工具回调的令牌;命令打印出来的内容会进入对话,随之发给模型服务商。
- Electron 在应用的代码运行之前自己读取的几个变量(如 `ELECTRON_RUN_AS_NODE`)挡不住,只有启动应用的环境带着它们时才起作用。不用 Electron 的熔断开关关掉这一项:git 的凭据助手与 SSH 包装正是带着它运行 GeoCode 的程序本身(`PATHS.md` 第 6 节)。
- 命令所用的 shell 自己读的启动文件(如 zsh 的 `~/.zshenv`)里设的变量,不在 GeoCode 的控制之内。

## 4. 与其他部分的关系

- `DESKTOP.md`:内核与壳服务端,本机的访问控制。
- `PATHS.md`:目录的位置,以及读取的用户环境。
- `GEOENGINE.md`:任务进程怎样运行;`PYTHON.md` 与 `QGIS.md`:各自在白名单上加的变量。
- `DEVELOPMENT.md`:开发版与打包版在环境变量上的差别。
