# Google Earth Engine

本文档说明 GeoCode 怎样让 GeoAgent 使用 Google Earth Engine:为什么不直接经 `shell` 运行 Python,一次运行怎样进行,以及几项核心设计。GeoEngine 的框架(进程、与主进程的通道、环境配置与状态)在 `GEOENGINE.md`,这里只写 GEE 自己的部分。

## 1. 为什么需要 `geerun`

GeoAgent 用 earthengine-api 写 Python 脚本:脚本在本地搭出计算图,计算在 Earth Engine 的服务器上完成,结果以打印、资产、本地的影像或 Google Drive 里的文件交回。这样的脚本经 `shell` 也能运行,但有五件事模型自己做不好,`geerun` 为它们而设:

| | 经 `shell` 直接运行 | 经 `geerun` 运行 |
|---|---|---|
| 运行多久 | 服务器算几分钟时脚本毫无输出,超时设短了误杀正常的计算,设长了卡死的脚本也要等满 | 脚本在等服务器时自动报活,只有真正卡住的才中止(第 3 节) |
| 结果留在哪 | 每次重跑都从原始影像重算;中间结果要自己导出、等待、起名;换一个对话就不知道之前做过什么 | 每次运行属于一个任务,耗时的结果存进任务,内容没变就沿用;答复开头列出任务里已有的资产(第 4 节) |
| 常见的步骤 | 读研究区、合成、下载每次从头写,细节写错常常不报错,只是结果不对 | 用 GeoCode 的 Python 包里写对了的标准函数,GeoCode 也因此知道每一步在做什么(第 5 节) |
| 信息给谁 | 等待、进度与脚本的打印混在一起进入模型的上下文;用户看不到进展;输出过长时,截掉的可能正是结尾的报错 | 等待与进度只给用户,在工具行实时显示;模型只读脚本的打印,过长时保留结尾(第 6 节) |
| 环境 | 模型自己找 Python、猜项目 ID、写初始化;出错时分不清是缺包、没登录、项目不对还是网络不通 | 用设置里配好的 Python 与项目,`ee` 已经初始化;没有就绪时,告诉模型缺什么、谁来补(第 7 节) |

前四项决定 GEE 的工作能不能做长、做对、做得连续,用户能不能看懂它在做什么;环境是前提,配好之后很少再碰到。

## 2. 一次运行

一次调用经过四方:内核里的工具、GeoEngine、用户的 Python 与 Earth Engine 的服务器。

1. 内核检查参数(这一步的用途、任务、脚本),请 GeoEngine 确认环境就绪、项目里的脚本文件存在,再按权限规则询问用户(第 8 节)。项目外的脚本文件等用户允许了它的目录之后再查,先查会透露文件在不在。
2. GeoEngine 用配置的 Python 启动一个进程,把 GeoCode 的运行脚本、这次的请求与 `geocode` 包经标准输入交给它,当前目录是会话目录。一次调用一个进程,脚本结束它就退出,不常驻,也不复用。
3. 运行脚本在请求的出口装上监视,以配置的项目初始化 Earth Engine,读出任务里已有的东西,然后执行 GeoAgent 的脚本;脚本里 `ee` 与 `gc` 直接可用。
4. 运行中,Python 把结构化的事件与脚本的输出写在同一路输出里;GeoEngine 把事件转成给用户的进度,把输出留给模型。
5. 脚本结束,内核把脚本所在的 Python、任务里已有的东西、脚本的打印与运行的结局拼成答复交给模型。

运行默认在前台。GeoAgent 也可以把它放到后台,做法与内核的 shell 命令一致:脚本开始执行时调用就返回,运行结束时同样的答复作为通知插进对话,并唤醒空闲的 GeoAgent;脚本开始之前就失败的(任务被占用、初始化失败等)照前台直接报错。前台的运行也能中途移到后台(内核有这个接口,界面暂不提供)。

前台的运行用户随时可以在对话里停止;后台的运行只在结束、空闲中止或应用退出时停下,应用重启后对话收到它被停止的通知。无论怎样停下,已经提交的导出都在服务器上照常完成。运行的生命周期(空闲时限、任务锁、Python 进程)只由 GeoEngine 管,内核只管谁在等这次运行、何时通知。

## 3. 不被误杀的运行

本地的 Python 只搭计算图、发请求、等结果,真正的等待都在向服务器要结果的那一刻:取值、提交与查询导出。这些请求都经同一个网络库发出,运行脚本守在这个出口上,有请求在等服务器回应就替脚本报活。所以运行时限按空闲计:脚本既没有输出、也没有在等服务器,持续两分钟才中止;服务器算得再久,脚本也不会因为没有输出被中止,GeoAgent 不必为此做任何事。替一个请求报活至多十分钟,卡死的请求因此仍会被中止。

不设总时长:Earth Engine 的速度不稳定,固定的上限会误杀长的下载与导出;只看有没有输出也不行,服务器在算时脚本本来就一声不响。出口看不到的等待(geedim 的分块下载、本地的计算),GeoCode 的函数以进度报活,模型自己写的代码要靠打印。

## 4. 任务与资产

GEE 的工作常要好几天、跨几个对话,耗时的结果要留在云端接着用,就像人自己用 Earth Engine 时把中间结果存成资产再往下做。所以每次运行都属于一个任务。

一个任务是用户资产里的一个文件夹 `GeoCode/<任务名>/`,用户在 Code Editor 里一眼看得懂;GeoCode 只管这个文件夹,不碰其他资产。每次调用都指明任务,`new_task` 新建,`task` 继续。任务名由 GeoAgent 按用途与日期取,如 `taipei-ndvi-20261008`;写错的名字被拒绝,不会被当成新任务。任务名与资产名由字母、数字、`_` 与 `-` 组成,至多 30 个字符:进行中的导出只在它的描述里写着「任务:资产:指纹」,而描述至多 100 个字符。这条规则在内核的工具、GeoEngine 与 Python 包里各写了一份,要一起改。

文件夹在第一次存资产时才建,只查询的任务不在云端留下任何东西。还没有文件夹的任务只在建它的对话里认得:内核按对话记下建过的任务名,不记进项目的 `.geocode/`,因为那里常被提交进 git,不属于项目的对话也无处可放。

一个任务同时只有一次运行,无论来自哪个对话:同一个任务的两次运行会抢着存同一个资产、互相取消对方的导出。不同的任务可以同时运行。

答复开头在脚本所在的 Python 之后是任务空间:已有的资产与它们的标题、说明,以及最近的其他任务,读的是脚本开始之前的样子。GeoAgent 不必另查就知道手头有什么,读这些也不耗计算配额。任务空间只写任务与资产的名字,不写完整路径:完整路径会诱使 GeoAgent 绕过 `gc` 直接存取,那样存下的资产没有说明与指纹。

脚本用 `gc.save` 把影像或表格存进任务,写上标题与说明,等导出完成再读回;`gc.load` 按名字读回本任务或其他任务的资产,也可以按完整路径读任何资产,写入则只经 `gc.save`。存一次,是用第一次运行的时间换之后每次的速度与配额,所以只存检查过、下游要反复用的结果(通常是合成)和用户要留下的结果。删除在云端不可逆,GeoAgent 只在用户明确要求时删除任务与资产。

`gc.save` 按指纹判断内容变没变:没变就直接沿用,变了就替换。指纹算进计算图读取的、`GeoCode` 文件夹里的资产的更新时间,因为上游的资产被替换后,读它的计算图本身并不变。公开数据集不算在内,它们几乎每天入库新影像,算进来的话,早已完成的合成也会显得变了;用户在 `GeoCode` 文件夹以外的资产同样不算。导出在服务器上运行,提交它的进程退出后照常继续;`gc.save` 在导出的描述里写下「任务:资产:指纹」,所以被停止的运行留下的导出,下一次同名的 `gc.save` 认得出来,内容相同就等它,不同就取消它。

## 5. 内置的 Python 包

GeoCode 的 Python 包 `geocode` 把常见的 GEE 操作做成标准的函数,脚本里 `import geocode as gc` 即可使用。没有它,同样是存一个合成、下载一幅影像,每个脚本的写法、出错的方式与打印都不一样,GeoCode 也无从知道脚本做到了哪一步。标准化带来三点:

- 做对:常见的步骤有现成的函数,模型不必知道每个坑。直接写的细节容易出错,错了又常常不报错,只是结果不对,例如研究区的直边被当成测地线弧、`normalizedDifference` 遇到负值就把水体掩掉。函数用错时报错,并说明怎样改。
- 可管理:关键的步骤经过 GeoCode 自己的函数,GeoCode 就知道每一步在做什么。例如资产经 `gc.save` 存进任务,才带着标题、说明与指纹,能被任务空间列出、被下一次运行沿用。
- 及时的反馈:每个函数用一句英文告诉工具行它在做什么,知道进度的带上百分比;结局(存了哪个资产、用了多久、内容没变而沿用)打印给模型。模型自己写的脚本只能靠打印,而打印全都进了模型的上下文。

处理函数以 geedim 为底,参数名、默认值与算法照它,在其上做对模型有意义的封装。函数进出都是普通的 `ee` 对象,模型随时可以混用标准写法;函数的价值放在标准写法难做对的地方:看清影像的覆盖与云况,避开写错也不报错的坑。打印只陈述事实,不替模型下判断。现在的函数覆盖一条核心链路:读研究区、取影像、合成、输出。

- `gc.region` 读本地矢量文件里的一个面要素作研究区。几何用原文件的坐标系建,并关掉测地线:GEE 在经纬度下默认把边当测地线,而 GIS 里的边是本坐标系中的直线,大范围的研究区边界会整体挪动几公里,不报错。旧椭球上的基准(北京 54、Tokyo、ED50 等)与 GEE 读不了的坐标系,由 GeoCode 照 QGIS 逐点换成经纬度再交给 GEE,因为 GEE 自己对旧基准的换算与 QGIS 差几米到几十米。没有坐标系、多个要素、无效几何、几何太复杂时报错,说明在 QGIS 里怎样修。
- `gc.images` 找出数据集在研究区与时间段内的影像,按拍摄汇总成表:同一天、同一颗卫星、同一条轨道的几景先拼起来,再给研究区内的覆盖与无云比例,因为研究区跨图幅时单景的数字既偏低又不能相加。去云的方法与参数照 geedim(Sentinel-2 用 Cloud Score+,Landsat 用 QA 波段);不支持去云的数据集照样可用,明说没有去云;缺 Cloud Score+ 的拍摄标出来,不显示成全是云。
- `gc.composite` 照 geedim 合成,能去云的数据集默认 q-mosaic,按研究区内的无云率排序;`dates` 只用表里挑出的日期或拍摄。合成后检查研究区内的空洞,分成没有影像与被云掩掉两类,给出各自的比例、经纬度范围与修法,覆盖不到 99.9% 时报错终止;研究区只用于排序与检查,结果不裁剪。合成本身没有固定的投影(GEE 按 EPSG:4326、1° 算),所以每个波段挂上它在源数据里自己的网格。
- 输出有三处:`gc.download` 下载成本地的 GeoTIFF,`gc.to_drive` 导出到 Google Drive,`gc.save` 存进任务,后两者等导出完成才返回。三者都不收研究区,裁剪是单独的一步,用标准写法 `clip`。一个文件只能有一套网格,所以默认用影像最细的那个波段的网格,不另换投影,更粗的波段采到这个网格上;要别的网格时显式给出。`gc.save` 与人手动存的资产一样,每个波段保留自己的数据类型。没有边界或没有自己网格的影像会被 GEE 拒绝或按 1° 的像元导出,所以报错说明怎样改。下载不留半截文件,也不覆盖已有的文件。

包不装进用户的 Python,每次运行随请求带去,版本总与应用一致。应用把 GeoEngine 放在自己的归档里,Python 读不到其中的文件,所以包的文件在构建时原样编进 GeoEngine,由运行脚本按文件导入,报错时 traceback 照常写出包里的文件名与行号。工具说明(`geerun.txt`)只讲模型怎么用,要紧处放在开头;核心函数只列签名与一行说明,各个可选参数怎样用、以后的函数,留给专门的技能,不让说明越写越长。

## 6. 运行中的信息

信息按读者分开:运行中的状态给用户,事实给模型。

模型在调用结束时得到一份答复:脚本所在的 Python(路径、版本与 GeoCode 用到的几个包的版本,模型据此在同一个环境里做别的事、照看这个环境)、任务空间、脚本的打印与报错、怎样结束。过长时只留结尾,报错不会被截掉。运行中的计时与进度对它写脚本没有用,不给它。用户在工具行实时看到运行的进展(第 9 节)。

两者在同一路输出里分开:以 GeoCode 的标记开头的行是给 GeoEngine 的事件(任务空间、脚本的起止、正在等待、函数的状态),其余是脚本自己的输出。脚本的输出随到随转给工具行,答复仍在结束时一次给模型。

## 7. 环境

GEE 在用户自己的 Python 里运行,要装齐 earthengine-api、geedim 2.0 以上与 geopandas 1.0 以上:更旧的版本能导入,却缺 `geocode` 包用到的接口;geedim 2.0 只能装在 Python 3.11 以上。下载直接用 geedim,不用 geemap:它的下载只是转调 geedim 已废弃的接口,又带着二十个直接依赖。GeoCode 不安装软件,也不改动用户的环境(`GEOENGINE.md` 第 1 节)。

Python 与 Google Cloud 项目在设置里选和填,项目 ID 只有用户知道,不猜。登录用 Google 账号,可以在设置里登录,也可以由 GeoAgent 在对话里发起。网络跟随用户自己的代理配置。

在设置里登录时,GeoEngine 启动的 Python 在本机回环地址上临时监听一个端口,等浏览器带回授权码,登录结束即关闭,这是 GeoEngine 不开端口的唯一例外。本机的其他程序可以借这个端口提前结束登录,但伪造的授权码没有用:换取凭据要用只有这个 Python 持有的校验码。

检查分本地与远端两段,把缺包、版本过旧、没登录、项目不对、连不上等问题分开报告;没有就绪时,每次调用 `geerun` 都再检查一次,修好之后不必重启应用;已就绪的环境在运行时初始化或启动失败,才重新检查。远端的失败按异常的类型与服务器给的原因归类,不匹配报错的文字,服务器的原话照附。

没有就绪时不执行脚本,告诉 GeoAgent 缺什么、哪些它能做、哪些要请用户做:找 Python、写配置、装包与发起登录,它可以在用户同意后去做;项目 ID 只能问用户。装包的命令按配置的 Python 给出:conda 环境用 conda-forge 安装,不与 pip 混装,因为 rasterio 与 geopandas 读文件的库各自带着一份 GDAL;命令写明最低版本,否则 pip 在旧 Python 上会悄悄装上旧版。Python 低于 3.11 时请 GeoAgent 征得同意后另建环境,而不是升级现有的环境。连不上时本地的环境是好的,提示只说是网络或 Google 的问题,不让 GeoAgent 去重装、改配置或重新登录。

## 8. 权限

`geerun` 执行任意 Python,风险与 `shell` 相同,所以权限与默认规则都照 `shell`:agent 本来就能经 `shell` 运行 Python,只问 `geerun` 守不住什么。它在设置里有自己的一行,用户给 `shell` 设的规则不管它;GeoCode 改动 GeoAgent 对 `shell` 的默认规则时,对 `geerun` 同样改动。规则与「始终允许」都按整个工具:脚本每次不同,按内容记住没有意义。询问之前先查环境与参数,不让用户批准一个注定执行不了的请求。

## 9. 界面

- 标题栏有 GEE 的指示灯;未登录与缺项目和未配置一样显示灰色,不算故障。
- 「地理环境」设置页按 Python、Google 账号、Cloud 项目三步配置。
- 对话里一次调用一行:这一步的说明,运行中加当前状态、进度与计时;展开是脚本的打印与报错。状态说的是 GeoCode 的函数在做什么,不在函数里而又在等服务器时显示正在等待;状态逐条显示,每条停留片刻。放到后台的运行,这一行一直显示运行中,直到结束的通知到来。
- 询问卡片显示请求原因与脚本的前几行(运行文件时只显示文件的路径),不加警示:任意的 Python 靠扫描认不准。

## 10. 验收

- 超过十分钟、期间没有打印的计算或下载能完整跑完;既不输出也不在等服务器的脚本在空闲时限后中止;前台运行时用户随时能停止。
- 后台运行在脚本开始后返回,结束时答复作为通知进入对话并唤醒空闲的 GeoAgent;开始之前就失败的直接报错;应用重启后,对话收到被停止的后台运行的通知。
- 只查询的任务不在用户的 GEE 里留下任何东西;写错的任务名被拒绝;任务在运行时,同一个任务的另一次调用被拒绝,别的任务照常运行;换一个对话指明同一个任务,能读到之前的资产接着做。
- 同样的内容重跑不再导出,内容变了就替换;资产在 Code Editor 里看得到标题与说明。
- 各种投影的研究区(含没有 EPSG 编号的定制投影、跨 180° 经线与极地)边界与 QGIS 一致;跨图幅的研究区,取影像的表给出每次拍摄的覆盖与无云比例;合成有空洞时报错,分清没有影像与被云掩掉;下载与导出得到影像最细波段的网格上的完整结果。
- 答复开头列出任务里已有的东西,不耗计算配额;答复不超过内核的上限,脚本的报错总在结尾;计时与进度只出现在工具行。
- 每种环境问题各自报告,GeoAgent 照提示能补齐它能做的部分,修好后不用重启应用;macOS 与 Windows 都能就绪,中文的路径与打印无误。
