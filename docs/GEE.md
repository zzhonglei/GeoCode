# Google Earth Engine

本文档说明 GeoCode 怎样让 GeoAgent 使用 Google Earth Engine:为什么不直接经 `shell` 运行 Python,一次运行怎样进行,以及几项核心设计。GeoEngine 的框架(进程、与主进程的通道、环境配置与状态)在 `GEOENGINE.md`,这里只写 GEE 自己的部分。

## 1. 为什么需要 `geerun`

GeoAgent 用 earthengine-api 写 Python 脚本:脚本在本地搭出计算图,计算在 Earth Engine 的服务器上完成,结果以打印、资产、本地的影像或 Google Drive 里的文件交回。这样的脚本经 `shell` 也能运行,但有五件事模型自己做不好,`geerun` 为它们而设:

| | 经 `shell` 直接运行 | 经 `geerun` 运行 |
|---|---|---|
| 运行多久 | 服务器算几分钟时脚本毫无输出,超时设短了误杀正常的计算,设长了卡死的脚本也要等满 | 脚本在等服务器时自动报活,只有真正卡住的才中止(第 3 节) |
| 结果留在哪 | 每次重跑都从原始影像重算;中间结果要自己导出、等待、起名;换一个对话就不知道之前做过什么 | 每次运行属于一个任务,耗时的结果存进任务,内容没变就沿用;答复里先列出任务里已有的资产(第 4 节) |
| 常见的步骤 | 读研究区、合成、下载每次从头写,细节写错常常不报错,只是结果不对 | 用 GeoCode 的 Python 包里写对了的标准函数,GeoCode 也因此知道每一步在做什么(第 5 节) |
| 信息给谁 | 等待、进度与脚本的打印混在一起进入模型的上下文;用户看不到进展;输出过长时,截掉的可能正是结尾的报错 | 等待与进度只给用户,在工具行实时显示;模型只读脚本的打印,过长时保留结尾(第 6 节) |
| 环境 | 模型自己找 Python、猜项目 ID、写初始化;出错时分不清是缺包、没登录、项目不对还是网络不通 | 用 GeoCode 内置的 Python 环境与设置里填的项目,`ee` 已经初始化;没有就绪时,告诉模型缺什么、谁来补(第 7 节) |

## 2. 一次运行

一次调用经过四方:内核里的工具、GeoEngine、内置环境的 Python 与 Earth Engine 的服务器。

1. 内核检查参数(这一步的用途、任务、脚本),请 GeoEngine 确认环境就绪、项目里的脚本文件存在,再按权限规则询问用户(第 8 节)。项目外的脚本文件等它的目录获准访问之后再查,先查会透露文件在不在。
2. GeoEngine 用内置环境 `base` 的 Python 启动一个进程(第 7 节),把 GeoCode 的运行脚本与这次的请求经标准输入交给它,当前目录是会话目录。一次调用一个进程,脚本结束它就退出,不常驻,也不复用。
3. 运行脚本在请求的出口装上监视,用固定位置的凭据与配置的项目初始化 Earth Engine(第 7 节),读出任务里已有的东西,然后执行 GeoAgent 的脚本;脚本里 `ee` 已经初始化,可以直接使用,GEE 的函数可以导入(第 5 节)。
4. 运行中,Python 把结构化的事件与脚本的输出写在同一路输出里;GeoEngine 把事件转成给用户的进度,把输出留给模型。
5. 脚本结束,内核把 Python 的版本、任务里已有的东西、脚本的打印与运行的结局拼成答复交给模型。

运行默认在前台。GeoAgent 也可以把它放到后台,做法与内核的 shell 命令一致:脚本开始执行时调用就返回,运行结束时同样的答复作为通知插进对话,并唤醒空闲的 GeoAgent;脚本开始之前就失败的(任务被占用、初始化失败等)照前台直接报错。前台的运行也能中途移到后台:界面上「移到后台」的按钮在有 shell 命令、子 agent 或 `geerun` 运行时出现,它把这一轮里所有阻塞的运行一并移到后台。与 shell 一样,等用户批准时按下不起作用;脚本开始之前就移到后台的,开始之前的失败也作为通知到来。

前台的运行用户随时可以在对话里停止。后台的运行用户可以在条带里停止,对话收到它被用户停止的通知,并唤醒空闲的 GeoAgent,与后台命令被停止一样。此外它只在结束、空闲中止或应用与内核退出时停下。因应用或内核退出而停下的后台运行,内核再次启动时对话收到它因重启停止的通知,不唤醒 GeoAgent,也不重跑。内核自己的重启恢复(连同接着做没做完的回合)只在服务模式下运行,GeoCode 以 `serve --stdio` 启动内核,不做。内核回收空闲工作目录的服务,不影响后台的运行与它的通知。无论怎样停下,已经提交的导出都在服务器上照常完成。运行的生命周期(空闲时限、任务锁、Python 进程)只由 GeoEngine 管,内核只管谁在等这次运行、何时通知。

## 3. 不被误杀的运行

本地的 Python 只搭计算图、发请求、等结果,真正的等待都在向服务器要结果的那一刻:取值、提交与查询导出。这些请求都经同一个网络库发出,运行脚本守在这个出口上,有请求在等服务器回应就替脚本报活。所以运行时限按空闲计:脚本既没有输出、也没有在等服务器,持续两分钟才中止;服务器算得再久,脚本也不会因为没有输出被中止,GeoAgent 不必为此做任何事。替一个请求报活至多十分钟,卡死的请求因此仍会被中止。

不设总时长:Earth Engine 的速度不稳定,固定的上限会误杀长的下载与导出;只看有没有输出也不行,服务器在算时脚本本来就一声不响。出口看不到的等待(geedim 的分块下载、本地的计算),GeoCode 的函数以进度报活,模型自己写的代码要靠打印。

## 4. 任务与资产

GEE 的工作常要好几天、跨几个对话,耗时的结果要留在云端接着用,就像人自己用 Earth Engine 时把中间结果存成资产再往下做。所以每次运行都属于一个任务。

一个任务是用户资产里的一个文件夹 `GeoCode/<任务名>/`,用户在 Code Editor 里一眼看得懂;GeoCode 只管这个文件夹,不碰其他资产。每次调用都指明任务,`new_task` 新建,`task` 继续。任务名由 GeoAgent 按用途与日期取,如 `taipei-ndvi-20261008`;写错的名字被拒绝,不会被当成新任务。任务名与资产名由字母、数字、`_` 与 `-` 组成,至多 30 个字符:进行中的导出只在它的描述里写着「任务:资产:指纹」,而描述至多 100 个字符。这条规则在内核的工具、GeoEngine 与 Python 包里各写了一份,要一起改。

文件夹在第一次存资产时才建,只查询的任务不在云端留下任何东西。还没有文件夹的任务只在建它的对话里认得:内核按对话记下建过的任务名,不记进项目的 `.geocode/`,因为那里常被提交进 git,不属于项目的对话也无处可放。

一个任务同时只有一次运行,无论来自哪个对话:同一个任务的两次运行会抢着存同一个资产、互相取消对方的导出。不同的任务可以同时运行。

答复开头在 Python 的版本之后是任务空间:已有的资产与它们的标题、说明,以及最近的其他任务,读的是脚本开始之前的样子。GeoAgent 不必另查就知道手头有什么,读这些也不耗计算配额。任务空间只写任务与资产的名字,不写完整路径:完整路径会诱使 GeoAgent 绕过 GEE 的函数直接存取,那样存下的资产没有说明与指纹。

脚本用 `gee.save` 把影像或表格存进任务,写上标题与说明,等导出完成再读回;`gee.load` 按名字读回本任务或其他任务的资产,也可以按完整路径读任何资产,写入则只经 `gee.save`。存一次,是用第一次运行的时间换之后每次的速度与配额,所以只存检查过、下游要反复用的结果(通常是合成)和用户要留下的结果。删除在云端不可逆,GeoAgent 只在用户明确要求时删除任务与资产。

`gee.save` 按指纹判断内容变没变:没变就直接沿用,变了就替换。指纹算进计算图读取的、`GeoCode` 文件夹里的资产的更新时间,因为上游的资产被替换后,读它的计算图本身并不变。公开数据集不算在内,它们几乎每天入库新影像,算进来的话,早已完成的合成也会显得变了;用户在 `GeoCode` 文件夹以外的资产同样不算。导出在服务器上运行,提交它的进程退出后照常继续;`gee.save` 在导出的描述里写下「任务:资产:指纹」,所以被停止的运行留下的导出,下一次同名的 `gee.save` 认得出来,内容相同就等它,不同就取消它。

## 5. GEE 的函数

GEE 的函数是 GeoCode 的 Python 包 `geocodekit` 的子包 `gee`(`GEOCODEKIT.md`),脚本里 `import geocodekit.gee as gee` 即可使用;为什么要有标准的函数、所有函数共同的约定,见那一篇的第 1、4 节。`gee` 只能在 `geerun` 里用:它要运行脚本初始化好的 Earth Engine 与任务。

直接写 GEE 的脚本,有些细节错了也不报错,只是结果不对,例如研究区的直边被当成测地线弧、合成没有自己的网格而按 1° 的像元导出。处理函数以 geedim 为底,参数名、默认值与算法照它,在其上做对模型有意义的封装;函数的价值放在标准写法难做对的地方:看清影像的覆盖与云况,避开写错也不报错的坑。核心链路是读研究区、取影像、合成、输出:

- `gee.region` 读本地矢量文件里的一个面要素作研究区。几何用原文件的坐标系建,并关掉测地线:GEE 在经纬度下默认把边当测地线,而 GIS 里的边是本坐标系中的直线,大范围的研究区边界会整体挪动几公里,不报错。旧椭球上的基准(北京 54、Tokyo、ED50 等)与 GEE 读不了的坐标系,由 GeoCode 照 QGIS 逐点换成经纬度再交给 GEE,因为 GEE 自己对旧基准的换算与 QGIS 差几米到几十米。没有坐标系、多个要素、无效几何、几何太复杂时报错,说明在 QGIS 里怎样修。
- `gee.images` 找出数据集在研究区与时间段内的影像,按拍摄汇总成表:同一天的几景先拼起来,Sentinel-2 与 Landsat 还分卫星与轨道,再给研究区内的覆盖与无云比例,因为研究区跨图幅时单景的数字既偏低又不能相加。去云的方法与参数照 geedim(Sentinel-2 用 Cloud Score+,Landsat 用 QA 波段);不支持去云的数据集照样可用,明说没有去云;缺 Cloud Score+ 的拍摄标出来,不显示成全是云。
- `gee.composite` 照 geedim 合成,能去云的数据集默认 q-mosaic,按研究区内的无云率排序;`dates` 只用表里挑出的日期或拍摄。合成后检查研究区内的空洞,分成没有影像与被云掩掉两类,给出各自的比例、经纬度范围与修法,覆盖不到 99.9% 时报错终止;研究区只用于排序与检查,结果不裁剪。合成本身没有固定的投影(GEE 按 EPSG:4326、1° 算),所以每个波段挂上它在源数据里自己的网格。
- 输出有三处:`gee.download` 下载成本地的 GeoTIFF,`gee.to_drive` 导出到 Google Drive,`gee.save` 存进任务,后两者等导出完成才返回。三者都不收研究区,裁剪是单独的一步,用标准写法 `clip`。一个文件只能有一套网格,所以默认用影像最细的那个波段的网格,不另换投影,更粗的波段采到这个网格上;要别的网格时显式给出。`gee.save` 与人手动存的资产一样,每个波段保留自己的数据类型。没有边界或没有自己网格的影像会被 GEE 拒绝或按 1° 的像元导出,所以报错说明怎样改。下载不留半截文件(被停止的运行来不及收尾,它留下的临时文件由 GeoEngine 在进程结束后删掉),也不覆盖已有的文件。

工具说明(`geerun.txt`)只讲模型怎么用,要紧处放在开头;列哪些函数、怎样列,照 `GEOCODEKIT.md` 第 3 节。

## 6. 运行中的信息

信息按读者分开:运行中的状态给用户,事实给模型。

模型在调用结束时得到一份答复:Python 的版本、任务空间、脚本的打印与报错、怎样结束。打印放不下时,先把连着出现三次以上的同一行合成一行并注明多出的次数,仍放不下再只留结尾,报错不会被截掉。运行中的计时与进度对它写脚本没有用,不给它。用户在工具行实时看到运行的进展(第 9 节)。

两者在同一路输出里分开:以 GeoCode 的标记开头的行是给 GeoEngine 的事件(任务空间、脚本的起止、正在等待、函数的状态、下载未完成的文件),其余是脚本自己的输出。脚本的输出随到随转给工具行,答复仍在结束时一次给模型。

## 7. 环境

GEE 只在内置 Python 环境的 `base` 里运行(`PYTHON.md` 第 8 节),不用 GeoAgent 的工作环境,也不支持用户自己的 Python。包的版本由锁定清单定下,GEE 的函数用到的 earthengine-api 与 geedim 的接口只需要对一个确定的版本核对;GeoAgent 往工作环境里装的包碰不到 GEE。代价是脚本只能用预装的包,工具说明写明这一点:要别的包的处理放到 `geerun` 之外,用工作环境去做。答复只写 Python 的版本,不写解释器的路径:知道了 `base` 在哪,GeoAgent 就可能拿它做自己的事、往里装包。下载直接用 geedim,不用 geemap:它的下载只是转调 geedim 已废弃的接口,又带着二十个直接依赖。

GEE 的检查等内置环境就绪才开始,在那之前状态停在检查中;环境准备失败时也一直停在检查中,窗口这时显示出错页,不经窗口的调用只得到「还在检查」。环境就绪时预热已经做完(`PYTHON.md` 第 6 节),检查与第一次运行碰不上冷加载:检查有时限,运行按空闲计时,而第一次加载动态库时脚本可能几十秒一声不响。GeoEngine 运行 `base` 的方式与运行内置环境的其他地方相同:隔离模式,只给网络相关的变量与 `HOME`(`PYTHON.md` 第 6.1 节)。

Google Cloud 项目在设置里填,写进 `machine.json` 的 `"gee": "<项目 ID>"`;项目 ID 只有用户知道,不猜。登录用 Google 账号,只在设置里完成:GeoAgent 不发起登录,因为登录的命令要写明 `base` 的解释器。

凭据只认 earthengine-api 自己的那一份,位置固定为主目录下的 `.config/earthengine/credentials`(macOS 按 `HOME`,Windows 按 `USERPROFILE`),设置里的登录写的就是它。检查与运行都从这个文件显式加载凭据,不像 earthengine-api 缺省那样退回 Google Cloud 的默认凭据(ADC):ADC 可以经环境变量指向一个服务账号,让 GEE 悄悄换一个身份;gcloud 登录得到的凭据常缺 Earth Engine 的授权范围;隔离运行时,它在两个平台上找得到的程度也不同。没有这个文件就是没登录,即使本机有 ADC。

Earth Engine 的请求与 geedim 的请求(`gee.download` 的分块下载等)都只按代理变量走,与模型服务的请求一样;不读系统设置里的代理。这是内置环境自己的做法(`PYTHON.md` 第 6.1 节),GEE 不另作处理。

在设置里登录时,GeoEngine 启动的 Python 在本机回环地址上临时监听一个端口,等浏览器带回授权码,登录结束即关闭。本机的其他程序可以借这个端口提前结束登录,但伪造的授权码没有用:换取凭据要用只有这个 Python 持有的校验码。

检查分本地与远端两段,把没登录、没有项目、项目不对、连不上等问题分开报告;没有就绪时,每次调用 `geerun` 都再检查一次,修好之后不必重启应用;已就绪的环境在运行时初始化或启动失败,才重新检查。远端的失败按异常的类型与服务器给的原因归类,不匹配报错的文字,服务器的原话照附。

没有就绪时不执行脚本,告诉 GeoAgent 缺什么、谁来补:没登录或凭据失效时,请用户在设置里登录;项目 ID 只能问用户,得到之后 GeoAgent 可以自己写进配置。连不上时提示只说连不上 Google,Earth Engine 的服务器出错或限流时只说它正忙,不附别的:网络的情况太多,怎样处理留给 GeoAgent 与用户在对话里商量。

## 8. 权限

`geerun` 执行任意 Python,风险与 `shell` 相同,所以权限与默认规则都照 `shell`:agent 本来就能经 `shell` 运行 Python,只问 `geerun` 守不住什么。它在设置里有自己的一行,用户给 `shell` 设的规则不管它;GeoCode 改动 GeoAgent 对 `shell` 的默认规则时,对 `geerun` 同样改动。规则与「始终允许」都按整个工具:脚本每次不同,按内容记住没有意义。询问之前先查环境、参数与脚本文件,不让用户批准一个注定执行不了的请求;任务被占用、不存在或正在运行,要到运行开始时才查得出。

## 9. 界面

- 标题栏有 GEE 的指示灯;未登录与缺项目显示灰色,不算故障:刚装好应用的用户就是未登录。
- 「地理环境」设置页按 Google 账号、Cloud 项目两步配置;就绪时只显示项目 ID,环境是 GeoCode 自带的,版本与路径对用户没有意义。
- 对话里一次调用一行:这一步的说明,运行中加当前状态、进度与计时;展开是脚本的打印与报错。状态说的是 GeoCode 的函数在做什么,不在函数里而又在等服务器时显示正在等待;状态逐条显示,每条停留片刻。放到后台的运行,这一行一直显示运行中,直到结束的通知到来;同时它像后台命令一样列在输入框上方的条带里,写着说明与已运行的时长,能单条或全部停止,会话列表里也有它的标记,会话的计时持续到它结束。
- 询问卡片显示请求原因与脚本的前几行(运行文件时只显示文件的路径),不加警示:任意的 Python 靠扫描认不准。批准与 `qgisrun` 一样只在卡片上(`QGIS.md` 第 8 节),因为托盘看不到脚本;这一点与 `shell` 不同。

## 10. 验收

- 超过十分钟、期间没有打印的计算或下载能完整跑完;既不输出也不在等服务器的脚本在空闲时限后中止;前台运行时用户随时能停止。
- 后台运行在脚本开始后返回,结束时答复作为通知进入对话并唤醒空闲的 GeoAgent,运行中它所在工作目录的服务被回收也一样;开始之前就失败的直接报错。
- 只有 `geerun` 在前台运行时也能移到后台;后台运行在条带里与后台命令并列,能在那里停止,对话收到被用户停止的通知;会话列表里有它的标记、计时持续到它结束,重新载入或另开窗口后依然如此。
- 只查询的任务不在用户的 GEE 里留下任何东西;写错的任务名被拒绝;任务在运行时,同一个任务的另一次调用被拒绝,别的任务照常运行;换一个对话指明同一个任务,能读到之前的资产接着做。
- 同样的内容重跑不再导出,内容变了就替换;资产在 Code Editor 里看得到标题与说明。
- 各种投影的研究区(含没有 EPSG 编号的定制投影、跨 180° 经线与极地)边界与 QGIS 一致;跨图幅的研究区,取影像的表给出每次拍摄的覆盖与无云比例;合成有空洞时报错,分清没有影像与被云掩掉;下载与导出得到影像最细波段的网格上的完整结果。
- 答复列出任务里已有的东西,不耗计算配额;答复不超过内核的上限,脚本的报错总在结尾;运行中的计时与进度只出现在工具行。
- 运行中重新载入窗口或另开窗口,工具行在几秒内恢复状态、计时与脚本已打印的内容,脚本在这期间一直等服务器、没有输出也一样。
- 每种环境问题各自报告,GeoAgent 照提示能补齐它能做的部分,修好后不用重启应用;macOS 与 Windows 都能就绪,中文的路径与打印无误。
- 设了代理变量时,检查、运行与 `gee.download` 的请求都经过代理,脚本直接用 geedim 也一样;只在系统设置里配了代理时,它们不经过代理。
- 第一次启动与重装内置环境之后,GEE 的检查在环境就绪之后才开始、不超时,马上开始的第一次运行也不被空闲时限中止。
- GeoAgent 往工作环境里装的包影响不到 GEE;本机只有 Google Cloud 的默认凭据、没有 Earth Engine 自己的凭据时报未登录。
