# Google Earth Engine

本文档说明 GeoCode 怎样让 GeoAgent 使用 Google Earth Engine:为什么不直接经 `shell` 运行 Python,一次运行怎样进行,以及几项核心设计。GeoEngine 的框架(进程、与主进程的通道、环境配置与状态)在 `GEOENGINE.md`,这里只写 GEE 自己的部分。

## 1. 为什么需要 `geerun`

GEE 的工作方式是:GeoAgent 用 earthengine-api 写 Python 脚本,脚本在本地搭出计算图,计算在 Earth Engine 的服务器上完成,结果以打印、存成的资产、下载到本地的影像或导出到 Google Drive 的文件交回。

GeoAgent 本来就能经 `shell` 运行任何 Python,GEE 脚本也不例外。但这样运行,有五件事模型自己做不好,`geerun` 就是为它们而设的工具:

| | 经 `shell` 直接运行 | 经 `geerun` 运行 |
|---|---|---|
| 运行多久 | 一次取值或导出可能在服务器上算几分钟而毫无输出,命令的超时设短了误杀正常的计算,设长了卡死的脚本也要等满 | 按空闲计时,脚本在等 Earth Engine 时自动报活,服务器算多久都不中止;真正卡住的才中止(第 3 节) |
| 结果留在哪 | 每次重跑都从原始影像重算,费时也费配额;中间结果要自己写导出、等待、起名;换一个对话,之前做过什么一概不知 | 每次运行属于一个任务,`gc.save` 把耗时的结果存进任务,内容没变就直接沿用;答复开头列出任务里已有的资产,换对话也能接着做(第 4 节) |
| 常见的步骤 | 去云、合成、读研究区、下载、导出每次从头写,细节容易写错,错了又常常不报错,只是结果不对 | 用 GeoCode 的 Python 包 `geocode` 里的函数,一个函数做对一件事,用错时报错并说明怎样改(第 5 节) |
| 信息给谁 | 脚本的打印、库自己的输出与等待混在一起;用户在运行时看不到进展;输出过长时,被截掉的可能正是结尾的报错 | 等待与导出的进度只给用户,在工具行实时显示;模型只读脚本的打印,过长时保留结尾(第 6 节) |
| 环境 | 模型自己找装了 earthengine-api 的 Python、猜项目 ID、写初始化;出错时分不清是缺包、没登录、项目不对还是网络不通,常以重装或重新登录了事 | 用设置里配好的 Python 与项目,脚本开始时 `ee` 已经初始化;没有就绪时,告诉模型具体缺什么、哪些它能做、哪些要请用户做(第 7 节) |

前四项是 `geerun` 的核心:它们决定 GEE 的工作能不能做长、做对、做得连续,用户又能不能看懂它在做什么。环境一项是前提,一次配好之后很少再碰到。

## 2. 一次运行

一次 `geerun` 调用经过四方:内核里的工具、GeoEngine、用户的 Python 与 Earth Engine 的服务器。

1. 内核检查参数(这一步的用途、任务、脚本)与这个对话建过的任务,请 GeoEngine 确认环境就绪、脚本文件存在,再按权限规则询问用户(第 8 节)。
2. GeoEngine 用配置的 Python 启动一个任务进程,把 GeoCode 的运行脚本、这次的请求与 `geocode` 包一起经标准输入交给它,当前目录是会话目录。一次调用一个进程,脚本结束它就退出,不常驻,也不在调用之间复用。
3. 运行脚本以配置的项目初始化 Earth Engine,在请求的出口装上监视,读出任务里已有的东西,然后执行 GeoAgent 的脚本。脚本直接使用 `ee` 与 `gc`,不必自己初始化。
4. 运行中,Python 把结构化的事件与脚本自己的输出一起写回;GeoEngine 把事件转成给用户的进度,把脚本的输出留给模型。
5. 脚本结束,内核把任务里已有的东西、脚本的打印与运行的结局拼成一份答复交给模型。

本地的 Python 只搭计算图、发请求、等结果,真正的计算都在服务器上。所以运行中最要紧的,是知道脚本此刻是在等服务器,还是卡住了(第 3、6 节)。

## 3. 不被误杀的运行

运行时限按空闲计,不设总时长。GEE 的筛选与计算只在本地搭出计算图,真正的等待都在向服务器要结果的那一刻(取值、下载、提交导出),而这些请求都经同一个网络库发出。运行脚本守在这个出口上,有请求在等服务器回应就替脚本报活,所以服务器算得再久,脚本也不会因为没有输出被中止,GeoAgent 不必为此做任何事。一个请求等了太久不再算活着,卡死的请求因此仍会被中止。脚本既没有输出、也没有在等服务器,持续一段时间才中止;脚本在本地做耗时的事时,打印进度就能保持运行。用户随时可以在对话里停止;已经提交的导出在服务器上照常运行。

不设总时长,是因为 Earth Engine 的速度不稳定,固定的上限会误杀长的下载与导出;只看有没有输出也不行,服务器在算时脚本本来就一声不响。出口之外还有几处等待看不到,见第 6 节。

## 4. 任务与资产

GEE 的工作常要好几天、跨几个对话,耗时的结果要留在云端接着用:人自己用 Earth Engine,也是把中间结果存成资产再往下做。GeoCode 在配置的 Cloud 项目下用一个文件夹 `projects/<项目>/assets/GeoCode/` 收纳它产生的资产,其中每个文件夹是一个任务,任务的资产都在里面。用户在 Code Editor 的资产面板里一眼看得出哪些是 GeoCode 建的、每个任务里有什么。GeoCode 只管理这个文件夹,不碰项目里的其他资产,也不碰用户的其他 Cloud 项目。

每次调用 `geerun` 都要给出这一步的用途、一个任务与一段脚本,缺一项或多给都直接报错,说明怎样改,不另设别的调用方式:`task` 在已有的任务里继续,`new_task` 新建一个,脚本是内联的代码或 `.py` 文件。任务名就是文件夹名,由 GeoAgent 取,工具说明要它写出用途与日期(如 `taipei-ndvi-20261008`)。GeoCode 不改动名字,只检查它由字母、数字、`_` 与 `-` 组成,至多 30 个字符。Earth Engine 自己允许 100 个字符,但进行中的导出只在它的描述里写着目标,GeoCode 把「任务:资产:指纹」写在那里,描述至多 100 个字符,所以任务名与资产名各限 30 个。新建时同名的任务已经存在,或这个对话已经建过同名的任务,就拒绝,提示在那个任务里继续或换个名字。

很多任务只做查询与统计,结果打印出来或下载到本地,并不产生资产,所以执行时不创建任何东西:任务的文件夹在第一次存资产时才建,`GeoCode` 文件夹不存在时一并建出;导出在提交时被拒或等待中失败,而这次新建的文件夹仍是空的,就删掉它。不等的导出在脚本结束后才失败,或运行在等待中被停止,文件夹可能留空,下一次运行的开头会报告失败的导出。

还没有文件夹的任务只在建它的对话里存在:内核按对话记下这个对话建过的任务名,存在内核自己的数据库里(插件的键值存储),重启应用后仍在,对话删除后留下的几个名字无害,不另清理。继续一个任务,要么它在 `GeoCode` 里有文件夹(存过资产,哪个对话都能继续),要么这个对话建过它;都不是就拒绝,脚本不执行,并列出最近更新的任务。写错的名字因此不会被当成一个新任务。任务没有对应的本地目录,记录也不写进项目:脚本仍是内联的代码或 `.py` 文件,当前目录仍是会话目录。

GeoAgent 每次拿到的答复由两部分组成:开头是 GeoCode 在执行脚本之前、同一次运行里读出的任务空间,其后是脚本的打印与报错。空间写明这个任务是新建还是继续、已有的资产(类型、波段、保存时间、标题与说明)、进行中的导出与资产上次保存之后失败的导出,以及最近更新的另外三个任务与其他任务的总数。GeoAgent 不必另查就知道手头有什么、哪些还在导出、可以跨任务取用哪些;更早的任务由用户提起。读这些只用 Earth Engine 的元数据,不做计算,不耗用户的计算配额。平常一个任务的资产与说明不过十几 KB;过长的说明截短,空间至多占答复上限的一半,超出时只省略末尾的资产行,其余留给脚本的打印。空间里只有任务与资产的名字,不写它们在 Earth Engine 里的完整路径:GeoAgent 按名字经 GeoCode 的函数存取,完整路径只用于用户给出的 `GeoCode` 以外的资产。

脚本经 GeoCode 的包存取资产(`import geocode as gc`),交给 GeoAgent 的只有两个函数,任务与资产的名字已在答复的开头,不另设函数去查。`gc.save` 把影像或表格存进本任务,写上 `title` 与 `description`,用户在 Code Editor 的资产详情里看得到;另记所属的任务、保存时间与内容的指纹,换了对话的 GeoAgent 读这些就知道每个资产是什么。指纹由计算图、网格,以及计算图读取的 `GeoCode` 资产各自的更新时间算出;公开数据集不算在内,它们几乎每天入库新影像,算进来的话,早已完成的合成也会显得变了。文件夹不能带属性,所以说明都在资产上。GEE 的计算图在导出之前从没被完整算过,导出就是第一次把它算出来,要排队,也要时间。`gc.save` 默认等导出完成,再返回从资产读出的数据:不等的话,下游的每个请求都会从源数据把上游再算一遍,与导出重复,等待只花时间,不花配额。同名而指纹相同的资产直接沿用,不再导出,脚本重跑时这一行几乎不花什么;内容变了就替换旧的,并打印一句警告;同一个资产已有导出在进行时,内容相同就等它,不同就取消它。存完就结束的最终结果可以不等。`gc.load` 按名字读:「资产」是本任务的,「任务/资产」是其他任务的,`projects/` 开头的是用户给的完整路径。`GeoCode` 以外的资产由用户告诉 GeoAgent 完整的路径,GeoAgent 不去浏览。GeoCode 的函数只往本任务的文件夹里写资产;GeoAgent 不主动删除任务与资产:删除在云端,不可逆,只在用户明确要求时做。

存中间结果是用第一次运行的时间换之后每次的速度与配额:导出走批处理,要排队,又比在线计算慢,第一次运行因此更慢;之后的运行直接读算好的像元,不再重算上游。所以工具说明要 GeoAgent 先探索、不存,合成经检查确认无误、下游还要反复用到时再存一次,通常就在合成之后,用户要留下的结果也存;一次性的查看、便宜的步骤、只要粗略或局部结果的下游与还在调整的步骤不存;在线计算超时或超出内存时,先存上游再往下算。GeoCode 不做结果缓存:引用资产的请求只写路径,资产被替换以后同样的请求会拿到旧的结果,不报错,只是结果错。`gc.save` 判断内容变没变时也会遇到同样的事,所以指纹里算进了读取的 `GeoCode` 资产的更新时间。

## 5. 内置的 Python 包

GeoAgent 直接用 earthengine-api 写脚本,有许多细节容易写错,而且错了往往不报错,只是结果不对:研究区转成经纬度后,原来的直边按测地线解释成了弧线;`normalizedDifference` 遇到负值就掩掉像元,水体因此缺失;导出提交之后不等它完成就往下算,下游的每个请求都把上游从源数据再算一遍。GeoCode 把这些收进自己的 Python 包 `geocode`,脚本里 `import geocode as gc` 就能用:一个函数把一件事做对,GeoAgent 不必每次从头写一遍,也不必知道每个坑。

包里的函数分两类:

- 存取任务的 `gc.save` 与 `gc.load`:把耗时的结果存成带说明与指纹的资产,按名字读回(第 4 节)。
- 处理函数:读取研究区、下载影像、导出到 Google Drive、检查覆盖度等,以 geedim 为底,只写面向模型的那一层,逐个设计(第 11 节)。

函数都照几条规则写:

- 交给 GeoAgent 的只有包的 `__all__` 里列出的名字,写进工具说明;其余模块以下划线开头,GeoAgent 用不着,也不必知道。
- 用错时报错,并说明怎样改,例如缺了标题与说明、存影像没给范围与分辨率、要读的资产还在导出。
- 过程中的状态以事件报告给用户,结局打印给模型(第 6 节)。
- 只用标准库与 GeoCode 要求装好的三个包(第 7 节),不依赖别的第三方 GEE 库。

包不装进用户的 Python:GeoEngine 不改动用户的环境。它随 GeoEngine 一起构建,每次运行随请求交给 Python,由运行脚本按文件导入,所以版本总与应用一致,用户在别处运行的脚本也碰不到它;脚本出错时,traceback 照常写出包里的文件名与行号。

## 6. 运行中的信息

信息按读者分开:运行中的状态给用户,事实给模型。

- 模型在一次调用结束时得到一份答复:开头是任务空间,其后是脚本的打印与报错,最后是怎样结束与用时。GEE 脚本把结果交给模型的唯一途径是打印,所以打印全部交给模型,过长时在工具结果的上限之内只留结尾:失败的脚本,报错与运行的结局都在结尾。运行中不给模型任何东西:等待的计时与导出的进度对它写脚本没有用,只占上下文。
- 用户在对话的工具行实时看到运行的计时、正在等待 Earth Engine 与已经等了多久、导出的状态与进度。这些进度与 `qgisrun` 的进度走同一条链路,经主进程与壳服务端的流式应答到达内核,再交给界面(`GEOENGINE.md` 第 3.1 节)。
- GeoCode 的 Python 函数照同样的分工:过程中的状态以事件报告,结局(导出了哪个资产、等了多久、内容没变而沿用)打印给模型。以后加的函数也一样,例如下载报告进度,下载的结果打印出来。

Python 交回的输出分两种:以 GeoCode 的标记开头的行是结构化的事件,其余是脚本自己的打印与报错。GeoEngine 逐行认出事件,事件不混进脚本的输出,脚本也不必为了让 GeoCode 知道什么而打印。事件有四类:

- 运行前的结论:读出的任务空间;或者初始化失败、读不出 `GeoCode` 文件夹、新建的任务重名、要继续的任务不存在,这几种都在脚本开始之前结束运行。
- 起止:脚本开始的标记在标准输出与标准错误上各发一次,因为两条管道之间没有先后;在它之前的是 earthengine-api 与 Python 自己的输出,只作诊断。结束的标记带着成败,没有它就是 Python 中途退出。
- 等待:有请求在等 Earth Engine 时,定时报告已经等了多久。
- 导出:`gc.save` 等待导出时,定时报告导出的状态与进度。

运行脚本知道脚本在等 Earth Engine,靠的是请求的出口:earthengine-api 的计算、取值、下载地址、提交导出、列出资产与查询导出,以及凭据的刷新,都经 `requests` 的会话发出,运行脚本在这一处记下每个请求何时发出、何时得到回应。它是运行中最主要的观察点,时限(第 3 节)与工具行的等待都靠它。出口之外还有几处等待它看不到:

- geedim 的分块下载经 aiohttp 并发,不经 `requests`,由调用它的处理函数自己报告进度(第 5 节)。
- 流式读取的应答正文(`requests` 的 `stream=True`)只有应答头经过出口;`urllib` 发出的请求(登录时换取凭据,初始化时读弃用资产的列表)完全不经过。
- 脚本用 multiprocessing 开的子进程重新启动 Python,没有这个出口,也没有初始化好的 `ee`。
- 脚本在本地的计算(如用 geopandas 处理大文件)既不发请求,也不输出。

导出的状态不经这个出口:导出在服务器上运行,提交它的进程退出后照常继续。它的状态、进度与失败的原因由 Earth Engine 的操作接口给出,GeoCode 靠导出描述里的「任务:资产:指纹」认出是哪一次(第 4 节),不依赖提交它的进程,换一次运行、重启应用之后都认得出。

## 7. 环境

执行载体是用户自己的 Python,conda、venv 或系统的都可以,要装有 earthengine-api、geedim 与 geopandas,三个都是就绪的必要条件,脚本不会跑到一半才发现缺包。GeoEngine 不安装软件,也不改动用户的环境(`GEOENGINE.md` 第 1 节),也不按版本号判断能不能用。

`machine.json` 的 `gee` 块记 Python 的路径与 Google Cloud 项目 ID。Python 由用户在设置里从找到的几个中选,或指定别处的;项目 ID 只有用户知道,在设置里填,或由 GeoAgent 问用户,不猜。登录用 Google 账号,凭据由 earthengine-api 存在它自己的位置,与用户在别处运行的 GEE 脚本共用;用户可以在设置里点登录,也可以由 GeoAgent 在对话里运行这个 Python 环境的 `earthengine authenticate`。网络跟随用户自己的配置:Python 认代理环境变量,没有设时读系统的代理,GeoCode 不探测代理,也不提供代理设置。

本地环境、登录与项目、能否连上 Earth Engine 三类事实各自会出问题,出问题时该做的事各不相同,所以检查分两段、逐步区分:本地一段查 Python、三个包、凭据与项目 ID,不联网;本地齐了,再以配置的项目初始化并算一个最小的结果,区分连不上与被拒绝,被拒绝再按服务器给的原因分为凭据失效、项目不存在、没有权限、接口未启用与其他。装包、登录、打开代理都不经过配置文件,所以看环境得出的失败在每次调用 `geerun` 时再检查一次,用户在终端里修好之后不必重启应用。

环境没有就绪时,`geerun` 不执行脚本,把提示交给 GeoAgent,写明它能自己做的与只能请用户做的:找 Python 与写配置、装包、发起登录,GeoAgent 都可以在用户同意后去做;项目 ID 只能问用户;连不上时,本地的环境是好的,提示只说网络有问题,要它不去重装、改配置或重新登录。

## 8. 权限

`geerun` 执行的是任意 Python,能读写文件、访问网络,风险与 `shell` 相同,所以权限照 `shell` 处理,默认问不问也与 `shell` 相同:agent 本来就能经 `shell` 执行任何 Python,只问 `geerun` 守不住什么,GEE 的工作又要反复执行小段脚本,每次询问徒增打扰。它在设置的工具权限里有自己的一行,用户给 `shell` 设的规则不管它;GeoCode 改动 GeoAgent 对 `shell` 的默认规则时(与内核的装配一起),对 `geerun` 同样改动。询问之前先查环境是否就绪、脚本文件在不在、参数与任务名合不合规,不让用户批准一个注定执行不了的请求。

## 9. 界面

- 标题栏有 GEE 的指示灯,颜色归类与 QGIS 相同(`GEOENGINE.md` 第 3.3 节),只是未登录与缺项目也归入灰色:它们和未配置一样是设置还没走完,不是故障。
- 设置的「地理环境」页里,GEE 的详情按配置的先后分三步:Python 环境、Google 账号、Cloud 项目,失败落在哪一步就标在哪一步。
- 对话里 `geerun` 一次调用一行:标志、用途与任务,运行中加计时、「正在等待 Earth Engine」与导出的进度,展开后是脚本的输出。
- 询问卡片写请求原因与脚本的前四行,其余只写省略了几行,不加警示:任意的 Python 靠扫描认不准,认不准的警示反而让人以为安全。

## 10. 验收

- 一次运行超过十分钟的计算或下载能完整跑完,期间没有任何打印也不被中止;既没有输出、也没有在等服务器的脚本在空闲时限后被中止;用户停止时任务进程随之结束。
- 调用缺了用途、任务或脚本,或者多给,都直接报错并说明怎样改;同名的任务已在或这个对话建过时新建被拒绝;继续一个既没有文件夹、也不是这个对话建的任务被拒绝,并列出最近的任务;对话里建过、没存资产的任务,重启应用后仍能继续;名字不合规则时拒绝。只查询、不存资产的任务在用户的 GEE 里不留任何东西;第一次存资产时 `GeoCode` 与任务的文件夹自动建出,导出在提交时被拒,或等待中的导出失败,都不留空文件夹。
- 答复开头写明任务、它的资产与说明、进行中与失败的导出、最近更新的另外三个任务,不耗计算配额,`GeoCode` 以外的资产不出现在其中;资产再多,答复也不超过内核的上限,脚本的报错仍在结尾。
- 存进任务的资产在 Code Editor 里看得到标题与说明;同样的内容重跑不再导出,内容变了就替换,读取的 `GeoCode` 资产被替换过也算内容变了;换一个对话指明同一个任务,GeoAgent 读到之前的资产并接着用。
- `geocode` 包不写进用户的 Python 环境;包里的函数用错时报错并说明怎样改,脚本出错时 traceback 指向包里的文件与行。
- 等待的计时与导出的进度出现在工具行,不出现在给模型的答复里;脚本的打印与报错完整地交给模型。
- 含中文的路径与打印正确无误。
- 配置指向装齐三个包的 Python、填好项目并登录之后,状态变为就绪,macOS 与 Windows 都是;每一种环境问题各自报告为对应的状态;没有配置时,GeoAgent 照提示自己找到 Python、装包、写好配置,登录与项目 ID 请用户完成;在终端里装包或登录之后,GeoAgent 再调用一次 `geerun` 就看到新的状态,不用重启应用。

## 11. 待定

- `geocode` 包的处理函数:以 geedim 为底逐个设计,候选有读取研究区(任意矢量格式,只接受一个要素,没有坐标系、空几何与无效几何都拒绝并说明怎样修)、分块下载成完整的 GeoTIFF(不留半成品)、导出到 Google Drive、研究区内的覆盖度检查,以及给耗时很长的本地计算报活;下载时目标文件已经存在,覆盖、编号还是报错,也在这时决定。每个函数的行为与验收在设计时写进本文档。
- 运行结束之后的导出:不等的导出,以及运行被停止后仍在进行的导出,完成时没有人告诉 GeoAgent,只有下一次运行开头的任务空间报告它进行中或失败。要不要在运行之外盯住导出、完成时通知 GeoAgent,怎样做在这时决定:放到后台的是整次运行还是只是导出的等待,查询导出要用用户的 Python 与凭据,由谁、何时去查,应用重开后怎样接上,与 `gc.save` 的等待怎样配合。
- 工具行是否按请求的种类(计算、取值、下载、提交导出)与限流后的重试细分显示,而不只是「正在等待 Earth Engine」。
