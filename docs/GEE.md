# Google Earth Engine

本文档说明 GeoCode 怎样让 GeoAgent 使用 Google Earth Engine:为什么不直接经 `shell` 运行 Python,一次运行怎样进行,以及几项核心设计。GeoEngine 的框架(进程、与主进程的通道、环境配置与状态)在 `GEOENGINE.md`,这里只写 GEE 自己的部分。

## 1. 为什么需要 `geerun`

GEE 的工作方式是:GeoAgent 用 earthengine-api 写 Python 脚本,脚本在本地搭出计算图,计算在 Earth Engine 的服务器上完成,结果以打印、存成的资产、下载到本地的影像或导出到 Google Drive 的文件交回。

GeoAgent 本来就能经 `shell` 运行任何 Python,GEE 脚本也不例外。但这样运行,有五件事模型自己做不好,`geerun` 就是为它们而设的工具:

| | 经 `shell` 直接运行 | 经 `geerun` 运行 |
|---|---|---|
| 运行多久 | 一次取值或导出可能在服务器上算几分钟而毫无输出,命令的超时设短了误杀正常的计算,设长了卡死的脚本也要等满 | 按空闲计时,脚本在等 Earth Engine 时自动报活,服务器算多久都不中止;真正卡住的才中止(第 3 节) |
| 结果留在哪 | 每次重跑都从原始影像重算,费时也费配额;中间结果要自己写导出、等待、起名;换一个对话,之前做过什么一概不知 | 每次运行属于一个任务,`gc.save` 把耗时的结果存进任务,内容没变就直接沿用;答复开头列出任务里已有的资产,换对话也能接着做(第 4 节) |
| 常见的步骤 | 读研究区、存资产、下载、导出每次从头写,每个脚本都不一样;细节容易写错,错了又常常不报错,只是结果不对 | 用 GeoCode 的 Python 包 `geocode` 里标准的函数:写对了的工具箱,自带进度与状态的反馈,GeoCode 也因此能管理整个流程(第 5 节) |
| 信息给谁 | 脚本的打印、库自己的输出与等待混在一起;用户在运行时看不到进展;输出过长时,被截掉的可能正是结尾的报错 | 等待与导出的进度只给用户,在工具行实时显示;模型只读脚本的打印,过长时保留结尾(第 6 节) |
| 环境 | 模型自己找装了 earthengine-api 的 Python、猜项目 ID、写初始化;出错时分不清是缺包、没登录、项目不对还是网络不通,常以重装或重新登录了事 | 用设置里配好的 Python 与项目,脚本开始时 `ee` 已经初始化;没有就绪时,告诉模型具体缺什么、哪些它能做、哪些要请用户做(第 7 节) |

前四项是 `geerun` 的核心:它们决定 GEE 的工作能不能做长、做对、做得连续,用户又能不能看懂它在做什么。环境一项是前提,一次配好之后很少再碰到。

## 2. 一次运行

一次 `geerun` 调用经过四方:内核里的工具、GeoEngine、用户的 Python 与 Earth Engine 的服务器。

1. 内核检查参数(这一步的用途、任务、脚本)与这个对话建过的任务,请 GeoEngine 确认环境就绪、脚本文件存在,再按权限规则询问用户(第 8 节)。
2. GeoEngine 用配置的 Python 启动一个任务进程,把 GeoCode 的运行脚本、这次的请求与 `geocode` 包一起经标准输入交给它,当前目录是会话目录。一次调用一个进程,脚本结束它就退出,不常驻,也不在调用之间复用。
3. 运行脚本以配置的项目初始化 Earth Engine,在请求的出口装上监视,读出任务里已有的东西,然后执行 GeoAgent 的脚本。脚本直接使用 `ee` 与 `gc`,不必自己初始化。
4. 运行中,Python 把结构化的事件与脚本自己的输出一起写回;GeoEngine 把事件转成给用户的进度,把脚本的输出留给模型。
5. 脚本结束,内核把任务里已有的东西、脚本的打印与运行的结局拼成一份答复交给模型。

本地的 Python 只搭计算图、发请求、等结果,真正的计算都在服务器上。所以运行中最要紧的,是知道脚本此刻是在等服务器,还是卡住了(第 3、6 节)。

## 3. 不被误杀的运行

运行时限按空闲计,不设总时长。GEE 的筛选与计算只在本地搭出计算图,真正的等待都在向服务器要结果的那一刻(取值、下载、提交导出),而这些请求都经同一个网络库发出。运行脚本守在这个出口上,有请求在等服务器回应就替脚本报活,所以服务器算得再久,脚本也不会因为没有输出被中止,GeoAgent 不必为此做任何事。一个请求等了太久不再算活着,卡死的请求因此仍会被中止。脚本既没有输出、也没有在等服务器,持续一段时间才中止;脚本在本地做耗时的事时,打印进度就能保持运行。用户随时可以在对话里停止;已经提交的导出在服务器上照常运行。

不设总时长,是因为 Earth Engine 的速度不稳定,固定的上限会误杀长的下载与导出;只看有没有输出也不行,服务器在算时脚本本来就一声不响。出口之外还有几处等待看不到,见第 6 节。

## 4. 任务与资产

GEE 的工作常要好几天、跨几个对话,耗时的结果要留在云端接着用,就像人自己用 Earth Engine 时把中间结果存成资产再往下做。所以每次运行都属于一个任务:

- 一个任务是用户资产里的一个文件夹 `GeoCode/<任务名>/`,用户在 Code Editor 里一眼看得懂。GeoCode 只管这个文件夹,不碰其他资产。
- 每次调用都指明任务:`new_task` 新建,`task` 继续。任务名由 GeoAgent 按用途与日期取,如 `taipei-ndvi-20261008`;写错的名字被拒绝,不会被当成新任务。
- 只查询、不存资产的任务不在云端留下任何东西:文件夹在第一次存资产时才建。
- 答复的开头是任务空间:已有的资产与它们的标题、说明,进行中与失败的导出,最近的其他任务。GeoAgent 不必另查就知道手头有什么,读这些也不耗计算配额。

脚本用两个函数存取资产:

- `gc.save` 把影像或表格存进任务,写上标题与说明,默认等导出完成再读回。内容没变就直接沿用,不再导出;变了就替换。
- `gc.load` 按名字读回本任务或其他任务的资产。

存一次,是用第一次运行的时间换之后每次的速度与配额。所以只存检查过、下游要反复用的结果(通常是合成)和用户要留下的结果;临时查看与还在调整的步骤不存。删除在云端不可逆,GeoAgent 只在用户明确要求时删除任务与资产。

## 5. 内置的 Python 包

没有它,GEE 的每一步都由模型从头写,每个脚本都不一样:同样是存一个合成、下载一幅影像,这次和下次的写法、出错的方式、打印的内容各不相同,GeoCode 也无从知道脚本做到了哪一步。GeoCode 的 Python 包 `geocode` 把常见的 GEE 操作做成标准的函数,脚本里 `import geocode as gc` 即可使用。标准化带来三点:

- 工具箱:常见的任务有现成、写对了的函数,模型不必每次从头写,也不必知道每个坑。直接写的细节容易出错,错了又常常不报错,只是结果不对,例如研究区的直边被当成测地线弧、`normalizedDifference` 遇到负值就把水体掩掉。函数用错时报错,并说明怎样改。
- 可管理:流程里的关键步骤经过 GeoCode 自己的函数,GeoCode 就知道每一步在做什么。例如资产经 `gc.save` 存进任务,才带着标题、说明与指纹,能被任务空间列出、被下一次运行沿用(第 4 节)。
- 及时的反馈:函数自己报告进度与状态,例如 `gc.save` 等待导出时报告导出的进度,下载函数报告下载了多少,用户在工具行实时看到;结局(存了哪个资产、等了多久、内容没变而沿用)打印给模型(第 6 节)。模型自己写的脚本只能靠打印,而打印全都进了模型的上下文。

包里的函数分两类:存取任务的 `gc.save` 与 `gc.load`(第 4 节);处理函数,如读取研究区、下载影像、导出到 Google Drive、检查覆盖度,以 geedim 为底,只写面向模型的那一层,逐个设计(第 11 节)。包不装进用户的 Python,每次运行随请求带去,版本总与应用一致。

## 6. 运行中的信息

信息按读者分开:运行中的状态给用户,事实给模型。

- 模型在调用结束时得到一份答复:任务空间、脚本的打印与报错、怎样结束。过长时只留结尾,报错不会被截掉。运行中的计时与进度对它写脚本没有用,不给它。
- 用户在工具行实时看到计时、正在等待 Earth Engine 与导出的进度。

两者在同一路输出里分开:以 GeoCode 的标记开头的行是给 GeoEngine 的事件(任务空间、脚本的起止、正在等待、导出进度),其余是脚本自己的输出,两者不混。

「正在等待」来自请求的出口:earthengine-api 的请求都经 `requests` 发出,运行脚本在这里记下每个请求何时发出、何时得到回应,时限(第 3 节)与工具行都靠它。geedim 经 aiohttp 的下载、本地的计算等少数情况不经过这个出口,要靠打印或函数自己报告进度。

导出在服务器上运行,提交它的进程退出后照常继续。它的状态从 Earth Engine 的操作接口查,靠导出描述里的「任务:资产:指纹」认出是哪一次,不依赖原来的进程。

## 7. 环境

GEE 在用户自己的 Python 里运行,要装齐 earthengine-api、geedim 与 geopandas;GeoCode 不安装软件,也不改动用户的环境(`GEOENGINE.md` 第 1 节)。Python 与 Google Cloud 项目在设置里选和填,项目 ID 只有用户知道,不猜;登录用 Google 账号,网络跟随用户自己的代理配置。

检查分本地与远端两段,把缺包、没登录、项目不对、连不上等问题分开报告,每次调用 `geerun` 时再检查一次,修好之后不必重启应用。没有就绪时不执行脚本,告诉 GeoAgent 缺什么、哪些它能做、哪些要请用户做。

## 8. 权限

`geerun` 执行任意 Python,风险与 `shell` 相同,所以权限与默认规则都照 `shell`:agent 本来就能经 `shell` 运行 Python,只问 `geerun` 守不住什么。它在设置里有自己的一行。询问之前先查环境与参数,不让用户批准一个注定执行不了的请求。

## 9. 界面

- 标题栏有 GEE 的指示灯;未登录与缺项目和未配置一样显示灰色,不算故障。
- 「地理环境」设置页按 Python、Google 账号、Cloud 项目三步配置。
- 对话里一次调用一行:用途与任务,运行中加计时、「正在等待 Earth Engine」与导出进度。
- 询问卡片显示请求原因与脚本的前几行,不加警示:任意的 Python 靠扫描认不准。

## 10. 验收

- 超过十分钟、期间没有打印的计算或下载能完整跑完;既不输出也不在等服务器的脚本在空闲时限后中止;用户随时能停止。
- 只查询的任务不在用户的 GEE 里留下任何东西;写错的任务名被拒绝;换一个对话指明同一个任务,能读到之前的资产接着做。
- 同样的内容重跑不再导出,内容变了就替换;资产在 Code Editor 里看得到标题与说明。
- 答复开头列出任务里已有的东西,不耗计算配额;答复不超过内核的上限,脚本的报错总在结尾。
- 计时与进度只出现在工具行,不出现在给模型的答复里。
- 每种环境问题各自报告,GeoAgent 照提示能补齐它能做的部分,修好后不用重启应用;macOS 与 Windows 都能就绪,中文的路径与打印无误。

## 11. 待定

- 处理函数:以 geedim 为底逐个设计,候选有读取研究区、分块下载成完整的 GeoTIFF、导出到 Google Drive、覆盖度检查与本地长计算的报活;每个函数的行为与验收设计时写进第 5 节。
- 运行结束之后的导出:不等的导出完成时没有人通知 GeoAgent,只有下一次运行的开头会报告。要不要、怎样在运行之外盯住导出并通知它,放到后台的是整次运行还是导出的等待。
- 工具行是否按请求的种类(计算、下载、提交导出)与限流重试细分显示。
