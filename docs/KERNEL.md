# Agent 内核:设计与迁移

## 1. 内核是什么

GeoCode 的会话循环、模型接入、OAuth 登录、权限系统与工具调度,由 OpenCode 的 agent 引擎承担。这是刻意的选择:这些子系统的正确性——尤其 OAuth 的 wire 协议——直接决定用户能否用已有订阅登录,自研或深改它们没有收益,只有风险。对 GeoCode 的其余部分,内核呈现为一组 HTTP API(供界面)与一个 MCP 客户端(供地理内核挂载工具),接近黑盒。

内核以**薄 fork** 的方式维护,与产品同仓但界限分明:上游 v1.18.18 的内核闭包(15 个包 + 根工程设施)以 vendor 方式存放在本仓 `kernel/` 目录下,原味落盘保存在专用的 `kernel-upstream` 分支——该分支只接受「上游版本的原样文件圈选」(圈选清单即 `scripts/kernel-manifest.txt`),内容零修改;`main` 经 subtree 合并持有 `kernel/` 并叠加我们的薄补丁。这套结构让升级内核成为一次真正的三方合并(git 自动重放薄补丁),而不是人肉 diff——**这句话在 v1.18.4 → v1.18.18 那次升级中被检验过了,数字见 §4.4**。

⚠️ **`kernel-upstream` 必须推到远端。** merge-base 就在那条分支上,它只存在于本机时,任何新 clone(包括换机器后的自己)都做不了三方合并,而**失去这个能力不会有任何报错**——本节这套结构会安静地退化成人肉 diff。`kernel/` 是独立的 bun 安装根(与仓根各自 `bun install`),构建产物(server bundle)供壳打包。我们对源码差异有一条铁律:**越薄越好**——差异越薄,合并上游的成本越低,薄到极致时升级内核约等于换一个依赖版本。

## 2. 内核的构成

`kernel/` 收纳上游 monorepo 中与 agent 引擎相关的最小闭包,分三层。包数随上游增删而变,现数用 `ls kernel/packages`。

**运行时**

| 包 | 职责 |
|---|---|
| `opencode` | CLI 入口、命令表、会话运行时,以及本地 HTTP server 本体 |
| `core` | 引擎主体:配置、工具、provider、存储、PTY、文件系统、XDG 路径 |
| `llm` | 模型协议适配 |
| `schema` / `protocol` | 类型与线协议底座 |
| `server` | httpapi 零件库。⚠️ 真正的 `Server.listen` 在 `opencode` 包内,勿混淆 |
| `plugin` / `sdk` / `codemode` | 插件契约、JS SDK、代码执行模式 |
| `effect-drizzle-sqlite` / `effect-sqlite-node` | 两个 sqlite 绑定 |

**TUI(2 包)**:`tui`,以及它此刻仍拖带的 `ui`——后者只为五个提示音文件被引用,是后续薄补丁的裁剪候选。

**工具层(2 包)**:`script`(构建常量)与 `http-recorder`(测试录放,零运行时字节)。

随行的根设施与包是一体的,缺一不可:bun catalog 版本表、依赖补丁集、bunfig、turbo、tsconfig,以及 `fix-node-pty` postinstall。

### 2.1 入口

生产入口是 `build-node` 构建:把 `src/node.ts` 打成 Node ESM bundle(内嵌 Web UI 被桩空,产物不含任何上游前端),供壳以 utilityProcess 运行;它在完整 Desktop 进程图中的位置见 `DESKTOP.md` §2。开发入口是 TUI(`opencode` 命令的终端形态)。⚠️ 它不能用来验证装配(§4.2)。

### 2.2 三条不可破坏的技术约束

| # | 约束 | 破坏它的后果 |
|---|---|---|
| 1 | `#pty` / `#sqlite` / `#fff` / `#db` 条件导入背后的 bun/node 双轨实现 | 内核不再能同时在 bun 与 Electron 的 Node 里运行——这是它两种形态并存的命脉 |
| 2 | 构建期抓取 models.dev 的模型快照 | 离线构建须以环境变量喂本地文件,否则构建失败 |
| 3 | PTY、文件监听、语法解析等原生依赖经 catalog 钉版,并保留 postinstall 修复钩子 | 原生模块在目标平台上装不起来 |

### 2.3 上游正在换引擎:v1 与 v2

上游内核当前**并行跑着两套实现**。v2 是 agent 引擎的重构,与 v1 的隔离是干净的:包、schema、HTTP 路径(`/agent` 对 `/api/agent`)全部分开,两套可以同时服务,v1 的 schema 与一条自动迁移集中收在 `core/src/v1/`。上游**按端点逐个搬**,不是一次性切换。

GeoCode 的装配**全部落在 v1**。原因不是字段名对不上(那有自动迁移),是**注入点**:装配层是代码内注入,而 v2 的配置只从磁盘文件读,两者之间没有通路。v2 那张表因此是上游出厂的编程 agent 阵容——没有 GeoAgent、没有 osmfetch、没有四个权限键与八个地理工具。

**判断:不适配,等上游自己迁完再决定。** 现在适配是对着移动靶,而产品链路不受影响——界面走 v1。隔离干净是这个判断成立的前提;风险不来自内核,来自**哪个客户端先跟进 v2**:上游 TUI 已经跟了(§4.2),GeoCode 的界面还没有。复查它的时机不是「定期关注」,是两件具体的事——**下次合并上游时**看 v2 侧改了多少,**界面阶段定 chamber 版本时**看它调了哪些 v2 端点。

## 3. 定制阶梯

GeoCode 的一切内核定制,按下面的优先级实现,只允许用尽可能高的层级;源码补丁是最后手段:

1. **配置** —— agent 定义与默认 agent、禁用内置 agent、权限规则、MCP 注册、技能扫描目录;
2. **环境变量** —— 数据目录定向(XDG 族)、服务口令;
3. **外挂进程** —— 地理工具经 MCP 进入引擎,技能经扫描目录进入引擎;
4. **界面** —— 纯展示层的取舍(如不显示某些斜杠命令)在界面代码完成;
5. **源码补丁** —— 每一处必须书面回答「为什么上面四层做不到」;要不要再配一个运行时绊线,按 CONVENTIONS.md §5 的判据单独决定。

第 5 级的「书面回答」集中在 §6:凡是屏蔽引擎既有机制的补丁,都在那份清单上,连同它的截断点与绊线。

这条阶梯建立在对引擎装配面的逐项验证上:agent 可以完全由配置定义并设为默认,内置 agent 可被真正禁用(从列表删除,而非隐藏);权限引擎按通配符匹配任意工具名与路径模式,足以表达「栅格文件禁止文本读取」「OSM 工具只许下载子代理使用」;数据目录完全由 XDG 环境变量决定,macOS 亦然。

**GeoCode 的装配目标**:GeoAgent 是唯一暴露的主 agent(地理科学专家人设,内置编码向 agent 禁用);子代理两个——osmfetch 承担全部 OSM 下载,其网络出口被权限规则锁死(只许 OSM 工具组,webfetch、websearch 与再派生子任务一律拒绝,防止提示注入把它变成任意抓取器),explore 做只读勘察,在地理这一侧只拿到读数据一项;地理能力默认对所有 agent 拒绝,再逐个 agent 按需开启,保证将来引入其他领域 agent 时边界不会静默扩大。这些目标的实际形态见 §5,逐项进度见 §4.1 的表。

**冻结区**:内核中 provider、auth、account 及模型协议相关的包永久与上游逐字节一致,合并时无条件取上游;`@opencode-ai/*` 包名、`OPENCODE_*` 环境变量、User-Agent 与 Referer 等 wire 指纹逐字保留。

## 4. 如何迁移 OpenCode 内核

### 4.1 重建定制:把旧版需求搬上阶梯

`kernel/` 从原味上游起步,不携带任何历史注入;GeoCode 的既有定制(旧版 fork 是现成的需求说明书)逐类以装配重新实现。每类独立提交、配绊线测试,实现一类验证一类:

| 既有源码注入 | 搬往哪一级阶梯 | 状态 |
|---|---|---|
| GeoAgent 定义、禁用内置 agent、默认 agent | 配置(agent 定义 + disable + default_agent) | 已完成(§5.1) |
| 基础人格与品牌 | 源码补丁(基础提示词选择器) | 已完成(§5.2) |
| 计划模式对 `build` 的硬依赖 | 源码补丁(判定通用化)+ 提示词文案 | 已完成(§5.3) |
| 数据目录命名空间 | 源码补丁(单一 `Brand` 模块) | 已完成(PATHS.md §5) |
| 地理能力的执行与环境管理 | 地理内核(**本进程内的服务层**,设计见 GEOKERNEL.md) | 已完成 |
| 数据面 HTTP 路由 | 同上,挂在内核自有的 httpapi 上 | 已完成(GEOKERNEL.md §7.7) |
| 地理工具注册 | 源码补丁(工具注册表)——理由见 TOOLS.md §7 | 已完成 |
| 地理工具权限分组 | 配置(四个权限组,按环境依赖划分)**+ 源码补丁**——`permission/index.ts` 的 `GEO` 映射,可见性层全靠它 | 已完成(TOOLS.md §4、§7) |
| osmfetch 子代理定义 | 配置(agent 定义 + 网络出口锁) | 已完成 |
| 栅格文件防文本误读 | **源码补丁**(`read` 把地理数据交接给 ReadGeoData) | 已完成 |
| 壳写完全局配置后让 Kernel 看见 | 源码补丁(`/global/dispose` 顺带失效全局配置缓存)——理由见 DESKTOP.md §5.2 | 已完成 |
| Windows shell 白名单 | 源码补丁(`core/src/shell.ts` 的候选顺序) | 未开始(CONVENTIONS.md §8) |
| 技能商店 | 受管目录 + 引擎扫描路径 | 未开始 |
| 面向程序员的斜杠命令裁剪 | 界面过滤 | 未开始(界面已原味迁入,适配未开始) |

「栅格文件防文本误读」那一行是唯一一次**阶梯下移**,值得单独看一眼:它原计划走配置的 glob 拒绝规则,实测做不到——文本类地理格式(`.geojson` `.gml` `.kml`)会通过 `read` 的全部检查,被当作纯文本在坐标数组中间截断,末尾还附一句「用 offset 继续」。这不是权限能拦的形态。完整论证在 TOOLS.md §7,而每一次下移都必须留下这样一段论证,否则阶梯就只是一句口号。

权限的两层键空间——执行层用工具声明的权限键,可见性层用工具 id——曾在这里记过一次订正,正本已迁到 TOOLS.md §4.1。要记住的一句是:**两层的名字都可能对不上,而两种失效都不出声**——一层是工具照常可见,另一层是调用被静默放行。

**补丁面**(口径即 CONVENTIONS.md §5 那条 grep,数字随时可复现)。两个数必须分开看,因为它们的性质相反:

| | 文件数 | 约束 |
|---|---|---|
| **打在上游文件上** | 源码 48 · 测试 13 | **只许收缩**——这是「薄」的全部含义 |
| 我们自有的新文件 | 81(地理内核 61 · 内核外 20) | 按设计增长,不属于补丁面 |

相加得到的和没有意义:它把一条必须收缩的量和一条应当增长的量凑在了一起。

**收缩发生过两类,都值得认出来。** 一类是补丁本身不产生行为(§4.3 的反例:`tui/src/routes/session/index.tsx` 上那处零行为的注释补丁,摘掉后文件回到与上游逐字节一致);另一类更容易漏——**补丁的前提消失了**。为「某个上游 agent 被禁用」而改写的文案,在那个 agent 回到阵容之后就该退回去。⟹ **补丁不是资产,是负债**:前提一变就要重新算账,而这类账不会自己浮上来,得主动去数。

⚠️ **增长只发生过一次,理由记在这里而不是让下一个人只看到一条被违反的约束。**新增的是 `cli/cmd/run/permission.shared.ts` 上的地理权限渲染。它无法避开:上游按**工具名**索引渲染规则(`tool.ts` 的 `TOOL_RULES`,且强制要求 `view`/`run`),而 `qgis`、`gee`、`osm`、`geodata` 是**权限键**——`qgis` 覆盖两个工具、`osm` 覆盖四个,没有一个工具叫这些名字,注册进去等于为不存在的工具编造渲染。上游把同样不是工具的 `external_directory` 与 `doom_loop` 放在 `permissionInfo` 里,这处补丁就并在它们旁边。

不做的代价不是「界面难看」:`qgis` 与 `gee` 都是 `ask`,而弹窗会退化成 `Call tool qgis` 两行字——**用户被要求批准一件没有告诉他内容的事**,而那次询问正是 TOOLS.md §4.3 里唯一剩下的守卫。⟹ 判据不是「能不能不加」,是**加它换回来的东西是否与「薄」的目的一致**:薄是为了让上游的改动能自动流进来,而这处是纯新增分支、不触碰上游任何既有逻辑(§4.3 的 ①),合并时冲突概率最低。

测试侧从 10 涨到 13,而这**不是补丁面增长**:那三处改动一直都在,只是从来没有标记,所以那条 grep 看不见它们。发现它们的不是清点,是 `git diff --name-status kernel-upstream main:kernel`——它不依赖标记,因此比 grep 更全,现在写进了 §4.4 的流程。**「只许收缩」约束的是改动,不是可审计性**;一处改了却查不到的地方,收缩它的办法是补标记而不是留着不数。

上游那些改动按性质分:

| 类别 | 规模 | 性质 |
|---|---|---|
| 磁盘身份 | 大宗 | 几乎全是一行替换,把字面量换成 `Brand.*`(PATHS.md §5) |
| 装配层接入 | 三处 | `geocode.ts` 的合并点、提示词选择器、计划模式判定 |
| **屏蔽清单** | 见 §6 的清单 | 每项书面回答「为什么装配做不到」 |
| 地理内核注入 | GEOKERNEL.md §10.1 的清单,外加 2 处上游测试 | 逐项列举、逐项配绊线,**不是零散生长而是一份可对账的表**。那 2 处是数据面并入根 API(#2)的连带:`RootHttpApi` 从此建不起来,除非测试自己的层图也提供 `GeoHandler` 与它读的两个服务 |
| 上游测试的夹具 | 少数几处 | 让夹具写「加载器会读的名字」;改名后一处共享夹具就救回约 230 个测试 |
| 浏览器工具的例外 | `plugin/loader.ts` 一处早退块 + 自有 `plugin/geocode-trusted.ts` + `config/geocode.ts` 两条规则 | 外部插件屏蔽不变,只多一个由进程拥有者点名、路径固定的文件;为何装配做不到:插件加载没有配置开关,而这个文件必须在内核进程内注册工具(DESKTOP.md §7.2) |

早期版本在这里写过「个位数文件」的目标,那是在地理内核注入之前定的,已被有计划的执行超过。**判据因此不再是数量,也不是「在不在某张清单上」**——GeoCode 是在上游代码上改出来的,注入多是常态,而按清单点名注入点的做法自己就会漂:那份清单曾把六处健康的补丁判成欠账,其中还有一处根本不存在。

判据落在两处:

- **形态**(§4.3)。同样一件事,占三行上游代码和占三十行,合并成本差一个量级;
- **可审计性**。每一处都必须被 CONVENTIONS.md §5 那条 grep 找到。**补丁的权威清单就是那条 grep**——它是代码本身,不会漂;文档记的是**为什么允许打这个补丁**(§6)和**什么不许碰**(GEOKERNEL.md §10.1 的注入点契约),不记「有哪些」。

### 4.2 验证:对着端点,不对着 TUI

内核装配的验证不需要 GeoCode 界面——这一点没变,但**测试台不是 TUI**。上游 TUI 列 agent 走的是 v2 端点(§2.3),那张表里没有 GeoCode 的任何东西;拿它确认装配,看到的是一份与事实相反的名单,而**看名单这一步不会有任何提示**——要到选中其中一个发消息,才会撞上 v1 的「Agent not found」。

验证对着 v1 的 HTTP 端点做:起内核,问 `/agent`,确认 GeoAgent 在列并成为默认、内置 agent 消失。权限规则与工具可见性由绊线覆盖,不靠肉眼(CONVENTIONS.md §5)。

### 4.3 注入形态:什么样的补丁在合并时便宜

补丁的**数量**不是成本,**形状**才是。一处补丁贵不贵,只取决于一件事:**它占用了多少行上游还在维护的代码**。按这个判据,树上的补丁分四种形态,从便宜到贵——新写补丁时应当尽量往上靠。

| | 形态 | 冲突面 | 树上的实例 |
|---|---|---|---|
| ① | **自有文件 + 装配面接入** | 零 | `config/geocode.ts`:整个装配层是新文件,只在配置流水线的合并点被调用一次 |
| ② | **大块自足 + 单点接线** | 只有接线那几行 | `snapshot/index.ts`:新增几乎全在一个自足的块里(导入 + 常量 + 一个具名函数),插进上游逻辑的只有 3 处 |
| ③ | **字面量 → 派生** | 只有那一行,且冲突可机械解 | `Brand.*` 那二十余处。上游改了那行,取它的新结构、重新套上 `Brand.` 即可 |
| ④ | **整段替换上游逻辑** | 整段 | `effect/runtime-flags.ts` 把两个开关的定义换成一个自己的助手 |

④ 只在**改写语义**时才不可避免。若目的仅仅是**屏蔽**,它就不该出现——包起来或早退能拿到同样的行为而冲突面为零(见下第四条)。

**② 最值得学。** 它的要害不在「新增得多」,而在**新增的位置**:整块放在上游从不改动的地方(文件顶部的常量区),真正插进上游逻辑的只有三处,而那三处占的都是最小面:一次具名调用,和一个带默认值的参数。**冲突面是那三行,不是整块的体量。**

反过来,④ 贵不是因为删得多,而是因为**被删的那段上游还在维护**:上游一改那段,冲突必然发生,而解冲突的人必须同时理解上游的新意图和我们当初删它的理由。

由此四条:

- **能新建文件就不改上游文件。** 阶梯第 5 级说的是「最后手段」,而最后手段里也分等级;
- **必须改上游文件时,把体量放在上游不去的地方,只留最小的钩子在它的逻辑里。** 钩子最好是一次**具名调用**——名字本身就是文档,而调用点只有一行;
- **追加,不要插入。** 往数组、清单、分支表的**末尾**加(`tool/registry.ts` 的八个工具就是这样接的),上游扩充自己的条目时改的是它自己那一段;
- **屏蔽上游代码,不要删除它,而且被屏蔽的行要逐字节不变**(CONVENTIONS.md §5 的闭合标记规矩)。删除是形态 ④,上游一改那段就冲突;原样包住则是纯插入,同一次改动会自动合入,并且留在原处看得见。`config/config.ts` 与 `config/tui.ts` 把上游块整段包进 `/* */`,`session/system.ts` 在函数首行加一句早退——最后这处因此从树上最贵的补丁变成零删除行,而上游恰好每个版本都在动那个选择器。
  ⚠️ 判据是**逐字节**,不是「留了锚点」。`plugin/index.ts` 把上游原文改写成带 ` * ` 前缀的注释行:锚点在,但每一行都被改过了,上游动那两行仍然冲突。

一条反例,记下来免得再犯:`tui/src/routes/session/index.tsx` 上有一处**纯注释补丁**——三行说明,零行为改动。它占着一个冲突位而不换来任何东西,而同一段话写在本文里一样成立。**不产生行为的东西不要写进上游文件。**

### 4.4 升级:按需合并上游

内核升级是可选的、按需的,停靠不设期限(当前基线:上游 v1.18.18,2026-08-18 合入)。

**这套流程已经走过一次,数字记在这里当参照**:v1.18.4 → v1.18.18,跨 14 个补丁版本、上游 319 个 commit、805 个文件改动。其中落在闭包内的 231 个,落在我们打过补丁的 53 个上游文件上的只有 **10 个**,而 git 自动合成了 7 个——**人手解的是 3 个文件、4 个冲突块**。补丁标记数、补丁面全集、上游套件的失败画像(88 失败 / unexplained 8,逐堆相同)合并前后一字未变——前两个的当时值不必记在这里,§4.4 的流程里那两条命令随时能重算。

那 3 处冲突不是随机的,全是 §4.3 分类里最贵的 ④ **整段替换上游逻辑**:提示词选择器、内置插件清单、以及选择器的测试。同一次合并里,二十余处 ③ 形态(`Brand.*` 字面量替换)一处都没冲突——`cli/cmd/mcp.ts` 被上游改了 3 次仍自动合成。**「贵的是形态不是数量」这句话,这次拿到了实证。**

**先做一次不落地的试合并。** 这一步的产出是一个数字——冲突文件数与冲突块数——而那个数字应当是「要不要升这一版」的**依据**,不是升完才发现的代价:

```bash
git merge --no-commit --no-ff -X subtree=kernel kernel-upstream
git diff --name-only --diff-filter=U     # 冲突落在哪些文件
git merge --abort                        # 不满意:工作树原样退回
```

**更便宜的一种试算,连工作树都不碰**(需要 kernel-upstream 已落盘目标版本):

```bash
git merge-tree --write-tree -X subtree=kernel main kernel-upstream
```

它把三方合并整个算在对象库里,退出码 0 即无冲突,非零时逐个列出冲突文件——不产生 commit、不动索引、不动工作树,因此在任何分支上、任何时候都能跑。

正式流程:

1. 在 `kernel-upstream` 分支落盘目标上游版本的原味闭包(一个 commit):

   ```bash
   git checkout kernel-upstream        # 或 git worktree add,以免切换主工作树
   ./scripts/kernel-vendor.sh v1.18.18
   ```

   脚本按 `scripts/kernel-manifest.txt` 从上游 tarball 取文件、整棵替换、`git add --force`——**`--force` 不是保险而是必需**,上游各级 gitignore 会静默吞掉它自己强制跟踪的文件(v1.18.4 的 `build-node.ts` 之鉴)。最后它做**文件集对账**:清单选中的文件集与暂存的文件集必须逐个相等,不等即拒绝并列出两侧的差。commit 仍由维护者亲自执行。

   ⚠️ **对账的两侧排序与比较都在 `LC_ALL=C` 下进行。** 只给 `sort` 设而漏掉 `comm`,`comm` 会用调用者的 locale 判断输入是否有序(实测 `zh_TW.UTF-8` 下即失准),把两侧都存在的路径**同时报成两侧独有**——照那份报告去改清单,会真的删掉一个从未缺失的文件,而少一行在下次合并时读作「上游删了它」,不产生冲突。这处缺陷两个 vendor 脚本都有过,`chamber-vendor.sh` 第一次真实升级时撞出来。

   **清单即闭包。** 改它一行,就是改「下次合并把什么读成上游的增删」,而两个方向都不产生冲突:少一行读作「上游删了这些文件」并把它们从 main 上移除,多一行读作「上游加了」。它因此是结构性改动而非偏好——这正是 §1 那句「圈选后的快照」在操作层面的全部含义。清单落成文件之前,这份选择只存在于做过它的那次会话里,没有任何东西能事后复核它;
2. `git merge -X subtree=kernel kernel-upstream`。**解冲突逐处手解,绝不整文件取某一方**——`--theirs` 会静默丢掉散落在同一文件里的其它补丁。逐处解时先看补丁属于 §4.3 的哪一种:③ 取上游的新结构、重新套上 `Brand.`;④ 对照标记块里留的上游原文,判断我们删它的理由是否还成立;
3. **合并后先对补丁面,再跑测试。** 两条命令,回答的问题不同,合并前后各取一次:

   ```bash
   git diff --name-status kernel-upstream main:kernel     # 补丁面全集,不依赖标记
   grep -rlE '// GeoCode:|--- GeoCode|"GeoCode: ' kernel/packages/ | wc -l
   ```

   前者是唯一看得见 `.txt` 与 `package.json` 那类**载不动标记**的补丁的手段,§4.1 那三处「改了却查不到」正是它查出来的;后者是 CONVENTIONS.md §5 的权威 grep,数的是可审计的那一部分。**任一数字变小就有补丁不见了,而它未必伴随任何冲突**——上游删掉或改名一个我们打过补丁的文件时,git 不报冲突,只是让那处补丁随文件一起消失;
4. 跑绊线套件。它回答的是另一个问题:**补丁还在,但还起作用吗**。上游重构会让一处补丁语法上完好而语义上被架空,只有运行时测试看得见;
5. **载不动标记的文件手工过一遍**:`.txt` 提示词与描述文件、以及两个 `package.json`——它们没有注释语法,那条 grep 看不见(CONVENTIONS.md §5)。清单很短,逐个 diff 即可。**`bun.lock` 例外:它与上游差着数千行,但那是闭包圈选后 `bun install` 的产物,不是补丁——冲突时删掉重新生成,永远不要手工解**;
6. **重装依赖,不要增量。** 上一步重新生成 `bun.lock` 之后,`bun install` 会补齐新锁文件要的包,却**不清掉不再被引用的旧版本**——同一个包的两个版本从此并存,而 TypeScript 把它们当成两个不同的类型。症状是几十条 `TS2322` / `TS2345`,报的路径在 `node_modules/.bun/` 底下,**读起来像是某处补丁被上游重构架空了**,而这正是第 4 步该抓的东西,极易误判。`rm -rf kernel/node_modules` 再装。实测数据记在 `DESKTOP.md` §9.2;
7. 构建内核 bundle,进入产品仓,全链路实机重测;
8. 任何一步不满意,回退停靠原版本。

**已知的升级债**,升级前逐条确认:

| 债 | 内容 | 引爆时机 |
|---|---|---|
| **装配层不在 v2** | 装配层是代码内注入,而 v2 的配置只从磁盘文件读(§2.3) | 某个客户端改用 v2 的 agent 端点时——后果不是「三个 agent 复活」这么轻,v2 侧**整个装配层不存在** |
| **计划模式的两份文案** | `session/prompt/plan-mode.txt` 让模型「派 general agent」,`tool/plan-exit.txt` 通篇 「switch to build agent」——两个名字装配层都禁用了 | 两者都在 `experimentalPlanMode` 之后休眠;该开关转正即高危 |

后一笔属于一种反复出现的形态:**上游把一个具体名字写进了本该抽象的地方,而我们恰好改了那个名字对应的东西**。这个形态在本项目已出现多次(计划模式提醒的 `=== "build"`、旧版权限的名字错配),因此列为常规动作:**凡在装配层改名或禁用,`.ts` 与 `.txt` 两侧都要扫**——早期排查只沿 `.ts` 做过,独立的提示词与描述文件因此全体逃逸。

### 4.5 迁移期间的安全网

迁移全程,旧版 GeoCode 保持可发布;`kernel/` 的每类装配与补丁都是独立 commit,可整步回退。历史经验反复证明:编译通过与测试全绿不等于运行时正确,凡涉及「配置期望被某个服务读到」的改动,必须追踪到读取方并用运行时测试锁定。

## 5. GeoCode 的 Agent 装配

上游内核是一台通用的 agent 引擎,它的出厂设定服务于编程助手:主 agent 叫 `build`,基础人格自称 OpenCode,子代理是代码搜索与代码任务。GeoCode 的个性不通过改造这台引擎获得,而是通过**装配**——一层薄薄的出厂设定,把引擎调成地理工作者需要的样子。本节记录装配的实际形态,它是 GeoCode Agent 内核区别于上游的全部内容。

装配层位于 `opencode/src/config/geocode.ts`,由 `config.ts` 在配置流水线的**最前端**合并。位置的选择即是语义:排在最前意味着这些是「出厂默认」,用户自己的配置仍可覆盖模型、温度乃至新增 agent——GeoCode 规定开箱是什么样,不剥夺用户调整的自由。将来若出现用户**不可**覆盖的安全红线,会另起一段在流水线**最末端**合并——那一段尚未建立,因为目前没有需要锁住的东西:地理能力的默认拒绝写在最前端这一段里,用户可以覆盖,与上游对待它自己每个工具的方式一致。

### 5.1 Agent 阵容

| Agent | 来源 | 角色 |
|---|---|---|
| GeoAgent | 装配层新增 | 唯一暴露的主 agent,默认选中 |
| explore | 上游保留,加一项权限 | 只读勘察:在代码项目里找路,在大批地理数据里筛出相关的几份 |
| osmfetch | 装配层新增 | 承担全部 OSM 下载,网络出口受权限锁定 |
| plan | 上游保留 | 计划模态(见 §5.3) |
| compaction / summary / title | 上游保留 | 内部功能 agent,用户不可见 |
| ~~build~~ / ~~general~~ | 上游定义保留,装配层禁用 | 编程向,与地理工作无关 |

两个被移除的 agent **都不是删代码删掉的**,而是在装配层声明 `disable: true`——内核收到该字段会把它们从 agent 表里真正删除(不是隐藏)。这样做的理由是合并成本:`agent.ts` 是上游改动最频繁的文件之一,在里面增删条目等于把自己放到每次升级的冲突路径上;而禁用只是我们自己文件里的一行数据,上游怎么重构都碰不到。

GeoAgent 与 osmfetch 因此是「由配置创建」的 agent,而 `agent.ts` 给这条路径上的每个 agent 打 `native: false`。**这一行现在改成读装配层的 `shippedAgents`**,让这两个也拿到 `true`。

⚠️ **这里原先写着「不必为它去改源码」,那个判断是错的**,记下来免得再犯:它成立的前提是这个标记只影响 TUI 的显示字样,而那是桌面壳落地之前的视野。壳里同一个标记控制**三件事** —— 侧栏分到「内置」还是「自定义」区、徽章显示 `system` 还是配置作用域、以及菜单里给的是**重置**还是**改名与删除**。也就是说不改的话,GeoCode 的主 agent 会被显示成用户自建的,还带一个可点的删除按钮,而我们只是借用的 `plan` 和 `explore` 反倒躺在内置区。对 GeoCode 用户来说,产品带来的四个 agent 就都是内置的。

改动落在 `agent.ts` 的那一个字面量上(形态 ③),名单在 `config/geocode.ts` 里与 `base()` 相邻——两者必须同时改。名单是**列举而非从 `base().agent` 推导**的,因为那个对象里装着三类:`plan` 与 `explore` 是上游的、本来就 native,`build` 与 `general` 出现在那里只是为了被禁用。

标记本身在内核里仍然只是展示:除了 agent 表自己,全内核只有 `cli/cmd/agent.ts` 的一次排序读它。

移除 `general` 之所以安全,是因为子代理由模型通过 `subagent_type` 参数主动指定,而 task 工具的可用清单是**动态生成**的——它按 agent 的 `task` 权限逐个过滤,清单里没有的名字模型根本看不见,不存在指向空名字的悬空调用。清单当前是 `explore` 与 `osmfetch` 两个。

这条过滤有一个反直觉的后果,记在这里免得重蹈:**用 `task: { "*": "deny" }` 做子代理白名单会让用户自定义的子代理静默消失**——它们定义了却不出现在清单里,而且无处报错。所以 GeoAgent 的 `task` 不写任何规则,plan 对 osmfetch 写的是 `ask` 而非 `deny`(TOOLS.md §4.4)。

**`explore` 留下来,装配层只给它加了一项权限:读地理数据。** 它不只是一个编程向的搜索 agent,更是上游**上下文卸载**机制的执行端——工具输出超限时的提示、`grep` 与 `glob` 对开放式搜索的建议,三处都把活派向它。移除它,这些提示会指向一份没有合适人选的清单,而每一份大输出都压回主 agent 自己的上下文窗口。用户也确实会带来代码:一个遥感处理项目就是一个脚本目录。

给它地理读取权,是因为地理数据有一个代码没有的性质:**文件名与内容无关**。`user-service.ts` 说明了自己是什么,`clip_2.tif` 什么也不说——所以在一个装了两百份数据的目录里挑出相关的那几份,只能逐个打开来看,而这正是该在别人的上下文里做的事。

但它只做收窄,不做转述:坐标系、范围、字段这些决策依据,由做决策的 agent 第一手读取,因为转述会掉一层而下游无从察觉。`qgis`、`gee`、`osm` 对它一律拒绝——**它能描述数据,不能改动数据**。

### 5.2 提示词体系

一次模型请求的系统提示词由五段拼接:基础提示词、环境信息、项目指令、MCP 工具说明、技能清单。后四段对所有 agent 无条件附加,**GeoCode 只改第一段**。

第一段的来源是个二选一:agent 若定义了自己的 `prompt` 就用它,否则由基础提示词选择器按模型家族给出——上游为此备了九份(Claude 用一份、GPT 系用另一份,依此类推),每一份都是为编程助手写的,每一份都以 「You are OpenCode」 开头。

GeoCode 把这个选择器改为恒定返回 `prompt/geocode.txt`。这个决定的关键不在于「换一份提示词」,而在于**改动位置**:若只给 GeoAgent 设置 `prompt`,那 plan、以及用户创建但正文为空的子代理仍会落到上游那九份上,继续自称 OpenCode;改选择器则一次覆盖所有没有自带提示词的 agent。九份上游文件原样留在树里——不删,只是不再被引用,恢复分模型选择只需还原这一个函数。

代价是放弃按模型家族调优。那些差异主要针对编程场景(例如给 GPT 系加强步骤约束),对地理任务不敏感;而 v1.18.18 新增的两条分支——Meta 系把模型名注入提示词、Kimi 改按 `providerID` 认——针对的是**那九份文件自身的占位符与自称**,`geocode.txt` 不含这类占位符,因此不适用。

⚠️ **不要用「GeoCode 以 Claude 生态为主」论证这件事。** 这句话曾经写在此处,而它不成立:装配层不钉任何模型(`config/geocode.ts` 没有 `model` 字段),用户配什么就跑什么,整个上游 provider 生态原样继承。它已经造成过一次误判——审查 v1.18.18 的压缩改造时,据它得出「上游为小模型做的改进与我们无关」,而小模型恰恰是我们的真实场景之一。**判据应当是「那份差异是否作用于我们实际使用的文件」,不是「我们的用户大概率用哪家模型」。**

`geocode.txt` 本身承袭旧版打磨多轮的 GeoAgent 提示词,逐字迁移:它保留了上游提示词中真正有价值的通用素养——不迎合用户、有分歧直说、不确定先查证——并在其上叠加地理工程规范:临时文件归置、产出必须验证、坐标系全程意识、按计算成本排序工作流。

**会话压缩的提示词是第二处改动,只改了一个词。** 压缩由一个隐藏的内部 agent 承担,而它跑在**会话当前的模型**上(`session/prompt.ts` 把 `lastUser.model` 传给 `compaction.create`),不存在专门的摘要模型——用户拿小模型跑地理会话时,压缩也是那个小模型。上游的 system 提示词把摘要说成「给另一个 **coding** agent 接手用的」,首次压缩的用户提示词里再说一次;两处的 「coding」 都去掉了。

一个词值得动手,是因为摘要是**后续所有轮次唯一能依据的东西**,而地理会话要留住的是坐标系、输出路径与数据缺口。同一处的另一半改动是 `SUMMARY_TEMPLATE` 里增设的 `## Plan and Rules` 段落(GEOKERNEL §10.1 #11)。这三处都载不动 `GeoCode:` 标记,可审计性由两条绊线承担:`opencode/test/geocode-compaction-prompt.test.ts` 断言 system 不再点名编程,`core/test/geocode-compaction-template.test.ts` 断言模板段落在两条 `buildPrompt` 分支里都还在——v1.18.18 把它拆成了「首次压缩」与「后续压缩」两条路,而后者才是长会话的常态。

### 5.3 计划模式

计划模式的本质是同一个 agent 被禁用编辑权限:plan 与主 agent 共用同一份人格,差别只在权限。内核用两种手段实现禁用——权限规则为通配拒绝时,工具**直接从模型的工具清单中移除**(而非调用后返回拒绝);更精细的规则才在执行前拦截。切换时,系统向用户消息注入一段模型可见、用户不可见的提醒:进入时告知只读约束,退出时告知已可执行。这些注入只在**发送消息**时发生,反复切换而不发消息不会产生任何注入。

GeoCode 保留整套机制,只做适配。上游多处假设「主 agent 永远叫 build」:退出计划模式时的提醒判定写死了这个名字,而 GeoCode 禁用了 build,该判定将永不成立、提醒会静默消失。判定因此改为「切到任何非 plan 的 agent」——这既修好了 GeoCode 的情况,也顺带修好了上游对自定义 agent 的同一缺陷。两段提醒文案中的 `build` 字样与对代码搜索子代理的点名,同样改为中性表述,以适配 GeoAgent 及将来的其他领域 agent。

上游另有一套让模型主动进出计划模式的工具(`plan_enter` / `plan_exit`),但它只完成了一半——权限、提示词、界面分支都在,进入工具的实现并不存在,退出工具则藏在实验开关之后且写死回到 build。GeoCode 不启用这套半成品。**那些硬编码原样留着,不加注释标注** —— 一处不产生行为的补丁只会占一个合并冲突位(§4.3 的反例就是它)。要动的地方在这里记着,**两处都写死了 `build`,而它在 GeoCode 里是禁用的**:`tool/plan.ts` 的 `PlanExitTool` 把注入消息的 `agent` 定为 `build`,`tui/src/routes/session/index.tsx` 的 `plan_exit` 分支调 `local.agent.set("build")`。实验开关转正时,两处连同界面一并改成切回默认 agent 并验证。

提示词文件有一个特殊性:它们的全部内容会原样送进模型,因而**无法承载 `GeoCode:` 注释标记**——那会污染指令。这类改动的可审计性只能由绊线测试提供:测试断言文件中不再出现 `build` 字样与被点名的子代理,上游合并若覆盖回来,测试立即变红。

### 5.4 一次刻意的推迟,和它的结果

地理工具的权限分组、osmfetch 子代理及其网络出口锁、栅格文件防文本误读——这三项在设计就绪之后,被**刻意推迟到地理工具真正存在之后**才装配。

理由是本项目反复重申的一条铁律:不做无法当场验证的改动。权限规则的失效方式极其隐蔽,它不报错,只是安静地不生效;在没有工具可拦截的情况下写拦截规则,等于把正确性押在阅读代码的自信上。旧版那次蛇形/驼峰的名字错配正是这种失效真实发生过的证据(TOOLS.md §4.1)。

三项现已全部落地(见 §4.1),推迟的收益也兑现了:每一条规则都写在工具存在之后,因此每一条都能用运行时测试确认它**确实命中**,而不是确认它**确实写了**——在权限上,这从来不是一回事。绊线覆盖四个角度:每个 agent 看得见哪些工具、每个工具实际用哪个键申请、一条按组写的规则是否恰好覆盖该组全部成员、以及每个 agent 实际能做什么。

## 6. 屏蔽清单

§3 的阶梯把源码补丁放在最后一级,并要求每一处**书面回答「为什么上面四层做不到」**。本节是那份回答的集中处:GeoCode 屏蔽了引擎的七项机制,每一项都因为配置、环境变量、外挂进程、界面这四层都表达不了,才落到源码。

清单**可枚举**是这件事成立的前提。DESIGN.md §2 把「产品边界优先由装配决定」列为原则,而不可枚举的例外等于没有原则。上游将来若为其中某项提供了配置开关,对应条目应当降级回阶梯第一级,并从本表移除。

**清单之外,配置面与上游同构。** 位置(全局 / 项目 / 环境变量 / 远程 / 系统受管)、合并优先级、六种配置形式、全部顶层字段与 `{env:}` `{file:}` 变量替换语法一律不变。用户可以直接照上游文档配置 GeoCode,只需把文件名换成品牌名(PATHS.md §5)。本节刻意不复述上游的字段表——复述必然漂移。

被屏蔽的配置项**不生效,也不提示**。这是有意的:提示要么落进用户看不见的日志,要么需要在界面上专门造一条只为解释缺席功能的通道,两者都不值得。

前两项合起来是同一个事实的两半:**打开一个文件夹不应该导致其中的代码被执行**。那个文件夹可能来自同事、下载或 clone。用户要扩展工具,通道是 MCP——进程外、可按 `mcp:<server>:*` 单独授权、不写我们的路径。

三、四、六项的分界是**归属**:关掉的是**不属于 GeoCode 体系**的位置——其他产品专有的(`.claude/`、`~/.opencode/`),以及写给任意 agent 工具的公共技能库(`.agents/skills`)。GeoCode 是地理助手而不是通用 agent,它的行为不该因为磁盘上存在别的工具的技能而改变。

保留的是**信息**而非**能力**:`AGENTS.md` 照读不误(全局那份在 `~/.config/GeoCode/`,项目那份是仓库对所有 agent 工具的声明)——项目的规矩我们收,项目往 GeoAgent 里注入新技能这条通道我们不收。**用户自定义技能没有被关掉**,只是改从我们自己的位置进:`~/.config/GeoCode/{skill,skills}`、项目 `.geocode/{skill,skills}`、或配置里的 `skills.paths`——关闭后前者仍被读到,实测过。

**连带去掉的**:上游会往每个配置目录(含用户项目里的那个)安装 `@opencode-ai/plugin` 并写一份 `.gitignore`,那是为了让用户自写的插件与工具能 import SDK。两者都不加载之后,这个安装失去服务对象,一并删除——用户项目里因此不会再出现 `node_modules/`(PATHS.md §3.3)。

**刻意保留的**,列出来以免被后来者顺手一起删掉:

- **内置插件系统**——模型 provider 全部以内置插件实现(`core/src/plugin/provider/` 下的一批文件)。屏蔽的是 `loadExternal` 这条外部加载路径,不是插件机制本身。字面量绊线专门断言 provider 的注册行仍在。
- **`Npm` 服务**——非内置 provider 靠它下载 SDK,LSP 与格式化器靠它装语言服务器。删掉的只是「往配置目录装插件 SDK」这一个调用点。
- **`plugin` 与 `tools` 配置字段**——schema 不动,用户写了照常解析,只是无人消费。这是「形式与上游一致」的要求。
- **MCP**——用户扩展工具的唯一通道,与插件系统零耦合(它不碰 `Npm`,只 spawn 用户配置的命令)。

**被截断后不可达的代码原样留着不删**(`cli/cmd/plug.ts`、`plugin/install.ts`、`loader.ts` 的解析辅助、`core/src/config/plugin/external.ts`)。删它们要动 import 与依赖列表,那是合并冲突最密的地方,而它们零运行时成本。绊线保证它们不会被重新接上。

绊线分两层:**行为**层在沙箱项目里放会留下证据文件的模块,断言它们从未被 import、工具未注册、目录里没有 `node_modules/`;**字面量**层断言五处截断仍在源码里,并同时断言 provider 的注册没被一起删掉。每一处都做过反证——还原截断,证据文件立刻出现。
