# Agent 内核:设计与迁移

## 1. 内核是什么

GeoCode 的会话循环、模型接入、OAuth 登录、权限系统与工具调度,由 OpenCode 的 agent 引擎承担。这是刻意的选择:这些子系统的正确性——尤其 OAuth 的 wire 协议——直接决定用户能否用已有订阅登录,自研或深改它们没有收益,只有风险。对 GeoCode 的其余部分,内核呈现为一组 HTTP API(供界面)与一个 MCP 客户端(供地理内核挂载工具),接近黑盒。

内核以**薄 fork** 的方式维护,与产品同仓但界限分明:上游 v1.18.4 的内核闭包(15 个包 + 根工程设施)以 vendor 方式存放在本仓 `kernel/` 目录下,原味落盘保存在专用的 `kernel-upstream` 分支——该分支只接受"上游版本的原样文件圈选",内容零修改;`main` 经 subtree 合并持有 `kernel/` 并叠加我们的薄补丁。这套结构让升级内核成为一次真正的三方合并(git 自动重放薄补丁),而不是人肉 diff。`kernel/` 是独立的 bun 安装根(与仓根各自 `bun install`),构建产物(server bundle)供壳打包。我们对源码差异有一条铁律:**越薄越好**——差异越薄,合并上游的成本越低,薄到极致时升级内核约等于换一个依赖版本。

## 2. 内核的构成

`kernel/` 收纳上游 monorepo 中与 agent 引擎相关的最小闭包,共 15 个包,分三层:**运行时 11 包**——`opencode`(CLI 入口、命令表、会话运行时与本地 HTTP server 本体)、`core`(引擎主体:配置、工具、provider、存储、PTY、文件系统、XDG 路径)、`llm`(模型协议适配)、`schema` 与 `protocol`(类型与线协议底座)、`server`(httpapi 零件库——注意真正的 `Server.listen` 在 opencode 包内,勿混淆)、`plugin`、`sdk/js`、`codemode` 及两个 sqlite 绑定包;**TUI 测试台 2 包**——`tui` 及其此刻仍拖带的 `ui`(仅因六个提示音文件被引用,是后续薄补丁的裁剪候选);**工具层 2 包**——`script`(构建常量)与 `http-recorder`(测试录放,零运行时字节)。随行的根设施:bun catalog 版本表、依赖补丁集、bunfig、turbo、tsconfig 与 `fix-node-pty` postinstall——它们与包是一体的,缺一不可。

生产入口是 `build-node` 构建:把 `src/node.ts` 打成 Node ESM bundle(内嵌 Web UI 被桩空,产物不含任何上游前端),供壳以 utilityProcess 运行;开发入口是 TUI(`opencode` 命令的终端形态),作为装配验证的测试台。三条技术约束必须敬畏:其一,`#pty`/`#sqlite`/`#fff`/`#db` 条件导入的 bun/node 双轨实现是内核既能 bun 跑又能在 Electron 的 Node 里跑的命脉,升级合并时不可破坏;其二,构建期会抓取 models.dev 的模型快照,离线构建须以环境变量喂本地文件;其三,PTY、文件监听、语法解析等原生依赖经由 catalog 钉版,postinstall 修复钩子必须保留。

## 3. 定制阶梯

GeoCode 的一切内核定制,按下面的优先级实现,只允许用尽可能高的层级;源码补丁是最后手段:

1. **配置** —— agent 定义与默认 agent、禁用内置 agent、权限规则、MCP 注册、技能扫描目录;
2. **环境变量** —— 数据目录定向(XDG 族)、服务口令;
3. **外挂进程** —— 地理工具经 MCP 进入引擎,技能经扫描目录进入引擎;
4. **界面** —— 纯展示层的取舍(如不显示某些斜杠命令)在界面代码完成;
5. **源码补丁** —— 每一处必须书面回答"为什么上面四层做不到",并配一个运行时绊线测试。

第 5 级的"书面回答"集中在 §6:凡是屏蔽引擎既有机制的补丁,都在那份清单上,连同它的截断点与绊线。

这条阶梯建立在对引擎装配面的逐项验证上:agent 可以完全由配置定义并设为默认,内置 agent 可被真正禁用(从列表删除,而非隐藏);权限引擎按通配符匹配任意工具名与路径模式,足以表达"栅格文件禁止文本读取""OSM 工具只许下载子代理使用";数据目录完全由 XDG 环境变量决定,macOS 亦然。

**GeoCode 的装配目标**:GeoAgent 是唯一暴露的主 agent(地理科学专家人设,内置编码向 agent 禁用);osmfetch 是唯一子代理(OSM 数据下载),其网络出口被权限规则锁死——只许 OSM 工具组,webfetch、websearch 与再派生子任务一律拒绝,防止提示注入把它变成任意抓取器;地理工具默认对所有 agent 拒绝、仅对 GeoAgent 放行,保证将来引入其他领域 agent 时地理能力边界不会静默扩大。这些目标的实现进度与实际形态见 §5——agent 阵容与人格已就位,涉及地理工具的权限部分待工具落地。

**冻结区**:内核中 provider、auth、account 及模型协议相关的包永久与上游逐字节一致,合并时无条件取上游;`@opencode-ai/*` 包名、`OPENCODE_*` 环境变量、User-Agent 与 Referer 等 wire 指纹逐字保留。

## 4. 如何迁移 OpenCode 内核

### 4.1 重建定制:把旧版需求搬上阶梯

`kernel/` 从原味上游起步,不携带任何历史注入;GeoCode 的既有定制(旧版 fork 是现成的需求说明书)逐类以装配重新实现。每类独立提交、配绊线测试,实现一类验证一类:

| 既有源码注入 | 搬往 | 状态 |
|---|---|---|
| GeoAgent 定义、禁用内置 agent、默认 agent | 配置(agent 定义 + disable + default_agent) | 已完成(§5.1) |
| 基础人格与品牌 | 源码补丁(基础提示词选择器) | 已完成(§5.2) |
| 计划模式对 `build` 的硬依赖 | 源码补丁(判定通用化)+ 提示词文案 | 已完成(§5.3) |
| 数据目录命名空间 | 源码补丁(单一 `Brand` 模块) | 已完成(见 PATHS.md) |
| osmfetch 子代理定义 | 配置(agent 定义 + 权限) | 待地理工具落地 |
| 地理工具权限分组 | 配置(按工具名圈组) | 待地理工具落地(§5.4) |
| 栅格文件防文本误读 | 配置(read 权限的 glob 拒绝规则) | 待地理工具落地 |
| 地理能力的执行与环境管理 | 地理内核(**本进程内的服务层**,设计见 GEOKERNEL.md) | 已完成 |
| 数据面 HTTP 路由 | 同上,挂在内核自有的 httpapi 上 | 已完成(GEOKERNEL.md §7.7) |
| 地理工具注册 | 工具注册表 + 权限分组 | 未开始(GEOKERNEL.md §11.2 是移交清单) |
| 技能商店 | 受管目录 + 引擎扫描路径 | 未开始 |
| 面向程序员的斜杠命令裁剪 | 界面过滤 | 未开始 |

一处订正:旧版的权限规则以 `geo_read`、`qgis_doc` 这类**蛇形名**书写,而地理工具的真实注册名是 `ReadGeoData`、`QgisDoc` 等**驼峰名**——两者从不匹配,那些规则很可能从未真正生效过。这是"配置期望被某个服务读到、却无人验证读取方"的典型事故。将来编写权限分组时必须以工具的真实注册名为准,并以运行时测试确认规则确实命中。

**补丁面的实际形态**(2026-08 实测:`GeoCode:` 标记出现在 57 个文件里——9 个是我们自有的新文件,39 处打在上游源码上,9 处打在上游测试上):

| 类别 | 规模 | 性质 |
|---|---|---|
| 磁盘身份 | 二十余处 | 几乎全是一行替换,把字面量换成 `Brand.*`(PATHS.md §5) |
| 装配层接入 | 3 处 | `geocode.ts` 的合并点、提示词选择器、计划模式判定 |
| **屏蔽清单** | **5 项 / 7 处截断** | 每项书面回答"为什么装配做不到",见 §6 |
| 地理内核注入 | §10.1 的清单 | 逐项列举、逐项配绊线,**不是零散生长而是一份可对账的表** |
| Windows shell 白名单 | 约 60 行 | 保证 GIS 工具链路径风格唯一 |
| 上游测试的夹具 | 9 处 | 让夹具写"加载器会读的名字";改名后一处共享夹具就救回约 230 个测试 |

早期版本在这里写过"个位数文件"的目标,那是 GEOKERNEL.md §10.1 那份注入点清单出现之前定的,已被有计划的执行超过。**判据因此从"文件数"改为"是否在清单上"**:补丁可以增加,但每一处都必须能在 GEOKERNEL.md §10.1、本文 §6 或本节找到条目,并配一个运行时绊线。找不到条目的补丁就是欠账。

定位命令见 CONVENTIONS.md §5——一条 grep 列全。

### 4.2 验证:以上游 TUI 为测试台

内核装配的验证不需要 GeoCode 界面:直接以终端形态运行内核,确认 GeoAgent 出现并成为默认、内置 agent 消失、权限规则生效、MCP 工具可调。这让内核迁移与界面开发完全解耦,零界面成本闭环。

### 4.3 升级:按需合并上游

内核升级是可选的、按需的,停靠不设期限(当前基线:上游 v1.18.4)。流程:

1. 在 `kernel-upstream` 分支落盘目标上游版本的原味闭包(一个 commit)。**落盘后必须做文件集对账**(快照文件清单 vs 提交文件清单)——上游各级 gitignore 会静默吞掉它自己强制跟踪的文件(v1.18.4 的 `build-node.ts` 之鉴);然后 `git merge -X subtree=kernel kernel-upstream`(薄差异使冲突极小;解冲突逐处手解,**绝不整文件取某一方**);
2. 运行绊线测试套件——每处源码补丁对应一个运行时测试,补丁被上游重构架空时测试变红,而不是靠人工排查静默失效;
3. 构建内核 bundle,进入产品仓,全链路实机重测;
4. 任何一步不满意,回退停靠原版本。

### 4.4 迁移期间的安全网

迁移全程,旧版 GeoCode 保持可发布;`kernel/` 的每类装配与补丁都是独立 commit,可整步回退。历史经验反复证明:编译通过与测试全绿不等于运行时正确,凡涉及"配置期望被某个服务读到"的改动,必须追踪到读取方并用运行时测试锁定。

## 5. GeoCode 的 Agent 装配

上游内核是一台通用的 agent 引擎,它的出厂设定服务于编程助手:主 agent 叫 `build`,基础人格自称 OpenCode,子代理是代码搜索与代码任务。GeoCode 的个性不通过改造这台引擎获得,而是通过**装配**——一层薄薄的出厂设定,把引擎调成地理工作者需要的样子。本节记录装配的实际形态,它是 GeoCode Agent 内核区别于上游的全部内容。

装配层位于 `opencode/src/config/geocode.ts`,由 `config.ts` 在配置流水线的**最前端**合并。位置的选择即是语义:排在最前意味着这些是"出厂默认",用户自己的配置仍可覆盖模型、温度乃至新增 agent——GeoCode 规定开箱是什么样,不剥夺用户调整的自由。将来需要用户**不可**覆盖的安全红线(地理工具的默认拒绝),会以第二段 `enforced()` 在流水线**最末端**合并;它此刻刻意留空,因为还没有需要锁住的东西。

### 5.1 Agent 阵容

| Agent | 来源 | 角色 |
|---|---|---|
| GeoAgent | 装配层新增 | 唯一暴露的主 agent,默认选中 |
| plan | 上游保留 | 计划模态(见 §5.3) |
| compaction / summary / title | 上游保留 | 内部功能 agent,用户不可见 |
| ~~build~~ / ~~explore~~ / ~~general~~ | 上游定义保留,装配层禁用 | 编程向,与地理工作无关 |

三个被移除的 agent **都不是删代码删掉的**,而是在装配层声明 `disable: true`——内核收到该字段会把它们从 agent 表里真正删除(不是隐藏)。这样做的理由是合并成本:`agent.ts` 是上游改动最频繁的文件之一,在里面增删条目等于把自己放到每次升级的冲突路径上;而禁用只是我们自己文件里的一行数据,上游怎么重构都碰不到。

GeoAgent 因此是"由配置创建"的 agent,内核会给它打上 `native: false` 标记。该标记只影响 agent 选择框里显示描述还是显示 "native" 字样,不影响任何能力,不必为它去改源码。

移除 `explore` 与 `general` 之所以安全,是因为子代理由模型通过 `subagent_type` 参数主动指定,而 task 工具的可用清单是**动态生成**的:清单里没有的名字,模型根本看不见,不存在指向空名字的悬空调用。当前子代理清单为空,osmfetch 落地后填充。

### 5.2 提示词体系

一次模型请求的系统提示词由五段拼接:基础提示词、环境信息、项目指令、MCP 工具说明、技能清单。后四段对所有 agent 无条件附加,**GeoCode 只改第一段**。

第一段的来源是个二选一:agent 若定义了自己的 `prompt` 就用它,否则由基础提示词选择器按模型家族给出——上游为此备了九份(Claude 用一份、GPT 系用另一份,依此类推),每一份都是为编程助手写的,每一份都以 "You are OpenCode" 开头。

GeoCode 把这个选择器改为恒定返回 `prompt/geocode.txt`。这个决定的关键不在于"换一份提示词",而在于**改动位置**:若只给 GeoAgent 设置 `prompt`,那 plan、以及用户创建但正文为空的子代理仍会落到上游那九份上,继续自称 OpenCode;改选择器则一次覆盖所有没有自带提示词的 agent。九份上游文件原样留在树里——不删,只是不再被引用,恢复分模型选择只需还原这一个函数。

代价是放弃按模型家族调优。那些差异主要针对编程场景(例如给 GPT 系加强步骤约束),对地理任务不敏感;GeoCode 又以 Claude 生态为主,这个取舍可以接受。

`geocode.txt` 本身承袭旧版打磨多轮的 GeoAgent 提示词,逐字迁移:它保留了上游提示词中真正有价值的通用素养——不迎合用户、有分歧直说、不确定先查证——并在其上叠加地理工程规范:临时文件归置、产出必须验证、坐标系全程意识、按计算成本排序工作流。

### 5.3 计划模式

计划模式的本质是同一个 agent 被禁用编辑权限:plan 与主 agent 共用同一份人格,差别只在权限。内核用两种手段实现禁用——权限规则为通配拒绝时,工具**直接从模型的工具清单中移除**(而非调用后返回拒绝);更精细的规则才在执行前拦截。切换时,系统向用户消息注入一段模型可见、用户不可见的提醒:进入时告知只读约束,退出时告知已可执行。这些注入只在**发送消息**时发生,反复切换而不发消息不会产生任何注入。

GeoCode 保留整套机制,只做适配。上游多处假设"主 agent 永远叫 build":退出计划模式时的提醒判定写死了这个名字,而 GeoCode 禁用了 build,该判定将永不成立、提醒会静默消失。判定因此改为"切到任何非 plan 的 agent"——这既修好了 GeoCode 的情况,也顺带修好了上游对自定义 agent 的同一缺陷。两段提醒文案中的 `build` 字样与对代码搜索子代理的点名,同样改为中性表述,以适配 GeoAgent 及将来的其他领域 agent。

上游另有一套让模型主动进出计划模式的工具(`plan_enter` / `plan_exit`),但它只完成了一半——权限、提示词、界面分支都在,进入工具的实现并不存在,退出工具则藏在实验开关之后且写死回到 build。GeoCode 不启用这套半成品;相关的硬编码以注释标注为债务,待其转正时连同界面一并修改与验证。

提示词文件有一个特殊性:它们的全部内容会原样送进模型,因而**无法承载 `GeoCode:` 注释标记**——那会污染指令。这类改动的可审计性只能由绊线测试提供:测试断言文件中不再出现 `build` 字样与被点名的子代理,上游合并若覆盖回来,测试立即变红。

### 5.4 尚未装配的部分

地理工具的权限分组、栅格文件防文本误读、osmfetch 子代理及其网络出口锁——这些都已设计就绪,但**刻意推迟到地理工具真正存在之后**。

理由是本项目反复重申的一条铁律:不做无法当场验证的改动。权限规则的失效方式极其隐蔽,它不会报错,只会安静地不生效;而 §4.1 记录的那个蛇形/驼峰命名错配,正是这种失效在旧版中真实发生过的证据。在没有工具可以拦截的情况下编写拦截规则,等于把正确性寄托在阅读代码的自信上。等工具落地,每一条规则都能当场被验证是否真的命中。

## 6. 屏蔽清单

§3 的阶梯把源码补丁放在最后一级,并要求每一处**书面回答"为什么上面四层做不到"**。本节是那份回答的集中处:GeoCode 屏蔽了引擎的五项机制,每一项都因为配置、环境变量、外挂进程、界面这四层都表达不了,才落到源码。

清单**可枚举**是这件事成立的前提。DESIGN.md §2 把"产品边界优先由装配决定"列为原则,而不可枚举的例外等于没有原则。上游将来若为其中某项提供了配置开关,对应条目应当降级回阶梯第一级,并从本表移除。

**清单之外,配置面与上游同构。** 位置(全局 / 项目 / 环境变量 / 远程 / 系统受管)、合并优先级、六种配置形式、全部顶层字段与 `{env:}` `{file:}` 变量替换语法一律不变。用户可以直接照上游文档配置 GeoCode,只需把文件名换成品牌名(PATHS.md §5)。本节刻意不复述上游的字段表——复述必然漂移。

被屏蔽的配置项**不生效,也不提示**。这是有意的:提示要么落进用户看不见的日志,要么需要在界面上专门造一条只为解释缺席功能的通道,两者都不值得。

| # | 屏蔽项 | 为什么前四层做不到 | 截断点 |
|---|---|---|---|
| 1 | 外部插件(配置里声明的 + `{plugin,plugins}/` 自动发现) | 配置里**没有**"关闭插件加载"这个键。而且加载有两条独立路径,其中 `core` 侧那条(内置的 `config-plugin`)不受任何开关约束——实测在 `OPENCODE_DISABLE_PROJECT_CONFIG=1` 下仍然执行了项目里的插件 | `plugin/loader.ts` 的 `loadExternal`(两个调用点的唯一必经处)+ `core/plugin/internal.ts` 摘掉 `ConfigExternalPlugin` 的注册 |
| 2 | 文件式工具 `{tool,tools}/*.{js,ts}` | 扫描写死在工具注册表的构建里,没有开关;它与 `plugin` 是**不同的扩展点**,关掉插件并不能关掉它 | `tool/registry.ts` 的发现处 |
| 3 | Claude Code 的 `CLAUDE.md` 与 `.claude/skills` | 上游有 env 开关,但**默认是开的**。靠启动方设 env 会静默失败,而且失败方向是开放的——桌面壳与测试台各是一条启动路径,漏一条就恢复读取 | `effect/runtime-flags.ts` 的两个默认值(env 仍可反向打开) |
| 4 | `~/.opencode` 家目录扫描 | 上游**没有任何开关**能挡它——`OPENCODE_DISABLE_PROJECT_CONFIG` 只管项目级 | `config/paths.ts` 整段删除。我们只有一个全局根,没有 `~/.geocode` 可改名 |
| 5 | 会话分享 | 有 env 开关但默认开;而且只翻模块常量的话 `create()` 会返回一个空 URL 而不是报错,配置面必须同时表态 | `share/share-next.ts` 的模块常量 + `geocode.ts` 的 `share: "disabled"` |

前两项合起来是同一个事实的两半:**打开一个文件夹不应该导致其中的代码被执行**。那个文件夹可能来自同事、下载或 clone。用户要扩展工具,通道是 MCP——进程外、可按 `mcp:<server>:*` 单独授权、不写我们的路径。

第三、四项的分界是**来源**而非功能:关掉的是**其他产品专有**的位置(`.claude/`、`~/.opencode/`),保留的是跨产品的**开放约定**(`AGENTS.md`、`.agents/skills`)——后者的内容是用户自己刻意放的。

**连带去掉的**:上游会往每个配置目录(含用户项目里的那个)安装 `@opencode-ai/plugin` 并写一份 `.gitignore`,那是为了让用户自写的插件与工具能 import SDK。两者都不加载之后,这个安装失去服务对象,一并删除——用户项目里因此不会再出现 `node_modules/`(PATHS.md §3.3)。

**刻意保留的**,列出来以免被后来者顺手一起删掉:

- **内置插件系统**——模型 provider 全部以内置插件实现(`core/src/plugin/provider/` 下 32 个文件)。屏蔽的是 `loadExternal` 这条外部加载路径,不是插件机制本身。字面量绊线专门断言 provider 的注册行仍在。
- **`Npm` 服务**——非内置 provider 靠它下载 SDK,LSP 与格式化器靠它装语言服务器。删掉的只是"往配置目录装插件 SDK"这一个调用点。
- **`plugin` 与 `tools` 配置字段**——schema 不动,用户写了照常解析,只是无人消费。这是"形式与上游一致"的要求。
- **MCP**——用户扩展工具的唯一通道,与插件系统零耦合(它不碰 `Npm`,只 spawn 用户配置的命令)。

**被截断后不可达的代码原样留着不删**(`cli/cmd/plug.ts`、`plugin/install.ts`、`loader.ts` 的解析辅助、`core/src/config/plugin/external.ts`)。删它们要动 import 与依赖列表,那是合并冲突最密的地方,而它们零运行时成本。绊线保证它们不会被重新接上。

绊线分两层:**行为**层在沙箱项目里放会留下证据文件的模块,断言它们从未被 import、工具未注册、目录里没有 `node_modules/`;**字面量**层断言五处截断仍在源码里,并同时断言 provider 的注册没被一起删掉。每一处都做过反证——还原截断,证据文件立刻出现。
