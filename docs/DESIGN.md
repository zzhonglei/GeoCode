# GeoCode 项目总体设计

## 1. 产品定位

GeoCode 是一个面向地理工作者的桌面 AI 应用:用户用自然语言描述地理任务,内置的 GeoAgent 调用 QGIS、GDAL、GEE 与 OSM 等专业工具完成数据处理,结果(栅格、矢量、属性表)直接在应用内可视化。它服务的是开地图、跑遥感、做空间分析的人,不是程序员;界面以地理工作流为中心,面向开发者的表面保持克制。

GeoCode 只有一种形态:桌面应用,macOS(arm64)与 Windows(x64)。不做 CLI、Web、移动端或编辑器插件——单一形态让一个人能把一件事做好。

## 2. 设计原则

**消费内核,而非改造内核。** GeoCode 的会话与推理能力来自 OpenCode 的 agent 引擎。我们不把自己的功能写进引擎源码,而是通过引擎公开的装配面(配置、环境变量、MCP、技能目录)把 GeoCode 组装出来;只有装配面确实无法表达的少量差异,才以最小补丁保留在内核里(详见 KERNEL.md)。上游演进时,我们的成本是"换一颗内核重新测试",而不是"把定制重新缝进新源码"。

**地理能力自成一体。** 一切地理专业逻辑——工具执行、环境探测、数据预览、技能商店——集中在独立的地理内核进程里,不依赖 agent 引擎的内部结构,只通过标准接口与引擎和界面对话。地理内核是 GeoCode 真正的技术资产,按独立系统来设计和测试。

**不需要的能力不进产品。** 引擎自带的开发者向特性(内置编码 agent、代码审查命令、多服务器连接等)不做删改,只是不装配、不显示。产品边界由装配决定,而不是由删除决定。

## 3. 系统构成

GeoCode 由四个部分组成,运行时是三类进程:

```
┌───────────────────────────────────────────────────────────┐
│ 桌面壳(Electron main + preload)                          │
│   窗口与菜单 · 进程生命周期 · 凭据分发 · 更新通知 · 深链   │
│                                                            │
│   ├── fork → Agent 内核(OpenCode 引擎,见 KERNEL.md)      │
│   └── fork → 地理内核(每工作区一实例,见 §3)              │
│                                                            │
│   界面(SolidJS,oc:// 协议加载)                           │
│     ├─ HTTP/SSE → Agent 内核(会话、消息、事件)            │
│     └─ HTTP/SSE → 地理内核(预览、环境状态、技能商店)      │
│                                                            │
│   Agent 内核 ── MCP ──> 地理内核(agent 调用地理工具)      │
└───────────────────────────────────────────────────────────┘
```

**桌面壳**是唯一的进程管理者:启动时拉起 Agent 内核,按打开的工作区拉起地理内核实例,把各服务的地址与随机口令经 preload 交给界面;退出时回收全部子进程。壳还负责内置 Playwright MCP 的装配(把打包内的 MCP 运行时以环境变量交给内核注册)。

**Agent 内核**承载会话循环、模型路由、OAuth 登录、权限裁决与工具调度,对 GeoCode 的其余部分接近黑盒:界面经 SDK 与其 HTTP API 对话,地理工具经 MCP 注册进来。

**地理内核**是双面进程。对 Agent 内核暴露 MCP 工具面:八个工具(读取地理数据、QGIS 文档、运行 Processing 算法、运行 GEE 脚本、四个 OSM 工具),工具名统一 `geo_` 前缀便于按前缀授权;预览图以 image content 返回,执行诊断(失败、超时、崩溃、环境未就绪、耗时、退出码)进结构化结果并置错误位,模型与界面读同一份事实;长任务靠进度心跳维持连接。对界面暴露 HTTP 数据面:矢量元数据与分页、栅格元数据与 WebP 贴图、环境状态 SSE 流、技能商店接口。两面必须同进程——工具执行会改变环境状态,状态既影响后续工具行为又要实时反映到界面,状态机与事件总线是单一事实源,拆开就是制造两份会漂移的事实。每个工作区一个实例,工作目录进程级固定,这消除了多工作区并发时上下文错配的整类问题,也给路径安全校验一个稳定锚点。

GDAL、QGIS、GEE 是用户机器上的外部软件,地理内核只探测、诊断、引导,绝不代为安装。GEE 具备网络自愈;QGIS 不做——它的故障几乎总是配置问题,修复即"改配置重启",自动重探没有真实场景。栅格预览的铁律是 alpha 通道必须保留:nodata 靠 alpha=0 透明,不靠 RGB 哨兵值,颜色拉伸会摧毁哨兵值;给模型与给界面是两条独立管线(PNG / WebP),各自维护 alpha。

技能商店是一个受管理的技能目录:安装即落盘到地理内核掌管的目录,该目录注册进引擎的技能扫描路径;启用与禁用表现为技能是否出现在目录中,引擎侧零感知。更新分双层:元信息随远程目录随时刷新;技能正文严格按语义化版本提示更新——只有真正影响 agent 行为的变更才值得用户点一次"更新"。

**界面**是纯 HTTP 客户端,不 import 任何内核代码,自身零特权。geo 预览基于 OpenLayers:栅格贴 WebP,矢量分页渲染地图与属性表,大数据集有尺寸闸门防渲染进程内存溢出。附件遵循三分法:数据文件给路径、文本代码内联、图片走视觉——地理数据从不以文本塞进模型上下文。保留 diff 视图与终端(agent 会替用户改脚本、跑命令,地理用户同样需要看见改动和一条命令行逃生通道);不显示 git 状态、工程向斜杠命令、多服务器入口。语言支持英文与简繁中文。

## 4. 安全与生命周期

所有本地服务只监听 127.0.0.1,每次启动生成随机口令,HTTP Basic 校验;渲染进程 contextIsolation、零 Node 权限,凭据经 preload 下发。权限裁决发生在 Agent 内核层,界面过滤只是体验不是安全。进程回收双保险:正常退出逐个终止;每次 spawn 登记 pid 与端口,崩溃后的下次启动扫描并清理孤儿。GeoCode 与用户自装的 OpenCode 完全隔离:经环境变量把内核数据根定向到自己的目录,数据、配置、登录态互不可见。

## 5. 分发与更新

单一安装包(dmg / exe),内含壳、界面静态资源、Agent 内核 bundle、地理内核 bundle,及资源目录中的 Playwright MCP 运行时。两个平台各自在对应系统构建,禁止交叉打包。不签名,首启引导用户通过系统警告。更新是通知式的:检查 GitHub Release,有新版仅提示并引导下载页,从不自动安装;检查失败(含 404)按"无更新"静默处理。

## 6. 路线

依次推进,每步独立可验证,旧版 GeoCode(v0.9.6)全程保持可发布:内核瘦身(以上游 TUI 为测试台)→ 地理内核剥离(先工具面后数据面)→ 界面迁入(只迁不裁)→ 壳与打包 → 与旧版逐功能对照验收并处理存量数据迁移。
