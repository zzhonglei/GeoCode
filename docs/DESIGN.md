# 设计

本文档说明 GeoCode 是什么、由哪些部分组成、为什么这样设计。实现进度不在这里。

## 1. 定位

GeoCode 是面向地理工作者的桌面 AI 应用。用户用自然语言描述地理任务,内置的 GeoAgent 调用 QGIS、GDAL、Google Earth Engine 与 OpenStreetMap 等工具完成处理,结果在应用内可视化。用户是做制图、遥感与空间分析的人,不是程序员,所以界面以地理工作流为中心,面向开发者的功能保持克制。

GeoCode 只做桌面应用,支持 macOS(arm64)与 Windows(x64)。

## 2. 原则

装配优先。GeoCode 建在 OpenCode(Agent 引擎)与 OpenChamber(桌面应用)之上。定制尽量通过配置、环境变量与插件完成;这些手段做不到时才修改上游源码,每处修改都要能被找到、写明理由。这样上游升级时,我们付出的是「换版本、重新验证」,而不是「把定制重新移植一遍」。

边界靠装配,不靠删除。上游里产品不需要的功能(编码 agent、多服务器连接、编辑器扩展等)不删源码,只是不启用、不显示。删掉的上游代码会在每次合并时回来。

地理能力自成一体。地理相关的逻辑集中在地理内核里,只经插件接口与引擎交互,不依赖引擎的内部结构,可以脱离桌面环境单独测试。

与用户已有的工具互不干扰。GeoCode 不读写用户自己安装的 OpenCode、OpenChamber 的数据与配置,也不受它们影响。

## 3. 构成

```
┌──────────────────────────────────────────────────┐
│ 壳(来自 OpenChamber)                            │
│   Electron main                                  │
│   ├─ 壳服务端(在 main 进程内)                   │
│   │    └─ 子进程:Agent 内核(来自 OpenCode)      │
│   │                 └─ GeoCode 插件 → 地理内核    │
│   └─ 界面(渲染进程)                            │
│        └─ HTTP / SSE → 壳服务端 → Agent 内核     │
└──────────────────────────────────────────────────┘
```

壳:Electron 主进程与壳服务端是进程的管理者。壳服务端为界面提供文件、终端、设置、通知等接口,以子进程启动 Agent 内核,并把内核的接口代理给界面。

Agent 内核:负责会话、模型接入与登录、权限裁决、工具调度。GeoCode 通过配置决定它的 agent 阵容与权限,GeoAgent 是默认的 agent。

GeoCode 插件:在内核进程里运行,经插件接口把地理内核接入引擎:注册地理工具、调整 agent 与请求上下文、发布环境状态。

地理内核:插件里的一层服务,对外有三个面:

- 工具面:模型可以调用的地理工具,按环境就绪条件分组授权(读取地理数据、QGIS、OpenStreetMap、Earth Engine);
- 状态面:环境状态的事件与快照,供界面显示;
- 数据面:供界面获取矢量与栅格的元数据、分页数据与预览图。

三个面在同一个进程里、共用一份状态:工具执行会改变环境状态,这份状态既影响后续的工具,也要实时显示在界面上。QGIS、GDAL、GEE 是用户机器上的外部软件,地理内核只探测、诊断与引导,不代为安装。

界面:纯 HTTP 客户端,不引用内核的代码。在上游界面的基础上加入地理数据预览(地图、属性表)与环境状态。界面语言提供英文、简体中文、繁体中文。

## 4. 安全

- 本地服务只监听 127.0.0.1,每次启动生成随机凭据。
- 渲染进程没有 Node 权限;内核的凭据只在壳服务端与内核之间使用。
- 权限在内核里裁决;界面上的隐藏只是体验,不是防线。
- 应用退出时回收全部子进程,包括内核派生的地理子进程。
- 发往模型厂商及其登录通道的内容保持上游原样:用户与上游生态共用这些通道,那是通道认可的身份。

## 5. 分发

一个安装包(dmg、exe)包含壳、界面、Agent 内核与 GeoCode 插件,用户不需要另外安装 OpenCode 或 OpenChamber。两个平台各自在本平台上构建。安装包不签名。更新只做通知:发现新版时提示并引导到下载页,不自动安装。

## 6. 待定

以下几项等拿到实物再定,这里先写下判断依据。

- 内核怎么打包。OpenCode 提供 bun 编译与 Node 单文件两种构建;OpenChamber 的桌面版把上游发布的可执行文件放进安装包,以子进程启动。依据:包体大小、启动时间、两个平台上构建是否稳定、与上游做法的距离。
- 数据面的接口。插件可以注册 RPC 方法,但只收发 JSON,而数据面要传二进制的预览图。依据:能不改上游源码就不改;需要改时,选改动点最少的方案。
- 工具执行中的权限询问。插件的公开接口能否让地理工具在执行中向用户询问权限,要对照实物确认;不能时,需要一处登记在案的上游修改。
- 数据隔离的手段。内核的数据、配置与缓存目录跟随 XDG 环境变量,也许不必改源码;目录与界面上显示的名称要不要换成 GeoCode,另行决定。依据:能用环境变量做到的,不改源码。

## 7. 路线

依次推进,每一步都能单独验证:品牌与数据隔离 → 内核装配(agent 阵容、权限、屏蔽项)→ GeoCode 插件与地理内核 → 壳的定制 → 地理界面 → 双平台打包 → 与第一版逐项对照验收。
