# 设计大纲

本文档是 GeoCode 的大纲:定位、建在什么之上、遵循什么原则、还有哪些问题没有决定、按什么顺序推进。各部分的具体设计,做到那一部分时再决定、再写。

## 1. 定位

GeoCode 是面向地理数据处理任务的桌面端智能体应用。用户通过自然语言描述地理任务派遣内置的 GeoAgent 调用 QGIS、GDAL、Google Earth Engine 与 OpenStreetMap 等工具或者 Python 代码完成各种 GIS、遥感数据处理分析任务。

GeoCode 只做桌面应用,支持 macOS(arm64)与 Windows(x64)。

## 2. 基础

GeoCode 建在两个开源项目之上,两者的源码都放在本仓库里(见 `UPSTREAM.md`):

- OpenCode,位于 `kernel/`:Agent 引擎,负责会话、模型接入与登录、权限裁决与工具调度,并提供在内核进程里运行的插件接口。
- OpenChamber,位于 `desktop/`:桌面应用。它的 Electron 主进程里运行一个服务端,为界面提供文件、终端、设置等接口,以子进程启动 OpenCode 的内核,并把内核的接口代理给界面。

两者怎样组成一个应用,见 `DESKTOP.md`。

## 3. 原则

装配优先。定制尽量通过配置、环境变量与插件完成;这些手段做不到时才修改上游源码,每处修改都要能被找到、写明理由(见 `CONVENTIONS.md`)。这样上游升级时,需要做的是「换版本、重新验证」,而不是「把定制重新移植一遍」。

边界靠装配,不靠删除。上游里产品不需要的功能不删源码,只是不启用、不显示。删掉的上游代码会在每次合并时回来。

只关该关的。上游的功能与 GeoCode 的定位明显冲突,或会把对话、凭据交给第三方时,才把它关掉;上游有意这样设计、要几个条件同时满足才会出问题的,照上游,不为假想的情况打补丁。补丁越少,合并越省事。

## 4. 待定

以下问题等做到对应的那一步再决定。

- 地理能力怎么接入内核:用内核插件,还是直接定制内核;地理工具与它们的权限、环境状态怎么交给界面。GeoCode 对内核的改动会很大,不预设只用插件。
- 界面怎么取地理数据:内核插件可以注册 RPC 方法,但只收发 JSON,而地理数据的预览是二进制的图像。
- 地理工具执行中怎么向用户询问权限:插件的公开接口能否做到,还是要改内核,要对照实物确认。
- 更新与签名:OpenChamber 自带自动更新;GeoCode 用不用它,安装包签不签名。

做这些决定时,按定制阶梯取最靠前的手段:能用配置或环境变量做到的,不改源码。

## 5. 路线

每一步都能单独验证。先把两个上游封装成一个应用(见 `DESKTOP.md`),再屏蔽 GeoCode 用不到的上游功能,再把路径与存储同用户安装的 OpenCode、OpenChamber 分开(见 `PATHS.md`),再把用户看到的名字、链接与版本换成 GeoCode 自己的(见 `DESKTOP.md` 第 6 节),图标与标志随后替换。之后的内核装配(agent 阵容、权限、屏蔽项)、地理能力接入内核、壳的定制、地理界面、双平台打包、与第一版逐项对照验收,顺序待定。
