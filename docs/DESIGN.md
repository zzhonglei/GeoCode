# GeoCode 项目总体设计

本文档描述 GeoCode 的**目标设计与其理由**:产品边界、设计原则、系统构成、安全与分发。
其中相当一部分尚未实现;本文档记录的是「应当是什么样、为什么」,不记录「现在是什么样」。
各部分的实现现状见 `OVERVIEW.md` §7。

## 1. 产品定位

GeoCode 是一个面向地理工作者的桌面 AI 应用:用户用自然语言描述地理任务,内置的 GeoAgent 调用 QGIS、GDAL、GEE 与 OSM 等专业工具完成数据处理,结果(栅格、矢量、属性表)直接在应用内可视化。它服务的是开地图、跑遥感、做空间分析的人,不是程序员;界面以地理工作流为中心,面向开发者的表面保持克制。

GeoCode 只有一种形态:桌面应用,macOS(arm64)与 Windows(x64)。不做 CLI、Web、移动端或编辑器插件——单一形态让一个人能把一件事做好。

## 2. 设计原则

**消费内核,而非改造内核。** GeoCode 的会话与推理能力来自 OpenCode 的 agent 引擎。我们不把自己的功能写进引擎源码,而是通过引擎公开的装配面(配置、环境变量、MCP、技能目录)把 GeoCode 组装出来;只有装配面确实无法表达的少量差异,才以最小补丁保留在内核里(详见 KERNEL.md)。上游演进时,我们的成本是"换一颗内核重新测试",而不是"把定制重新缝进新源码"。

**地理能力自成一体。** 一切地理专业逻辑——工具执行、环境探测、数据预览、技能商店——集中在地理内核里,不依赖 agent 引擎的内部结构,只通过标准接口与引擎和界面对话。它与引擎同进程(§3 记了为什么),但**边界靠依赖方向而非进程边界维持**:引擎不认识地理内核,地理内核只依赖引擎公开的日志、路径与事件总线。它是 GeoCode 真正的技术资产,按独立系统设计、有自己的测试门(`scripts/test-gate.sh`)。

**不需要的能力不进产品。** 引擎自带的开发者向特性(内置编码 agent、代码审查命令、多服务器连接等)不做删改,只是不装配、不显示。产品边界优先由装配决定,而不是由删除决定。

但装配面并非无所不能。引擎有几处机制**没有任何配置开关**——最典型的是"打开一个文件夹就加载并执行其中的插件与工具文件",而那个文件夹可能来自同事、下载或 clone。这类边界只能在源码里截断:每处取模块的最顶层单点,配绊线,并登记进 KERNEL.md 的屏蔽清单。清单可枚举是这条例外的前提——不可枚举的例外等于没有原则。

## 3. 系统构成

GeoCode 由桌面应用层、Agent 内核与地理内核三部分组成。桌面应用层迁自 OpenChamber,
Agent 内核迁自 OpenCode;两者都以可继续合并上游的薄 fork 维护。完整的桌面封装、进程与
迁移设计见 `DESKTOP.md`。

```
┌───────────────────────────────────────────────────────────┐
│ GeoCode Desktop(来自 OpenChamber)                        │
│   Electron main + preload                                 │
│   ├─ Shell Runtime(同进程、本机内部服务)                  │
│   ├─ utilityProcess → Agent 内核(OpenCode,见 KERNEL.md)  │
│   │                    └─ 地理内核(见 GEOKERNEL.md)       │
│   └─ React renderer                                       │
│       └─ HTTP/SSE → Shell Runtime → Agent 内核            │
└───────────────────────────────────────────────────────────┘
```

**Electron main**是唯一的进程管理者:它以 OpenCode Desktop 已验证的 `utilityProcess` 形态
拉起 Agent 内核,同时在本进程内启动 Shell Runtime。Shell Runtime 承接 OpenChamber React UI
所需的文件、终端、设置与通知等内部 API,并将 Agent API 代理到内核。renderer 只获得访问
Shell Runtime 所需的连接信息,拿不到 Kernel 口令(口令会进入哪些进程的环境见 `DESKTOP.md`
§6.2)。退出时壳只给内核发终止信号,由内核在退出前清扫正在运行的地理子进程;它们各自成组,壳杀不到。

**Agent 内核**承载会话循环、模型路由、OAuth 登录、权限裁决与工具调度,对界面接近黑盒——
界面使用与内核同源的 SDK,经 Shell Runtime 代理其 HTTP API。

**地理内核**是这个进程内的一层服务,不是独立进程。它向上提供三个出口面:

- **工具面**是门面 API,工具层据此注册八个工具(读取地理数据、QGIS 文档、运行 Processing 算法、运行 GEE 脚本、四个 OSM 工具),按四组授权——读取地理数据、QGIS、OSM、Earth Engine,各对应用户面临的一种环境就绪条件(TOOLS.md);
- **状态面**是三个环境状态事件加一个快照端点,经宿主事件通道广播;
- **数据面**是 HTTP 端点,供界面取矢量元数据与分页、栅格元数据与 WebP 贴图。

三个面之上有一条共同要求:**模型与界面读同一份事实**。预览图以 image content 返回模型,执行诊断(失败、超时、崩溃、环境未就绪、耗时、退出码)进结构化结果并置错误位;长任务靠进度心跳维持连接。

**三个面必须同进程**,这条不因架构改变而失效:工具执行会改变环境状态,而该状态既影响后续工具行为、又要实时反映到界面。状态机与事件总线是单一事实源,把任何一个面拆到别的进程去,就是制造两份会漂移的事实。

**为什么不按工作区拉起独立进程。** 早期设计是那样,实现时改了:地理内核持有的状态几乎全是**机器级**的——`machine.json` 描述的是这台机器上 QGIS/GDAL/GEE 装在哪,工具链就绪度与网络可达性同样是本机事实。按工作区拆进程等于把同一份事实复制 N 份:N 个配置监听器盯同一个文件、N 套状态机报同一个真相、N 条五秒一次的探测循环——而那个节奏的成本论证,前提正是全机只有一个探测者。真正属于工作区的只有"哪些文件可读"一项,由数据面的显式路径边界解决(GEOKERNEL.md §7.8),而那条检查在独立进程形态下同样省不掉:恶意路径照样能逃出进程的工作目录。

GDAL、QGIS、GEE 是用户机器上的外部软件,地理内核只探测、诊断、引导,绝不代为安装。GEE 具备网络自愈;QGIS 不做——它的故障几乎总是配置问题,修复即"改配置重启",自动重探没有真实场景。栅格预览的铁律是 alpha 通道必须保留:nodata 靠 alpha=0 透明,不靠 RGB 哨兵值,颜色拉伸会摧毁哨兵值;给模型与给界面是两条独立管线(PNG / WebP),各自维护 alpha。

技能商店是一个受管理的技能目录:安装即落盘到地理内核掌管的目录,该目录注册进引擎的技能扫描路径;启用与禁用表现为技能是否出现在目录中,引擎侧零感知。更新分双层:元信息随远程目录随时刷新;技能正文严格按语义化版本提示更新——只有真正影响 agent 行为的变更才值得用户点一次"更新"。

**界面**迁自 OpenChamber shared React UI,是纯 HTTP 客户端,不 import 任何内核代码,
自身零特权。geo 预览基于 OpenLayers:栅格贴 WebP,矢量分页渲染地图与属性表,大数据集有尺寸
闸门防渲染进程内存溢出。附件遵循三分法:数据文件给路径、文本代码内联、图片走视觉——
地理数据从不以文本塞进模型上下文。保留 diff 视图与终端(agent 会替用户改脚本、跑命令,
地理用户同样需要看见改动和一条命令行逃生通道);不显示 git 状态、工程向斜杠命令、多服务器
入口。语言支持英文与简繁中文。

## 4. 安全与生命周期

所有本地服务只监听 127.0.0.1,每次启动生成随机凭据,Agent Kernel 使用 HTTP Basic 校验;
渲染进程 contextIsolation、零 Node 权限,只经 preload 获得 Shell Runtime 连接信息。权限裁决发生
在 Agent 内核层,界面过滤只是体验不是安全。进程回收:正常退出时内核清扫全部地理子进程;崩溃时
内核随 main 一起结束,留下的地理子进程不补救(GEOKERNEL.md §12)。GeoCode 与用户自装的 OpenCode 完全隔离:
经环境变量把内核数据根定向到自己的目录,数据、配置、登录态互不可见。

## 5. 分发与更新

单一安装包(dmg / exe),内含 Electron 壳、React 静态资源、Shell Runtime、Agent 内核 bundle
(地理内核在其中),及产品所需资源。用户不另装 OpenCode、OpenChamber、CLI 或 Server。
两个平台各自在对应系统构建,禁止交叉打包。不签名,首启引导用户通过系统警告。更新是通知式的:
检查 GitHub Release,有新版仅提示并引导下载页,从不自动安装;检查失败(含 404)按"无更新"
静默处理。

## 6. 路线

依次推进,每步独立可验证,旧版 GeoCode(v0.9.6)全程保持可发布:内核瘦身(以上游 TUI
为测试台)→ 地理内核 → 工具层与权限 → OpenChamber 契约实验 → Shell vendor 与 Desktop
profile → Kernel Host / SDK / 代理 → 最小桌面闭环 → 地理界面 → 双平台打包 → 与旧版逐功能
对照验收并处理存量数据迁移。详细阶段与验收门见 `DESKTOP.md` §10–§11。

推进顺序与设想有过一次偏离,值得记下:**数据面先于工具面完成**,因为数据面能脱离 Agent 独立验证。各部分的实现现状见 `OVERVIEW.md` §7;内核交给工具层的职责清单见 `GEOKERNEL.md` §11。
