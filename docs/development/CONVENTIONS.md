# 开发规范

开发 GeoCode 时要守的规则:原则、产品约束、基于上游的目录、代码、交给模型的文字、测试、验证、文档与提交。规则只在这里;怎样安装、构建与运行见 `DEVELOPMENT.md`,怎样运行测试见 `TESTING.md`。

每条规则都写了它防的是什么。规则划的是边界,边界之内怎样做由开发者判断;遇到规则没有料到的情况,照它的理由判断,拿不准时问维护者。

## 1. 原则

- 从简。做能满足当前需求的最简单方案,不为假想的需求加参数、配置、抽象与机制。规则也一样:新增规则或检查之前,先确认现有的覆盖不了。
- 加防御之前的三问。加一道检查、校验、兜底或测试之前,先回答:它防的是谁;那一方能不能从别处做到同样的事;它是否只为罕见的情况。答不上来就不加。过度的防御让代码难读,还会让真正的边界淹没在一堆不起作用的检查里。
- 值得做的三条标准。审查、审计或自查报出的问题,三条都满足才修:
  - 会真的发生:正常使用或升级上游时会碰到,而不是构造出来的极端条件;
  - 后果要紧:损坏数据、写进别的产品的目录、失败显示成成功或空结果、突破安全边界、升级上游时悄悄失效;
  - 修法相称:比问题轻;会让代码明显变复杂的,宁可写进注释或文档。

  只为好看的改写、防不会发生的情况,都不算。三问管的是要不要加一道防御,三条标准管的是要不要修一个报出来的问题。
- 一个事实只放一处。代码里的常量、清单与规则只写一份;确实放不到一处时,在每一处注明另外几处在哪。分散的副本迟早对不上,而且不报错。
- 代码要读起来像所在那棵树里已有的代码(第 4 节)。
- 代码按 macOS 与 Windows 都会运行来写,开发中测不了 Windows 时也一样。
- 文档用中文;代码、注释、提交信息与交给模型的文字用英文;`AGENTS.md` 是给 AI 助手的指令,用英文。文档与注释不用 emoji,不用粗体。

## 2. 产品约束

写任何部分都要守的约束;各部分自己的约束在它的设计说明里。

- 路径隔离。GeoCode 的目录、文件名与读写的一切,都与 OpenCode、OpenChamber 分开(`PATHS.md`);同一个目录,写入方与所有读取方用同一个来源。不读取其他 AI 产品(如 Claude Code、Codex、Cursor)的配置、文件、凭据与技能。用户为通用工具配置的内容照常读取(`PATHS.md` 第 8 节)。
- 限制一项功能,要限制在它生效的那一层,即发请求、读文件、执行命令的地方。只藏起界面的入口不算:别的入口照样走得到。
- 用户看到的产品名只有 GeoCode。
- 地理数据没有撤销。工具的输出不覆盖已有的文件,撞名时在文件名后加 `_1`、`_2`,取最小的空号;不留下写了一半的文件。
- 失败不当成空结果。请求或读取失败时报告失败,不当作没有数据:「没有数据」会被当成事实用下去。

## 3. 基于上游的目录

`kernel/` 基于 OpenCode,`desktop/` 基于 OpenChamber,GeoCode 持续合并它们的新版本。每改一处上游的代码,之后每次合并都可能为它付一次代价,所以这两个目录里有额外的约束:

- GeoCode 的逻辑放在所在包的 `geocode/` 目录;上游的文件里只留调用它的一两行,每处改动用 `GeoCode:` 注释标记。
- 不格式化、不重排、不顺手清理上游的行,不把上游的代码复制出来改。
- 改变上游的行为(关闭功能、改默认值、改文案与交互)之前,先与维护者讨论。

这两个目录的改动由维护者把关。

## 4. 代码

GeoCode 自己的代码在 `geoengine/`、`scripts/`,以及 `kernel/`、`desktop/` 各包的 `geocode/` 目录(`kernel/` 的测试例外,见第 6 节)。

格式化工具只用在 GeoCode 自己的文件上,上游的文件从不格式化。prettier 的配置在 `kernel/` 与 `geoengine/` 的 `package.json` 里(不加分号,行宽 120),用于 `geoengine/` 与 `kernel/` 里 GeoCode 自己的文件;`desktop/` 与 `scripts/` 没有格式化工具,照就近文件的风格写:`desktop/` 单引号、有分号,`scripts/` 单引号、不加分号。

### 4.1 `kernel/`

照 OpenCode 的写法(它的风格指南在 OpenCode 仓库根目录的开发指南里)。要点:

- 逻辑放在一个函数里,除非能复用或组合;不为只用一次的逻辑抽函数。分支多的函数,主体写主要流程,细节放到下方、以真实概念命名的小函数里。
- 用 `const`,以三元表达式或提前返回代替重新赋值;只用一次的值直接内联。
- 不用 `else`,用提前返回。
- 能推断的类型不标注;不用 `any`;`filter` 用类型守卫保住推断。
- 尽量不用 `try`/`catch`。
- 导入不起别名,不用 `import *`,不在类型位置写 `import("…")`。启动路径上的重模块用动态导入。
- 少解构,用点号访问。
- 外部输入只在边界校验一次,之后传递有类型的值。
- Effect:先把服务绑定到变量再调用方法;同步逻辑不包成 Effect;解析不可信的 JSON 用 Effect 的 Schema。
- 优先用 Bun 的 API,如 `Bun.file()`。

### 4.2 `desktop/`

- 改一个模块之前,先读离它最近的 `DOCUMENTATION.md`。
- 界面调用内核只经 `@opencode/client`。
- 入口与桥接层保持薄,逻辑放进各自的模块。

### 4.3 `geoengine/`

TypeScript 与 Effect,写法照 `kernel/`(第 4.1 节),只有「优先用 Bun 的 API」一条不适用:

- `src/` 只用 Node 的 API:GeoEngine 在 Electron 的辅助进程里以 Node 运行。Bun 只用来安装依赖与打包,只有 `script/` 下的构建脚本能用 Bun 的 API。
- 相对导入写 `.ts` 扩展名,只用能直接擦除的类型语法:测试由 Node 直接运行,不经编译。

`geoengine/python/` 是 GeoCode 的 Python 包 `geocodekit`:

- 只依赖内置 Python 环境里预装的包。
- 写法照 PEP 8,行宽 120;结构、公开的名字与函数的约定照 `GEOCODEKIT.md`。
- 只用两个解释器都支持的写法:单元测试用 `PATH` 里的 `python3` 运行它,可能比内置环境的 3.13 旧(macOS 自带的是 3.9)。

### 4.4 `scripts/`

shell 脚本用 POSIX sh(`#!/bin/sh`),要能在 macOS 自带的 sh 上运行。

### 4.5 注释

- 只为不明显的约束和出人意料的行为写注释:一句短从句,写在会被改错的那一行旁边,说明它为什么这样写。
- 注释描述代码,不描述进度与历史;改动的经过与测量数据写进提交信息。
- 注释不引用文档:要说明的理由直接写在注释里。文档会改写与重组,引用随之失效。
- 指向代码写文件路径与符号名,不写行号:行号随改动漂移,漂移了也没有提示。文档同样如此。
- 测试里的注释只说明它防的是哪种失败。

## 5. 交给模型的文字

交给模型的文字包括:工具名、工具与参数的说明、工具的答复与报错、给模型的环境提示、技能、提示词,以及 `geocodekit` 公开函数的说明(docstring)。它们直接决定模型怎样工作,措辞的一点差别就会改变它的做法。

- 经维护者审定后才能提交。
- 用英文写。示例按英文、简体中文、繁体中文的顺序给出;只能用英文的(标签、键、编号)只给英文。
- 工具的说明照 OpenCode 自带工具的写法:第一句以动词开头,说工具做什么,接着说返回什么、上限与默认值;该用别的工具时直说(use … instead)。
- 用法写成短的祈使句;理由只在它改变做法时才写。只关于一个参数的规则,写进那个参数的说明。
- 大写的强调只用在模型常犯、犯了就会失败、得出错误结果或白白空等的地方。到处强调等于没有强调。
- 答复只陈述事实:执行了什么、得到了什么、怎样结束。下一步由模型判断,答复不替它决定,也不写「告诉用户」这类话:它解决不了的自然会告诉用户。需要它动手的地方例外:环境没有就绪时的提示,以及请求在执行之前被拦下时,说明怎样改才能执行。
- 模型不是开发者。只告诉它做事需要的,不讲 GeoCode 的内部实现,不给它底层的错误:看到它们,它只会去修自己修不了的东西。

## 6. 测试

- 测试只写在审阅看不出来的运行时行为上:会被静默破坏的(如跨文件的副本、上游改了名字),或破坏后果严重的(损坏用户数据、写进别的产品的目录)。改动很小、审阅一眼看得出的不写;已被别的测试覆盖的路径不再加。界面的外观与交互、交给模型的文字不写测试。
- 复杂的行为,如界面、进程的监管、升级上游后的判断,不搭程序化的检查装置,而是写成检查事项,在打包版上亲自看:为它们搭的装置比被测的东西还难维护。
- 断言后果,不断言措辞。
- 新写的测试先证明它会失败:撤掉它保护的改动,确认它变红(做法见 `TESTING.md` 第 9 节)。从没红过的测试,不知道它守不守得住。
- 只碰替身的写成单元测试;接真实外部软件(QGIS、Earth Engine 等)的写成真实软件的测试,只测替身证明不了的。两种不放进同一个文件;几个文件共用的夹具放进共用的模块。
- 测试只写临时目录,不写真实的主目录。
- 「写入配置、期望某个服务读到」的改动,追到读取方,在运行时确认。
- 测试失败时,先分清是代码的问题还是环境的问题。检查是用来发现问题的:不为了让它通过去改测试、放宽检查或跳过,除非测试本身写错了;遇到就停下来报告。
- 产品代码里不为测试加开关(如缩短等待的时间):测试真的等,产品代码才是被测的那一份。

测试放在约定的位置才会被运行器找到;放在别处的,运行器不运行,也不一定报出来:

- `kernel/`:各包的 `test/` 目录,文件名以 `geocode-` 开头或放进 `test/geocode/`。在上游已有的测试文件中加的用例,名称以 `GeoCode: ` 开头,运行器只运行这些用例。
- `desktop/`:`ui/src/geocode/`(`.test.ts`、`.test.tsx`)、`web/server/geocode/`(`.test.js`、`.test.mjs`)与 `electron/geocode/`(`.test.mjs`),都在 `desktop/packages/` 下。在上游测试文件里加的用例不会被运行。
- `geoengine/`:`test/unit/` 是单元测试,按能力域分目录,引擎本身的直接放在 `test/unit/` 下;`test/real/` 是真实软件的测试,每个能力域一个文件;`test/support/` 是共用的夹具。
- `scripts/`:脚本旁边的 `.test.mjs`。

加了新的能力域或新的桌面包,在 `scripts/test.mjs` 里登记它的测试与 `changed` 的挑选规则。

## 7. 验证

每项改动按它的类型做必做的检查,改动属于几类就做几类的。命令见 `DEVELOPMENT.md` 第 7 节与 `TESTING.md`。

| 改动 | 必做 |
|---|---|
| 只改文档、注释 | 自己读一遍 diff |
| 代码(自有代码或对上游的补丁) | 类型检查、lint、`node scripts/test.mjs changed`;改了 `desktop/` 再跑 `own-anti-slop.mjs` |
| 能力域里碰真实软件的代码 | 再跑这个能力域的真实软件套件 |
| 访问控制、环境变量、进程的生命周期 | 再在写入检测下跑一次真实的会话 |
| 打包、启动、文件的位置与读写 | 再打包,跑打包版的两项检查 |
| 地理工具的接法(内核、壳与 GeoEngine 之间) | 再打包,跑 `geo.mjs` |
| 升级上游 | 全部套件(`all`)与打包版的两项检查 |

测试按时机跑,越到后面跑得越全:

- 写代码、反复试时,只跑改到的那个测试文件(`--file`)。
- 完工之前跑 `changed`。
- 一批工作结束时,跑这批工作碰过的能力域的完整测试(单元加真实软件),再打包跑一遍打包版的检查;最后的改动不碰运行时的边界与真实软件时,把单元测试完整跑一遍就够了。
- `all` 只在升级上游与维护者要求时跑。
- `gee` 的真实软件套件与 `geo.mjs --gee` 花的是这台电脑登录的 Earth Engine 账号的额度,跑之前先征得账号主人的同意。

几种改动的验证不在自动测试里:

- 改了 `gee.save`(存资产),另在真实 Earth Engine 上试一次:单元测试的替身不覆盖它。
- 改了请求 OSM 公共服务的方式,另对真实服务手动试一次:对公共服务的检查不做成自动测试,它会给社区的服务器添负担,结果又随服务的忙闲而变。
- 冒烟与对话只用假模型或免费模型,不用付费的密钥,也不改请求去冒充 OpenCode。
- 界面的外观与交互,以及打包版检查测不到的界面部分(服务商登录、权限确认弹窗、打开项目、终端、聊天模式、设置保存),由人在打包版上试。

## 8. 文档

### 8.1 写文档是提炼

文档写的是想清楚之后的结论,不是把知道的都摆出来。动笔之前,先想清楚这部分最关键的是什么:解决什么问题,做了哪几个决定,为什么这样定。写下的每一句都要经得起一问:读者少了它,会不会误解或做错?不会就不写。

- 讲原则,不列清单。能用一条原则说清的,不逐项列举;需要举例时,一两个就够。
- 细节只在它本身就是决定,或不知道就会做错时才写。维护者定下、代码照着实现的决定,文档是它的源头。
- 长度不代表认真。罗列与堆砌省掉的是思考,读的人反而要替作者去提炼。

### 8.2 每份文档写什么

| 文档 | 写什么 |
|---|---|
| `README.md` | GeoCode 是什么、由哪几部分组成、文档的清单 |
| 设计说明(`docs/` 下) | 定位、核心的决定与理由、边界与约束、与其他部分的关系 |
| `PATHS.md` | 用户电脑上与项目里每个文件的用途与删除的后果;它是参考清单,打包版的检查也对照它,所以要列全 |
| `CONVENTIONS.md` | 必须守的规则与理由 |
| `DEVELOPMENT.md`、`TESTING.md` | 怎样做,与不知道就会踩的坑 |
| `AGENTS.md` | 做什么事读什么,与底线 |

设计说明每篇开头一段摘要,说明这部分是什么与最关键的几个决定;同一层用同一个骨架(定位、核心设计、边界与约束、与其他部分的关系),`DESIGN.md` 是入口,不套骨架。设计说明以 GeoCode 为中心,所基于的项目只在说明 GeoCode 自身的设计所必需时提及。

### 8.3 写法

- 写决定本身,不写经过:为什么改、试过什么,写进提交信息。
- 写现状,不写待办、计划与验收清单。
- 一个事实只写一处,下层引用上层。引用别的文档写文件名,文件名在 `docs/` 里不重复。
- 发现不对的,把那句改对,不在旁边追加解释。
- 段落讲道理,条目列并列的规则、步骤与清单。句子要短,一句说一件事。用陈述句,不用「我们」「你」这类人称代词。
- 标点:`,` `:` `;` `(` `)` 用半角,`。` `、` 用全角,引号用「」。

### 8.4 更新

改动让文档里某句话不再成立时,在同一批改动里把它改对。加、删或改名一篇文档时,更新 `README.md` 的清单。

## 9. 提交

- 提交信息的格式是 `type(scope): summary`,类型取 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`chore`、`revert`;需要时后接一两句英文说明,改动的经过与测量数据写在这里。不带 AI 署名。
- 分支名不超过三个词,用连字符分隔,不带类型前缀。
- 改完与提交前完整读一遍 `git diff`:命令可能改得比想的多。
- 一批改动分成几次提交时,每一次都要能单独通过它该过的检查(第 7 节)。
- 会随安装包分发的作者、版权与发布者信息,不自动填写真实姓名与邮箱。
