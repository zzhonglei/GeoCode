# 开发规范

开发 GeoCode 时要守的规则:原则、产品约束、代码、测试、文档与提交。怎样安装、构建、运行与测试,见 `DEVELOPMENT.md`。

## 1. 原则

- 从简。做能满足当前需求的最简单方案,不为假想的需求加参数、配置、抽象与机制。规则也一样:新增规则或检查之前,先确认现有的覆盖不了。
- 不过度防御。加一道检查之前先回答三个问题:它防的是谁;那一方能不能从别处做到同样的事;它是否只为罕见的情况。答不上来就不加。
- 一个事实只放一处。代码里的常量、清单与规则只写一份;确实放不到一处时,在每一处注明另外几处在哪。
- 代码要读起来像所在那棵树里已有的代码(第 3 节)。
- 代码按 macOS 与 Windows 都会运行来写,开发中测不了 Windows 时也一样。
- 文档用中文;代码、注释与提交信息用英文。`AGENTS.md` 是给 AI 助手的指令,用英文。

## 2. 产品约束

写任何部分都要守的约束;各部分自己的约束在它的设计说明里。

- 路径隔离。GeoCode 的目录、文件名与读写的一切,都与 OpenCode、OpenChamber 分开(`PATHS.md`);同一个目录,写入方与所有读取方用同一个来源。不读取其他 AI 产品(如 Claude Code、Codex、Cursor)的配置、文件、凭据与技能。用户为通用工具配置的内容照常读取(`PATHS.md` 第 8 节)。
- 限制一项功能,要限制在它生效的那一层,即发请求、读文件、执行命令的地方。只藏起界面的入口不算。
- 用户看到的产品名只有 GeoCode。
- 地理数据没有撤销。工具的输出不覆盖已有的文件,撞名时在文件名后加 `_1`、`_2`,取最小的空号;不留下写了一半的文件。
- 失败不当成空结果。请求或读取失败时报告失败,不当作没有数据。
- 交给模型的文字(工具名、说明、参数、答复、报错、技能与提示词)经维护者审定后才能提交。

## 3. 代码

`kernel/` 与 `desktop/` 里,GeoCode 自己的模块放在所在包的 `geocode/` 目录。格式化工具只用在 GeoCode 自己的文件上:`geoengine/`、`scripts/`、各包的 `geocode/` 目录,以及 `kernel/` 测试里以 `geocode-` 开头的文件。

### 3.1 `kernel/`

照 OpenCode 的写法(它的风格指南在 OpenCode 仓库根目录的开发指南里)。要点:

- 逻辑放在一个函数里,除非能复用或组合;不为只用一次的逻辑抽函数。分支多的函数,主体写主要流程,细节放到下方、以真实概念命名的小函数里。
- 用 `const`,以三元表达式或提前返回代替重新赋值;只用一次的值直接内联。
- 不用 `else`,用提前返回。
- 能推断的类型不标注;不用 `any`;`filter` 用类型守卫保住推断。
- 尽量不用 `try`/`catch`。
- 导入不起别名,不用 `import *`,不在类型位置写 `import("…")`。启动路径上的重模块用动态导入。
- 少解构,用点号访问。
- 外部输入只在边界校验一次,之后传递有类型的值。
- Effect:先把服务绑定到变量再调用方法;同步逻辑不包成 Effect;解析不可信的 JSON 用 Effect 的 Schema。
- 优先用 Bun 的 API,如 `Bun.file()`。

### 3.2 `desktop/`

- 格式以就近的文件为准:单引号,有分号。
- 改一个模块之前,先读离它最近的 `DOCUMENTATION.md`。
- 界面调用内核只经 `@opencode/client`;入口与桥接层保持薄,逻辑放进各自的模块。

### 3.3 `geoengine/`

TypeScript 与 Effect,写法照 `kernel/`(第 3.1 节),只有「优先用 Bun 的 API」一条不适用:GeoEngine 在 Electron 的辅助进程里以 Node 运行,所以 `src/` 只用 Node 的 API;Bun 只用来安装依赖与打包,只有 `script/` 下的构建脚本能用 Bun 的 API。相对导入写 `.ts` 扩展名,只用能直接擦除的类型语法,测试因此由 Node 直接运行。

`geoengine/python/` 是 GeoCode 的 Python 包 `geocodekit`:只依赖内置 Python 环境里预装的包;写法照 PEP 8,行宽 120;结构、公开的名字与函数的约定照 `GEOCODEKIT.md`。单元测试用 `PATH` 里的 `python3` 运行它,可能比内置环境的 3.13 旧(macOS 自带的是 3.9),所以只用两者都支持的写法。

### 3.4 `scripts/`

shell 脚本用 POSIX sh(`#!/bin/sh`),要能在 macOS 自带的 sh 上运行。

### 3.5 注释

- 只为不明显的约束和出人意料的行为写注释:一句短从句,写在会被改错的那一行旁边,说明它为什么这样写。
- 注释描述代码,不描述进度与历史;改动的经过与测量数据写进提交信息。
- 注释不引用文档:要说明的理由直接写在注释里。文档会改写与重组,引用随之失效。
- 指向代码写文件路径与符号名,不写行号。
- 不用 emoji,不用粗体。
- 测试里的注释只说明它防的是哪种失败。

## 4. 测试

- 测试只写在审阅看不出来的运行时行为上:会被静默破坏的(如跨文件的副本),或破坏后果严重的(损坏用户数据、写进别的产品的目录)。改动很小、审阅一眼看得出的不写;已被别的测试覆盖的路径不再加。界面的外观与交互、交给模型的文字不写测试。
- 断言后果,不断言措辞。
- 新写的测试先证明它会失败:撤掉它保护的改动,确认它变红。
- 只碰替身的写成单元测试;接真实外部软件(QGIS、Earth Engine 等)的写成真实软件的测试,只测替身证明不了的。两种不放进同一个文件;几个文件共用的夹具放进共用的模块。
- 测试只写临时目录,不写真实的主目录。
- 「写入配置、期望某个服务读到」的改动,追到读取方,在运行时确认。
- 测试失败时,先分清是代码的问题还是环境的问题。不为了让测试通过而改测试,除非测试本身写错了。
- 提交前运行类型检查、lint 与 `node scripts/test.mjs changed`;改动涉及文件的位置与读写时,在写入检测的监视下跑一次真实会话(`DEVELOPMENT.md` 第 7、8 节)。

测试放在:`kernel/` 的包的 `test/` 目录,文件名以 `geocode-` 开头或放进 `test/geocode/`,在那里已有的测试文件中加的用例,名称以 `GeoCode: ` 开头;`desktop/` 各包的 `geocode/` 目录;`geoengine/` 的 `test/unit/`(单元测试)、`test/real/`(真实软件的测试)与 `test/support/`(共用的夹具)。

## 5. 文档

### 5.1 分类

| 文档 | 读者 | 内容 |
|---|---|---|
| `README.md` | 所有人 | GeoCode 是什么、由什么组成、文档在哪 |
| `docs/` 下的设计说明 | 想了解 GeoCode 的人 | 各部分的核心设计思想 |
| `docs/development/` 下的开发文档 | 开发 GeoCode 的人 | 本文档,以及怎样构建、运行与测试 |
| `AGENTS.md` | AI 助手 | 在本仓库工作的指令 |

设计说明按层级组织:`docs/` 下是总体设计 `DESIGN.md`、应用外壳 `DESKTOP.md` 与文件和存储 `PATHS.md`;`docs/geoengine/` 下是地理引擎的框架 `GEOENGINE.md` 与它的各部分(内置 Python 环境、Python 包与各能力域)。新的能力域加在 `docs/geoengine/` 里。

### 5.2 设计说明写什么

设计说明讲各部分的核心设计思想,不是开发日志、规划书,也不是代码的完整映射;实现的细节读代码。

- 写:定位,即解决什么问题、为什么需要它;核心设计,即关键的做法与理由,包括为什么不用看起来更自然的另一种;边界与约束,即不做什么、必须守什么;与其他部分怎样配合。
- 不写:每个文件、函数与参数做什么;具体的数值、流程的每一步、界面文案与交给模型的文字原文;验收清单、待定、待验证与下一步;经过、日期与谁做的决定;已知的小毛病。
- 判断:代码改了这一处、文档也得跟着改的,不写进文档。例外是维护者定下、代码照着实现的决定,这时文档是源头。`PATHS.md` 也是例外:它完整列出 GeoCode 在用户电脑上产生的文件,供用户查阅与删除。
- 每篇开头一段摘要,说明这部分是什么与最关键的几个决定。同一层的文档用同一个骨架:定位、核心设计、边界与约束、与其他部分的关系;`DESIGN.md` 是入口、`PATHS.md` 是参考清单,不套这个骨架。下层不重复上层,引用它。
- 以 GeoCode 为中心。GeoCode 所基于的项目,只在说明 GeoCode 自身的设计所必需时提及。
- 一个事实只写在一处,别处引用它。引用别的文档写文件名,文件名在 `docs/` 里不重复。
- 改代码时,同一批改动里更新受影响的文档。

### 5.3 写法

- 说明与理由写成段落,并列的规则、步骤与清单才列条目。句子要短,一句说一件事。
- 用陈述句写规则与事实,不用「我们」「你」这类人称代词。
- 标点:`,` `:` `;` `(` `)` 用半角,`。` `、` 用全角,引号用「」。不用 emoji 与粗体。
- 指向代码写文件路径与符号名,不写行号。

## 6. 提交

- 提交信息的格式是 `type(scope): summary`,类型取 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`chore`、`revert`;需要时后接一两句英文说明,改动的经过与测量数据写在这里。不带 AI 署名。
- 分支名不超过三个词,用连字符分隔,不带类型前缀。
- 提交前完整审阅 diff。一批改动分成几次提交时,每一次都要能单独通过检查。
- 会随安装包分发的作者、版权与发布者信息,不自动填写真实姓名与邮箱。
