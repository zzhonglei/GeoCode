# 地理引擎

GeoEngine 是 GeoCode 自己的组件,提供应用的全部地理能力:管理用户电脑上的地理执行环境,执行地理任务。它是一个独立的进程,不开端口,只与主进程通信;agent、工具与权限都在内核,GeoEngine 只负责做事。内置的 Python 环境与各能力域(QGIS、GEE、OSM)是它里面互不依赖的模块,共用同一套进程执行、环境配置与环境状态的机制。

本文讲这套共用的框架。内置的 Python 环境见 `PYTHON.md`,GeoCode 的 Python 包见 `GEOCODEKIT.md`,各能力域见 `QGIS.md`、`GEE.md` 与 `OSM.md`。

## 1. 定位

地理任务与 agent 平常的工作不同:一次空间分析可能运行几十分钟、占用大量内存,调用的外部程序可能卡住或崩溃。放进内核或壳服务端,一次出问题的任务就可能拖垮整个应用。所以地理能力单独成一个进程。

GeoEngine 做两件事:

- 管理环境:找到用户装好的软件(如 QGIS)列给用户选择,验证它能否真正运行,把问题整理成给用户的诊断与给 GeoAgent 的提示。它不替用户选择,不安装软件,也不改动用户已有的环境。唯一的例外是 GeoCode 自带的 Python 环境,由它在 GeoCode 的数据目录里准备与管理。
- 执行任务:接收内核里的地理工具交来的任务,执行中回报进度,结束时返回结果。

## 2. 在应用中的位置

```
Electron 主进程
 ├─ 壳服务端
 │    └─ 子进程:内核(地理工具在这里)
 ├─ 辅助进程:GeoEngine
 │    └─ 任务子进程:QGIS、Python 等外部程序
 └─ 界面
```

GeoEngine 运行在 Electron 的辅助进程里,由主进程启动与监管,随应用启动与退出。它只与主进程通信:内核交来的工具任务、界面对环境的查询与设置,都先到壳服务端、经过它的访问控制(`DESKTOP.md`),再由主进程转给 GeoEngine。

一次地理工具调用这样走:

```
内核里的工具 ──> 壳服务端 ──> 主进程 ──> GeoEngine ──> 任务子进程
             <── 进度……结果(逐行的流)
```

内核里的工具先按权限规则决定是否执行,再以内核的回调令牌调用壳服务端的地理工具接口;这个接口只确认来电的是应用自己的内核,不做权限判断。agent 执行的命令也读得到这个令牌、能直接调用它,这与 agent 在 shell 里直接运行 QGIS 等价,同样归 shell 的权限管,所以不另设防。答复是逐行的流,先是进度,最后是结果。整条链路上没有比任务更短的超时;工具调用被取消时,请求随之断开,一路转成对这个任务的中断。界面查询与设置环境走另一组接口,用窗口的令牌;环境状态变化时,由 GeoEngine 推送,经壳服务端广播给界面。

两种失败分开处理。外部程序失败、卡住或崩溃,只是一次任务失败,结果照常返回给 GeoAgent。GeoEngine 自己起不来或异常退出,说明应用本身出了问题:应用显示出错页,只能重启应用恢复。GeoEngine 不被自动拉起,正在执行的任务以失败结束、不重试,因为执行到一半的任务未必能安全地重跑。

## 3. 结构

GeoEngine 用 TypeScript 与 Effect 编写,构建成一个文件打进应用。它分两层:

- 基础设施:与地理领域无关的机制,即与主进程的通道、进程执行、环境配置与环境状态。
- 能力模块:内置的 Python 环境与每个能力域各一个。启动时依次注册:登记自己的环境状态与配置块,在后台开始环境检查,交出自己的方法;方法以 `<能力域>.<方法>` 命名,如 `qgis.run`。模块之间互不调用,一个能力域要用另一个准备好的东西时,只读它发布的状态:GEE 与 OSM 从内置 Python 环境的状态取得解释器。

不是每个模块都有配置与状态。OSM 用的是公共服务与内置环境,没有要配置与检查的东西;内置 Python 环境有状态,没有配置块,也不提供工具。

### 3.1 通道

GeoEngine 与主进程之间只有一条消息通道,走五类消息:请求与应答、进度、中断、状态推送,以及生命周期的通知(启动完成、退出前的清扫、每个任务进程的登记与注销)。

请求带编号,应答按编号对应;长任务在应答之前按同一编号回报进度。被中断的请求仍然给出应答,主进程等到它才了结这次请求。方法预期内的失败(参数写错、环境没有就绪等)带着自己的代码与说明交回,其余的错误一律报成内部错误:一个任务出了意外,只是这一次请求失败,不会拖垮引擎。

### 3.2 进程执行

外部程序都经同一个执行机制启动。每次执行都要写明怎样计时:总时长,或连续多久没有输出;不限时也要显式写出,不能因为漏写而无限等待。长时间运行的任务按空闲计时:只要还在报告进度,就不会被误杀,所以工具调用本身不设总时限。

外部程序不会随 GeoEngine 退出,由它负责结束:任务被中断、应用退出时(主进程先等它清扫完),结束的都是整棵进程树。每个任务进程在启动与结束时向主进程登记,GeoEngine 崩溃时,由主进程结束它留下的任务。POSIX 上每个任务是自己的进程组;Windows 没有进程组,任务在运行时按进程树强制结束,任务自己退出之后留下的子进程不再结束,因为进程号可能已被复用。

### 3.3 环境配置

每个能力域的环境信息记在配置目录 `machine.json` 里的一块:外部软件的位置与所需的标识,如 QGIS 的路径、GEE 的 Cloud 项目。它不并进内核的 `geocode.json`:后者在加载时读取,`machine.json` 保存即生效;它记的是这台电脑上的安装与登录的账号,换一台电脑就不再成立。

用户在设置里的选择由 GeoEngine 写进文件,发现的结果不写。用户手改与 GeoAgent 改同样生效:GeoEngine 监听这个文件,只重新检查变了的那几块。写入时以文件当时的内容为底,别处刚做的改动不会被抹掉。文件不支持注释,因为 GeoEngine 也写它,写回时注释留不住。文件被改得无法解析时,各能力域都进入配置错误的状态,GeoEngine 不覆盖它,以免抹掉用户手写的内容。

### 3.4 环境状态

每个能力域有一份环境状态,取值是这个能力域定义的几种状态之一,如检查中、就绪与各种失败;状态整体替换,变化时推给界面。新一轮检查开始时,上一轮还没落定的结果作废,界面不会看到过时的状态。有配置块的能力域都有「配置错误」这一种;未配置不算故障,刚装好应用的用户不该看到报错。

失败时有两类信息,给不同的读者:

- 诊断给用户:定位问题所需的事实,如路径、版本、各检查项的结果与原始错误。它与状态一样是日志式的信息,只用英文,不附建议。
- 提示给 GeoAgent:以陈述事实的语气写明缺什么、在哪里补,只有用户能做的(如登录)写明只有用户能做,不写请用户做什么。不给底层的错误与实现:GeoAgent 不是开发者,看到它们只会去修自己修不了的东西。没有确定的补救时(如网络不通)只陈述事实。

地理工具执行之前先看环境:检查中就等它落定,等待有上限;没有就绪就不执行,把提示交给 GeoAgent。有的变化不经过配置文件(如在原处重装软件),所以每个能力域自己决定工具调用时要不要再检查一次。

### 3.5 给 GeoAgent 的文字

工具的说明、参数说明、答复与报错,以及 `geocodekit` 公开函数的说明,都是交给 GeoAgent 的文字,用英文写。

说明照 OpenCode 自带工具的写法:第一句以动词开头,说工具做什么,接着说返回什么、上限与默认值;该用别的工具时直说(use … instead)。用法写成短的祈使句,理由只在它改变做法时才写。只关于一个参数的规则,写进那个参数的说明。大写的强调只用在模型常犯、犯了就会失败、得出错误结果或白白空等的地方。

工具的答复只陈述事实:执行了什么、得到了什么、怎样结束。下一步由 GeoAgent 判断,答复不替它决定,也不写「告诉用户」这类话:它解决不了的自然会告诉用户。需要它动手的地方例外:环境没有就绪时的提示,以及请求在执行之前被拦下时,说明怎样改才能执行。

GeoAgent 不是开发者。工具的说明、答复与报错只告诉它做事需要的,不讲 GeoCode 的内部实现。

示例按英文、简体中文、繁体中文的顺序给出;只能用英文的(标签、键、编号)只给英文。

### 3.6 地理工具的共同做法

各能力域的工具形态不同,下面这些做法是共同的,能力域的文档只写自己的不同之处。

- 命名:照 OpenCode 自带工具的写法,全小写,不用下划线(下划线是命名空间的标记),也不以 `geocode` 开头,以免与壳交给 agent 的 `geocode_web` 等工具混淆。它们直接列在模型的工具清单上,不收进 Code Mode。
- 权限照最接近的自带工具:读数据的照 `read`,查阅与检索的默认放行,运行任意 Python 的照 `shell`;执行 QGIS 算法与下载 OSM 数据各有自己的规则,见下一条。设置的工具权限里,地理工具只能按整个工具选允许、询问或拒绝,不按资源写规则:地理用户写不了 `gdal:*` 这样的规则,要放宽的由询问卡片上的「始终允许」记住,它同样由内核按项目保存。OSM 的四个工具共用一行。行名与上游的一样用英文、不翻译,只把缩写与品牌写对。
- 询问之前先拦下注定执行不了的请求:内核检查参数,再请 GeoEngine 确认环境就绪、输入的文件在,不让用户批准一个注定失败的请求。这一步不运行任务。
- 地理工具自己守住项目的边界:交给模型看的数据、执行算法与下载数据的输出在会话目录与项目以外时,即使规则允许也询问,除非这个目录有过「始终允许」;只由 QGIS 或 GeoEngine 读、模型看不到内容的输入不问,如算法的输入与 OSM 的边界文件。对整个工具的「始终允许」不算,否则点一次就让这道检查形同虚设。读用上游访问项目外目录的那张卡片,按目录记住。这道检查不是安全边界:agent 改用 `read` 或 `shell` 仍能读写同样的文件,它们的边界照上游;它守的是地理工作的主路,让用户在项目外的数据交给模型、被写之前看到。要问的几件事合在一张卡片上,一次调用至多一张。运行任意 Python 的工具照 `shell`,不另加这道检查。
- 运行与下载只在应用里的询问卡片上批准:卡片写明这一步的用途、要做什么、写到哪里与需要的警示,托盘与系统通知显示不了这些,只能拒绝或打开对话。用途由模型用用户的语言写一句,显示在卡片与对话里。
- 地理工具在对话里的行由 GeoCode 自己绘制,询问卡片的外框与设置里的规则沿用上游的组件。运行与下载的行以用途为标题,运行中显示计时,有进度才显示百分比,不估算进度。
- 运行的答复超出内核给工具结果的上限时,只留输出的结尾并注明:内核自己的截断只留开头,会丢掉报错与怎样结束。

## 4. 边界与约束

- 权限在内核。agent、工具的定义与权限都在内核:地理工具与内核自带的工具一样作为内置插件编进内核,直接用内核的权限服务,由权限规则决定是否询问,在设置里同样管理。它们不经插件 API 提供,因为插件 API 交给工具的上下文发不起询问。询问之前到达 GeoEngine 的只是环境与参数的检查,可以读取环境与输入的数据,但不运行任务;GeoEngine 自己不做权限判断。
- 不开端口。与外界的全部通信经过主进程;以后加任何通道,都不能让本机的其他程序直接连到 GeoEngine。唯一的例外是在设置里登录 GEE 时的临时端口(`GEE.md`)。
- 启动不能卡住。能力模块全部注册完才报告启动完成,主进程等不到就显示出错页;所以环境检查都放在后台,用状态推送报告进展。注册时出错的能力模块被跳过,引擎照常启动。
- 一个任务不能拖垮引擎:大块数据交给外部程序处理,不整块读进引擎的内存。
- 应用被强制结束、崩溃或断电时,留下的任务会自己跑完,不做补救:它们不损坏数据、不会累积,而补救要在每次启动里长期维持正确。
- 内核回收空闲的工作目录时,正在前台执行的长任务(QGIS 算法、GEE 运行、OSM 下载)不算空闲。读数据与查看 OSM 不在其中,它们各有几分钟的总时限,到时停下并告诉 GeoAgent,远短于内核回收的门槛。
- 外部程序的输出按 UTF-8 读取。Windows 上的命令行程序默认用系统的本地代码页输出,启动时要让它以 UTF-8 输出,否则中文的报错与路径会变成乱码。
- 任务进程只拿网络、账户、临时目录与系统自身的环境变量,用户为自己的工具设的变量不交给它们(`ENVIRONMENT.md` 第 2.3 节)。设置里「环境变量」页的变量只在 GeoEngine 启动时读,改了要重启应用。
- GeoEngine 自己写的文件只放在 GeoCode 的目录里(`PATHS.md`)。外部软件运行时照它的默认位置写自己的配置与缓存,不归 GeoCode 管。
- macOS 与 Windows 同等对待,两个平台的安装布局与路径规则都要覆盖。

## 5. 与其他部分的关系

- 内核:地理工具是内核的内置插件,负责参数、权限与交给模型的答复;它们经壳服务端调用 GeoEngine 的方法。
- 壳服务端与主进程:壳服务端为地理工具与界面各开一组接口并做访问控制,主进程启动、监管 GeoEngine,并在它崩溃时显示出错页(`DESKTOP.md`)。
- 内置的 Python 环境:GeoEngine 的一个模块,GEE 与 OSM 在它里面运行(`PYTHON.md`);GeoCode 的 Python 包随它装进环境(`GEOCODEKIT.md`)。
- 能力域:每个能力域一篇,只写自己的部分,框架照本文(`QGIS.md`、`GEE.md`、`OSM.md`)。
