# 内置的 Python 环境

GeoCode 自带一套装好常用地理包的 Python 环境:用户装好 GeoCode 之后,不需要再装任何 Python 软件,也不需要联网准备环境。GeoAgent 处理数据、GEE 与 OSM 的工具都在它上面运行。这套环境属于 GeoCode:随安装包分发,由 GeoEngine 在 GeoCode 的数据目录里就地安装与管理,与用户电脑上的 Python、conda 与 GDAL 双向隔离。它分两层:只由安装产生的 `base`,与 GeoAgent 可以自由装包的工作环境。

## 1. 定位

地理用户多半不会自己搭 Python 环境:conda 的环境与频道、pip 与 conda 混装的冲突、Windows 上编译不出来的 GDAL,每一样都可能让人在第一步就放弃。而 GeoAgent 几乎每个任务都要用 Python 读写与处理地理数据,`geerun` 也离不开它。所以 GeoCode 自带一套环境。

这套环境属于 GeoCode:它放在 GeoCode 的数据目录里,只由 GeoCode 准备与替换。用户自己装的 Python、conda 与它们的配置,GeoCode 不碰;QGIS 用它自带的 Python(`QGIS.md`),与这套环境无关。反过来,用户电脑上的 Python、conda、GDAL 与它们的配置也不能影响这套环境:地理用户的电脑上常有好几套 GDAL(conda 的、QGIS 的、OSGeo4W 的),它们的环境变量与配置文件一旦被读到,这套环境就会加载不属于它的插件与数据(第 2.5 节)。

## 2. 核心设计

### 2.1 组成

环境的全部包,包括 Python 本身,都来自 conda-forge,只用这一个频道。conda-forge 是社区维护的软件源,也是地理 Python 生态的标准来源:GDAL 在这里是完整的一套,PyPI 上没有现成的安装包。不用 Anaconda 公司的 defaults 频道:它与镜像它的仓库要商业授权。用户的电脑上不装 conda,也看不到它。

- 解释器是 Python 3.13,小版本固定,只跟补丁版本:补丁版本不改变包的安装位置与二进制接口,换小版本会让所有带编译代码的包与已建的虚拟环境失效,所以按一次重大升级单独处理。
- 预装的包只收 GeoAgent 在地理任务里经常要用的;同一个包有只含核心的版本时取它。清单在 `geoengine/environment/pixi.toml`。用得少的包由 GeoAgent 按需装进工作环境。
- 两个平台共用一份锁定清单,每个包的版本都带校验和:同一段脚本在两个平台上的行为才一致,出了问题也能复现。间接依赖由各平台自己解析,不强求完全一致。
- 环境里只有一份 GDAL,rasterio、pyogrio 与 GDAL 官方的 Python 接口都用它。PyPI 上的 rasterio、pyogrio 各带一份 GDAL,用 pip 往工作环境里重装它们,就盖过了环境里的那一份。
- 环境不带中文字体:系统自带的字体随操作系统授权,只能调用,不能随 GeoCode 分发。出图要中文时,由 GeoAgent 选用系统里的中文字体。

环境不放进 `PATH`:用户在终端里、GeoAgent 在 shell 里敲 `python`,仍是用户自己的那一个,不打乱用户已有的环境与习惯。

### 2.2 两层

环境分两层,是为了让 GeoAgent 能自由装包,而预装的部分不会被它改坏:

- `base` 只由安装产生与替换,运行时不往里装包。它带着禁止 pip 与 uv 往里装包的标记。
- 工作环境是继承 `base` 的虚拟环境:预装的包都能直接导入,GeoAgent 额外装的包只进这里;同名的包在这里装了别的版本,也只在这个环境里生效。只有一个工作环境,不按项目分开:它够用,也最简单。

`base` 不能挪动:conda 的包在安装时把所在的位置写进一些文件,包括二进制文件,GDAL 靠它找驱动插件与数据,curl 与 OpenSSL 靠它找证书。所以 `base` 在用户的电脑上就地安装,不在打包时装好再搬过来。

恢复不需要专门的入口:GeoEngine 每次启动时缺什么补什么。工作环境装坏了,删掉它,下次启动时从 `base` 重建,额外装的包随之清空;`base` 坏了,删掉整个环境,下次启动时重新安装(位置见 `PATHS.md` 第 3.2 节)。

### 2.3 构建与分发

环境的定义放在 `geoengine/environment/`,用 pixi 一族的工具:开发时解析两个平台的依赖、写出锁定清单;打包时按锁定清单下载一个平台的全部包、核对校验和、打成一个文件;用户电脑上由 pixi-unpack 把它装成一个 conda 环境。用户的电脑上只多一个 pixi-unpack。

包随安装包分发,放在应用归档之外(pixi-unpack 读不了归档里的文件),不在用户的电脑上下载:准备环境不需要联网,两岸的用户一样。代价是安装包因此变大。许可证见 `DESKTOP.md` 第 2.6 节。

### 2.4 在用户电脑上的准备

环境由 GeoEngine 的一个模块准备与管理(`GEOENGINE.md`),它发布环境的状态,就绪时带两层的解释器,失败时带诊断。准备在后台进行,不阻塞 GeoEngine 的启动;失败不重试,下次启动再准备。

环境的标识是它的定义与装法的校验和:这个平台的锁定清单、解包工具 pixi-unpack 的版本,以及暂存脚本里装法的版本号,脚本里真的改变装法的改动才改它。三者不变,重新打包、改动脚本的其余部分,标识都不变,用户装上只是重新打包的新版时不必重新安装。GeoEngine 启动时比较装好的与应用自带的标识:一致就直接使用,否则删掉旧的、重新安装,标识在安装完成后最后写入。安装中途应用退出或失败,标识不在,下次启动从头再装,不会用到装了一半的环境。旧的 `base` 不留作退路:新环境只能装在同一个位置上,装不好时旧的也用不上。

GeoEngine 写进 `base` 的文件(禁止装包的标记、设环境变量的启动文件与 GeoCode 的包 `geocodekit`)不算在标识里,每次启动逐个与这一版 GeoCode 自带的比较内容,不同的与缺了的重写,多出来的删掉。比的是文件本身而不是版本:新版改了它们,或开发时改了它们,下次启动用的就是新的,不必重装环境;只有标识变了才重装。核对或重写失败算准备失败:启动文件不对时 Python 照常运行,只是变量没设,GDAL 会不报错地出错。

就绪之前,先把预装的重包导入一遍,即预热:macOS 第一次加载一个新的动态库时会检查它,刚装好的环境第一次导入要等很久,期间一声不响;预热放在就绪之前,GEE 的检查与第一次运行就碰不上这段冷加载,不会被误判为卡住。会在用户主目录里写配置的包(如 matplotlib)不预热。预热只为提速,失败不影响就绪。用到这套环境的能力域等它就绪。

### 2.5 环境变量与隔离

环境自己的变量,即 conda 激活环境时会设的那些,由环境自己设:GeoEngine 在 `base` 里写入一个启动文件,这套环境的 Python 每次启动都先执行它,不论由谁、以什么方式启动,工作环境的 Python 与它启动的子进程也一样。它按解释器自己所在的位置算出 GDAL 与 PROJ 的数据、驱动插件与投影数据库的位置,覆盖用户环境里的同名变量;Windows 上另设证书的位置(用户自己设了的除外),并让环境与它启动的程序先加载自己的 DLL。运行它的一方因此不必设任何变量,也就不会漏设。其中两项是有意的选择:

- PROJ 按需联网下载网格并缓存。不开的话,需要网格的转换(如椭球高与海拔高之间)不报错,却退回误差可达几十米的近似转换。
- 不读用户主目录下的 GDAL 配置文件:那里的选项能关掉驱动、改掉行为。

GeoEngine 运行这套环境的 Python 时,以隔离模式启动,不读 `PYTHON` 开头的变量,也不加载用户目录里的包;环境变量只取任务进程的白名单(`ENVIRONMENT.md` 第 2.3 节)。

代理的规则与内核、壳服务端相同(`ENVIRONMENT.md` 第 2.5 节),不认 `ALL_PROXY`,不支持自动代理脚本(PAC)。环境里的库本来各有各的做法(有的没有变量时去读系统设置,有的连变量也不读),所以启动文件在 Python 启动时整理这些变量,并在相关的网络库被导入时调整它们的默认行为。用户给 GeoCode 设了代理,GEE、GDAL 与 GeoAgent 的脚本都跟着走;脚本里显式给的代理照样优先。

### 2.6 界面

界面不单独显示这套环境。主窗口的加载动画一直显示到环境就绪(含预热)才收起,所以用户在窗口里的操作碰不上环境还没好;第一次启动与重装环境之后要等较久,这时标志下面写明正在做什么,免得用户以为卡住了。准备失败时显示出错页(`DESKTOP.md` 第 2.5 节),只能重启应用,重启会再准备一次。

### 2.7 重装与更新

GeoCode 没有自动更新,用户卸载旧版、安装新版;卸载只删应用本身,数据目录与其中的环境留着。新版自带的环境标识不变时,环境直接沿用;标识变了,替换 `base`、重建工作环境,GeoAgent 额外装的包随之清空:它们是对旧的 `base` 装的,留着可能与新的预装包不兼容。

## 3. 边界与约束

- `base` 只由 GeoEngine 改变:安装,与每次启动时核对、换掉它自己的文件;GeoAgent 与任何运行都不往里装包。
- 只有锁定清单、解包工具的版本或装法变了才重装环境。
- 准备环境不联网。环境自己的机制在运行时只有需要网格的坐标转换联网;GEE、OSM 与 GeoAgent 的脚本按各自的需要联网。
- 环境的安装只写在 GeoCode 的数据目录里,临时文件也在其中;pip、matplotlib 这类软件运行时照它们的默认位置写缓存与配置,不归 GeoCode 管。
- 隔离有它的限度:在 shell 里运行这个 Python,要以 `-I` 启动才挡得住用户设的 `PYTHONPATH` 与个人目录里装的包;直接运行 GDAL 的命令行工具不经过 Python,用户的 GDAL 变量与配置文件照样影响它。
- 两个平台用同一份锁定清单,只用 conda-forge 一个频道。

## 4. 与其他部分的关系

- GeoEngine:环境由它的一个模块准备与管理,怎样运行环境里的 Python 也放在它的基础设施里(`GEOENGINE.md`)。
- GEE 与 OSM:它们的脚本只在 `base` 里运行,不用工作环境,结果因此是确定的(`GEE.md`、`OSM.md`)。
- GeoCode 的 Python 包:GeoEngine 把它装进 `base`,工作环境继承它(`GEOCODEKIT.md`)。
- QGIS:用 QGIS 自带的 Python,不用这套环境(`QGIS.md`)。
