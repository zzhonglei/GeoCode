# 内置的 Python 环境

GeoCode 自带一套装好常用地理包的 Python 环境:用户装好 GeoCode 之后,不需要再装任何 Python 软件,也不需要联网准备环境。GeoAgent 处理数据、GEE 与 OSM 的工具都在它上面运行。这套环境属于 GeoCode:随安装包分发,由 GeoEngine 在 GeoCode 的数据目录里就地安装与管理,与用户电脑上的 Python、conda 与 GDAL 双向隔离。它分两层:只由安装产生的 `base`,与 GeoAgent 可以自由装包的工作环境。

## 1. 定位

地理用户多半不会自己搭 Python 环境:conda 的环境与频道、pip 与 conda 混装的冲突、Windows 上编译不出来的 GDAL,每一样都可能让人在第一步就放弃。而 GeoAgent 几乎每个任务都要用 Python 读写与处理地理数据,`geerun` 也离不开它。所以 GeoCode 自带一套环境。

这套环境属于 GeoCode:它放在 GeoCode 的数据目录里,只由 GeoCode 准备与替换。用户自己装的 Python、conda 与它们的配置,GeoCode 不碰;QGIS 用它自带的 Python(`QGIS.md`),与这套环境无关。反过来,用户电脑上的 Python、conda、GDAL 与它们的配置也不能影响这套环境:地理用户的电脑上常有好几套 GDAL(conda 的、QGIS 的、OSGeo4W 的),它们的环境变量与配置文件一旦被读到,这套环境就会加载不属于它的插件与数据(第 6 节)。

## 2. 组成

环境的全部包,包括 Python 本身,都来自 conda-forge,只用这一个频道。conda-forge 是社区维护的软件源,也是地理 Python 生态的标准来源:GDAL 在这里是完整的一套,PyPI 上没有现成的安装包。不用 Anaconda 公司的 defaults 频道:它与镜像它的仓库要商业授权,conda-forge 的包不在其中。用户的电脑上不装 conda,也看不到它。

- 解释器是 Python 3.13,小版本固定,只跟补丁版本。补丁版本不改变包的安装位置与二进制接口;换小版本会让所有带编译代码的包与已建的虚拟环境失效,所以按一次重大升级单独处理。
- 预装的包只收 GeoAgent 在地理任务里经常要用的:GDAL 与它的 Python 接口、命令行工具与各种格式的驱动,GEE 用的 earthengine-api 与 geedim,以及矢量、栅格、多维数据、科学计算与出图的常用包;同一个包有只含核心的版本时取它,不带用不到的可选依赖。清单在 `geoengine/environment/pixi.toml`。用得少的包由 GeoAgent 按需装进工作环境(第 3 节)。
- 两个平台共用一份锁定清单,每个包(含间接依赖)在两个平台上是同一个版本并带校验和:同一段脚本在两个平台上的行为才一致,出了问题也能复现。
- 环境里只有一份 GDAL,rasterio、pyogrio 与 GDAL 官方的 Python 接口都用它。它的命令行工具在环境里,不在 `PATH` 上(第 7 节)。
- 环境不带字体:系统自带的字体随操作系统授权,只能调用,不能随 GeoCode 分发。出图要中文时,由 GeoAgent 选用系统里的中文字体。

## 3. 结构

```
<数据目录>/python/
├── base/            基础环境:解释器、预装的包与 GDAL,以及 GeoCode 的包 geocodekit
├── base.json        base 的标识,安装完成后最后写入
├── proj/            PROJ 下载的网格的缓存
└── envs/default/    工作环境:继承 base 的虚拟环境
```

环境分两层,是为了让 GeoAgent 能自由装包,而预装的部分不会被它改坏:

- `base` 只由安装产生与替换,运行时不往里装包。它带着 `EXTERNALLY-MANAGED` 标记,pip 与 uv 拒绝往里装包。
- `envs/default` 是以 `--system-site-packages` 建的虚拟环境:预装的包都能直接导入,GeoAgent 额外装的包只进这里;同名的包在这里装了别的版本,也只在这个环境里生效。只有一个工作环境,不按项目分开:它够用,也最简单。

`base` 不能挪动:conda 的包在安装时把所在的位置写进一些文件,包括二进制文件,GDAL 靠它找驱动插件与数据,curl 与 OpenSSL 靠它找证书。所以 `base` 在用户的电脑上就地安装(第 5 节),不在打包时装好再搬过来。

恢复不需要专门的入口:GeoEngine 每次启动时缺什么补什么。工作环境装坏了,删掉 `envs/default`,下次启动时从 `base` 重建,额外装的包随之清空;`base` 坏了,删掉整个 `python/`,下次启动时重新安装。

## 4. 构建与分发

环境的定义放在 `geoengine/environment/`:pixi 的项目文件 `pixi.toml` 与锁定清单 `pixi.lock`,以及构建要用的三个工具的版本与校验和。三个工具都是单个可执行文件:pixi 在开发者的电脑上解析两个平台的依赖、写出锁定清单;pixi-pack 在打包时按锁定清单下载一个平台的全部包、核对校验和、原样打成一个文件;pixi-unpack 在用户的电脑上把这个文件里的包装成一个 conda 环境。它们装的都是 conda-forge 的包,用户的电脑上只多一个 pixi-unpack。

打包时为每个平台打出它的包,与那个平台的 pixi-unpack 一起放进应用的资源目录,在 `app.asar` 之外,因为 pixi-unpack 读不了归档里的文件。包随安装包分发,不在用户的电脑上下载:准备环境不需要联网,两岸的用户一样。代价是安装包因此变大。

随环境分发的各个包的许可证声明,与两个上游的一起放在发布仓库(`DESKTOP.md` 第 7 节)。其中有 LGPL 的库,也有少数 GPL 的库,都是 conda-forge 构建这些包的方式带来的,以动态库的形式随包分发,GeoCode 自己的代码不链接它们。

## 5. 在用户电脑上的准备

环境由 GeoEngine 的一个模块准备与管理(`GEOENGINE.md`),它发布环境的状态:检查中、准备中(安装、建立工作环境或预热)、就绪(带 `base` 与工作环境的解释器),或失败(带诊断:哪一步、原因与命令打印的内容)。准备在后台进行,不阻塞 GeoEngine 的启动;失败不重试,下次启动再准备。

环境的标识是它的定义的校验和:这个平台在锁定清单里的各个包、三个工具与构建脚本。它由构建脚本写在包旁边:定义不变,重新打包也不变,用户装上只是重新打包的新版时不必重新安装。GeoEngine 启动时比较它与 `base.json`:一致、且 `base` 的解释器在,就直接使用;否则删掉旧的 `base.json`、`base` 与工作环境,用 pixi-unpack 把包装进 `base`(它的临时目录也放在 `python/` 下),删掉只在编译与调试时用的文件,最后写入 `base.json`。安装中途应用退出或失败,标识不在,下次启动清掉留下的东西从头再装,不会用到装了一半的环境。旧的 `base` 不留作退路:新环境只能装在 `base` 的位置上,装不好时旧的也用不上。

GeoEngine 写进 `base` 的文件(`EXTERNALLY-MANAGED` 标记、设环境变量的启动文件与 GeoCode 的包 `geocodekit`)不算在标识里,每次启动逐个与这一版 GeoCode 自带的比较内容:不同的与缺了的重写,多出来的删掉。比的是文件本身而不是版本:新版改了它们,或开发时改了它们,下次启动用的就是新的,不必重装环境;只有锁定清单变了才重装。每个文件先写成临时文件再整个挪到位,`base` 里不会有写了一半的文件。核对或重写失败算准备失败:启动文件不对时 Python 照常运行,只是变量没设,GDAL 会不报错地出错。工作环境不在时(刚装好的 `base` 总是这样),从 `base` 重建它。

就绪之前,先用 `base` 的解释器把预装的重包导入一遍,即预热,每次启动都做。macOS 第一次加载一个新的动态库时会检查它,刚装好的环境第一次导入要等很久,期间一声不响;预热放在就绪之前,GEE 的检查与第一次运行就碰不上这段冷加载,不会因为时限或空闲计时被误判为卡住。matplotlib 不预热:导入它会在用户的主目录建它的配置目录。预热只为提速,失败只记日志,不影响就绪。

用到这套环境的能力域等它就绪:GEE 在那之前停在检查中,OSM 的调用在有上限的时间里等它。

## 6. 环境变量与隔离

环境自己的变量,即 conda 激活环境时会设的那些,由环境自己设:GeoEngine 在 `base` 里写入一个启动文件,这套环境的 Python 每次启动都先执行它,不论由谁、以什么方式启动,工作环境的 Python 与它启动的子进程也一样。它按解释器自己所在的位置算出路径,覆盖用户环境里的同名变量:

- GDAL 与 PROJ 的数据、驱动插件与投影数据库的位置。
- PROJ 按需联网下载网格,缓存在 `python/proj/`。不开的话,需要网格的转换(如椭球高与海拔高之间)不报错,却退回误差可达几十米的近似转换;不需要网格的转换不联网。
- GDAL 的配置文件指向一个不存在的文件,不读用户主目录下的 `~/.gdal/gdalrc`:那里的选项能关掉驱动、改掉行为。
- Windows 上另设证书的位置(用户自己设了的除外)与 `PATH`,让环境与它启动的程序先加载自己的 DLL。

运行它的一方(GeoEngine、GeoAgent 的 shell 与以后别的入口)因此不必设任何变量,也就不会漏设。

GeoEngine 运行这套环境的 Python 时,以隔离模式启动:Python 不读 `PYTHON` 开头的变量,也不加载用户目录里的包;环境变量只从用户的环境里取网络相关的(代理与证书)与 `HOME`,其余一个也不给,因为 conda 的 `PYTHONPATH`、`PATH` 里 QGIS 与 OSGeo4W 带的 GDAL 都会让它加载不属于自己的东西。给 `HOME` 只为指明主目录,开发时的沙箱靠它挡住真实的主目录。

代理也是环境的一部分,规则与内核、壳服务端相同(`DESKTOP.md`):只按 `HTTP_PROXY`、`HTTPS_PROXY` 与 `NO_PROXY` 联网,大小写皆可,两种都有时以小写的为准;本机的回环地址总是直连;不读系统设置里的代理,也不认 `ALL_PROXY`。环境里的库本来各有各的做法(有的没有变量时去读系统设置,有的连变量也不读),所以启动文件在 Python 启动时整理这些变量,并在相关的网络库被导入时调整它们的默认行为。用户给 GeoCode 设了代理,GEE、GDAL 与 GeoAgent 的脚本都跟着走,GeoAgent 不必考虑代理;脚本里显式给的代理照样优先。自动代理脚本(PAC)不支持。

## 7. GeoAgent 怎样使用

GeoAgent 得到工作环境的 Python 的绝对路径,运行脚本、装包都用它。环境不放进 `PATH`:用户在终端里、GeoAgent 在 shell 里敲 `python`,仍是用户自己的那一个,不打乱用户已有的环境与习惯。

环境的变量由它自己设好,所以 GeoAgent 在 shell 里用路径直接运行这个 Python 就能用。但 shell 里是用户的环境,有两样启动文件挡不住:用户设的 `PYTHONPATH` 与个人目录里装的包,要以 `-I` 启动才挡得住;直接运行 GDAL 的命令行工具不经过 Python,用户的 GDAL 变量与配置文件照样影响它。由此,GeoAgent 用这套环境的规矩是:

- 运行这个 Python 都加 `-I`。
- 先用预装的包;缺的包用工作环境的 pip 装进工作环境,照 `shell` 的权限询问。
- 不用 pip 重装预装的包:PyPI 上的 rasterio、pyogrio 等各带一份 GDAL,装进工作环境就盖过了环境里的那一份。
- 不往用户自己的 Python 里装包,不全局安装,不另建环境。
- GDAL 的处理用它的 Python 接口做;要用环境里的命令行工具,从这个 Python 里启动它们,让它们继承环境的变量。
- 工作环境装坏了,删掉 `envs/default` 并请用户重启 GeoCode。

pip 与 matplotlib 这类软件把缓存与配置写在它们自己的默认位置,不归 GeoCode 管。

## 8. 界面

界面不单独显示这套环境:标题栏没有它的指示灯,设置里也没有它的一行。主窗口的加载动画一直显示到环境就绪(含预热)才收起,所以用户在窗口里的操作碰不上环境还没好;第一次启动与重装环境之后要等一两分钟,这时标志下面写明正在做什么、加载到第几个包,免得用户以为卡住了。准备失败时,窗口显示 GeoCode 的出错页,写明失败在哪一步与原因,只能重启应用,重启会再准备一次。迷你聊天窗口只在失败时显示出错页,不等环境。

## 9. 重装与更新

GeoCode 没有自动更新,用户卸载旧版、安装新版;卸载只删应用本身,数据目录与其中的环境留着。新版自带的环境标识不变时,环境直接沿用,第一次启动不用等;标识变了,替换 `base`、重建工作环境,GeoAgent 额外装的包随之清空:它们是对旧的 `base` 装的,留着可能与新的预装包不兼容。完全卸载时要删的位置里有这个环境(`PATHS.md`)。

## 10. 边界与约束

- `base` 只由 GeoEngine 改变:安装,与每次启动时核对、换掉它自己的文件;GeoAgent 与任何运行都不往里装包。
- 只有锁定清单变了才重装环境。
- 准备环境不联网;运行时只有需要网格的坐标转换联网。
- 环境只写在 GeoCode 的数据目录里,安装时的临时文件也在其中。
- 两个平台用同一份锁定清单,只用 conda-forge 一个频道。
- 环境自己的变量与对代理的做法只由它的启动文件定,运行它的一方不设。

## 11. 与其他部分的关系

- GeoEngine:环境由它的一个模块准备与管理,怎样运行环境里的 Python 也放在它的基础设施里(`GEOENGINE.md`)。
- GEE 与 OSM:它们的脚本只在 `base` 里运行,不用工作环境,结果因此是确定的(`GEE.md`、`OSM.md`)。
- GeoCode 的 Python 包:GeoEngine 把它装进 `base`,工作环境继承它(`GEOCODEKIT.md`)。
- QGIS:用 QGIS 自带的 Python,不用这套环境(`QGIS.md`)。
