# GeoCode 的 Python 包

`geocodekit` 是 GeoCode 自带的 Python 包,装在内置的 Python 环境里。它把各能力域常见的地理操作做成标准的函数:GeoCode 的工具(如 `geerun`)在运行的脚本里用它,GeoAgent 自己写的脚本也可以用它。包按能力域分子包,公开的只有 `__all__` 列出的名字,函数遵守同一套约定;它的版本就是 GeoCode 的版本,由 GeoEngine 装进环境,每次启动按内容核对。

## 1. 定位

没有标准的函数,同样是读一个研究区、存一个结果,每个脚本的写法、出错的方式与打印都不一样,GeoCode 也无从知道脚本做到了哪一步。标准的函数带来三点:

- 做对:常见的步骤有现成的函数,模型不必知道每个坑。直接写的细节容易出错,错了又常常不报错,只是结果不对。函数用错时报错,并说明怎样改。
- 可管理:关键的步骤经过 GeoCode 自己的函数,GeoCode 就知道每一步在做什么,例如存进 GEE 任务的资产带着标题、说明与指纹,能被下一次运行沿用。
- 及时的反馈:在 GeoCode 的工具里,函数告诉工具行它在做什么;结局打印给模型。

GeoCode 的地理能力多半以这个包的新函数出现,所以它的结构与约定先定下来:新的能力域与专题照着加,不必改动已有的部分。

## 2. 结构

包按能力域分子包,一个能力域一个,以能力域的简称命名;脚本按能力域导入子包,用简短的名字,如 `import geocodekit.gee as gee`。现在有两个:

- `gee`:Google Earth Engine 的函数(`GEE.md`)。
- `osm`:OSM 工具运行的模块与它们读的预设库(`OSM.md`)。它没有公开的函数,只供工具调用,给 GeoAgent 的说明里不提它。

按能力域分,是因为各能力域的函数处理的对象与能用的场合不同:`gee` 的函数进出 Earth Engine 在云端的对象,只能在 `geerun` 里用;处理本地数据的能力域,函数在哪里都能用。同一个概念在两个能力域里可以各有一个同名的函数,返回的对象不同,不会混淆。GeoEngine 的代码、测试与文档也按能力域分,改一个能力域只动包里它那一块。

一个子包里分两层。几乎每个脚本都用到的核心链路的函数直接放在子包里,如 `gee.region`、`gee.composite`、`gee.download`,不该藏深;专题各开一个命名空间,如 `gee.water`,一个专题有了几个函数才开,层次最多到专题这一层,再深模型与人都难记。专题之间、子包之间不互相调用公开的函数;要共用的(读本地的研究区、向工具行报告、输出文件的命名)放进下划线开头的内部模块。这样每个专题都能单独改动,共用的部分只有一份。

两个名字是有意避开的:包不叫 `geocode`,PyPI 上已有一个同名的地理编码包,而「geocode」在地理学里本来就是地理编码的意思,模型会误解它,也可能为了地理编码把那个包装进工作环境;子包不用 `map` 这类名字,`from geocodekit import map` 会盖掉 Python 自带的 `map`。

## 3. 公开的接口

公开的接口是子包与专题的 `__all__` 列出的名字,其余都是内部的,可以随时改动。公开的名字会进入模型的用法,所以:

- 改名或删除公开的名字与参数时,在同一批改动里改掉工具说明与技能里的写法。
- 公开函数的说明(docstring)是交给模型的文字,GeoAgent 可以用 `help()` 读到;它与工具说明一样用英文,写法照 `GEOENGINE.md` 第 3.5 节,经维护者审定。
- 工具说明只列核心链路的函数,各有完整的签名与一行说明:没有技能时,GeoAgent 凭工具说明也要能用好它们。专题的函数与用法写进技能,不让工具说明越写越长。

## 4. 函数的约定

每个公开的函数都照下面的约定写,新能力域的函数也一样。约定在内部模块里各实现一次,各子包共用。

- 进出:函数进出的是这个能力域通用的对象(Earth Engine 的 `ee` 对象、GeoPandas 的 GeoDataFrame、文件路径),模型随时可以与标准写法混用。函数的价值放在标准写法难做对的地方,不把标准写法再包一层。
- 参数:同一个概念在各子包里用同一个参数名;函数建在某个库之上时,参数名、默认值与算法照那个库(GEE 照 geedim)。
- 出错:用错时报错,说明怎样改;不吞掉错误,不返回空的结果。
- 打印:只陈述事实(存了什么、在哪、用了多久、沿用了什么),不替模型下判断。
- 进度:在 GeoCode 的工具里,函数用一句英文告诉工具行它在做什么,知道进度的带上百分比。
- 输出文件:不覆盖已有的文件,不留写了一半的文件。

## 5. 运行的场合

函数在两种场合里运行:GeoCode 的工具由 GeoEngine 在内置环境的 `base` 里启动,函数向工具行报告进度,全部子包都能用;GeoAgent 自己的脚本在 shell 里、在工作环境里运行,函数不报进度,只能用不依赖工具场合的子包。

工具的运行脚本在 GeoAgent 的脚本开始之前设好场合:先在共用的内部模块里记下是哪个工具在运行、进度往哪里报,再导入子包,做能力域要的准备(GEE 初始化 Earth Engine、设好任务)。没有设好场合时,函数照常运行,只是不报进度:在 shell 里,脚本的输出全部进了模型的上下文,进度行对模型写脚本没有用。依赖工具场合的子包(如 `gee`)在场合之外导入即报错,说明它只能在哪个工具里用。

导入要轻:导入 `geocodekit` 不加载任何子包,导入子包不加载它的专题,用到才加载。子包再多,导入也不变慢;`gee` 也不会在没有 Earth Engine 的地方被意外加载。

## 6. 安装与更新

源码在 `geoengine/python/`,一个标准的 Python 项目。它不经 pip 构建与安装,所以不声明构建后端;它的版本就是 GeoCode 的版本号(`DESKTOP.md` 第 6 节),项目文件只声明版本是动态的,不另写一份,没有第二处要对齐。构建 GeoEngine 时,包的文件与 GeoCode 的版本号原样编进它的代码,随它分发:打包版里 GeoEngine 在应用的归档中,Python 读不到那里的文件,编进代码的 GeoEngine 随时取得到。构建因此不需要 Python。

GeoEngine 自己把包的文件写进 `base`,并写下标准的安装记录:`pip show geocodekit` 看得到它,`importlib.metadata` 读得到版本,报错的回溯指向磁盘上的文件。`base` 不让 pip 往里装包(`PYTHON.md` 第 3 节),装这个包的只有 GeoEngine,方式与它写启动文件相同:每次启动把磁盘上的每个文件(连同安装记录)与这一版 GeoCode 自带的逐个比较内容,不同的与缺了的重写,多出来的删掉(`PYTHON.md` 第 5 节)。用到的总是这一版 GeoCode 的包:开发时改了包,下次启动用的就是改过的;中途退出留下的半截包、被改坏的包,下次启动同样被换掉。工作环境继承 `base`,所以 GeoAgent 的脚本直接导入就能用。

没有采用的做法:

- 随每次运行把包的源码交给 Python:只到得了 GeoCode 的工具,GeoAgent 自己的脚本用不上。
- 做成 conda 包写进锁定清单:包每改一次,环境的标识就变,环境整个重装。
- 只装进工作环境:GeoCode 的工具在 `base` 里运行,用不到;工作环境又会被 GeoAgent 改动。
- 按 GeoCode 的版本号判断要不要重写:开发时版本号不变,改了包也不会重写。
- 每次启动先删掉整个包再写:删与写之间,别的 GeoCode 或还没结束的运行可能导入到缺了的文件。

## 7. 边界与约束

- 包只由 GeoEngine 装进 `base`;GeoAgent 不往任何环境里装 `geocodekit`。
- 包只依赖 `base` 里预装的包。新函数要用新的包,同一批改动里把它加进锁定清单,用户更新到这一版时环境随之重装。在 GeoAgent 的脚本里,函数用的是工作环境里的包;GeoAgent 用 pip 重装过预装的包时,函数可能出错。
- 公开的接口只是 `__all__` 列出的名字;子包之间、专题之间不互相调用公开的函数。
- 导入 `geocodekit` 与它的子包不加载暂时用不到的部分。

## 8. 与其他部分的关系

- 内置的 Python 环境:包装在它的 `base` 里,工作环境继承它(`PYTHON.md`)。
- GeoEngine:构建时把包编进代码,启动时装进环境(`GEOENGINE.md`)。
- GEE 与 OSM:`gee` 是 GEE 的函数,`osm` 是 OSM 工具运行的模块(`GEE.md`、`OSM.md`)。
