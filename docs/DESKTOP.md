# 桌面应用

本文档说明 GeoCode 桌面应用由什么组成,以及它遵循的几条基本约束:内核只为应用服务,应用只在本机为一个用户工作,只有应用自己的窗口与它发出的凭证能访问它,它的行为由用户的设置与配置文件决定、不受应用自己的环境变量影响,用户看到的产品只有 GeoCode。

## 1. 定位

GeoCode 是一个应用,安装、启动、退出都只有一个入口,用户不需要另装别的软件才能对话。

它是单机、单用户的桌面应用:不让其他设备连进来,不连接本机以外的内核或服务器,不在用户没有需要时向上游的服务器发请求。连接模型服务(包括取模型目录与服务商图标)是内核的正常工作,地理工具检索与下载数据、登录 GitHub 这类用户要用的功能也要联网,都不在此列。用户只通过 GeoCode 的窗口使用它,没有网页版与命令行。

与这个定位不冲突的功能都保留,包括 git、Issue 与 PR 这类面向代码的功能:地理数据处理同样是重代码的工作。不属于任何项目的对话要做好,地理用户多半没有建项目的习惯。

## 2. 组成

```
Electron 主进程
 ├─ 壳服务端(在主进程内运行)
 │    └─ 子进程:内核(serve --stdio)
 ├─ 辅助进程:GeoEngine(地理引擎,见 GEOENGINE.md)
 └─ 界面(渲染进程)── HTTP、SSE、WebSocket ──→ 壳服务端
```

界面只与壳服务端通信,不直接连内核:壳服务端把内核的接口代理给界面,转发时附上内核的口令,界面拿不到这个口令。两个服务都只监听 127.0.0.1。

## 3. 内核

内核是应用的私有组件:只由这个应用启动,只为它服务,随它退出。壳以 `serve --stdio` 启动它:口令每次启动随机生成并显式传入,内核读取后从自己的环境里删掉,agent 执行的命令不会继承它;内核把标准输入当作租约,应用正常退出或被强制结束,内核都随之退出。重启与退出只经壳持有的子进程结束内核,不按端口找进程,因为内核退出后旧端口可能已被别的程序占用。

安装包里的内核由本仓库的 `kernel/` 构建,对内核的修改这样才能进入安装包。打包出的应用只用安装包里的内核,不用设置、环境变量或 `PATH` 指向的别的内核;内核缺失时显示出错页,让用户重新安装 GeoCode。构建方法见 `DEVELOPMENT.md` 第 4 节。

一个项目的行为只由它自己和用户的全局设置决定。用户与项目的配置,内核只从两处读:全局配置目录,以及会话所在的目录本身(用户添加的项目文件夹或它的 worktree;不属于项目的对话是它自己的聊天目录)。不往上级目录查找,不读本机的系统配置与托管设置,不读其他 AI 应用的目录,不接受配置里列出的外部技能、说明文件与远程下发的配置;插件只来自应用自己的托管配置。这样,下载来的文件夹放在哪里、本机装了哪些别的 AI 工具,都不会改变 agent 的行为。「技能」等设置页也只在这两处读写。例外是子目录里的 `AGENTS.md`:agent 用 `read` 读那个子目录里的文件时,内核把它一并带上。

会话目录里的项目配置照常生效:它能启动 MCP 服务与格式化命令、放宽权限、读项目以外的文件,打开带配置的项目时内核不询问是否信任。项目是用户自己添加的,这和用户在终端里运行项目里的脚本是同一回事。

## 4. 本机访问控制

只监听 127.0.0.1 挡不住本机:任何程序都连得上壳服务端,浏览器里的网页也能,因为 WebSocket 不受跨域限制,DNS 重绑定还能让网页以同源的身份发请求。能调用壳服务端,就能让 agent 以用户的身份执行命令、读写文件。所以要防的是浏览器里的网页、其他用户、沙箱内的程序与扫描本机端口的脚本;以用户身份运行、不受沙箱限制的程序本来就能修改用户的文件,不在此列。

壳服务端只认 GeoCode 自己的窗口。它要求口令,口令每次启动随机生成,只在主进程的内存里,没有人输入它。主进程凭它为窗口签发一个令牌,令牌本身只在主进程与窗口的内存里(数据目录里只记它的摘要),每次启动换新;会话的签名密钥也每次启动随机生成。设备令牌、配对与会话重置这些让别处取得令牌的途径都关闭。令牌失效时,界面提示重启应用,不出现登录页。

窗口之外只有几类来访者,各凭各的凭证,能做的事各有范围:

- 状态接口(健康检查、版本、系统信息、取一个空闲端口)不要凭证,只报告状态或给出一个端口号。
- 内核的工具回调凭每次启动内核时生成的回调令牌,只能调用交给 agent 的那几个工具接口与地理工具的接口(`GEOENGINE.md` 第 2 节)。agent 执行的命令也读得到这个令牌。
- git:仓库绑定了账号时,它的 git 配置指向 GeoCode 的凭据助手,助手凭数据目录里每次启动换新的密钥取得这个仓库绑定的账号的凭据。这份密钥换得到任何已绑定的仓库的凭据,但读得到它的程序本来就读得到数据目录里的 GitHub 登录。应用自己发起的克隆、拉取与推送另经一个本机端口取凭据,每次操作凭一个一次性的随机数。
- 文件预览:预览页的地址里带一个随机的授权码,闲置十分钟失效。

另有两道防线。壳服务端只接受以 `127.0.0.1` 或 `localhost` 访问的 HTTP 请求,挡住 DNS 重绑定;WebSocket 的升级请求不经过这道检查,只靠令牌。内核的每个接口请求都要口令,口令不留在壳的环境变量里,应用内的终端与其他子进程无法绕过壳直接访问内核。

## 5. 环境变量

应用的行为由用户的设置与配置文件决定,不受环境变量控制;环境变量只为用户的工具服务。从哪里取得、交给谁、哪些不认,见 `ENVIRONMENT.md`。

## 6. 名字与标志

用户在应用里看到的产品只有 GeoCode:菜单、窗口标题、通知、设置里的说明与出错提示都用这个名字,需要单独指内核这个部件时叫「内核」(英文 kernel)。可以连接的第三方服务保留它们自己的名字。应用里指向 GeoCode 的链接只有两个:About 里的发布仓库 `https://github.com/zzhonglei/GeoCode-Release`,以及报告问题时打开的源码仓库的 Issue 页;上游的社区、文档站与发布页不出现。About 只显示名字、版本与发布仓库的链接。

GeoCode 有自己的版本号,与两个上游的版本号无关:它只写在 `desktop/packages/electron/package.json` 的 `build.extraMetadata.version`,打包时盖掉上游的版本,GeoCode 的其他部分(如 Python 包 `geocodekit`)也从这里取。

只换用户看得到的名字。内部的名字照上游:界面的协议与来源、事件与 IPC 的名字、环境变量、存储键、接口路径与包名。改它们用户看不到任何区别,却让每次合并上游都多出冲突;改界面的来源还会清空界面记住的状态。GeoCode 新增的部分用自己的名字:交给 agent 的工具以 `geocode` 命名,地理工具照内核自带工具的写法命名(`GEOENGINE.md` 第 3.6 节);数据与配置的位置用 `geocode` 的名字,与用户装的 OpenCode、OpenChamber 分开(`PATHS.md`)。

发给第三方的技术身份也照上游:内核请求模型服务时带的请求头,以及各服务商登录用的客户端登记。对方按这些登记放行,改了会让登录与请求失效。在应用里登录 GitHub 时,用户授权的是 GeoCode 自己登记的应用,不申请修改工作流文件的权限。

应用的进程在系统的进程列表里也叫 GeoCode。内核是独立的可执行文件,系统按文件名显示它,所以构建出的内核放进应用时改名为 `geocode-kernel`;它在命令行里的自称与 `--version` 的输出仍是上游的,壳据此核对版本。清理上次异常退出留下的内核时,壳只认这个名字的进程,不碰用户自己运行的 OpenCode。

应用起不来时显示自己的出错页:内核启动失败或安装不完整、GeoEngine 起不来或异常退出、内置的 Python 环境准备失败,都在这一页说明发生了什么,给出错误原文与日志的位置,提供重启、复制诊断信息与报告问题的入口,内核与设置这类重试可能恢复的情况另有重试。出错页不引导用户安装别的软件或连接别的主机。连壳服务端都起不来、或签发不了窗口令牌时没有界面可用,应用以系统的错误提示框说明原因与日志位置后退出。出错页只有英文,错误原文照原样给出,不翻译也不改名,其中可能出现上游的名字。

GeoCode 的标志是一个带波纹的球体、一道倾斜的轨道与轨道上一颗琥珀色的星。应用里画标志的地方(应用与菜单栏图标、启动画面、界面、工具行的小图标、网页图标)都用它;彩色的标志只有轨道的颜色随明暗主题变化。启动时星沿轨道公转:从窗口出现到界面可用,标志先后由主进程的启动页、界面的入口页与界面自己的启动遮罩画出,三处对着同一个时钟,换阶段时星不回到起点。这份图形在三个文件里各写了一遍(`desktop/packages` 下的 `electron/geocode/loading-mark.mjs`、`web/index.html`、`ui/src/geocode/BrandMark.tsx`),没有编译关系把它们连起来:改标志时三处一起改,由 `BrandMark.test.tsx` 核对它们一致。图标怎样生成见 `DEVELOPMENT.md` 第 6 节。

## 7. 许可证

源码仓库里的许可证覆盖代码:根目录的 `LICENSE` 是 GeoCode 自己的 MIT 许可证;`kernel/` 与 `desktop/` 下的代码保留上游各自的版权声明与许可证(`kernel/LICENSE`、`desktop/LICENSE`),上游自己带进来的第三方代码也保留它们原有的许可证文件。

安装包在资源目录的 `licenses/` 里(macOS 上是 `GeoCode.app/Contents/Resources/licenses/`)带着两个上游与终端用的代码与字体(T3 Code 的适配层、Ghostty、Symbols Nerd Font)的许可证,它们的代码编进了应用。内置 Python 环境的各个包在环境里带着各自的许可证文件。完整的声明放在发布仓库里:两个上游、随内置 Python 环境分发的各个包(其中有以动态库形式随包分发的 LGPL 与少数 GPL 的库,GeoCode 自己的代码不链接它们),以及随 GeoEngine 分发的数据(如 OSM 的标签预设库)。About 里的链接指向发布仓库。

## 8. 边界与约束

- 壳服务端运行在要求口令的模式下,上游「没有口令就不能开隧道、不能监听本机以外的地址」的保险因此不再起作用:只监听 127.0.0.1 与不开隧道要由 GeoCode 自己守住,不能放开。
- 文件预览:页面里的脚本读不到页面所在项目以外的文件(聊天目录里的页面限于它所在的文件夹),但服务端凭授权码交出的范围更宽,壳的数据目录与所有聊天目录里的文件都在内,并跟随符号链接。这是上游的做法,GeoCode 不改。
- 内核的版本号与自称是上游的,壳靠它核对版本,所以不改。

## 9. 与其他部分的关系

- `DESIGN.md`:GeoCode 的定位与原则,这里的边界由它们而来。
- `PATHS.md`:应用、内核与 GeoEngine 在用户电脑上与项目里产生的文件,以及读取的用户环境。
- `ENVIRONMENT.md`:环境变量从哪里取得、交给谁。
- `GEOENGINE.md`:GeoEngine 作为主进程的辅助进程运行,地理工具经壳服务端的回调接口到达它,出错时用这里的出错页。
- `PYTHON.md`:内置的 Python 环境怎样处理代理。
- `DEVELOPMENT.md`:构建内核、开发时怎样启动,以及开发版与打包版在访问控制与环境变量上的差别。
