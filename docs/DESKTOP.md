# 桌面应用

本文档说明 GeoCode 桌面应用由什么组成,以及它遵循的几条基本约束:内核只为应用服务,应用只在本机为一个用户工作,只有应用自己的窗口与它发出的凭证能访问它,它的行为只由用户的设置与配置文件决定、不受环境变量影响,用户看到的产品只有 GeoCode。

## 1. 组成

GeoCode 是一个应用,安装、启动、退出都只有一个入口,用户不需要另装 OpenCode。

```
Electron 主进程
 ├─ 壳服务端(OpenChamber 的服务端,在主进程内运行)
 │    └─ 子进程:内核(OpenCode,serve --stdio)
 ├─ 辅助进程:GeoEngine(地理引擎,见 GEOENGINE.md)
 └─ 界面(渲染进程)── HTTP、SSE、WebSocket ──→ 壳服务端
```

界面不直接连内核:壳服务端把内核的接口代理给界面,转发时附上内核的口令,界面拿不到这个口令。两个服务都只监听 127.0.0.1,壳服务端只接受 GeoCode 自己的窗口(第 4 节)。

## 2. 内核

内核是应用的私有组件:只由这个应用启动,只为它服务,随它退出。壳以 OpenCode 为私有内核设计的 `serve --stdio` 方式启动它:每次启动随机生成口令并显式传入,内核读取后把口令从自己的环境里删掉,agent 执行的命令不会继承它;内核把标准输入当作租约,应用正常退出或被强制结束时,内核随之退出。重启与退出只经壳持有的子进程结束内核,不按端口找进程:内核退出后,旧端口可能已被别的程序占用。上游的两种做法都不用:OpenChamber 用的普通 `serve` 会把口令留给 agent 执行的命令,OpenCode 桌面版的常驻服务在应用退出后仍在运行,还与用户自己装的 OpenCode 共用数据。

安装包里的内核由本仓库的 `kernel/` 构建,对内核的修改这样才能进入安装包。打包出的应用只用安装包里的内核,不用设置、环境变量或 `PATH` 指向的 `opencode`;内核缺失时报错,不引导用户另装 OpenCode。构建方法见 `DEVELOPMENT.md` 第 4 节。

一个项目的行为只由它自己和用户的全局设置决定。用户与项目的配置,内核只从两处读:全局配置目录,以及会话所在的目录本身,即用户添加的项目文件夹或它的 worktree,不属于项目的对话则是它自己的聊天目录。会话目录里子目录的 `AGENTS.md` 是例外:agent 用 `read` 读那个子目录或其中的文件时,内核照上游把它一并带上。上游还会往上级目录查找配置,读本机的系统配置目录与 macOS 的 MDM 托管设置(机构给 OpenCode 统一下发配置的地方),读 Claude Code 等其他应用的技能目录,接受配置里列出的外部技能与插件,以及远程下发的配置(包括 OpenCode Console 随它的模型服务一起下发的组织策略与 MCP),这些 GeoCode 都不读;插件只来自应用自己的托管配置。这样,下载来的文件夹放在哪里、本机装了哪些别的 AI 工具,都不会改变 agent 的行为。「技能」等设置页也只在这两处读写。读到的项目配置照上游仍能启动 MCP 服务与格式化命令、放宽权限、读项目以外的文件(`{file:…}`),并让内核克隆它列出的仓库。打开带配置的项目时,内核不询问是否信任。

## 3. 边界

GeoCode 是单机、单用户的桌面应用。让其他设备连进来的机制(局域网访问、设备配对、中转与公网隧道),连到本机内核以外主机的机制(远程实例、SSH、外部内核),以及不经用户操作就发往上游服务器的请求(更新检查、使用上报、推送),都关闭;连接模型服务是内核的正常工作,取模型目录与服务商图标也在其中,不在此列。OpenChamber 的网页版、VS Code 扩展、移动端与命令行不构建、不发布,用户只通过 GeoCode 的窗口使用它。

上游的其余功能按 `DESIGN.md` 第 3 节的原则取舍,落到具体功能上是两条:第三方代码与项目以外的文件不能改变应用的行为,对话与凭据不在用户没有需要时交给第三方。所以用户不能自己往 GeoCode 里安装扩展与插件,GeoCode 不提供代码片段、Jev、Linear 与 GitLab 集成(GitLab 集成在启动时就读取 glab 的登录,并以 OpenChamber 登记的应用联系 gitlab.com;内核的 GitLab 模型服务商不在此列),不读 OpenChamber 的企业策略,不读其他 AI 应用的登录凭据与其他 agent 工具的目录,也不采用 OpenChamber 让团队提交进项目的共享设置(它会给壳加上在本机执行的命令;内核照 OpenCode 读项目自己的配置,见第 2 节);界面语言只提供英文、简体中文与繁体中文。

与定位不冲突的功能照上游保留,git 这类面向代码的功能也在其中:地理数据处理同样是重代码的工作。GitHub 的 Issue 与 PR 看板(GitLab 与 Linear 随集成关闭)、HTML 文件的预览、项目的笔记、待办与计划,都照上游保留。不属于任何项目的对话要保留并做好,因为地理用户多半没有建项目的习惯。

关闭照 `DESIGN.md` 第 3 节不删源码,在功能所在的地方关掉。壳服务端拒绝相应的接口,主进程拒绝相应的命令,界面隐藏入口、停掉自动发出的请求;界面的隐藏只是配合,拒绝发生在壳服务端与主进程。输入框的 shell 模式(开头打 `!` 直接执行命令)是例外,只在界面关掉:内核执行命令的接口只有窗口能调,而窗口里的终端本来就能在同一目录执行同样的命令,拒绝它收窄不了什么。

## 4. 本机访问控制

只监听 127.0.0.1 挡不住本机:任何程序都连得上壳服务端,浏览器里的网页也能,因为 WebSocket 不受跨域限制,DNS 重绑定还能让网页以同源的身份发请求。能调用壳服务端,就能让 agent 以用户的身份执行命令、读写文件。所以要防的是浏览器里的网页、其他用户、沙箱内的程序与扫描本机端口的脚本;以用户身份运行、不受沙箱限制的程序本来就能修改用户的文件,不在此列。

壳服务端只认 GeoCode 自己的窗口。它运行在上游的口令模式下,口令每次启动随机生成,只在主进程的内存里,没有人输入它;上游「无口令、只要令牌」的模式不用,因为在那个模式下多数 WebSocket 不做认证,会话 cookie 也可以伪造。主进程为窗口签发一个令牌,只存在于主进程与窗口的内存里,每次启动换新。设备令牌与会话重置的接口关闭,会话的签名密钥也每次启动随机生成,窗口以外没有取得令牌或会话的途径。窗口之外,除了健康检查、版本、系统信息与取一个空闲端口这几个状态接口(只报告状态或给出一个端口号),壳服务端只接受内核的工具回调:它用每次启动内核时生成的回调令牌,只能调用交给 agent 的那几个工具接口与地理工具的接口;agent 执行的命令也读得到这个令牌(`GEOENGINE.md` 第 2 节)。git 是第三个来访者:仓库绑定了账号时,它的 git 配置指向 GeoCode 的凭据助手,助手用数据目录里每次启动换新的密钥调用壳服务端的凭据接口,取得这个仓库绑定的账号的凭据。这份密钥换得到任何已绑定的仓库的凭据,但读得到它的程序本来就读得到数据目录里的 GitHub 登录。第一次以绑定的账号经应用克隆、拉取或推送时,壳另在本机回环地址上开一个端口,直到应用退出;每次操作凭一次性的随机数从这里取一次凭据。文件预览也不带令牌:预览页的地址里带一个随机的授权码,闲置十分钟失效。页面里的脚本读不到页面所在项目以外的文件内容(聊天目录里的页面限于它所在的文件夹);服务端凭授权码交出的范围更宽,壳的数据目录与所有聊天目录里的文件都在内,并跟随符号链接。这是上游的做法,GeoCode 不改。另有两道防线:壳服务端只接受以 `127.0.0.1` 或 `localhost` 访问的 HTTP 请求,挡住 DNS 重绑定(WebSocket 的升级请求不经过这道检查,只靠令牌);内核的每个接口请求都要口令(配对链接与终端凭证也不例外;接口以外的路径只回 404),口令不留在壳的环境变量里,应用内的终端与其他子进程无法绕过壳直接访问内核。令牌失效时,界面提示重启应用,不出现登录页。

口令模式下,上游「没有口令就不能开隧道、不能监听非本机地址」的两道保险不再起作用,所以第 3 节对隧道的关闭与只监听 127.0.0.1 不能放开。

## 5. 环境变量

GeoCode 通过界面配置,不接受以环境变量给出的配置。用户环境里以 `OPENCODE_`、`OPENCHAMBER_`、`OTEL_`、`BUN_`、`ELECTRON_` 开头的变量是内核、壳与运行时的设置,能把配置与数据改到别处、从指定路径加载程序、把数据发往别处或打开调试功能。打包出的应用按前缀忽略它们,上游以后新增的同前缀变量也在内,Windows 上比较前缀不区分大小写。Electron 运行时在应用代码之前自己读取的几个变量(如 `ELECTRON_RUN_AS_NODE`)挡不住,只有启动应用的环境带着它们时才起作用:从终端启动,或在 Windows 的环境变量里设了它们。其余变量是用户自己的环境,包括 `PATH`、语言、代理、证书与各种工具链的变量,照常交给内核、GeoEngine、agent 执行的命令与终端:agent 调用 conda、GDAL、PROJ 这些地理工具,靠的就是它们。

代价是上游只能用环境变量调整的功能不再可用,例如内核的几个管理开关与 OpenTelemetry 遥测;OpenCode 自家模型服务的密钥改在服务商页填写。开发时的启动脚本正是用这些变量传参数,所以从启动环境继承来的这些变量只在打包出的应用里忽略;设置里填的与交给 GeoEngine 的,开发版里同样去掉。外部内核、远程服务器这类只能用环境变量打开的机制,就是靠这条规则关闭的,开发版里仍能打开它们。

设置里的「环境变量」给内核、GeoEngine、git、终端与项目动作再添加变量,页面里填的同前缀变量同样不交给内核与 GeoEngine。每个项目还可以添加自己的变量,或配置一条 direnv、devenv、nix 这类命令来导出变量。项目的变量不交给内核与 GeoEngine。这条命令只取自用户的设置,不取自仓库,只在用户操作(提交、打开终端、运行项目动作等)时执行;它运行的工具会读项目里的 `.envrc`、`flake.nix` 这类文件。在页面里设的变量对 agent 执行的命令与地理工具都生效,何时生效见 `GEOENGINE.md` 第 4 节;GeoEngine 运行内置的 Python 环境时只给其中网络相关的变量与 `HOME`(`PYTHON.md` 第 6 节)。

代理照上游:内核与壳服务端只认 `HTTP_PROXY`、`HTTPS_PROXY` 与 `NO_PROXY`,大小写皆可,本机的回环地址总是直连,不读系统设置里的代理,也不认 `ALL_PROXY`(内核只在 WebSocket 上认它)。两种大小写都设了、值又不同时,上游并不一致:内核的模型请求(Bun 的 fetch)以小写的为准,壳服务端与内核的 WebSocket 以大写的为准。内置的 Python 环境照同一条规则,两种都有时与模型请求一样以小写的为准(`PYTHON.md` 第 6 节)。窗口与浏览器面板经 Chromium 联网,照上游跟随系统的代理设置。

## 6. 名字与标识

用户在应用里看到的产品只有 GeoCode:菜单、窗口标题、通知、设置里的说明与出错提示都用这个名字(出错页里照原样给出的错误原文除外,见下),需要单独指内核这个部件时叫「内核」(英文 kernel,繁体中文「核心」)。OpenCode Zen 这类可以连接的第三方服务,保留它们自己的名字。应用里指向 GeoCode 与上游的链接只有两个:About 里的发布仓库 `https://github.com/zzhonglei/GeoCode-Release`,以及报告问题时打开的源码仓库 `https://github.com/zzhonglei/GeoCode`;上游的社区、文档站与发布页不出现。GeoCode 有自己的版本号,与两个上游的版本号无关:它只写在 `desktop/packages/electron/package.json` 的 `build.extraMetadata.version`,打包时盖掉上游的版本,GeoCode 的其他部分(如 Python 包 `geocodekit`,`GEOCODEKIT.md` 第 6 节)也从这里取;两个上游 `package.json` 里的 `version` 是上游的,合并时照上游。About 只显示名字、版本与发布仓库的链接;两个上游的许可证声明放在发布仓库里,不进安装包。

壳交给 agent 的工具(浏览器、通知等)以 `geocode` 命名;地理工具是内核的内置工具,照 OpenCode 自带工具的写法命名(见 `QGIS.md` 第 1 节)。在应用里登录 GitHub 账号时,用户授权的是 GeoCode 自己登记的应用,默认不申请修改工作流文件的权限。

只换用户看得到的名字。内部的名字照上游:界面的协议与来源、事件与 IPC 的名字、环境变量、存储键、接口路径与包名。改它们用户看不到任何区别,却让每次合并上游都多出冲突;改界面的来源还会清空界面记住的状态。

应用的各个进程在系统的进程列表里也用 GeoCode 的名字。内核是一个独立的可执行文件,系统按文件名显示它的进程,所以构建出的内核在放进应用时改名为 `geocode-kernel`;它在命令行里的自称与 `--version` 的输出仍是 OpenCode 的,壳据此核对版本。清理上次异常退出留下的内核时,壳只认这个名字的进程,不会碰用户自己运行的 OpenCode。

发给第三方的技术身份照上游保留:内核请求模型服务时带的请求头,以及各服务商登录用的客户端登记。对方按这些登记放行,改了会让登录与请求失效。服务商的登录方式同样跟随 OpenCode,GeoCode 不改,各家服务商的登录适配只能由上游维护。

内核起不来、安装不完整这类情况,应用显示自己的出错页:说明发生了什么,给出错误原文与日志的位置,提供重试(安装不完整时没有)、重启、复制诊断信息与报告问题的入口,不引导用户安装 OpenCode 或连接别的主机。内核启动失败一经壳服务端确认就显示这一页,不等界面把重试次数用完。GeoEngine 起不来或异常退出时也显示这一页,给出主进程记下的原因与它最后的错误输出(为什么不提供重试见 `GEOENGINE.md` 第 2 节)。内置的 Python 环境准备失败时同样显示这一页,只能重启,重启会再准备一次;准备好之前,窗口停在加载动画上(`PYTHON.md` 第 8 节)。连壳服务端都起不来、或签发不了窗口令牌时没有界面可用,应用以系统的错误提示框说明原因与日志位置后退出。出错页只有英文,错误原文照原样给出,不翻译也不改名,其中可能出现上游的名字。

GeoCode 的标志是一个带波纹的球体、一道倾斜的轨道与轨道上一颗琥珀色的星。应用里画标志的地方(应用与菜单栏图标、启动画面、界面、工具行的小图标、网页图标)都换成它,上游的方块与字标不出现;服务商登录后浏览器里的回调页用横版的字标。彩色的标志只有轨道的颜色随明暗主题变化,macOS 的应用图标在深色外观下也保留彩色。

启动时星沿轨道公转。从窗口出现到界面可用,标志先后由主进程的启动页、界面的入口页与界面自己的启动遮罩画出,三处对到同一个时钟,换阶段时星不回到起点。这份图形在三个文件里各写了一遍(`desktop/packages` 下的 `electron/geocode/loading-mark.mjs`、`web/index.html`、`ui/src/geocode/BrandMark.tsx`),没有编译关系把它们连起来:改标志时三处一起改,由界面包 `geocode/` 目录里的测试核对它们一致。图标怎样生成见 `DEVELOPMENT.md` 第 6 节。

## 7. 验收

- 在没有装 OpenCode 的电脑上,应用启动后直接可以对话,用的是 `kernel/` 构建的内核,即使 `PATH`、设置或环境变量指向别的 `opencode` 也一样;正常退出与强制结束之后都没有残留的内核进程;agent 执行的命令与应用内的终端不继承内核的口令。
- 设置与界面里没有远程、局域网、配对、隧道等入口,对应的接口与命令被拒绝;运行期间,除了取模型目录与服务商图标,应用不自动向上游的服务器发出请求。
- 对话里只出现全局配置目录与会话目录本身的指示与技能(第 2 节所说的子目录的 `AGENTS.md` 除外);项目的上级目录、其他应用目录、本机的系统配置目录与 MDM 托管设置里的配置与插件都不起作用。
- 访问接口与内核的、不带令牌的 HTTP 请求与 WebSocket 连接都被拒绝(健康检查、版本这类状态接口,以及凭各自密钥访问的 git 凭据接口与文件预览除外),Host 不是 `127.0.0.1` 或 `localhost` 的 HTTP 请求也被拒绝;窗口带着令牌时一切正常,令牌失效时显示重启提示。
- 打包出的应用从带着第 5 节那五种前缀变量的环境启动(Electron 自己先读的几个除外),行为不变,用户环境里的这些变量到不了内核、GeoEngine 与 agent 执行的命令,在设置的「环境变量」里填的也一样;命令所用的 shell 自己读的启动文件(如 zsh 的 `~/.zshenv`)里设的不在此列。其余变量照常到达。
- 三种界面语言下,用户在应用里与进程列表里看到的产品都只有 GeoCode(出错页里的错误原文除外)。
