# 桌面应用

GeoCode 桌面应用由什么组成,以及它守的几条基本约束:内核只为应用服务,应用只在本机为一个用户工作,只有应用自己的窗口与它发出的凭证能访问它,它的行为由用户的设置与配置文件决定、不受应用自己的环境变量影响,用户看到的产品只有 GeoCode。

## 1. 定位

GeoCode 是一个应用,安装、启动、退出都只有一个入口,用户不需要另装别的软件才能对话(`DESIGN.md` 第 3 节)。它不连接本机以外的内核或服务器,不在用户没有需要时向上游的服务器发请求。连接模型服务(包括取模型目录与服务商图标)、地理工具检索与下载数据、登录 GitHub 这类用户要用的功能照常联网。用户只通过 GeoCode 的窗口使用它,没有网页版与命令行。

与这个定位不冲突的功能都保留,包括 git、Issue 与 PR 这类面向代码的功能:地理数据处理同样是重代码的工作。不属于任何项目的对话要做好,地理用户多半没有建项目的习惯。

## 2. 核心设计

### 2.1 组成

各进程的关系见 `DESIGN.md` 第 2 节。界面只与壳服务端通信(HTTP、SSE、WebSocket),不直接连内核:壳服务端把内核的接口代理给界面,转发时附上内核的口令,界面拿不到这个口令。壳服务端与内核都只监听 127.0.0.1。

### 2.2 内核

内核是应用的私有组件:只由这个应用启动,只为它服务,随它退出。壳以 `serve --stdio` 启动它:口令每次启动随机生成并显式传入,内核读取后从自己的环境里删掉,agent 执行的命令不会继承它;内核把标准输入当作租约,应用正常退出或被强制结束,内核都随之退出。重启与退出只经壳持有的子进程结束内核,不按端口找进程,因为内核退出后旧端口可能已被别的程序占用。

安装包里的内核由本仓库的 `kernel/` 构建,对内核的修改这样才能进入安装包。打包出的应用只用安装包里的内核,不用设置、环境变量或 `PATH` 指向的别的内核;内核缺失时显示出错页,让用户重新安装 GeoCode。

一个项目的行为只由它自己和用户的全局设置决定。用户与项目的配置,内核只从两处读:全局配置目录,以及会话所在的目录本身(用户添加的项目文件夹或它的 worktree;不属于项目的对话是它自己的聊天目录)。不往上级目录查找,不读本机的系统配置与托管设置,不读其他 AI 应用的目录。远程下发的配置只接受用户登录的 OpenCode 服务账户带来的模型服务与网页搜索,其余不收。配置项的写法与含义都照上游,改的只是从哪里读,另外关掉会把配置指定的文字放进提示词、或加载代码的几项:配置里列出的说明文件、技能的路径与网址,以及全局与项目配置里写的插件。插件只来自应用自己交给内核的托管配置。这样,下载来的文件夹放在哪里、本机装了哪些别的 AI 工具,都不会改变 agent 的行为。例外是子目录里的 `AGENTS.md`:agent 用 `read` 读那个子目录里的文件时,内核把它一并带上。

会话目录里的项目配置照常生效:它能启动 MCP 服务、语言服务与格式化命令,指定 shell,放宽权限,读项目以外的文件。其中在本机运行命令的几项要用户先信任:内核第一次为这个文件夹工作之前,壳把它们列出来问用户,不信任时 agent 不能在这里工作,文件与 Git 变更照常可看。壳检查的正是内核会读的那几处,不检查插件,因为内核不加载项目里的插件。答复按仓库记在数据目录,同一仓库的 worktree 共用;这几项一改变就再问一次。下载来的仓库带着项目配置,打开它不会悄悄运行里面的命令。

### 2.3 本机访问控制

只监听 127.0.0.1 挡不住本机:任何程序都连得上壳服务端,浏览器里的网页也能,因为 WebSocket 不受跨域限制,DNS 重绑定还能让网页以同源的身份发请求。能调用壳服务端,就能让 agent 以用户的身份执行命令、读写文件。所以要防的是浏览器里的网页、其他用户、沙箱内的程序与扫描本机端口的脚本;以用户身份运行、不受沙箱限制的程序本来就能修改用户的文件,不在此列。

壳服务端只认 GeoCode 自己的窗口。它以要求凭证的模式运行,主进程直接为窗口签发令牌:令牌只在主进程与窗口的内存里(数据目录里只记它的摘要),每次启动换新;会话的签名密钥也每次启动随机生成。设备令牌、配对与会话重置这些让别处取得令牌的途径都关闭。令牌失效时,界面提示重启应用,不出现登录页。

窗口之外只有几类来访者,各凭各的凭证,能做的事各有范围:

- 状态接口(健康检查、版本这类)不要凭证,只报告状态或给出一个空闲端口。
- 内核凭每次启动内核时生成的回调令牌,只能调用应用交给内核的插件所用的接口,包括地理工具的接口(`GEOENGINE.md` 第 2.1 节)。agent 执行的命令也读得到这个令牌。
- git:仓库绑定了账号时,它的 git 配置指向 GeoCode 的凭据助手,助手凭数据目录里每次启动换新的密钥取得这个仓库绑定的账号的凭据。读得到这份密钥的程序,本来就读得到数据目录里的 GitHub 登录。应用自己发起的克隆、拉取与推送另凭一次性的随机数取凭据。
- 文件预览:预览页的地址里带一个随机的授权码,闲置一段时间失效。

另有两道防线。壳服务端只接受以 `127.0.0.1` 或 `localhost` 访问的 HTTP 请求,挡住 DNS 重绑定;WebSocket 的升级请求不经过这道检查,只靠令牌。内核的每个接口请求都要内核的口令,口令不留在壳的环境变量里,应用内的终端与其他子进程无法绕过壳直接访问内核。

### 2.4 环境变量

应用的行为由用户的设置与配置文件决定,不受环境变量控制;环境变量只为用户的工具服务(`ENVIRONMENT.md`)。

### 2.5 名字、版本与标志

用户在应用里看到的产品只有 GeoCode:菜单、窗口标题、通知、设置里的说明与出错提示都用这个名字,需要单独指内核这个部件时叫「内核」。可以连接的第三方服务保留它们自己的名字。应用里指向 GeoCode 的链接只有它的仓库与报告问题的入口,上游的社区、文档站与发布页不出现。

只换用户与模型看得到的名字。内部的名字照上游:界面的协议与来源、事件与 IPC 的名字、环境变量、存储键、接口路径与包名。改它们用户看不到任何区别,却让每次合并上游都多出冲突;改界面的来源还会清空界面记住的状态。交给模型的名字算作看得到的:模型在对话里会提到它们。所以壳交给 agent 的工具,不论来自上游还是 GeoCode,都以 `geocode` 命名(如 `geocode_web`);内核里管理应用自身的工具也移到 `geocode` 命名空间(`KERNEL.md` 第 2.1 节)。GeoCode 新增的其他部分也用自己的名字:地理工具照内核自带工具的写法命名(`GEOENGINE.md` 第 2.8 节);数据与配置的位置用 `geocode` 的名字(`PATHS.md`)。发给第三方的技术身份也照上游:内核请求模型服务时带的请求头,以及各服务商登录用的客户端登记,改了会让登录与请求失效。在应用里登录 GitHub 时,用户授权的是 GeoCode 自己登记的应用,不申请修改工作流文件的权限。

GeoCode 有自己的版本号,与两个上游的版本号无关:它只写在 `desktop/packages/electron/package.json` 的 `build.extraMetadata.version`,打包时盖掉上游的版本,GeoCode 的其他部分(如 `geocodekit`)也从这里取。版本号从 1.0.0 开始,只在发布时改;发布的那次提交打上 `v<版本号>` 的标签,安装包作为这个标签的 Release 放在 GeoCode 的仓库里。

应用的进程在系统的进程列表里也叫 GeoCode。内核是独立的可执行文件,放进应用时改名为 `geocode-kernel`;它在命令行里的自称与 `--version` 的输出仍是上游的,壳据此核对版本,所以不改。清理上次异常退出留下的内核时,壳只认这个名字的进程,不碰用户自己运行的 OpenCode。

应用的内核、GeoEngine 或内置的 Python 环境起不来时,显示 GeoCode 自己的出错页,说明发生了什么,给出错误原文与日志的位置,提供重启与报告问题的入口。内核第一次启动失败,出错页就出现,壳在后台接着重试。内核在界面停止重试之前起来的,出错页自己退去;之后才起来的,要点重试。GeoEngine 不重试(`GEOENGINE.md`)。出错页不引导用户安装别的软件或连接别的主机。连壳服务端都起不来、或签发不了窗口令牌时,应用以系统的错误提示框说明原因与日志位置后退出。出错页只有英文,错误原文照原样给出,其中可能出现上游的名字。

GeoCode 的标志是一个带波纹的球体、一道倾斜的轨道与轨道上一颗琥珀色的星,应用里画标志的地方都用它。启动时的动画由三处分别画出,这份图形因此在三处各写了一遍,由测试核对它们一致。

新会话页的标题另用像素风的横向字标 GEOCODE,问句挪进输入框作提示文字,页面上只留字标与输入框;发出第一条消息后,输入框的提示回到平常的说法。字标按原图网格的四分之三显示,窗口太矮时不显示,深浅两种主题共用一份。

### 2.6 许可证

源码仓库里,根目录的 `LICENSE` 是 GeoCode 自己的 MIT 许可证;`kernel/` 与 `desktop/` 下的代码保留上游各自的版权声明与许可证,上游自己带进来的第三方代码也保留它们原有的许可证文件。

上游与几个随附组件的许可证随安装包分发,在应用的 `licenses/` 里。随内置 Python 环境分发的包里有 LGPL 与少数 GPL 的库,它们以动态库的形式随包分发,GeoCode 自己的代码不链接它们。

## 3. 边界与约束

- 壳服务端运行在要求凭证的模式下,上游「没有口令就不能开隧道、不能监听本机以外的地址」的保险因此不再起作用:只监听 127.0.0.1 与不开隧道要由 GeoCode 自己守住,不能放开。
- 关闭的上游功能,关在发请求、读文件、执行命令的那一层(`CONVENTIONS.md` 第 2 节):壳服务端的接口拒绝,主进程的命令拒绝,只藏起界面的入口不算。
- 文件预览:页面里的脚本读不到页面所在项目以外的文件,但服务端凭授权码交出的范围更宽,壳的数据目录与所有聊天目录里的文件都在内,并跟随符号链接。这是上游的做法,GeoCode 不改。

## 4. 与其他部分的关系

- `DESIGN.md`:GeoCode 的定位与原则,这里的边界由它们而来。
- `PATHS.md`:应用、内核与 GeoEngine 在用户电脑上与项目里产生的文件,以及读取的用户环境。
- `ENVIRONMENT.md`:环境变量从哪里取得、交给谁。
- `GEOENGINE.md`:GeoEngine 作为主进程的辅助进程运行,地理工具经壳服务端的回调接口到达它,出错时用这里的出错页。
- `DEVELOPMENT.md`:构建内核、开发时怎样启动,以及开发版与打包版在访问控制与环境变量上的差别。
