# GeoCode 系统概览

## 1. 文档范围

本文档是 GeoCode 文档集的入口,按执行时序介绍系统的组件构成与控制流:从应用启动、
环境就绪,到一次工具调用的完整路径,以及结果的返回通道。末尾记录各部分的实现现状
(§7)与其余文档的分工(§8)。

产品定位与设计原则不在本文档内,详见 `DESIGN.md`。各模块的完整设计与契约同样不在此处;
本文档在需要处给出指引,不复述其内容。

不在范围内:界面实现、打包与分发、各模块的内部设计。

---

## 2. 术语

下表定义本文档使用的术语,并涵盖阅读其余文档所需的基本概念。

| 术语 | 定义 |
|---|---|
| Agent 内核 | 由 OpenCode agent 引擎承担的会话循环、模型接入、登录、权限裁决与工具调度 |
| 薄 fork | 对上游内核仅施加最小源码补丁的维护方式;补丁面越薄,版本升级成本越低 |
| 装配 | 通过配置、环境变量、外挂进程与界面实现定制,而非修改内核源码。源码补丁为最后手段 |
| 装配层 | 承载装配结果的配置模块,提供 GeoCode 的出厂默认值 |
| 地理内核 | GeoCode 自有的地理能力服务层,与 Agent 内核同进程,二者互不引用 |
| 基础设施模块 | 地理内核的底层四模块:配置、子进程执行、网络、状态 |
| 能力模块 | 地理内核的上层四模块:QGIS、GEE、OSM、GDAL |
| 出口面 | 地理内核对外的三个接口面:工具面(供模型)、状态面(供界面显示环境)、数据面(供界面取数据) |
| 就绪门禁 | 能力模块可用性的前置检查。环境未就绪时工具不执行 |
| 中间态 | `resolving`、`building` 等表示处理进行中的状态,是状态集合的正式成员 |
| 环境头 | 工具输出开头的一段说明,记录本次执行所用的外部软件安装与版本 |
| 出口锁 | 对子代理施加的权限约束,限制其可访问的外部服务与可派生的子任务 |
| 绊线测试 | 针对特定源码补丁的运行时测试。补丁被上游重构架空时该测试失败 |
| 旧版 | GeoCode v0.9.x,已可发布的既有产品。当前代码树为重建,旧版作为需求参照 |

## 3. 组件构成

### 3.1 进程形态

目标形态由 Electron 桌面壳、Shell Runtime、React 界面与 Agent 内核构成(详见
`DESKTOP.md` §2)。Shell Runtime 迁自 OpenChamber Web Server,但只作为 Electron main 内的
本地服务存在,不构成 GeoCode Web 产品。桌面壳以 `utilityProcess` 拉起 Agent 内核;
界面只连接 Shell Runtime,由后者代理 Agent API,Kernel 口令不进入 renderer。

OpenChamber 迁入 `desktop/` 后只叠了很薄的一层补丁,状态见 §7。开发期的装配验证对着内核的 HTTP 端点做,
**不对着终端形态**——上游 TUI 读的是另一张 agent 表(详见 `KERNEL.md` §4.2)。

### 3.2 地理内核的服务组成

地理内核不是独立进程,而是 Agent 内核进程内的一层服务。其服务图挂载为单一节点
`GeoKernel.node`,以降低上游合并成本(详见 `GEOKERNEL.md` §2.4)。

```
GeoKernel.node
├── 基础设施层(四模块,相互独立,构建顺序不受约束)
│   ├── config     读取与监听 machine.json,按块派发变更
│   ├── runtime    子进程执行:创建、输出投递、计时、终止
│   ├── net        网络可达性:路径解析、探测、监视
│   └── status     状态记账:存储、提交、发布,并防止陈旧结果覆盖较新结果
└── 能力层(构建于基础设施之上)
    ├── qgis       环境解析、算法目录、执行管线、数据读取
    ├── gee        依赖链探测、远端授权、脚本执行
    ├── osm        客户端可靠性、查询构建、空间范围、转换、落盘
    └── gdal       工具链发现、矢量管线、栅格管线
```

算法目录(`QgisCatalog`)同为服务组的成员。服务组的成员对外可见,而节点的私有依赖不可见;
若算法目录仅作为 QGIS 模块的依赖存在,工具层将无法获取该实例,只能另行构建一个空目录。

### 3.3 同进程约束

三个出口面必须位于同一进程。工具执行会改变环境状态,该状态既影响后续工具行为,
又需实时反映至界面。状态机与事件总线是单一事实源,将任一出口面拆分至独立进程,
等同于产生两份会漂移的事实(详见 `DESIGN.md` §3)。

## 4. 启动与环境就绪

### 4.1 外部软件的处理原则

QGIS、GDAL 与 GEE 是用户机器上的外部软件。GeoCode 仅执行探测、诊断与引导,
不代为安装。

### 4.2 环境状态模型

探测结果不是二值判定,而是一个状态集合。以 QGIS 为例:

| 状态 | 含义 |
|---|---|
| `unconfigured` | 用户尚未配置 |
| `config-error` | 配置文件语法错误,附出错位置 |
| `path-missing` | 配置的路径不存在 |
| `not-qgis` | 路径存在,但目标不是 QGIS 安装 |
| `resolving` | 环境解析进行中 |
| `ready` | 环境可用 |

完整状态集合与迁移规则详见 `GEOKERNEL.md` §4.7 与 §4.8。

中间态是集合的正式成员而非状态缺失。环境解析与算法目录构建耗时可达数十秒,
用户会观察该过程;若以「无状态」表示,界面无法区分「正在处理」与「未配置」
(详见 `GEOKERNEL.md` §2.4)。

### 4.3 网络可达性监视

网络模块以固定间隔复检可达性,当前值为 5 秒;连续两轮失败后放弃当前路线并重新解析。

该间隔的取值依据:探测仅执行 TLS 握手,不携带凭据、不访问 API 路径,因此不进入远端
服务的配额与滥用检测视野,间隔选择仅涉及本地开销(详见 `GEOKERNEL.md` §3.3)。
调整该间隔需重新论证。

### 4.4 配置生效机制

用户配置分为两个文件:

| 文件 | 内容 | 生效方式 |
|---|---|---|
| `geocode.json` | 内核与 Agent 配置:模型、代理人、权限 | 实例加载时读取 |
| `machine.json` | 本机地理环境:各外部软件的位置与标识 | 保存即生效 |

二者分离的原因是生效语义相反。单一文件内并存两种生效方式,用户无法判断哪些改动需要
重启(详见 `PATHS.md` §3.2)。

`machine.json` 划分为 `qgis`、`gee`、`gdal` 三个块。配置监听器检测到文件变更后按块比对
指纹,仅对内容发生变化的块触发重探。

**已知限制**:在同一路径上重装外部软件而不修改配置时,块指纹不变,不会触发重探,
需重启应用。`/geo/reload` 端点不能规避此限制,因为去重过滤器位于其下游。

## 5. 工具调用路径

### 5.1 装配层与权限模型

装配层(`config/geocode.ts`)在配置流水线的最前端合并,提供出厂默认值;
用户配置合并于其后,因而可以覆盖。

装配层首先将全部地理能力置为拒绝。四个权限组如下:

| 权限组 | 覆盖范围 |
|---|---|
| `geodata` | 读取地理数据 |
| `qgis` | QGIS 处理引擎:算法文档与算法执行 |
| `osm` | 公共 OSM 服务 |
| `gee` | Earth Engine |

四个组均不可省略,而理由比它读起来严重。权限引擎给每个 agent 的规则集以 `"*": "allow"`
开头,任何未被后续规则命中的键都落回这条地板;`evaluate` 结尾那句看似安全的
`?? { action: "ask" }` 对任何真实 agent 都不可达。因此缺失任一条拒绝规则,未授权 agent
的调用不是被询问,而是**静默放行**——不报错、不弹窗、不留痕(详见 `TOOLS.md` §4.2)。

权限分组依据环境依赖而非功能。四个组对应用户实际面对的四种就绪条件,
「关闭某一组」在用户认知中对应「该环境未配置」;按功能分组(读 / 写 / 查)不具备
这一对应关系。

各 agent 的授权范围:

| Agent | 授权 | 说明 |
|---|---|---|
| GeoAgent | `geodata`、`qgis`、`gee` | 唯一暴露的主 agent。**不含 `osm`** |
| explore | `geodata`,其余照上游的只读白名单 | 子代理,只读勘察:筛出相关数据,不改动数据 |
| osmfetch | `osm`、`geodata`、`bash`、`glob`,其余通配拒绝 | 子代理,承担全部 OSM 下载 |
| plan | `geodata` 放行;`qgis` 询问、其中 `doc:*` 放行;`gee` 询问 | 计划模态 |

OSM 工具组不授予 GeoAgent 属于刻意的能力隔离:所有面向公共服务的下载经 osmfetch
子代理执行,其网络出口受权限规则限制。因此四个 OSM 工具不出现在 GeoAgent 的工具清单中。

### 5.2 两层键空间

同一工具在两个层面使用不同的键:

| 层 | 键 | 判定位置 | 效果 |
|---|---|---|---|
| 可见性 | 工具 id,经映射表转换为权限组名 | `Permission.disabled` | 工具从模型的工具清单中移除 |
| 执行 | 工具在 `ctx.ask` 中声明的权限键 | `Permission.evaluate` | 调用时放行、询问或拒绝 |

两层的失效表现不同:执行层失效表现为弹窗或拒绝,可见性层失效表现为静默的可见。
涉及权限的改动须分别验证两层,并以运行时测试确认规则命中(详见 `TOOLS.md` §4.1)。

### 5.3 执行序列

以 `RunQgisAlgorithm` 为例,工具执行按下列顺序进行。顺序本身构成设计约束。

| # | 步骤 | 说明 |
|---|---|---|
| 1 | 取环境头快照 | 在权限询问之前取。询问可能持续较久,期间环境可能变化,且拒绝响应亦需携带环境说明 |
| 2 | 权限询问 | 执行层裁决,以算法 id 为匹配对象。位于所有写入动作之前 |
| 3 | 等待就绪门禁 | 处于中间态时轮询等待,有上限 |
| 4 | 重取环境头 | 门禁通过后再取一次,以反映等待期间的变化 |
| 5 | 参数预检 | 对照算法目录检查参数,仅产生建议,不阻断执行 |
| 6 | 预定输出路径 | 实现「不覆盖既有文件」约束 |
| 7 | 工作目录外写入询问 | 目标位于工作目录之外时向用户询问 |
| 8 | 创建父目录 | 缺失时创建,而非报错 |
| 9 | 替换参数 | 将改道后的实际路径写回参数 |
| 10 | 创建子进程 | 见 §5.4 |
| 11 | 解析实际落点 | 执行成功后确认输出的真实路径 |

三个步骤需要展开说明。

**步骤 5 不阻断执行。** 算法目录的元数据无法表达全部参数约束。以其作为拦截依据时,
元数据的缺口将表现为「用户无法运行该算法」。因此预检仅输出提示,由 QGIS 报告真实错误
(详见 `GEOKERNEL.md` §4.12)。

**步骤 6 的依据。** 地理数据不纳入检查点机制——单景遥感影像会使快照仓库大于项目本身。
撤销操作因此对地理数据不可用,不覆盖是唯一的防护手段。目标名称被占用时采用编号:
`out.shp` 改写为 `out (1).shp`。

该约束有两项例外:目录型输出(写入既有目录是正常用法),以及自带「已存在文件处理方式」
参数的算法(此类算法中目标文件存在正是调用意图)。

**步骤 11 的必要性。** 当输出路径的扩展名不被识别或缺失时,QGIS 会追加其默认扩展名:
请求 `/data/result` 时实际写入 `/data/result.gpkg`。报告必须指向实际存在的文件,
否则调用方将持有无法打开的路径。

### 5.4 子进程模型

GeoCode 不直接调用 QGIS 的 API。QGIS 携带独立的 Python 解释器、标准库、Qt 与 GDAL,
执行因此以该解释器为宿主:

```
<QGIS 环境中的 Python> -c <引导脚本> <算法 id> <参数 JSON>
```

引导脚本在该解释器内初始化 QGIS,调用 `processing.run`,并将结果按约定标记写入标准输出。

脚本以内容哈希命名的方式物化至缓存目录,内容变更即产生新文件名,因此不存在执行到
旧版本脚本的可能(详见 `GEOKERNEL.md` §4.13)。

子进程在 macOS 上被置为新进程组的组长,使整棵进程树可被一次性发送信号;
代价是子进程不随宿主进程终止,退出时须显式回收。Windows 不具备进程组机制,
该平台通过 `taskkill /T` 拆除进程树(详见 `GEOKERNEL.md` §3.2)。

### 5.5 结果返回

一次执行产生两份输出,面向不同消费方。

**面向模型的文本输出**,按固定顺序组织:

```
环境头        本次使用的 QGIS 安装与版本
预检提示      步骤 5 产生的建议
执行输出      中间部分可裁剪
落点说明      实际写入路径,及原请求路径未被改动的说明
终止横幅      结束方式:成功 / 失败 / 超时 / 崩溃 / 取消
耗时页脚
```

输出超限时的裁剪方向与上游机制相反。上游保留开头、丢弃结尾,而归因所需信息全部位于
结尾,因此地理工具自行管理截断:裁剪中间,保留两端(详见 `TOOLS.md` §5)。

**面向界面的结构化字段**:算法 id、耗时、退出码、输出落点、是否部分完成。
界面不解析文本输出。同一事实在两个通道中必须一致,但各自读取对应通道。

## 7. 实现现状

本节记录当前代码树中各部分的实现状态。修改本节时应更新既有条目,不应追加新的现状描述。

| 部分 | 状态 | 可核对依据 |
|---|---|---|
| 地理内核:基础设施四模块与能力四模块 | 已完成 | `geo/index.ts` 的服务组 |
| 三个出口面 | 已完成 | 工具面见工具注册表;状态面见状态事件;数据面见 §6 |
| 工具层:八个工具注册 | 已完成 | `tool/registry.ts` 的内置工具数组 |
| 工具层:四组权限装配 | 已完成 | `config/geocode.ts` |
| 两个子代理:osmfetch 与 explore | 已完成 | `config/geocode.ts` 中的定义、出口锁与地理读取权 |
| 凭据脱敏的三处出口:状态事件 / 诊断包 / 日志 | 未开始 | `NetRedact` 全仓无生产调用方 |
| React 界面(OpenChamber) | 身份、存储路径与关闭入口的界面侧已改;地理适配未开始 | `desktop/packages/ui`,自有部分在 `src/geocode/` |
| 桌面壳:Kernel Host | 启动与退出时的终止已完成;§5.2 的重启委托未做 | `desktop/packages/electron/geocode/` |
| 桌面壳:身份隔离与配置面收口 | 已完成 | appId 为 `ai.geocode.desktop`,壳数据在 `~/.config/GeoCode/desktop`;面向内核的七类设置由 `scripts/settings-roundtrip.sh` 逐类往返 |
| Shell Runtime(OpenChamber) | 靠上游 skip-start 接入内嵌 Kernel;数据根、内核根、配置链与关闭的入口已收口 | `desktop/packages/web`,自有部分在 `server/geocode/` |
| 技能商店 | 未开始 | 地理内核中无对应模块 |

表中的「已完成」指实现完整,**不指已经验证**。两者的差距是当前的主要风险:

- 数据面在真实工具链与真实影像上走通了完整 HTTP 链路;关停清扫在真实应用的退出路径上验过
  (`DESKTOP.md` §5.3),绊线打在壳的内核入口上,并以「去掉信号处理则子进程变孤儿」反证过;
- 桌面身份与数据根在 macOS 上端到端验过:应用启动、界面进入、会话创建,落盘对账确认
  `~/.config/openchamber` 与 `~/.config/opencode` 零写入;
- Kernel Host 只在 macOS arm64 上验过;暂存脚本挑选平台原生包的那段逻辑,别的平台一次都没跑过;
- **Windows 侧一次实机运行都没有。** 布局判定与路径组装以注入平台的方式做了单测,覆盖的
  是决策逻辑;而进程启动、文件名编码、真实安装布局只能由实机回答——这类未知不是审阅能
  消除的。

当前完整可用的控制流为:

```
用户输入 → 模型 → 权限裁决 → 就绪门禁 → 工具执行 → 数据落盘 → 结果返回模型
```

数据面端点已实现但无消费方——迁入的 OpenChamber 界面尚未接这些端点。因此结果的呈现
目前仅通过模型在会话中的文本描述完成。

界面迁入后,本节的实现状态需同步修订。
