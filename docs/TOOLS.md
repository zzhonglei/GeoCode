# 工具层与权限

## 1. 这一层是什么

地理内核提供执行能力,Agent 内核提供会话与调度,**工具层是把两者接起来的那一层**:它把地理内核的门面 API 包装成模型可调用的工具,并决定哪个 agent 能调哪一组。

本文回答的问题是:这些职责**由谁承担、放在哪里**。内核交出来的契约本身不在这里——正本是 GEOKERNEL.md §11 的移交契约,本文只引用不复制,因为复述必然漂移(KERNEL.md §6 立过同一条规矩)。

依赖方向:工具层依赖地理内核的门面与 Agent 内核的工具契约。地理内核不认识工具层;Agent 内核只在登记在册的注入点上引用它(§7)。

## 2. 引擎的形状:会咬到我们的那几条

上游的工具契约(`tool/tool.ts` 的 `Tool.define`)不在这里复述。只记录**违反了就出事**的约束,每条都实测确认过。

| # | 约束 | 在哪 | 后果 |
|---|---|---|---|
| 1 | **不自报截断就被代截**——`Tool.define` 的包装只在 `metadata.truncated !== undefined` 时放行,否则调 `truncate.output` | `tool/tool.ts` | 见 §5,对地理工具是致命的 |
| 2 | `ctx.metadata()` 走 `updateToolCall`,**是实时广播** | `session/tools.ts` | 环境头绝不能走这里(GEOKERNEL §9.1 第二条硬性形态) |
| 3 | 附件形态是 `{ type:"file", mime, url:"data:<mime>;base64,…" }`,id 与会话字段由装配层补 | `tool/read.ts` 构造,`session/tools.ts` 补全 | 预览图给模型的唯一通道 |
| 4 | **权限过滤发生在最后一步**,不在工具注册表里 | `session/llm/request.ts` 的请求装配 | 注册表只按 provider 与模型家族筛 |
| 5 | 工具是 `Effect<Info, never, R>`,`R` 传导到注册表 | `Tool.define` 的签名 | 见 §7:这是必须打补丁的根因 |
| 6 | 参数解码失败抛 `InvalidArgumentsError`,`formatValidationError` 可定制 | `tool/tool.ts` | GEOKERNEL §11 那条"参数 JSON 解析失败的归因文案"的挂点 |

第 5 条值得展开。上游给了两条装配路径接入自定义工具——配置目录扫描 `{tool,tools}/*.ts`、插件的 `tool` 字段——**两条都经 `fromPlugin`**(`tool/registry.ts`),而它把工具锁死在插件形态:Zod 参数、`Promise` 执行、**没有 Effect 服务上下文**。地理工具必须 `yield* GeoQgis.Service` 一类,插件形态给不了,也没有全局逃生口能把服务句柄递进去。

所以地理工具进不了那两条装配路径,只能补丁注册表本身——这是 §7 那四处补丁里的第一处,也是唯一一处由引擎的类型形状逼出来的。

## 3. 八个工具

| 工具 id | 能力 | 权限键 | pattern | 门禁 |
|---|---|---|---|---|
| `ReadGeoData` | 读矢量/栅格元信息与预览 | `geodata` | 文件路径 | QGIS 统一门禁 |
| `QgisDoc` | 算法文档与检索 | `qgis` | `doc:<action>:<target>` | 同上 |
| `RunQgisAlgorithm` | 执行 Processing 算法 | `qgis` | 完整调用 `id(k=v, …)` | 同上 |
| `RunGeeScript` | 执行 GEE 脚本 | `gee` | 脚本路径 | GEE 三层状态 |
| `OsmSearch` | 搜索地名与要素 | `osm` | 查询串 | 无环境 |
| `OsmProbe` | 下载前侦察数据量 | `osm` | 各个 extent | 无环境 |
| `OsmGetObjects` | 按对象下载 | `osm` | 输出路径 | 无环境 |
| `OsmGetFeatures` | 按范围与标签批量下载 | `osm` | 输出路径 | 无环境 |

**权限键有四个:`geodata` / `qgis` / `osm` / `gee`**,与工具 id 是多对一。id 是模型看到的名字,键是用户在配置里读写的名字,两者刻意不同——`ReadGeoData` 对模型准确,`geodata` 对人准确。桥接它们的映射表在 `permission/index.ts`(§4.1)。

**工具 id 逐字沿用旧版**,不改名。它们是模型看到的名字,而旧版那八份经多轮打磨的描述文件通篇以它们为准(§8);改名等于让那份积累失去锚点,换来的只是好看一点。

**分组按环境依赖划分,不按功能。** "关掉一组"在用户心里对应"这套环境我没配",这个心智模型是准确的;按功能分组(读 / 写 / 查)则不是。

四个组,三种就绪条件——`geodata` 与 `qgis` 共用 QGIS 那一个门禁,因为工具侧的数据读取**走 QGIS 的 Python**(GEOKERNEL §7.9),QGIS 没就绪它一样不能用。

⚠️ **门禁检查一律在授权询问之前。** 用户绝不该为一个环境根本跑不了的操作做决定——问了也只有一个结果,而且 `always` 会把这次批准记下来,于是那唯一一次询问被花在了一个什么都没做的调用上。做几次之后,弹窗就成了走过场,而它真正要拦住什么的那天也就拦不住了。

这条对 QGIS 尤其重要:它不是可选能力,而是新用户**第一件要配的东西**,所以"还没配好"是每台机器都会经过的状态。GEE 同理,而且它整个四步配置期间都不询问——Agent 反复调用工具读下一步指引,那些调用不是需要谁批准的决定(§4.3)。

⚠️ 判据是**已经确定的失败**,不是"当前不可用":探测中(`probing`/`resolving`/`checking`)与状态尚未建立都照常放行——**没有答案不等于否定答案**,而门禁本身就是用来等出结果的。

⚠️ `ReadGeoData` 的检查位置比另外两个更靠前,在 `external_directory` 守卫**之前**:那道守卫也是一次询问,而且是用户在这里唯一会遇到的(因为 `geodata` 本身放行)。只放在 `ctx.ask` 前面不够。

两者仍然分开,因为**门禁与授权是两件事**:读一个图层,和跑一个会写盘的算法,是用户会分开考虑的两种授权,尽管它们恰好需要同一套环境。这个区分不是理论上的——osmfetch 拿的正是它:有 `geodata` 用来验证自己刚下载的东西,没有 `qgis`,因为验证下载是读,跑算法是别人的活。

## 4. 权限体系

### 4.1 两层键空间

这是最容易搞错的地方:**同一个工具在两个层面用不同的键**。

| 层 | 用什么键 | 判定 | 效果 |
|---|---|---|---|
| **可见性** | 工具 id(`ReadGeoData`),经映射表换成组名 | `Permission.disabled` | 工具**从模型的工具清单里消失** |
| **执行** | 工具在 `ctx.ask` 里声明的权限键(`geodata`) | `Permission.evaluate` | 调用时放行 / 询问 / 拒绝 |

可见性层原本不接受自定义:`disabled` 直接拿工具 id 去查规则,只为 edit/write/apply_patch 与三个 MCP 资源工具做过映射。GeoCode 加了第三张表 `GEO`,把八个工具 id 映到四个组名。**没有它,一条 `"osm": "deny"` 只拦得住执行,四个 OSM 工具照样出现在模型的清单里。**

⚠️ 这张表**缺一项不会报错**——规则写了,只是从不被查。所以两层各配各的绊线,而不是从一层推断另一层。

一处订正留在这里,因为它是这个区分为什么要紧的证据:早期曾记载旧版的蛇形权限规则"很可能从未真正生效过"。实测不成立——旧版规则**在执行层精确命中**,落空的只有可见性层。

由此要记住的是:**两层的名字都可能对不上,而两种失效都不出声。** 可见性层对不上,规则写了却从不被查,工具照常出现在模型的清单里;执行层对不上,没有规则命中,裁决落回该 agent 规则集的**地板**——GeoAgent 的地板是引擎的 `"*": "allow"`,于是静默放行(§4.2 ②);osmfetch 自带 `"*": "deny"`,于是拒绝。**同一个笔误,在两个 agent 身上是相反的后果**——而两种后果都不会有人告诉你。

### 4.2 三条裁决语义

**① 只有"通配全拒"才让工具消失。**

```
"qgis": "deny"                    → QgisDoc 与 RunQgisAlgorithm 一并从模型清单消失
"qgis": { "buffer": "deny" }      → 两者仍在册,只在 pattern 命中 buffer 时拒
```

两种是**不同的产品行为**。地理工具一律用前者,不做算法级细则——规则读起来就是产品行为,不需要在两种语义之间换算。

一个键下的两个工具靠 **pattern 命名空间**分档:`RunQgisAlgorithm` 用算法 id 作 pattern,`QgisDoc` 用 `doc:` 前缀。计划模态正是靠这一点做到"查文档随便查、执行要问"(见 §4.3)。

**② 引擎地板是 `"*": "allow"`,所以缺一条拒绝就等于放行。**

`evaluate` 的结尾确实写着一句看上去很安全的兜底:

```ts
findLast(...) ?? { action: "ask", permission, pattern: "*" }
```

**但任何真实 agent 都够不到它。** 每个 agent 的规则集是 `Permission.merge(defaults, user)`,而引擎 `defaults` 的第一条就是 `"*": "allow"`(`agent/agent.ts`),`findLast` 永远能命中它,兜底那一支只对空规则集成立。

实测:向 GeoAgent 问一个没人写过规则的键,拿到的是 `allow`。

所以四条地理拒绝**一条都不能少**。少了哪一条,未授权的 agent 调那一组工具会被**静默放行**——不报错、不弹窗、不留痕,而且四个键之间已经没有共同前缀可以兜住第五组。这是边界失效里最坏的一种形态,也是这一条写在这里的全部理由。

**③ 后来者胜,而 agent 层永远在最后。**

合成顺序是 `defaults → 全局 user → agent 自己的`(`agent/agent.ts` 的 `Permission.merge` 两处),裁决用 `findLast`。所以 agent 级规则盖过全局规则。

同一条规则里,键序也有语义:`fromConfig` 按 `Object.entries` 顺序生成规则。**泛的写前面、具体的写后面**,写反了结果相反。

### 4.3 装配

```jsonc
"permission": { "geodata": "deny", "qgis": "deny", "osm": "deny", "gee": "deny" },

"agent": {
  "GeoAgent": {
    "permission": {
      "geodata": "allow",
      "qgis": { "*": "ask", "doc:*": "allow" },
      "gee": "ask"
    }
  },
  "explore": {
    "permission": { "geodata": "allow" }
  },
  "osmfetch": {
    "permission": {
      "*": "deny",
      "osm": "allow", "geodata": "allow", "bash": "allow", "glob": "allow",
      "external_directory": "ask"
    }
  },
  "plan": {
    "permission": {
      "geodata": "allow",
      "qgis": { "*": "ask", "doc:*": "allow" },
      "gee": "ask",
      "task": { "osmfetch": "ask" }
    }
  }
}
```

**四个键必须逐条写,没有通配可用。** 名字取的是用户读得懂的词,代价就是它们之间不存在共同前缀:将来加第五组,这里必须加第五行,不会被自动兜住。

**GeoAgent 不放行 `osm`**:OSM 下载只走 osmfetch 子代理,这是刻意的能力隔离。

**explore 只加 `geodata` 一项**,其余照搬上游——它自带 `"*": "deny"` 与一份只读白名单。开这一项,是因为地理数据的文件名说明不了内容,筛选只能逐个打开;不开别的,是因为它做的是收窄候选而非改动数据,所以 `qgis`、`gee`、`osm` 就留在全局拒绝上(角色见 `KERNEL.md §5.1`)。

**osmfetch 的出口锁是 `"*": "deny"` 加一份短白名单**,不是点名禁几样。白名单里每一项都有具体用途:`osm` 是它的本职;`geodata` 用来读回自己刚写下的东西——它的提示词要求在报告成功之前验证一遍;`bash` 与 `glob` 用来看产物。

`external_directory: "ask"` 单独列出来,因为它是把上游默认**恢复**回来:通配拒绝会让一个再正常不过的、位于工作目录之外的输出路径被直接回绝,而上游对这种情况的处理是问用户。

`patterns` 这一维留给操作对象(哪个文件、哪个算法、哪种文档查询),不用来区分工具。计划模态的 `qgis: { "*": "ask", "doc:*": "allow" }` 正是靠它做到"查文档随便查、执行要问"。占用这一维去区分工具,就再也写不出"允许读 `./data/*.tif`,其他要问"。

**两个执行类的键都会问,这是 GeoCode 唯一比上游更严的地方。** 上游七个内置 agent 的权限值只有 `allow` 与 `deny`,没有任何一个工具默认 `ask`——`edit`/`write`/`bash` 全落在引擎的 `"*": "allow"` 上。那在**那边**站得住,因为改错了能撤销:快照存着可回滚的版本。地理数据被刻意排除在快照之外(GEOKERNEL §10.1 #6,体积理由),所以同一道权衡在**这边**答案不同。"一开始就别毁"本来就是输出编号而非覆盖的理由,这条只是同一规则在编号够不着的地方的第二个实现。

分界不是按工具画的,是按**这次操作会不会改用户的磁盘**:

| | 权限 | 理由 |
|---|---|---|
| `ReadGeoData`、`QgisDoc` 的 `doc:*` | **allow** | 只读、可逆,而且是模型完成任何任务的必经之路。为它们弹窗只会训练用户闭眼点确认——那会连带耗掉下面两个的注意力 |
| `RunQgisAlgorithm`、`RunGeeScript` | **ask** | 会写盘,而撤销够不着 |

而编号够不着的范围不小。`QgisDestination.reserve` 按**参数类型**认输出,对它认得出的那部分可靠,对其余完全无声——实测一份 3.44 目录:**422 个算法里 366 个声明 destination 参数,56 个一个都不声明,而那 56 个里约 26 个照写不误**。形态有三种:atlas 出图把一整个目录写进类型为 `file` 的普通参数、`native:truncatetable` 清空自己的 `INPUT`(文档原话 `deleted features cannot be restored`)、`native:alignrasters` 把输出路径藏在数组元素的字典里。

⚠️ **这个缺口不能用清单补。** 算法目录是在**用户那台机器上、用他那一版 QGIS** 建出来的(`catalog.ts` 的 `EXPORT_SCRIPT`),3.28 LTR 少几十个算法、Windows 上 GDAL provider 的组成也不同——把这 56 个 id 写死进产品,等于把一台 macOS + 3.44.9 的偶然状态当成全部。`DESTINATION_TYPES` 之所以站得住,是因为它枚举的是 **QGIS API 的类型常量**而不是算法。⟹ 在没见过的 QGIS 版本上仍然成立的守卫只剩一个:**把调用如实摆给用户,由他判断**。

**所以 `RunQgisAlgorithm` 只问一次,pattern 是完整调用。** 询问里带算法 id 和全部参数(`native:buffer(INPUT=/data/a.shp, DISTANCE=100, OUTPUT=/out/b.shp)`),`always` 保持 `["*"]`——批一次就安静到应用重启(上游把批准放在 `InstanceState` 的内存里,它自己的提示文案就写着 `until OpenCode is restarted`)。**不设第二道 `external_directory` 询问**,尽管上游 read / write / bash 各设一道。它说的严格更少——只报一个目录,不报算法也不报参数;而它能看见的又只是 `reserve` 看得见的那部分,对上面那 26 个算法一声不吭,却让每次普通调用多付一次弹窗。

**而 `gee` 问的是另一件事,所以弹窗形态也不同。** QGIS 之所以能把调用摊开,是因为那次调用**读得懂**:一个算法 id 加若干参数,扫一眼就能判断路径去了哪。GEE 脚本没有这个性质——它是任意 Python,`download_image(image, "…", roi)` 把输出路径放在代码里的字符串字面量里,工具层看不见;而把几十行脚本折进弹窗,只会得到一个没人读的对话框。**一个从不被读的提示比没有提示更坏,因为它制造了"我审过了"的错觉。**

⟹ 两种询问,两种粒度:

| 键 | 授权的是 | 弹窗内容 | 上游对应 |
|---|---|---|---|
| `qgis` | 这一次**操作** | 算法 id + 每个参数一行,路径绝对原样 | `bash` 的完整命令 |
| `gee` | 这一项**能力** | 只说"要执行 Earth Engine 脚本" | `task`:点名子代理,不假装知道它会做什么 |

GEE 授权的是凭据、配额,以及影像落到磁盘某处——不是任何一行 Python。脚本调用本就远少于算法调用,加上 `always`,实际成本是每次应用运行一次弹窗。

⚠️ 这两种形态由 `cli/cmd/run/permission.shared.ts` 渲染,**不在 `tool.ts` 的 `TOOL_RULES` 里**:那张表按工具名索引,而这四个是权限键(`qgis` 覆盖两个工具、`osm` 覆盖四个)。上游把同样不是工具的 `external_directory` 与 `doom_loop` 放在同一处。没有它,`ask` 会退化成 `Call tool qgis` 两行字——**批准一件没被告知内容的事**,而那次询问是这里唯一剩下的守卫(KERNEL.md §4.1 记了这处补丁面增长的判据)。

**pattern 里的路径写成什么形式,跟着对齐目标走,不做全局统一:**

| 工具 | 对齐 | 路径形式 | 判据 |
|---|---|---|---|
| `ReadGeoData` | `read` | **worktree 相对** | 上游 `read` 的 pattern 就是同一个表达式 |
| `OsmGetObjects` / `OsmGetFeatures` | `write` | **worktree 相对** | 上游 `write` 的 pattern 就是相对 title |
| `RunGeeScript` | `task` | **worktree 相对**;内联脚本用标识符 `inline_script` | 它是一条路径,归一化后才能被规则稳定匹配 |
| `RunQgisAlgorithm` | `bash` | **绝对、原样** | 上游 `bash` 的 pattern 就是完整命令原文 |

⚠️ **归一化不只是形式问题。** 路径若原样透传,它同时是**存在性检查、权限 pattern 与执行入参**的取值——一条相对路径于是按 `process.cwd()` 解析,而工具的一切其它判断都以实例目录为基准:检查问的可能是一个文件,真正跑的是另一个。所以除 `RunQgisAlgorithm` 外,四个工具都在入口处解析一次(`!isAbsolute → resolve(instance.directory, …)`,Windows 上再过一次 `normalizePath`),之后只用解析后的那个值。

⚠️ QGIS 这边**必须**是绝对路径:这个询问存在的唯一意义,就是让用户一眼看出 `/Users/me/thesis/data/final.shp` 在工作目录之外,而相对形式恰好把这件事藏起来。照搬 OSM 的归一化会静默抽掉整个设计的依据。

### 4.4 阵容与上游一一对应

task 规则不发明自己的机制,逐个对应上游的形状:

| GeoCode | 对应上游 | task 规则 |
|---|---|---|
| GeoAgent | build | **无**——继承 defaults 的放行,用户自定义的子代理即刻可派、即刻出现在 task 工具的描述里 |
| plan | plan | `{ "osmfetch": "ask" }`。位置对应上游的 `{ general: "deny" }`——点名那个有副作用的子代理——但动作是 `ask` 而非 `deny`,理由见下。`explore` 不点名,落到放行:它只读,而只读正是规划本身要做的事 |
| explore | explore | 通配拒绝之下 `task` 不在白名单里,不得递归派生(上游自带) |
| osmfetch | (自有) | 同上——出口锁的一部分 |

**为什么 plan 用 `ask` 而不是 `deny`。** `describeTask` 会把被拒绝的子代理**从清单里删掉**,而一个不知道 osmfetch 存在的规划者写不出含下载的计划。上游在同一处犯的是反方向的错:它的计划模式提示词让模型去派 `general`,而它的权限拒绝了 `general`——名字在指令里,不在清单里。

一个被否决的方案要记下来,因为它看上去很聪明。曾试过给 GeoAgent 写 `task: { "*": "deny", "osmfetch": "allow" }` 当子代理白名单。否决,两个代价当场兑现:白名单让**用户自定义的子代理静默消失**——`describeTask` 按权限过滤,定义了却不出现,无处报错;plan 的通配拒绝打翻两个上游测试(它们断言 plan 可派只读与自定义子代理)。为一份白名单付这两样,影响面不成比例。

## 5. 输出超限由工具自管

### 5.1 为什么不能用上游机制

上游是 **head 截断**:保留开头、丢弃结尾,超限全文写盘,模型拿到前 2000 行或 50 KB。而 GEOKERNEL §11 要求"不能静默消失"的东西**恰恰都在结尾**——五种终止路径的横幅、耗时页脚、`drainIncomplete`/`truncated` 的呈现、接在非零退出上的结构化错误。

一次超限的算法执行,上游机制会**精确切掉归因所需的全部信息**,只留下前 2000 行进度刷屏。这不是截得不够好,是截反了方向。

逃生口在 `Tool.define` 的包装里:自设 `metadata.truncated` 即完全跳过 `truncate.output`。判定是 `!== undefined`,所以 `false` 也算表过态。

### 5.2 五种策略

| 策略 | 工具 | 做法 |
|---|---|---|
| **不产生大输出** | 四个 OSM 工具 | 数据落盘(GEOKERNEL §6.7 落盘契约),输出只给路径与统计摘要。丢失按 id 点名,而 id 列表本身按 `MAX_IDS` 截断 |
| **自设预算 + 丢样本** | `ReadGeoData` | **不落盘**。整份 payload 内联进 output,50 KB 预算;超限时从尾部丢样本要素并报出丢了几个。预览图走附件不进正文 |
| **检索类裁剪** | `QgisDoc` | 限条数返回并说明还有更多。只多取一条以区分"恰好 10"与"至少 11",所以给得出"多于 10",给不出确切的 N |
| **执行类结构化保留** | `RunGeeScript` | 裁剪发生在**中间**,两头不可裁;超限时写盘并给 `outputPath` |
| **输出形状由引导脚本规划** | `RunQgisAlgorithm` | **不设预算**。它打出什么由我们的引导脚本决定,而那份脚本把每一路都写得有界 |

后两种同属执行类却不同待遇,判据是 GEOKERNEL §8.4 立过的那一条:**谁控制输出的节奏**。GEE 的脚本由模型撰写,想打多少打多少,所以要预算;QGIS 的算法从目录里选,输出经我们自己的引导脚本,形状因此是我们定的——进度量化到 10% 档且只在递增时打(整场至多十一行),算法名与启动各一行,参数警告按参数个数,相似候选取前五条。

更根本的一条支撑它:**算法的结果不随用户数据的规模增长**。Processing 把逐要素的发现写进**输出图层**,留在 feedback 日志里的只有进度与摘要——实测五千个无效多边形过 checkvalidity、fixgeometries 与 buffer,日志不足 1 KB(2026-08-05,同一笔记在 `geo-qgis-run.ts` 的 `Metadata` 类型注释上)。

第五种同样自设 `metadata.truncated`,只是它恒为 `false`。**那是一句表态,不是占位**:表了态上游的 head 截断就不会跑(§5.1),而它恰好会砍掉结尾那几样必留的。

第四种的形状:

```
<环境头>            必留
…<中间输出裁剪 N 行>…
<尾部保留>          必留
<终止横幅>          必留
<耗时页脚>          必留
```

⚠️ 第五种有一条**我们够不到的边**:引导脚本末尾把 `feedback.textLog()` 整份打出来,而那份不是我们打的进度行,是 QGIS 把算法自己 `pushInfo` / `pushWarning` 累积起来的。GEOKERNEL §8.4 恰好把算法执行归为"被调用的实现自行决定是否产生输出,**我们无法插手**"的那一类。上面那笔实测覆盖的是最常见的脏数据场景,**其外的量级没有数据**。

⚠️ 还有一条形状上的事实,别按内核 runtime 的 4 MB 去理解它:算法执行走增量投递,而 `outputLimit` 只在汇总模式下设置(`geo/runtime/index.ts`),所以 `output-limit` 那条终止路径对它**永不触发**。真正兜住它的是上面那条设计论证,不是运行时的某个数。

**`truncated: true` 不必然伴随 `outputPath`。** 这个字段承载两种语义:一种是"文本被切了,完整版在 `outputPath`"(`RunGeeScript`),另一种借自上游 `read` 的"还有更多,用 offset 继续"(`ReadGeoData` 丢样本要素时)。后者没有完整版可指。**读这个字段的一方必须同时看有没有 `outputPath`**,不能只看那个布尔值。

## 6. 共享零件

八个工具共享一批职责。各写一遍就是八份会漂移的实现,所以它们集中在 `tool/geo-tool.ts`:

| 零件 | 承担什么 |
|---|---|
| `settledQgisGate` / `settledGeeGate` | 门禁检查与中间态等待,带上限 |
| `qgisHeader` / `geeHeader` | 环境头快照。**只前缀于返回值**,绝不经 `ctx.metadata`(§2 第 2 条) |
| `gateStatus` / `geeGateStatus` | 环境未就绪时的指导文案,整组同一个声音 |
| `terminationBanner` | 五种终止路径的横幅 |
| `elapsedFooter` | 耗时页脚 |

**它是一组被调用的零件,不是一层包住 `Tool.define` 的壳。** 八个工具各自 `Tool.define`,各自决定调哪几个;截断策略、结构化错误提取、参数归因文案也都留在各工具里。

这个形态的代价是"记得调"仍然是每个工具的责任。收益是每个工具的执行序自己读得出来,而那个序本身就是设计——顺序错一步,后果是具体的(OVERVIEW.md §5.3)。

### 6.1 凭据不靠这一层拦住

早期设想是让这一层在构造输出的那一刻统一调 `NetRedact`,做成唯一出口,"脱敏从要记得八次变成结构上不可能漏"。**实际不是这样**:`NetRedact` 在生产代码里的调用点为零。

真正起作用的是更上游的一件事——状态面只携带 `RouteId`(`geo/net/types.ts`),凭据从不进入可展示的数据。**不取用,胜过取用后再擦干净。**

这条有过一次实证。`geo/net/discovery.ts` 原本走的正是"擦干净"那条路:把用户的代理声明整串拿来,再交给脱敏函数。而脱敏依赖 URL 解析,解析不了就原样返回——密码里有一个 `/` 就漏。改法不是把脱敏写得更严,是**不再取那一串**,改成从解析出的字段拼一个标识。没有可擦的东西,就没有擦不干净。

## 7. 注入点与绊线

工具层对上游有**三处**源码补丁:

1. **`tool/registry.ts`**(GEOKERNEL §10.1 注入点 #9)——三件事:地理工具进 `builtin` 数组;`node` 的 `deps` 加 `GeoKernel.node`;以及把上游对配置目录 `{tool,tools}/*.{js,ts}` 的扫描整段换成空数组。第二件是 §2 第 5 条的必然结果——工具的服务依赖 `R` 会传导到注册表,层图因此把"工具依赖地理内核"显式化。第三件行为面最大,理由归屏蔽清单(KERNEL.md §6):打开一个文件夹不应导致其中的代码被执行,用户扩展工具的通道是 MCP。
2. **`tool/read.ts`**(注入点 #10)——地理数据文件交给 `ReadGeoData`,十余行。
3. **`permission/index.ts`**——`disabled()` 查表时多一张 `GEO` 映射,把八个工具 id 映到四个组名。**可见性层能成立全靠它**(§4.1),而它此前不在这份清单上。

第 2 处值得说明为什么非补丁不可。`read` 打不开地理数据,但它**失败的方式有两种**,而危险的是第二种:二进制格式(`.shp` `.tif` `.gpkg`)撞上它的二进制守卫,止于"无法读取二进制文件"——是死路,但至少是显式的;而**文本格式**(`.geojson` `.gml` `.kml` `.gpx` `.asc`)会一路通过所有检查,被当作纯文本读取、在坐标数组中间截断,末尾还附一句"用 offset=N 继续"。模型拿到的是一段看起来像数据的碎片,并被鼓励继续索取更多。这不是配置能拦的,提示词也只是软约束。

**屏蔽范围严格等于 `ReadGeoData` 能打开的格式**,比共享分类学窄。规则是:**只把调用方指向真的能干这活的工具**。分类学认作地理、而 `ReadGeoData` 不支持的格式(`.nc` `.tab` `.osm` …)不在其中——为它们点名另一个工具属于替用户猜工作流,而非交接;侧车文件(`.prj` `.cpg` `.dbf` `.qmd`)同样不在其中——它们是值得直接读的小文本,而 `ReadGeoData` 不收它们作输入。两条边界都沿用旧版,理由旧版注释里写着:handing off would be misleading。

清单与 `ReadGeoData` 的支持集**共用同一份数组**(`tool/geo-handoff.ts`)。旧版在 `read.ts` 里手抄了一份副本,靠人记得同时改两处;一份数组让这两侧的漂移在结构上不可能发生。

但还有第三侧:**`geo-read.txt` 为模型把格式逐个拼写出来**,那份拼写又是手抄。数组扩了而描述没跟,模型就会拒绝一个工具本可以打开的文件,并把较短的那份清单当作全部事实报出去。这一侧由绊线绑定——它拿描述文本与数组逐项比对,两个方向都验过。

其余全部落在装配层配置或新增文件。

地理工具与上游原生工具**同级平铺在 `tool/` 下**,不另设子目录:它们是 GeoCode 内置核心工具集的一部分,不是外挂。`geo-` 文件名前缀保住可审计性,而新增文件在合并时永不冲突。

绊线三条,都必须做反证(去掉改动看是否变红):

1. 八个工具 id 确实出现在 `registry.ids()` 里;
2. **换一个 agent 调用时工具确实不在模型清单中**——断言"拦住了",不是断言"写了规则";并且从 `GEO` 表里删掉任何一项都会转红,否则那张表就是写了没人查;
3. `read` 的交接自己有一套(`test/geocode-read-handoff.test.ts`),其中的行为半用真的 `read` 跑一个真的 `.geojson`——**这条防的失败不是异常,是一个看起来很像数据的答案**:被截在坐标数组中间,末尾还附一句"用 offset 继续"。

第二条是旧版事故的直接教训:规则写进去了不等于命中了。

## 8. 描述文件

八份描述(`tool/geo-*.txt`)迁自旧版,经过多轮打磨,逐字迁移。迁移时有四处不能照抄,四处的理由至今成立:

| 文件 | 改了什么 | 为什么值得记下 |
|---|---|---|
| `geo-qgis-run.txt` | 三处点名的旧工具名改成新 id | **旧版事故的镜像**:描述里写一个名字、注册表用另一个,模型照做就失败。因此凡改名,`.ts` 与 `.txt` 两侧都要扫(KERNEL.md §4.4) |
| `geo-osm-search.txt` | **新写**耗时说明 | 不写,Agent 会把正常等待判成卡死并重试,而重试只是再付一次同样的代价 |
| `geo-gee-run.txt` | 去掉架构词 sidecar;补上 `download_image` 的 `dtype` | 前者对模型没有意义;后者代码里一直有,旧版描述漏了。心跳契约本就完备,而其中那个 60s 由绊线钉在 `IDLE_FLOOR_SECONDS` 上——模型会按它来摆放 `heartbeat()` |
| `geo-read.txt` | **整块参数说明删掉,改写进 schema 的 annotate**;另新增四条(绝对路径、跨模式忽略、取消契约、QGIS 未就绪) | 参数说明写在 schema 上,模型从工具定义里就能读到,不必在描述里再抄一遍——这是描述文件里唯一一次**减法**大于加法 |

描述文件**无法承载 `GeoCode:` 标记**——内容原样送进模型,注释会污染指令。可审计性只能由绊线提供,与提示词文件同一处理方式(KERNEL.md §5.3)。

绊线读描述常量本身,而断言写的是**后果而不是措辞**:"不点名裁剪"、"不许出现 never overwritten"、"必须点名 OVERWRITE"。这样措辞可以继续改进,而约束不会跟着松掉——一条钉死原句的断言,会在下一次改写时被顺手放宽。
