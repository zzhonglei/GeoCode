# GEOKERNEL.md — GeoKernel 地理执行内核设计

> 本文档确定 GeoKernel 的模块划分、职责边界、横切契约与对外接口,并逐个展开各模块的
> 详细设计。主动放弃的能力集中列于 §12。
> 与 KERNEL.md(Agent 内核装配)、TOOLS.md(工具层与权限)、PATHS.md(路径与身份)平级互补。

---

## 1. 概述

### 1.1 定位

GeoKernel 是 GeoCode 的**地理执行内核**:一个纯服务层,承载产品的全部地理数据处理执行
能力,向上提供三个出口面(工具面、状态面、数据面)。

它的职责范围严格限于"地理能力的执行与环境管理"。Agent、工具定义、权限规则属于 Agent
内核与工具层,由它们调用 GeoKernel 的门面完成工作。

### 1.2 能力范围

| # | 能力域 | 内容 |
|---|---|---|
| R1 | **数据感知与预览** | 读取矢量/栅格的元信息(图层、字段统计、波段、CRS、范围),生成预览图像 |
| R2 | **空间处理** | 调用 QGIS Processing 算法库执行空间分析,提供算法文档与检索 |
| R3 | **云端遥感计算** | 执行 Google Earth Engine 脚本:初始化、加载研究区、覆盖度分析、导出与下载 |
| R4 | **数据获取** | 搜索地名与要素、下载前侦察数据量、按范围与标签批量下载 OSM 数据 |

### 1.3 设计约束

| # | 约束 | 影响 |
|---|---|---|
| C1 | 运行于 Electron sidecar 的纯 Node 运行时 | 全部代码使用 Node 标准 API |
| C2 | 支持 macOS arm64 与 Windows x64 | 环境发现需覆盖两套安装布局与编码规则 |
| C3 | 外部软件(QGIS/GDAL/Python)由用户自行安装 | 内核负责发现、验证与指导,安装与修复属于用户 |
| C4 | 用户网络环境差异显著,部分区域访问受限 | 网络可达性是一等设计对象,需自动适配并持续监视 |
| C5 | 用户具备 GIS 专业背景,非软件工程背景 | 配置项极简、诊断可执行、状态可视 |
| C6 | 单次执行可达数分钟 | 执行原语需支持流式输出、中断与防呆超时 |

### 1.4 非目标

- 不定义 Agent、工具与权限规则;
- 不安装或修复用户的外部软件;
- 不提供制图输出、PostGIS、地理编码能力(能力地图留位,不在本期范围)。

## 2. 架构

### 2.1 分层

GeoKernel 分为两层:**基础设施层**提供与地理领域无关的通用机制,**能力层**在其上实现四个
地理能力域。能力层各模块之间互不依赖,共同依赖基础设施层。

```
                    出口面(消费者在 GeoKernel 之外)
   ┌──────────────┐      ┌──────────────┐      ┌──────────────┐
   │    工具面     │      │    状态面     │      │    数据面     │
   │  门面 API     │      │  事件 + 快照  │      │  HTTP 端点    │
   └──────┬───────┘      └──────┬───────┘      └──────┬───────┘
 ═════════╪═════════════════════╪═════════════════════╪═════════
          │                     │                     │
   ┌──────┴─────────────────────┴─────────────────────┴───────┐
   │  能力层                                                   │
   │   ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────────┐ │
   │   │  QGIS   │  │   GEE   │  │   OSM   │  │    GDAL     │ │
   │   │ 空间处理 │  │ 遥感计算 │  │ 数据获取 │  │  数据平面    │ │
   │   └─────────┘  └─────────┘  └─────────┘  └─────────────┘ │
   ├───────────────────────────────────────────────────────────┤
   │  基础设施层                                                │
   │   ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────────┐ │
   │   │ Config  │  │ Runtime │  │   Net   │  │   Status    │ │
   │   │ 环境配置 │  │ 进程执行 │  │ 网络出口 │  │  状态记账    │ │
   │   └─────────┘  └─────────┘  └─────────┘  └─────────────┘ │
   └───────────────────────────────────────────────────────────┘
```

### 2.2 模块清单

| 层 | 模块 | 职责 | 子模块 | 章节 |
|---|---|---|---|---|
| 基础设施 | **Config** | 机器环境配置的加载、监控与变更分发 | schema、loader、watcher、differ | §3.1 |
| 基础设施 | **Runtime** | 子进程执行原语:启动、交付、时钟、终止 | spawn、delivery、clocks、terminate、output | §3.2 |
| 基础设施 | **Net** | 网络可达性的全部决策:路径解析、探测、监视与判定 | targets、discovery、resolver、probe、tunnel、classifier、monitor、route、redact | §3.3 |
| 基础设施 | **Status** | 状态的存储、提交、发布与快照 | registry、commit、publisher、snapshot | §3.4 |
| 能力 | **QGIS** | QGIS 环境管理与空间处理执行 | lifecycle、env、catalog、executor、scripts | §4 |
| 能力 | **GEE** | GEE 环境管理与遥感脚本执行 | lifecycle、setup、runtime-check、executor、pylib | §5 |
| 能力 | **OSM** | OSM 数据获取 | client、http、query、search、convert、geometry、output | §6 |
| 能力 | **GDAL** | 面向前端的预览数据生产 | env、inspector、vector、raster、cache、access | §7 |

### 2.3 依赖关系

依赖方向单一,自上而下:

```
能力层  ──依赖──▶  基础设施层  ──依赖──▶  宿主内核(日志、路径、事件总线)
```

三条规则:

1. **能力模块之间零依赖**。QGIS 不调用 GDAL,GEE 不调用 OSM。共同需要的能力下沉到基础
   设施层。访问远程服务的两个模块(GEE、OSM)都经 Net 而非彼此。
2. **基础设施模块之间互不依赖**,四者各自只依赖宿主内核。这一点由 §3.3 的取舍保证:Net
   的全部探测在进程内完成(套接字层面的握手与协议问答),不启子进程,因而不依赖 Runtime。
3. **基础设施层不感知地理领域**。它处理进程、网络、文件、状态,不理解 CRS、波段或算法。

### 2.4 设计原则

1. **单一归属**。每个概念只有一个实现:进程执行在 Runtime,网络可达性在 Net,状态记账
   在 Status,环境配置在 Config。能力模块只实现自己的领域逻辑。
2. **机制与判断分离**。基础设施层提供机制(怎么执行、怎么探测、怎么记账),能力模块做
   判断(什么算就绪、什么时候重探、如何呈现)。
3. **状态先于文案**。状态集合与迁移关系是稳定契约;面向用户与 Agent 的指导文案是其上的
   可替换表现层。
4. **中间态是一等状态**。探测、构建、校验过程可持续数十秒,用户与工具都会观察到它们,
   因此它们在状态集合中显式存在。
5. **诚实优先于乐观**。任何"可用"结论都建立在真实验证之上;无法确定时报告不确定,并给出
   下一步。
6. **薄注入**。GeoKernel 是宿主内核中的纯新增目录,对宿主的修改点收敛在 §10.1 的清单内,
   每处配套绊线测试。

### 2.5 目录形态

```
core/src/filesystem/geo-extensions.ts       GIS 文件分类学(宿主内核共享)
opencode/src/geo/
  index.ts                                  门面出口
  config/          Config 模块
  runtime/         Runtime 模块
  net/             Net 模块
  status/          Status 模块
  qgis/            QGIS 模块(含 Python 脚本与生成链)
  gee/             GEE 模块(含 Python 运行时库)
  osm/             OSM 模块
  gdal/            GDAL 模块
schema/src/geo-event.ts                     状态事件定义
opencode/src/server/routes/instance/httpapi/
  groups/geo.ts, handlers/geo.ts            数据面 HTTP 端点
```

数据面落在**宿主内核自有的那套 httpapi**,而非 `protocol` / `server` 两个包:后者只依赖
`core`,够不到 `opencode/src/geo/` 下的服务。路径不带 `/api` 前缀,§7.7 与 §9.3 所列路径即
最终形态。

**两组端点分挂两处**,依据是它们各自需要知道什么:

| 端点 | 挂载 | 依据 |
|---|---|---|
| 状态快照、配置重读 | 根 API(与 `global` 同级) | GeoKernel 每进程构建一次、与工作目录无关(§10.2),不需要位置路由 |
| 五个预览资源 | 实例 API | 它们接收外部路径,而 §7.8 要求路径落在工作区内——"哪个工作区"只能由位置路由回答 |

服务本身仍是进程级的:预览端点经位置路由取得的是**边界**,不是另一份内核。

## 3. 基础设施层

### 3.1 Config — 环境配置

**职责**:维护用户机器环境描述文件的唯一读取路径,监控其变更,并将变更按影响范围分发给
相关能力模块。

**子模块**

| 子模块 | 内容 |
|---|---|
| schema | 结构定义与宽容解析 |
| loader | 读取、解析、模板播种 |
| watcher | 文件监控与变更防抖 |
| differ | 按块比较,产出定向变更信号与块指纹 |

**对外提供**

| 接口 | 内容 |
|---|---|
| 块读取 | 指定配置块的当前值 |
| 块变更通知 | 该块的值发生实质变化时推送 |
| 块指纹 | 该块当前值的稳定标识,供下游产物绑定其配置来源 |
| 解析状态 | 文件当前是否可解析,不可解析时携带出错位置 |
| 快照 | 全部块的当前值,供状态面一次取全 |
| 显式重读 | 立即重读文件并分发。监听失效时的逃生口,也让刚写过文件的设置界面获得确定的生效时机,而非与去抖赛跑(§12)|

#### 配置块是变更的基本单位

每个能力域对应一个配置块。块同时是三件事的粒度:**变更分发**、**指纹计算**、**解析失败的
影响范围**。能力模块只订阅自己的块,一个域的配置改动不会惊动其他域。

#### 变化按归一化后的值判定,不按文件文本

**编辑器重排格式、调整键序、增删注释,不构成变化。** 否则用户在带自动格式化的编辑器中保存
一次,就会触发一轮数十秒的环境重探。

因此比较的对象是解析并归一化后的块值,而非文件文本。

#### 块指纹

指纹按块计算,用途是让下游产物能够绑定"产生它的那份配置"。数据面的缓存键即使用它:工具链
配置改变后,旧产物自动失效;而修改其他块不会误伤。

**文件不可解析期间,指纹取一个专用值,而非沿用上一份有效值。** 沿用会让产物继续绑定在一份
系统已经读不出来的配置上。取专用值不付出代价:该窗口内全部块处于错误态,没有能力模块在运行,
不会产生新产物;语法错误修好后指纹回到原值,已缓存的产物随即重新有效。专用值**按块取,不共用
一个**,以免两个块在只以指纹为键的消费者处相撞。

#### 监控配置目录而非配置文件

编辑器普遍以"写入临时文件、改名替换"的方式保存,这会使针对单个文件的监听失效。因此监听
配置所在目录并按文件名过滤,同时施加防抖——一次保存常触发多个文件系统事件。

**监听之外须有一个拉取式逃生口**(显式的立即重读入口,经数据面暴露)。两个理由:监听可能
建立失败或中途死亡,而旧版靠周期性哈希轮询兜底的做法已被有意放弃(见 §12),没有逃生口时
用户唯一的补救是重启应用;设置界面写完文件后调用它,得到**确定性的生效时机**,而不是与监听
防抖赛跑。

#### 解析失败是一种错误状态

文件不可解析时,**全部配置块判定为错误**并携带出错位置,能力模块据此进入各自的不可用状态。
不保留上一份有效值继续运行:那会造成文件内容与实际行为不一致,用户面对的是一个自相矛盾
的系统。语法错误是用户在保存那一刻就应当知道的事。

从不可解析恢复为可解析时,**全部块无条件重新分发**——此前各模块已进入错误状态,需要完整
的一轮重新解析,而非增量判断。

#### 订阅自带当前值

块的**订阅**入口发出的是"当前值 + 后续变更":订阅先建立,当前值从**已建立的订阅内部**发出。
理由与 §9.2 对状态面的要求相同——先读后订阅会漏掉落在两次调用之间的那次变更,而把当前值
放进订阅里等于把这个窗口消灭掉,不必要求每个调用方记住顺序。代价是该窗口内的变更会到达
两次,按指纹去重即可,消费者不必关心。

另有一个**一次性读取**入口,用于不打算继续订阅的场合(如 GEE 的自愈重探:它只需知道"此刻
配置是什么"就去重跑一次探测)。规则很简单:**读完还要订阅的,一律用订阅入口**——那正是上面
那个窗口的来源。

#### 三条容错

- **未知键忽略**:一处键名笔误只使该项失效,不牵连同一文件中的其他配置;
- **编码兼容**:剥离字节序标记,兼容常见编辑器的保存行为;
- **首次播种**:以独占方式创建空模板,防止并发启动时的竞写。

两种文件形态(`.json` 与 `.jsonc`)同时存在时**按固定顺序合并、同名键后者胜**。并存本身是
用户的失误而非受支持的用法,但它必须落到一个确定的结果上,不能取决于遍历顺序。

### 3.2 Runtime — 进程执行

**职责**:提供 GeoKernel 全部子进程执行的统一原语。它承担进程的启动、输出交付、异常判定
与终止收场;**判定的阈值由调用方给出,收场的方式由 Runtime 决定**。

**子模块**

| 子模块 | 内容 |
|---|---|
| spawn | 进程启动、参数与环境注入、标准输入投递 |
| delivery | 输出交付:增量回调与汇总两种模式 |
| clocks | 时钟:总时长与空闲时长,可独立启用 |
| terminate | 终止序列:信号升级、进程树清理、异常终止识别、排空与结算 |
| output | 输出通用件:截断、耗时格式化、结构化错误提取 |

#### 职责边界:什么算异常 vs 如何收场

| 事项 | 调用方 | Runtime |
|---|---|---|
| 多久无输出算卡住 | 决定 | 执行 |
| 总共跑多久算失控 | 决定 | 执行 |
| 输出如何交付 | 决定 | 执行 |
| 空闲时钟在哪一刻刷新 | — | **固定** |
| 终止后是否排空输出 | — | **固定** |
| 终止如何升级、清理到什么范围 | — | **固定** |
| 调用如何保证返回 | — | **固定** |

右侧四项**看似策略,实为正确性不变量**——它们没有"另一种合理选择",做成选项只会让不同
调用方各自赌一次,其中一些必然赌错。判据可以概括为一句:**调用方决定"什么算异常",
Runtime 决定"如何正确收场"**。

#### Runtime 只负责执行,不持有生命周期

"何时该结束"始终属于发起执行的那一方——被用户取消的工具调用、正在拆除的会话、准备退出的
应用。Runtime 不替他们决定,因此**这些控制必须是显式接口,而不是藏在一次阻塞调用背后**。

| 接口 | 用途 |
|---|---|
| 启动 | 返回运行中的句柄,而非等到结束 |
| 句柄:终止 | 从外部叫停。幂等——停止按钮会被按两次,拆除也会与用户动作撞车 |
| 句柄:当前输出 | **运行期间即可读**,不必等结束才知道进行到哪 |
| 句柄:结果 | 落定时完成,可重复等待 |
| 清单 | 列出全部在跑的执行,供外部管理者查看与叫停 |
| 全部终止 | 会话拆除与应用退出 |

阻塞式调用只能提供其中第一项,而且只提供给"愿意在启动前就准备好一个信号"的调用方。

#### 三条异常通道必须都成立

执行期的意外不止一种形态,而它们走的是不同的路:

| 情形 | 通道 | 要求 |
|---|---|---|
| 用户取消工具调用 | 宿主传入的停止信号 | 杀掉进程树,**返回正常结果**并标注原因,不抛异常——已产生的输出正是此刻最该给出的东西 |
| 外部管理者叫停 | 句柄的终止接口 | 同上;幂等 |
| 所属纤程被中断 | 作用域关闭 | 进程树必须被清理。此路径**无法返回结果** |

**第三条在工具路径上不应当发生,这要靠装配保证,不靠 Runtime 补救。** 宿主的工具体经
`EffectBridge.promise` 运行,即 `Effect.runPromise` 起的**游离根纤程**;放弃 promise 无法
中断它,取消因此只有信号一条入口。地理工具必须按同一方式接入——这是工具层落地的硬约束。
宿主还有一处配套动作值得照做:工具被取消后,其输出照样记账,而不是连同调用一起丢弃。

内核内部的调用方(例如被 fork 进某个作用域的探针)仍可能被中断。该路径清理完整但**无法
汇报**——正在等待结果的那一方,恰恰就是被拆除的东西。两者都要的调用方应传入信号并在中断时
触发它,让执行改走第一条通道收场。

三条通道**收敛到同一套终止序列**:中断路径不依赖底层 spawner 的作用域释放去杀进程,而是在
作用域收尾时触发同一个停止开关。两者都能杀掉进程树,但只有一条路径意味着升级顺序与清理范围
在三种情形下必然一致,而不是各自成立。

#### 进程走失:三层防线与一处无解

上面三条通道都建立在"我们自己还活着"之上。**应用被突然关掉时,没有一条成立。**

问题的根源同时也是进程树清理的前提:子进程在 POSIX 上被置为**新进程组的组长**——这让整组可以
被一次性信号覆盖,但也意味着**它不随我们一起死**。父进程消失后它被 reparent 继续运行,而用户
在界面上再也看不到它。一个跑到一半的空间分析会就这样一直占着 CPU 与内存。

| 层 | 覆盖 | 机制 |
|---|---|---|
| 作用域收尾 | 取消、拆除、正常退出 | 上表三条通道 |
| **进程退出钩子** | 一切走到"进程正在退出"的路径,含直接调用退出 | 遍历在跑的进程组**同步**下杀。同步是硬要求:退出钩子里跑不了异步 |
| **宿主的信号处理** | 收到终止信号(桌面壳关闭服务进程) | 见 §10.1 |
| —— | **强制杀死、崩溃、断电** | **进程内无解** |

**信号处理属于宿主,不属于本模块。** 注册一个终止信号的监听器会压掉运行时的默认行为,等于让
本模块替整个应用决定怎么关机——这与"Runtime 只负责执行"直接冲突。因此本模块只提供一个**同步
的立即清扫**接口,由宿主在它自己的关停路径上调用。

**最后一行不做任何补救,这是决定而非遗漏。** 它没有进程内的解法,带外手段则都要付出与收益
不成比例的代价:让脚本轮询父进程要求每个脚本模板都携带这段逻辑并在其中长期正确;把进程标识
落盘则要连同启动时刻与命令行一起比对,才能绕开标识复用。前三层已经覆盖了用户会遇到的全部
正常路径,而这一行的后果**有界**——留下的是一个终会自己跑完的进程,不是数据损坏,也不会累积。

另有两种不属于"取消"但同样要求不挂起的情形:**可执行文件不存在**(用户机器上最可能出错
的一件事)必须立刻失败,而不是等到时钟走完;**调用方的输出回调自身抛错**不改变进程的结论
——进程做了什么与我们如何处理它,是两件事。

#### 两个正交的轴

执行的形态由两个相互独立的轴描述,而非若干固定组合:

| 轴 | 取值 |
|---|---|
| **输出交付** | 增量回调 / 结束时汇总 |
| **时钟** | 总时长、空闲时长——**各自可选,可同时启用** |

由此覆盖三类真实用法:

| 交付 | 时钟 | 用途 |
|---|---|---|
| 汇总 | 总时长 | 环境探针、依赖探测、远端校验、启动器导出、目录导出、命令行调用 |
| 增量 | 空闲时长 | 算法执行、脚本执行 |
| 增量 | 空闲 + 总时长 | 持续产生输出但可能永不结束的任务 |

第三种组合覆盖一个真实缺口:陷入循环且每轮都产生输出的任务,仅有空闲时钟时**永远不会被
终止**。有人值守时可手动中断,而自主运行的场景无人值守,需要一道宽松的总时长兜住。

**约束:两个时钟至少启用一个。** 一个都不给意味着无界等待,这是遗漏而非选择,应当直接
拒绝而非默默挂起。

#### 时钟语义

| 时钟 | 起点 | 重置 | 判定 |
|---|---|---|---|
| 总时长 | 进程启动 | 不重置 | 累计运行时长超限 |
| 空闲时长 | 进程启动 | **每次输出到达** | 距最近一次输出超限 |

空闲时钟有两处实现约束,均属正确性而非偏好:

**刷新点在"输出到达",不在"消费完成"。** 输出交付给调用方后,其处理可能较慢(写盘、更新
界面);若在处理完成后才刷新时钟,消费端的耗时会被计入空闲预算,导致健康任务被误杀。
**任务是否健康由它是否产生输出决定,与我们处理得多快无关。**

**这条要求读取与消费真正分离,不只是把刷新写在回调之前。** 输出流是拉取式的:读取与消费同处
一个循环时,下一块只有在上一块处理完之后才会被读出来——刷新写在回调前还是回调后,量到的间隔
都是**消费端的节奏**,只差一个相位。因此读取端须独立推进,经一个缓冲交给消费端。缓冲**有界**
(§3.2 末:任何无界的累积都需要一个界),这个界同时划出保证的边界:消费端落后在缓冲以内时,
空闲时钟量的是真实到达间隔;落后到填满缓冲时背压生效,两者的节奏重新合一。

**以周期比对判定,而非每次输出重置定时器。** 高频输出的任务每秒可产生大量片段,逐个重置
定时器代价可观;固定间隔比对"当前时刻与最近输出时刻"的开销恒定,代价是判定精度以轮询
间隔为界——对以秒计的时限完全够用。

#### 终止序列

```
    进程启动
       │
       ├── 时钟触发 ┐
       ├── 中断信号 ├──▶ 发起终止 ⏱ 结算时钟启动
       ├── 异常终止 ┘         │
       │                     ├─▶ 请求终止
       └── 正常退出 ─┐        ├─▶ 宽限期
                    │        ├─▶ 强制终止
                    │        └─▶ 清理进程树
                    │                │
                    └───────┬────────┘
                            ▼
                       排空输出流 ── 结算时限内未完成 ──▶ 放弃排空并标注不完整
                            │
                            ▼
                  返回:退出码、终止原因、输出
```

**排空在所有路径上执行**,正常退出同样需要——否则最后一批输出丢失。这一条在超时与中断
路径上尤其关键:那正是调用方最需要知道"进行到哪一步"的时刻。

**清理范围是整棵进程树**。子进程通常还会派生自己的子进程,只终止直接子进程会留下孤儿。

#### 结算时限:从发起终止起算

结算时限保证的是**调用必然返回**,而非任务必须结束。它针对一个具体现象:进程已被强制终止,
但输出流始终不关闭——孙进程继承了输出句柄并保持其开启,排空因而无限期挂起。

**起点是"发起终止动作"那一刻,不是调用开始。** 若从调用开始计时,增量交付模式下一个持续输出的
健康任务(合法运行数小时)会被误杀。以终止动作为起点,健康任务完全不受影响,只有终止后的
收尾被限时。

更准确地说,起点是**排空开始**那一刻。正常退出路径上没有"终止动作",但同一个故障照样成立
——子进程已退出,孙进程仍持有输出句柄。既然排空在所有路径上执行(见上),限时也必须覆盖所有
路径,否则"调用必然返回"在最常走的那条路上反而不成立。两者在终止路径上是同一时刻。

超时未排空完时,返回已获得的输出并标注可能不完整。**这不是新的终止原因**——原因仍是超时
或中断,"排空未尽"是附加事实。

#### 异常终止识别

存在一种情形:进程实际已死,但输出流未关闭(系统的崩溃报告器持有了句柄)。此时进程不再
产生输出,空闲时钟会正常走完——但那意味着白等满整个时限才发现。

因此在周期比对中顺带检查进程存活,已死即判定为异常终止。**该检查平台相关**:在某些平台上,
正常退出的进程会短暂呈现为不存活,启用会将成功完成的长任务误判为崩溃,因此按平台开关。

#### 参数面

**必需三项**:可执行文件与参数、交付模式、**至少一个时钟**。其余(工作目录、标准输入、
环境变量、中断信号)是常规的进程启动参数。

两项有默认值但必须可调,各自对应一类真实需求:**宽限期**(需要在退出前清理临时文件的任务
要更长的窗口)、**汇总模式的输出上限**(产出较大的调用需要更高的上限)。

**Runtime 内部固定**

结算时限、轮询精度、终止升级顺序、空闲时钟的刷新点、排空保证。这些描述的是终止流程本身的
正确性与速度,与任务性质无关;暴露它们只会增加调用方需要理解的概念,却改善不了任何决策。

#### 输出处理

**增量模式**的输出逐块交付,Runtime 不做累积,规模由调用方掌握。

**汇总模式**在 Runtime 内累积,因此需要一道上限:失控的进程(错误循环、意外的调试输出)
可能产生极大的输出并耗尽内存。超限即终止并标注。**任何无界的累积都需要一个界**——这与
数据获取模块对远程响应的护栏是同一类保护。

**环境注入**采取继承宿主环境并叠加的方式,而非替换。理由与 §4.3 原则 8 一致:执行环境求
完整,缺少一个基础变量即可能导致启动失败;叠加层承载调用方组装的专用环境。

**输出通用件**三项跨模块共用:输出截断(附截断标记)、耗时格式化(统一的人类可读形式)、
结构化错误提取(脚本以约定形式输出错误时,从中取出该错误而非呈现整段原始文本)。

### 3.3 Net — 网络出口

**职责**:管理本机到各远程目标的网络出口。它是 GeoKernel 中**唯一**处理网络可达性的模块,
拥有与网络有关的全部决策:如何解析路径、何时探测、如何探测、多久复验、在什么条件下改变
连通性判断、如何恢复。

**子模块**

| 子模块 | 内容 |
|---|---|
| targets | 目标注册表:远程能力在此声明其目标端点 |
| discovery | 代理候选发现,结果全局共享 |
| resolver | 按目标解析可用路径:直连优先,候选回退 |
| probe | 探针:直连握手、代理协议问答、隧道内目标验证 |
| tunnel | CONNECT 握手的唯一实现,探测与实际请求共用 |
| route | 路由的两种形态:子进程环境注入与进程内 agent |
| classifier | 失败判定:识别失败性质,区分需要立即响应与需要防抖的信号 |
| monitor | 监视循环:复验节奏、判定变更、快速降级、自动恢复 |
| redact | 凭据脱敏:出口信息的统一过滤 |

**对外提供**

| 接口 | 内容 |
|---|---|
| 目标注册 | 声明一个连通性需要被判定的目标 |
| 状态读取 | 目标当前的连通性状态与所用路径标识 |
| 代理告知 | 本机是否存在可用代理。经真实 CONNECT 握手验证,不信任声明 |
| 变更通知 | 状态变化时的推送 |
| 路由形态 | 当前路径的两种可用形态:**子进程环境注入**与**进程内路由** |

#### 路径解析:直连优先,代理回退

**第一步:直连探测。** 对目标做一次真实握手。成功即采用直连,代理发现完全不启动——网络
可直达的用户(以及使用全局接管式代理的用户)永远停在这一步,代理机制对他们完全隐形。

**第二步:代理回退(仅当直连失败)。** 候选来源两处:

| 来源 | 内容 |
|---|---|
| 用户显式声明 | 进程环境中的代理变量。覆盖"约定清单之外的代理"(企业代理、非常规端口),也是对用户显式意图的尊重 |
| 知名端口约定 | 主流代理软件工作时开放的本地端口,内置常量,按真实反馈增补 |

**端口约定这一层承担主要负载。** 图形界面启动的应用不继承 shell 的环境变量,第一层因而在多数
真实机器上是空的——它只在从终端启动时才有值。而代理软件**无论是否开启"系统代理"模式,都会开
一个本地端口**,所以端口层覆盖的正是同一批用户。

**不去读取操作系统的代理设置**,这是有意的:它能额外覆盖的只有"改了默认端口且开启了系统代理"
这一窄条,而代价是一套平台相关的读取、缓存失效与死端口判定逻辑。落在这条窄缝里的用户,可以
通过设置环境变量走第一层。

**这不是端口扫描**:不枚举用户机器的任何端口,只对约定清单中的少数端口逐个发起协议问答。

候选一律经完整验证后才被采用,来自环境变量者亦然——变量可能陈旧,指向早已关闭的代理。

**仅 SOCKS 形态的声明直接跳过**:消费端运行时需额外的可选依赖才能处理该协议,缺失时抛出
异常,反而破坏本来直连正常的用户。

**候选发现的结果全局共享**(哪些端口应答为代理),而**路径选择与连通性判定按目标独立**——
不同目标的可达性互不牵连,某个目标不可达不影响其他目标。

#### 探针规格

**直连探针**:对目标完成一次真实握手。握手完成才证明抵达了真实端点——中途的连接重置、
域名解析失败、超时都会使其失败。证书校验保持开启。

**代理探针:三段问答**,同时完成"是不是代理"与"能不能用"两项判定:

| 段 | 动作 | 判定 |
|---|---|---|
| 1 | 建立到本地端口的连接 | 仅说明有程序在监听,可能是任何本地服务 |
| 2 | 发起代理协议的隧道请求 | **只有代理会正确应答**。非代理服务在毫秒级暴露并被跳过,对其无副作用 |
| 3 | 在隧道内对目标完成真实握手 | 握手成功才是"能到达目标的代理" |

**第 3 段不可省略**:部分代理软件对上游是否可达并不预先验证,会先行应答成功。仅凭第 2 段
的应答判定可用,会在网络断开时得出"可达"的错误结论。

#### 监视

监视器是连通性的唯一状态机,节奏、阈值与恢复策略全部在此,消费者不复制其中任何一段。

#### 探测为什么可以跑得很密

复验间隔取**秒级**,红绿一致。这个选择成立的前提是一条必须写明的性质:

> **探针不带凭据、不打任何 API 路径。** 远端的配额与滥用检测按"项目 + 凭据"计量,一次未认证的
> 握手根本不进入它们的视野。

因此间隔的取舍**只关乎我们自己的开销**,而我们自己的开销是一次握手。这条论证是**承重的**:
后来者若在没有新理由的情况下把间隔调长,就是拿本模块存在的意义(尽快知道)去换一项已被
论证为可忽略的成本。

反过来,**带凭据的远端校验(§5.5)才是会碰风控的那一层**,它的触发条件与退避另有规定。两层
的分工是:未认证的探针高频回答"路通不通",带凭据的校验低频回答"授权还成不成立"。

**消费者对"转为可达"的反应若代价昂贵,节流的责任在消费者一侧**,不在此处。把 Net 的信号
钝化以保护下游,会让状态面同时失去真实性与时效性。

#### 三层递进的开销

每一轮探测按开销从低到高排列,前一层否决即不进入后一层:

| 层 | 代价 | 回答 |
|---|---|---|
| 网卡检查 | **微秒级,零网络流量** | 本机有没有可发包的出口 |
| 已持有路由的复验 | 一次握手 | 那条既有路径还通不通 |
| 完整候选流程 | 一次握手 + 少量本机问答 | 有没有别的路可走 |

第一层的价值不在于快,而在于**没有网络时整轮不产生任何流量**——合上盖子的笔记本、飞机上的
机器,在等待期间的开销是零。它同时也是 §3.3 快速降级所指的那个无歧义信号。

第三层只在手中无路由时进入,而其中的本机问答须使用**远短于远端握手的时限**:发现阶段全部
发生在回环上,关闭的端口毫秒级拒绝,唯一昂贵的情形是"端口开着但不应答",短时限正是用来
兜住它的。

| 机制 | 设计 |
|---|---|
| 按需驱动 | 有订阅者才运行,无人关心的目标不消耗探测 |
| 路由感知复验 | 直连路由验直连,代理路由验"经该代理还能否抵达目标"——用户断网与代理软件退出因此走同一条检测路径,只是失败点不同 |
| 滞回 | 模糊故障(超时、抖动)需连续同向判决才翻转,避免链路抖动造成状态闪烁。**只对失败方向设门槛**:恢复凭一次判决即成立,因为"与真实端点完成握手"不会偶然发生,而失败有大量无辜成因。慢于放弃、快于恢复,是有意的不对称 |
| **快速降级** | 接口级断网信号无歧义,**首个判决即降级**,不做防抖 |
| 自动恢复 | 转为不可达即清除已验证路由,复验改走完整候选流程;用户重开代理软件后自动被拾取,无需任何界面操作 |

失败信号只作二分——**硬性断网**(走快速通道)与**其他失败**(防抖处理)。二分只为驱动行为,
不用于生成文案:面向用户的网络故障提示是统一的一句,原始错误作为诊断详情随状态透传。

#### 路由形态

同一条已解析路径对不同消费者提供不同形态。两者的差异源于**访问发生在哪里**:

| 形态 | 消费者 | 内容 | 施加时机 |
|---|---|---|---|
| **子进程环境注入** | 在子进程中访问远程服务 | 该运行时可识别的代理环境变量 | **进程启动时**,整个进程生命周期内固定 |
| **进程内路由** | 在当前进程中访问远程服务 | 可直接用于网络请求的路由对象 | **每次请求时**逐次指定 |

**两种形态不可互相替代**:进程内的网络访问不读取环境变量,子进程也无法接收进程内对象。
这是运行方式的客观差异,不是可以合并的重复。

**进程内路由取运行时标准库自带的连接代理对象形态**,而非某个 HTTP 客户端库的调度器。理由是
§10.3:内核只用 Node 标准 API,以保证 sidecar 与命令行行为一致——而那类调度器需要引入一个在该
运行时下并不可解析的依赖。代价明确且落在消费者身上:**使用该形态的模块经标准库发起请求,而非
`fetch`**。隧道的建立与探针共用同一份实现,因此"验证通过的路径"与"实际承载流量的路径"不可能
出现分歧。

**施加时机的差异同样是本质的,不是实现细节:**

- 子进程一经启动,其环境不可更改;因此路由在启动那一刻确定,该进程的全部网络访问共用它;
- 进程内访问则**逐次携带路由**,而不是把它装到全局。进程级设置会波及内核做的所有其他事情,
  而发起方只是某一个模块在决定自己的流量怎么走。

**三项配套约束**:

| 约束 | 适用 | 说明 |
|---|---|---|
| 本机地址直连例外 | 子进程形态 | 指向本机的访问不得经过代理。子进程中的本地回调、本地服务若被路由到代理,将无法送达 |
| **直连需显式清除** | 子进程形态 | 宿主进程若继承了代理变量,而解析结果是直连,必须把这些变量在子进程环境中**置空**。只做"不注入"不够——继承下来的旧值会让"直连"名不副实 |
| 凭据的双份形态 | 两种形态 | 路由可能携带凭据。**使用时用完整形态,输出时用脱敏形态**(见下),二者并存而不相互替代 |

**覆盖边界**:路由只提供给**目标已注册**的访问。访问由用户任意指定的远程地址时,Net 无从
预先验证该地址的可达路径,因而不提供路由——这类访问沿用宿主进程自身的网络环境。

#### 脱敏

代理地址可能携带凭据,因此**一切外向输出前统一剥离,保留主机与端口以维持可诊断性**。外向
出口有三处——状态事件、诊断信息、日志——**漏掉任何一处都等于没做**。

### 3.4 Status — 状态记账

**职责**:为各能力模块的环境状态提供统一的存储、并发安全提交、变更发布与快照聚合。

**子模块**

| 子模块 | 内容 |
|---|---|
| registry | 状态槽注册与存储 |
| commit | 提交协议:单写者约束、代际守卫、变更去重 |
| publisher | 变更发布到宿主事件通道 |
| snapshot | 快照聚合与对外暴露 |

**对外提供**

| 接口 | 内容 |
|---|---|
| 槽注册 | 能力模块声明其状态槽 |
| 领取令牌 | 开始一轮解析,获得该轮的代际令牌 |
| 提交 | 以令牌提交状态值 |
| 单槽读取 | 指定槽的当前值,未注册时为空 |
| 快照 | 全部槽的当前值 |
| 变更事件 | 按槽发布的状态变化 |

#### 职责边界

| 事项 | 能力模块 | Status |
|---|---|---|
| 探测方式与重探时机 | 拥有 | 不介入 |
| 状态类型定义 | 拥有 | 聚合、不解释 |
| 就绪与否的判断 | 拥有 | 不解释 |
| 诊断与指导信息 | 拥有 | 搬运 |
| 视觉呈现形式 | 拥有 | 不定义 |
| 槽存储与单写者约束 | — | 提供 |
| 并发提交守卫 | — | 提供 |
| 变更去重与发布 | — | 提供 |
| 快照聚合 | — | 提供 |

#### 提交协议:代际令牌

三个能力模块都需要"过期结果不得覆盖新结果"。该机制在 Status 实现一次,不由各模块自行
重复:

```
模块开始一轮解析  →  领取该轮的代际令牌
                          ↓
              异步工作(可长达数十秒、可含多个阶段)
                          ↓
        携带令牌提交  →  Status 比对:非当前令牌即丢弃
```

**令牌覆盖整轮,而非单个阶段。** 由多个阶段构成的解析(如环境验证后接目录构建)全程使用
同一枚令牌:新一轮开始后,上一轮进行中的后续阶段结果自然作废,模块无需自行判断其有效性。

中间态的发布同样经由提交,因此过期的解析连中间态也无法写入。

**单写者**:每个槽只有其注册者可以提交。

#### 变更去重

提交时与槽的当前值比较,相同则不发布。这使周期性探测(如网络监视)在状态稳定期间不产生
事件噪音。

#### 发布与快照

- 事件按槽发布,载荷为**完整状态对象**(整槽替换语义),非持久化;
- 快照聚合全部槽,供新接入的客户端一次性获取当前全貌。

## 4. QGIS 模块

### 4.1 职责与子模块

**职责**:管理 QGIS 运行环境,并在该环境中执行空间处理算法与数据读取脚本。

**服务对象**:R2 空间处理;R1 的 Agent 侧数据读取与预览。三类能力共享同一个 QGIS Python
环境。

| 子模块 | 内容 | 设计 |
|---|---|---|
| lifecycle | 状态槽归属;启动与配置变更的响应;两阶段串联;向 Status 提交 | §4.10 |
| env | 环境解析、验证;产出可用环境对象与诊断 | §4.3–§4.6 |
| catalog | 算法元数据的构建、缓存与检索 | §4.11 |
| executor | 在已验证环境中执行算法与脚本 | §4.12 |
| scripts | 环境探针、目录导出、数据读取的 Python 脚本与生成链 | §4.13 |

**内部依赖**:`lifecycle → env`、`lifecycle → catalog → executor`。env 与 catalog 互不
可见,各自只对 lifecycle 负责,状态槽因此只有一个写者。

**环境解析是本模块的核心复杂度所在**(§4.3–§4.6):用户机器上的 QGIS 在平台、安装方式、
版本与用户给出的路径形态四个维度上组合变化,而三类能力全部建立在"成功导入 QGIS"这一
前提上。

### 4.2 配置输入

配置项 `qgis` 是一个**位置提示**,接受以下形态:

| 形态 | 示例 |
|---|---|
| QGIS 自带解释器的完整路径 | `/Applications/QGIS-LTR.app/Contents/MacOS/bin/python3` |
| 应用包路径 | `/Applications/QGIS-LTR.app` |
| 安装根目录 | `C:\OSGeo4W` |
| 启动器脚本路径 | `C:\OSGeo4W\bin\python-qgis-ltr.bat` |
| 安装内的中间层目录 | `C:\OSGeo4W\apps\qgis-ltr` |

全部形态推导出同一结果。用户无需了解哪一种是"正确"的写法。

绝对路径的存在性判定较宽松(允许提示指向目录或脚本);相对路径直接判定为无效——相对路径
在配置文件中几乎总是笔误,而对其做宽松处理会把当前工作目录误认为有效输入。

### 4.3 环境解析:问题空间、原则与流程

#### 问题空间

用户机器上的 QGIS 在四个维度上组合变化:

| 维度 | 取值 | 造成的差异 |
|---|---|---|
| 平台 | macOS / Windows | 目录布局、环境变量集合、动态库加载机制均不同 |
| 安装方式 | macOS:官方应用包、包管理器、源码构建<br>Windows:网络安装器、独立安装包 | 前缀位置、是否附带官方启动器、组件是否齐全 |
| 版本 | 影响解释器位置、标准库布局、Qt 主版本、组件目录结构 | 同一平台内部仍有多套布局 |
| 位置提示形态 | 解释器 / 应用包 / 安装根 / 启动器 / 安装内中间层目录 | 推导的起点不同 |

同一台机器上还可能**同时存在多套安装**(长期支持版与当前版并存),或同一资源有多个副本
(多个投影数据目录)。因此解析不是一次查找,而是一次**带排序的候选选择**。

#### 总体流程

```
配置输入
   │  可达性预检
   ▼
① 定位安装根 ───── 标志物验证失败 ──▶ 判定为非 QGIS 安装
   │
   ▼
② 解析解释器与前缀(候选枚举 + 确定序排名)
   │
   ▼
③ 组装环境(平台各自的策略)
   │
   ▼
④ 探针验证(分步排除)
   │
   ├── 失败 ──▶ ⑤ 回退重试 ──▶ 仍失败 ──▶ ⑥ 产出诊断
   ▼
已验证环境对象
```

#### 十条解析原则

平台实现各异,但都遵循同一组规则。

**1. 提示只用于定位安装,解释器由安装决定。** 用户提供的路径叶子节点可能属于另一套版本
布局。流程始终是"提示 → 安装根 → 由安装根推导解释器",而非直接使用提示。唯一例外:提示
的文件名符合解释器命名形式**且该文件确实存在**时可直接采用。

**2. 优先采用厂商自己的答案,并为我们的场景显式叠加。** 当安装附带官方的环境组装脚本时,
运行它并采纳其结果,而不是重建一份——它由 QGIS 项目维护,随版本演进。但厂商脚本是为**它
自己的使用场景**准备的,我们的场景(无界面、输出被程序解析)需要额外设置。叠加层必须
显式且极小,每一项都要能说清"为什么厂商脚本不可能设它"。

**3. 多候选并存时按确定序排名,不取首次命中。** 凡是可能存在多个有效答案的地方——子前缀、
启动器、Qt 根、投影数据目录——都以固定优先级排序后选取。取"第一个找到的"会让选择随文件
系统的遍历顺序漂移,同一台机器上的两次运行可能得到不同结果。

**4. 验证载荷,而非容器。** 目录存在不代表内容可用:投影目录必须含有投影数据库文件,
应用包必须含有 QGIS 标志物,子前缀必须同时含有模块目录与可执行目录。

**5. 动态库搜索模式是单向门(Windows)。** 一旦向解释器注册动态库搜索目录,它即切换到
受限搜索模式,可执行搜索路径对**级联加载**永久失效。因此依赖级联的路径绝不注册,不依赖
级联的路径必须注册且集合足够宽——核心库的级联依赖散布在多个组件目录中。

**6. 探针验证能力,而非导入。** 模块导入成功不足以证明功能可用。典型情形:投影库导入正常,
但数据库缺失或版本不匹配,直到用户处理自定义坐标系的数据时才失败。探针直接执行一次真实
的坐标变换。

**7. 子进程标准输出是嘈杂的共享通道。** QGIS 及其依赖在导入、初始化、退出三个阶段都可能
写入标准输出。脚本以**单行标记**输出结构化结果,消费端从标记的最后一次出现处提取,并在
输出后立即退出以跳过清理阶段。标记缺失与内容非法是**两种不同的失败**:前者说明脚本未
到达输出点(启动崩溃),必须把原始输出交给用户。

**8. 执行环境求完整,展示环境求安全。** 同一份环境数据有两个用途:交给子进程执行,以及
呈现给用户诊断。二者要求相反——执行需要完整(缺一个变量就可能导入失败),展示需要过滤
(其中含有从宿主进程继承的敏感值)。**过滤只在展示出口施加,不裁剪执行环境**。若需限制
子进程可见的敏感值,应按"已知的敏感项"排除,而非按"已知的必需项"保留:我们清楚自己有
哪些敏感变量,却无法穷举 QGIS 需要哪些变量。

**9. 有些失败发生在任何用户代码之前。** 解释器自身的启动阶段(如标准库定位、文件系统
编码初始化)若失败,任何环境变量都无法挽救,修复必须落在文件系统布局上。

**10. 可恢复处宽松,不可恢复处严格。** 可达性预检对绝对路径放宽——后续流程有能力从不精确
的提示中恢复;对相对路径直接拒绝——它在配置中几乎总是笔误,宽松处理会把干净的"找不到"
变成后期难以归因的探测错误。

#### 可达性预检

| 情形 | 判定 |
|---|---|
| 配置为空 | 未配置 |
| 相对路径 | 不可达 |
| Windows 绝对路径 | 提示本身或其父目录存在即放行(后续可从安装中发现启动器)|
| macOS 绝对路径 | 提示本身存在,或路径中含有应用包祖先(通过或未通过标志物验证均可),即放行 |

macOS 一行放行未通过验证的应用包祖先,是有意的:那条路径已经有了确定的结论(非 QGIS),
让它走完解析才能得到这个准确结论,拦在预检只会退化成一句笼统的"路径不可达"。

### 4.4 macOS 环境解析

#### 安装形态

| 形态 | 特征 |
|---|---|
| 官方应用包 | 前缀位于应用包的可执行目录,资源位于同级的资源目录 |
| 包管理器与源码构建 | 常规 Unix 布局,资源位于前缀下的共享目录 |

#### 定位前缀:三级回退

| 级 | 方法 | 覆盖的提示形态 |
|---|---|---|
| 1 | 沿提示路径上溯,遇到应用包可执行目录段即取为前缀 | 提示是解释器完整路径 |
| 2 | 扫描提示路径各段,取应用包段并拼接其可执行目录 | 提示是应用包路径或包内任意位置 |
| 3 | 取提示路径的上两级 | 非应用包安装 |

**标志物验证嵌在扫描过程中**:候选目录必须含有 QGIS 的可执行文件(无界面处理程序或
主程序),验证失败则继续扫描后续段。任何应用包都有可执行目录,缺少这项验证时,一个无关的
应用包路径会被静默接受为 QGIS 前缀。第 1 级同样做这项验证:命中即是已验证的答案,**未命中
不是判决**——记下该目录后继续走第 2、3 级,由后续级别或逃生口定夺。

**已验证标记与逃生口**。解析结果携带一个"是否经标志物验证"的标记,预检据此放行(见 §4.3
预检表):第 3 级从不验证任何东西,若无此标记,一个根本不存在的提示会通过预检,最终以探针
脚本外衣下的启动错误呈现,把用户引向脚本而非路径。

标志物缺失本身**不足以否决一个真实存在的解释器**(原则 10):提示指向的文件名符合解释器
形式且确实存在时,以记下的可执行目录为前缀交给探针裁决——QGIS 派生版与裁剪安装真实存在,
对它们探针是唯一诚实的判官。提示不是解释器时,仍得到干净的"非 QGIS"结论。

#### 解析解释器:两套版本布局

| 布局 | 解释器位置 |
|---|---|
| 较早版本 | 前缀下的可执行子目录中,名称不带版本号 |
| 较新版本 | 前缀根下,名称带次版本号,无中间目录层 |

**预解析纪律**(原则 1 的具体化):仅当提示的文件名符合解释器命名形式**且该文件确实存在**
时直接采用;否则一律回到布局推导。

这条纪律针对一类具体故障:用户在较新版本上给出较早布局形状的路径,文件名看似合理但文件
并不存在。按名采用会启动一个不存在的路径,而失败信息指向用户"写对了"的那个路径。

#### 资源定位

三类资源(投影数据、GDAL 数据、Python 模块)在两种安装形态下各有同构的候选位置,取首个
存在者。两条不显然的规则:

- **投影数据目录额外验证载荷**——目录存在不够,必须含有投影数据库文件(原则 4);
- **模块搜索路径收集全部候选**(及其插件子目录)并保留进程已有的值,而非取首个。它是一个
  路径列表,多处并存是正常状态。

#### 解释器根修复

较新版本把标准库直接放在资源目录下的版本号目录中,缺少解释器预期的中间包装层。解释器在
初始化文件系统编码的阶段即中止——该阶段早于任何用户代码,环境变量无法干预(原则 9)。

做法是在应用缓存目录内建立符合解释器预期的链接结构,并将解释器根指向它。三条约束:

| 约束 | 内容 |
|---|---|
| 探测标准库根**不使用目录类型判定** | 部分安装以符号链接共享标准库,而类型判定对"指向目录的符号链接"返回否定。改为直接检查其中是否含有编码模块目录 |
| 幂等 | 已存在时先比对指向是否正确:正确则复用,否则删除重建。用户更换安装位置不会留下陈旧链接 |
| 仅对带版本号的解释器名启用 | 不带版本号的命名走的是另一套查找行为,不存在这个错配 |

**兜底**:布局探测未命中、但探针失败于解释器启动阶段时,同样尝试构造链接结构后重试一次。
未知的新布局因此也能被接住。

### 4.5 Windows 环境解析

#### 安装形态

| 形态 | 特征 |
|---|---|
| 网络安装器 | 根目录下有组件目录与可执行目录,多组件共存于同一根 |
| 独立安装包 | 相同的组件布局,根目录命名不同 |

两者共享"组件目录下按版本号命名的解释器目录"与"可执行目录下的官方启动器脚本"两项约定。

#### 定位安装根

两条策略并列尝试:

| 策略 | 方法 |
|---|---|
| 路径段扫描 | 逐段检查提示路径,段名包含 QGIS 或安装器的标识子串(大小写不敏感)即作为候选根,并要求其可执行目录下存在官方启动器。自左向右尝试每个匹配段,以覆盖嵌套布局 |
| 中间层修正 | 提示指向安装内的中间层目录(其下同时存在模块目录与可执行目录)时,上溯两级得到真实根 |

段扫描是纯字符串操作,系统调用次数与匹配段数成正比而非与路径深度成正比;同时它天然排除
误判——散落在其他位置的用户自制包装脚本,因其祖先路径不含标识子串而不会被当作安装根。

**中间层修正为两轨共用**,以免桥接轨与手工轨对"根"的理解产生分歧。

#### 候选与排名

| 对象 | 候选来源 | 优先级 |
|---|---|---|
| 启动器 | 可执行目录下的三种命名 | 长期支持版 > 当前版 > 开发版 |
| QGIS 子前缀 | 解释器同级的组件目录、根下组件目录、两项约定命名 | 长期支持版 > 当前版 > 开发版 > 其他以 QGIS 命名者 |
| Qt 根 | 根下组件目录 | 较新主版本优先,每个版本覆盖两种大小写命名 |
| 投影数据目录 | 六个约定候选;未命中则在根下做有界深度搜索(跳过缓存目录与第三方包目录)| 约定候选按序;搜索结果按位置模式排名,同名次者按路径长度 |

Qt 根的优先级不是偏好而是必需:较新 QGIS 仅链接新版 Qt,若只搜索旧版则 Qt 目录未被注册,
表现为核心模块导入失败。

子前缀候选须同时含有模块目录与可执行目录方可入选(原则 4)。

#### 双轨激活

**轨一:桥接**

令官方启动器执行一段最小程序,输出其组装完成的完整环境,再经单行标记提取以隔离启动器自身
的回显。五项约束,每项都有它必须如此的理由:

| 约束 | 理由 |
|---|---|
| 程序**单行且纯 ASCII** | 命令解释器对多行内容与非 ASCII 字符的处理在不同语言环境下不一致 |
| 采纳前校验关键变量存在 | 前缀、解释器根、可执行搜索路径。最后一项尤其不能少——本轨完全依赖它做级联加载,缺失时验证能过而真正执行时失败 |
| 解释器**以导出结果为准** | 启动器知道它自己配置的是哪一个;用户提示在本轨中仅用于定位安装 |
| **完整采纳,不裁剪** | 原则 8 |
| 动态库目录**留空** | 原则 5。本轨依赖可执行搜索路径的级联,一旦注册动态库目录,该级联永久失效 |

**叠加层**(原则 2),仅两项:

| 项 | 为什么启动器不可能设它 |
|---|---|
| 解释器的标准流与文件名编码 | 启动器面向交互式使用,不知道有程序在解析它的输出。缺少此项时,非英语语言环境下的输出会按系统代码页编码,而消费端按 UTF-8 解码 |
| 插件搜索路径前置 | 启动器导出的模块搜索路径只含模块目录,插件目录依赖 QGIS 初始化时追加;而算法框架的初始化早于该追加。前置时须去重 |

**轨二:手工组装**(启动器缺失或导出失败)

解释器定位为四级回退:已解析的根 → 任一非空根候选 → 由提示的解释器形状推导 → **按内容
上溯**;在其下的组件目录中寻找解释器,仍未找到才退回提示本身,让探针把提示原样呈现在诊断中。

第四级按内容而非按名称识别安装根(原则 4):含有组件目录、或其可执行目录下有官方启动器的
祖先目录即是根。它覆盖前三级都miss的一种真实形态——安装目录被改名为不含产品名的字样,
且提示指向根级解释器垫片而非组件目录内的解释器;没有这一级,回退会停在垫片的父目录上,
照着一棵空树组装环境。

**子前缀选择尊重显式意图**:同一安装内并存多个版本子前缀时按固定序取(§4.3 原则 3),但
当提示本身就是一个完整的子前缀目录时,它排在固定序之前——固定序是用来打破用户没有表态的
平局的,用户指名了 dev 却拿回它旁边的 LTR,是在回答没被问到的问题。

本轨需自行复刻官方启动器所做的全部设置:前缀与根锚点、解释器根、数据与驱动目录、模块搜索
路径、Qt 插件路径、可执行搜索路径、编码、虚拟文件系统缓存。这些照着启动器的行为复刻即可,
**其中三项不能照直觉写**:

| 项 | 约束 |
|---|---|
| QGIS 前缀 | 路径分隔符转为正斜杠,**且仅此一个变量需要**——QGIS 内部解析偏好该形式,其余变量保持平台原生形式 |
| 投影数据 | **两个变量名同时写入**,不同版本读取不同的那一个 |
| 动态库目录 | 集合必须**宽**(原则 5):除根与前缀的可执行目录外,还须涵盖**全部组件的可执行目录**。核心库的级联依赖散布其中,窄集合在较新版本上失效 |

动态库目录的注册通过在执行脚本前插入引导代码完成。**执行脚本文件时须改写为等价的内联执行
形式**(设置参数向量、将脚本目录置于模块搜索路径首位、以主模块名运行)——因为引导必须早于
目标脚本的首个导入生效。

#### 桥接轨的输出纪律

启动器继承宿主进程的完整环境,其中含有敏感值。因此:

- 桥接失败时,日志**只记录输出的字节数**,不记录原始内容。成功的导出内容含未经处理的
  敏感值,失败路径的错误流可能含启动器的变量回显;
- 展示用的环境视图在**产出诊断时**过滤(原则 8),执行用的环境保持完整。

### 4.6 环境验证与回退

#### 探针

在候选环境中分步验证,每一步对应一类明确的安装问题:

| 步 | 验证内容 | 失败含义 |
|---|---|---|
| 1 | GDAL 绑定可导入 | 解释器不含 GDAL 绑定,常见于提示指向了系统解释器 |
| 2 | 完成一次自定义坐标系到地理坐标系的变换,并校验结果为有限值 | 投影数据库缺失或库版本不匹配 |
| 3 | QGIS 核心库可导入 | QGIS 安装不完整 |
| 4 | 算法框架可初始化 | 算法能力不可用 |

**第 1 步失败立即输出并退出**,不再执行后续步骤:后续步骤必然失败,继续执行只会产生
误导性的次生错误。

第 2 步独立存在的理由见原则 6。

#### 失败分级

| 级别 | 判据 | 携带内容 |
|---|---|---|
| 进程级失败 | 超时、中断、非零退出 | 终止原因 |
| 无标记 | 输出中找不到标记 | **原始输出**——脚本未到达输出点,说明是解释器启动阶段崩溃 |
| 标记内容非法 | 提取到的内容无法解析 | 原始输出 |
| 步骤失败 | 对应字段缺失或为否 | 该步骤捕获的原始错误与调用栈 |

#### 回退

| 触发 | 动作 |
|---|---|
| Windows 桥接轨探测失败 | 以手工轨重新组装并重试一次 |
| macOS 探针失败于解释器启动阶段,且标准库布局探测未命中 | 尝试构造解释器根链接结构后重试一次 |

回退各自只进行一次。回退成功时,来源标记记录最终生效的轨道;回退仍失败时,诊断包呈现
**最后一次尝试**的完整信息,并附带已尝试过的轨道。

### 4.7 状态集合

**主状态**

| # | 状态 | 类型 | 含义 |
|---|---|---|---|
| 1 | `unconfigured` | 终态 | 配置项缺失 |
| 2 | `path-missing` | 终态 | 位置提示指向的路径不存在,或提示为相对路径 |
| 3 | `not-qgis` | 终态 | 路径存在,但标志物缺失,不是 QGIS 安装 |
| 4 | `resolving` | **中间态** | 解析与组装进行中 |
| 5 | `probing` | **中间态** | 探针运行中 |
| 6 | `gdal-missing` | 终态 | 验证第 1 步失败 |
| 7 | `proj-broken` | 终态 | 验证第 2 步失败 |
| 8 | `core-missing` | 终态 | 验证第 3 步失败 |
| 9 | `probe-timeout` | 终态 | 探针超时 |
| 10 | `probe-failed` | 终态 | 探针异常退出,或输出无法解析 |
| 11 | `ready` | 复合 | 第 1–3 步通过;算法能力由子维度描述 |
| 12 | `config-error` | 终态 | `machine.json` 不可解析,携带出错位置。§3.1 规定解析失败使全部块进入错误态——把它显示成"未配置"会与用户眼前的文件自相矛盾 |

`resolving` 与 `probing` 分列,因为二者的耗时特征与失败模式不同:前者的成本集中在启动器
导出与目录搜索,后者在探针执行。合并会丢失定位信息。

**`ready` 的子维度**

| 子维度 | 取值 | 含义 |
|---|---|---|
| 算法框架 | 可用 / 不可用 | 验证第 4 步的结果 |
| 算法目录 | 构建中 / 就绪 / 失败 / 未进入 | 目录阶段的进展 |

算法框架不可用时,目录阶段不进入,目录子维度取"未进入"。

### 4.8 状态迁移

**触发源两个**:应用启动、`machine.json` 的 `qgis` 块变更。

```
触发 ──▶ resolving ──┬──▶ unconfigured / path-missing / not-qgis        (同步判定)
                     │
                     └──▶ probing ──┬──▶ ready ──▶ 目录阶段(算法框架可用时)
                                    │
                                    └──▶ gdal-missing / proj-broken /
                                         core-missing / probe-timeout / probe-failed
```

三条迁移纪律:

1. **无自动重探**。失败态不自行恢复,状态变化只由触发源驱动。

   本模块因此不设 GEE 那样的自愈重探(§5.8)。两个理由,**以成本为主**:

   **重探在这里是复合动作,不是一次探针。** 目录依附于产生它的那次环境验证(下一条),
   所以任何重探都连带作废并重建算法目录;而目录又是统一就绪的前提(§4.9)——重建期间
   **三类能力全部停摆**。把重探挂在"工具重试"上,等于让一次重试有可能冻结整个模块数十秒。
   GEE 的常态复查则是向 Net 读一个已有结论,网络正常时不产生任何耗时,因此它付得起每次
   调用都查一遍。

   **其次,可修复的缝隙很窄。** QGIS 的修复动作几乎全是修改配置项,而配置变更已被监控
   覆盖;唯一的例外是重装,而重装通常会改变安装路径(版本号就在目录名中),因此仍然经由
   配置变更这条路。真正落在缝隙里的只有"重装到完全相同的路径"一种情形。
2. **阶段依附**。新一轮解析开始时,进行中的目录构建结果作废——目录属于产生它的那一次
   环境验证。
3. **代际守卫**。并发探测下,过期结果不覆盖新结果(由 Status 的提交协议提供)。

### 4.9 就绪门禁

QGIS 模块对外提供**单一就绪判定**,三类能力共用:

```
就绪 = 主状态 ready 且 算法框架可用 且 算法目录就绪
```

调用方得到二选一的结果:

| 结果 | 内容 |
|---|---|
| 就绪 | 已验证环境对象,可直接用于执行 |
| 未就绪 | 状态标识 + 指导信息 + 诊断包 |

**统一门禁的理由**:三类能力运行在同一个环境中,环境的可用性是同一个事实;环境故障的
修复动作也是同一个。若不同能力返回不同说法,调用方会将其判断为不同问题并分别诊断。
一个环境,一个结论,一份指导。

能力模块内部的执行入口接收**已验证环境对象**,而非自行查询状态,消除判定与执行之间的
时间窗口。

### 4.10 诊断与编排

**诊断包**。失败态携带定位问题所需的全部事实:选定的解释器、推导出的前缀、生效的动态库
目录、存在性检查结果、探针的原始输出。其中三项需要额外说明:

| 项 | 说明 |
|---|---|
| **候选集与选择** | 各排名项(子前缀、投影数据目录、Qt 根、启动器)的候选清单**与**最终选中项 |
| 环境变量 | 生效的变量集合,**在此出口过滤**(§4.3 原则 8);执行用的环境保持完整 |
| 来源标记 | 生效的轨道,以及已尝试过的轨道(仅 Windows)——两轨的失败成因完全不同 |

**存在性检查**逐项验证并列出结果,覆盖:各模块搜索路径下的 QGIS 包入口、各动态库目录下的
核心库、Qt 核心库(**限定在形似 Qt 根的目录内检查**,否则全量检查产生噪音)、投影数据库
文件、GDAL 数据目录。用户由此直接看到缺失项,无需查阅日志。

**检查项必须按轨道各自定义**。上述检查中依赖"动态库目录"的两项,在 macOS 与 Windows 桥接轨上
都无从取值——这两条路径不注册动态库目录(§4.3 原则 5)。若沿用同一组检查项,**最常用的两条
路径反而诊断最弱**。这两条路径需要各自的等价项:macOS 取安装内的库目录,桥接轨从导出的可
执行搜索路径中取。

**候选集与选择**服务于一类特定问题:选择本身可能是错的。当一台机器上并存多套安装或多份
资源副本时,仅呈现"选中了什么"不足以判断故障成因;同时呈现"还有哪些可选",用户与 Agent
便能直接判断是否应改用另一个候选。该信息进入状态界面的提示区。

**lifecycle 编排**

| 职责 | 内容 |
|---|---|
| 状态归属 | 持有 QGIS 状态槽,是唯一写者 |
| 触发响应 | 订阅 Config 的 `qgis` 块变更;应用启动时首次触发 |
| 阶段串联 | 环境验证通过且算法框架可用时,进入目录构建阶段 |
| 提交时机 | 每阶段结束即提交状态,不等待后续阶段 |
| 并发安全 | 提交附带代际,过期结果丢弃 |
| 门禁供给 | 对外提供 §4.9 的单一就绪判定 |

### 4.11 算法目录

**消费者**两类,这是它称作目录而非文档的原因:

| 消费者 | 用途 |
|---|---|
| 算法检索 | 浏览分组、读取详情、模糊搜索、未命中时的相近候选 |
| 执行前预检 | 参数校验、算法标识的相近候选 |

**数据来源**:QGIS 自身是算法元数据的唯一真相源,目录由导出脚本在已激活环境中运行产生。

**导出范围**:随 QGIS 分发的三个官方处理提供者。第三方插件提供的算法不在当前范围内。

**导出内容**:每个算法记录标识、名称、分组、描述、参数(名、类型、是否必填、默认值、
枚举选项)、输出、帮助文本。

**帮助文本逐字保留**,不做重写或裁剪——它是 QGIS 官方维护的权威描述。仅补充两项它不含的
结构化事实:必填参数清单、含默认值的参数清单。

**产出为英文,这是运行方式带来的性质,不是一项设置**。导出脚本在一个未安装界面翻译的环境中
构造处理框架,框架的文本接口因而回落到源字符串,而源字符串即英文。**任何使导出改走完整应用
启动流程的改动,都会静默切换为用户的界面语言。**

保持英文是有意的:目录的首要消费者是语言模型,模型对英文内容的准确度高于其他语言;算法标识
本身也是英文,统一语言消除了标识与描述之间的语言错位。**下游另有一处依赖**——面向官方文档的
深链由算法显示名推导,显示名一旦被本地化,链接即失效。

**深链的推导规则**(工具层实现,但规则在此存档——它是旧版踩坑后校准出来的,凭直觉重写必错):

- 提供者 → 文档路径:`gdal:` → `gdal`,`native:`/`qgis:` → `qgis`,其余回落到索引页;
- 页面名:分组名转小写并**删除**全部非字母数字字符(无横线);
- 锚点:**由显示名推导**——转小写、去 `&`、非字母数字连续段折叠为单个横线、去首尾横线。
  官方文档站为每个算法生成的章节锚点正是这种"显示名横线 slug";旁边虽然存在按算法标识拼出的
  占位锚点,但目录反链解析到的是前者。**按算法标识推导锚点对所有多词名称都是坏链**,单词名
  能命中纯属巧合;
- 锚点失效时的兜底指引:在页面内搜索"Algorithm ID: <标识>"。

**生命周期**:每次环境验证通过后构建一次,结果驻留内存,进程结束即释放。不设磁盘缓存——
免去缓存目录、版本键与失效规则,并消除"同版本号的不同安装读到彼此缓存"的风险;构建耗时
在数秒量级,且在后台进行,期间状态为"目录构建中"。

**检索接口**

| 接口 | 输入 | 输出 |
|---|---|---|
| 列出分组 | — | 分组名与算法计数 |
| 列出分组内算法 | 分组名 | 算法标识与名称 |
| 读取算法 | 算法标识 | 完整记录 |
| 搜索 | 关键词 | 按相关度排序的结果 |
| 相近候选 | 未命中的输入 | 最接近的若干候选 |

**查找的宽容度**。这些接口的消费者是语言模型,而模型不会拼错单词——它**换写法**。同一个算法,
目录打印的是 `native:reprojectlayer — Reproject layer`,模型之后写出来的可能是 `Reproject Layer`、
`reproject layer` 或 `reproject_layer`;分组打印的是 `Vector geometry`,模型写 `Vector Geometry`。
因此**目录必须认得自己打印过的东西**,查找前对两侧做归一化:转小写,删除全部非字母数字字符。
归一化后为空的输入视为无输入,不当通配。

算法标识按由严到宽尝试,**完整标识之下的一切都是容差,而容差绝不猜**——某一层的键指向多于一个
算法时,该层不挑,而是把**它拒绝在其间做选择的那个集合**原样交出:

| 顺序 | 匹配 | 多于一个时 |
|---|---|---|
| 1 | 完整标识 | 不可能,它是唯一无歧义的键 |
| 2 | 归一化后的标识,带或不带提供者前缀 | 判为歧义,返回候选集合 |
| 3 | 归一化后的**显示名** | 同上 |

不猜的理由是代价不对称。实测一份 3.44 目录:**11 组短标识跨提供者重名**(`gdal:slope` 与
`native:slope` 等),**8 个显示名指向多个算法**(`Raster calculator` 指向 4 个),而它们的参数集
完全不同。取先到者意味着调用方可能执行了一个自己没有要求的算法**且永远不会发现**;判为歧义
只多一次往返。这是本模块少数几处"宁可答不出,不可答错"的地方。

**歧义与真未命中是两种结局,不能合并**:前者该说"从这几个里挑",后者该说"换关键词搜"——建议
相反。而且拒绝挑选的那一刻,候选集合已经算好了;合并成一个"没找到"会把它丢掉,逼调用方用模糊
匹配重新猜一遍,猜出来的既不是同一个集合,也不保证完整。因此查找接口给出三种结局:命中、歧义
(带候选)、未命中;只关心命中的调用方用薄封装,歧义在那里读作"没有"。

因此 `resolve("dissolve")` 返回歧义与 `native:dissolve`、`gdal:dissolve` 两条候选;
`resolve("native:dissolve")` 立即命中。**完整标识是目录在每处输出里都优先打印它的原因。**

分组名同样归一化后比较,并且与"列出分组"走**同一条 UNGROUPED 归类**——列得出来的分组名,必须
查得到。

### 4.12 执行管线

**两类调用,一条管线**:

| 调用 | 实现 |
|---|---|
| 算法执行 | 以标准算法运行脚本承载,参数随调用传入 |
| 脚本执行 | 以给定脚本承载,数据读取走此路径 |

```
接收已验证环境对象 → 组装命令 → Runtime 执行(增量交付) → 输出处理 → 结构化结果
```

**接收已验证环境对象**而非自行查询状态,消除判定通过到进程启动之间配置被修改的时间窗口。

**参数预检**。执行前依据目录元数据检查:未知参数、缺失的必填参数、明显不合法的取值、
算法标识未命中时的相近候选。

**缺席的必填参数分两类,合并即失效**。QGIS 只暴露"是否可选"一个标志,但大量非可选参数
自带默认值——实测一份 3.44 目录,1858 个必填参数里 **869 个有默认值,覆盖 74% 的算法**。
若仅凭"非可选且缺席"就报缺失,一次**完全正确**的调用会触发最多十二条警告,读者随即学会
整体忽略这个通道,而剩下 989 个真正的遗漏也就再没人看。因此:

| 情形 | 产出 |
|---|---|
| 缺席且**无**默认值 | 逐条警告,并说明没有默认值、QGIS 会失败 |
| 缺席但**有**默认值 | **一条陈述**,列出本次实际生效的默认值 |

后者带上取值,是因为那正是本次运行的真实行为,调用方可能想覆盖它;而默认值只在目录里
有现成的,脚本内检查要拿到得重新查。这条也是脚本内检查不再重复报告同一批参数的原因——
两侧各说自己独有的那部分。

一条通则:**能判定就不要对冲**。旧措辞"QGIS 可能回落到默认值,也可能失败"本身就是这个
检查在声明它没有去看紧挨着的 `defaultValue`。

**预检产出提示,不阻断执行**。预检依据的是导出的元数据,而部分参数约束无法在元数据中
完整表达,QGIS 运行期的校验才是权威。若预检阻断,元数据的不完整会变成用户不能执行。
预检的价值在于把"少写了一个必填参数"这类问题在毫秒内反馈,而非等待数十秒后由 QGIS 报错。

**输出协议**

| 通道 | 内容 |
|---|---|
| 标准输出 | 执行过程文本,逐块回调给调用方 |
| 标准错误 | 失败诊断,失败时提取 |
| 单行标记 | 需要结构化返回的脚本在此输出结果 |

**超时与中断**

算法执行属于超时分类中的**第三方控制输出**一档(§8.4):算法自身决定是否报告进度,而
**大量算法整段沉默**——我们无法向第三方的算法实现中插入心跳。因此:

- 采用**空闲超时**而非总超时;
- **时限值由调用方在调用时给定**,带下限与默认值。只有调用方了解本次任务的数据规模与
  算法性质,内核无从预估;
- **进度契约**:算法运行脚本按完成比例定期输出进度,既向用户呈现进展,也为空闲计时提供
  心跳。会报告进度的算法因此可以运行任意长时间;
- **该参数以"总时长"的语义呈现给调用方**,这是有意选择而非疏漏,理由见 §8.4;
- 调用方的中断信号触发进程树清理;
- 任一终止路径都保留已产生的输出,并附带终止原因。

**并发**:每次执行是独立子进程,执行管线自身无共享状态,并发调用互不干扰。

### 4.13 脚本资产

**四类脚本**

| 脚本 | 用途 | 消费者 |
|---|---|---|
| 环境探针 | 分步验证环境(§4.6)| env |
| 目录导出 | 导出算法元数据 | catalog |
| 算法运行 | 执行指定算法并输出进度 | executor |
| 数据读取 | 矢量元信息、栅格元信息、栅格预览 | executor |

**共同约束**,四条均源于运行宿主是 QGIS Python:

1. **单行标记输出协议**。QGIS 及其依赖在导入与退出阶段向标准输出写入无关内容,对完整
   输出做整体解析不可靠;
2. **UTF-8 由子进程环境强制**,而非仅靠脚本内的源码编码声明——后者只影响源码解析,不影响
   标准流的编码。**环境组装的每一条轨道都要设置**(§4.4–§4.5),一条都不能漏;
3. **输出结果后立即退出**,跳过清理阶段,避免其输出混入标记之后的内容;
4. **故障处理器须在导入 QGIS 之前启用**。损坏的安装会在动态库加载阶段发生段错误,该错误在
   语言层面无法捕获;处理器装在导入之后等于没装,而没有它则完全没有诊断信息。

第 2 条的严重性高于直觉:数据读取脚本输出的是**未转义的结构化文本**(以保留中文属性值),
因此编码错误影响的是**正文本身**,而不只是诊断信息。这与那些以纯 ASCII 转义形式输出的脚本
不同——那里编码只影响人类可读的错误消息。

**数据读取脚本的产出**

| 脚本 | 产出 |
|---|---|
| 矢量读取 | 图层信息、要素总数、几何类型、坐标系、范围、字段统计、要素抽样 |
| 栅格读取 | 尺寸、波段统计、坐标系、范围、像元大小 |
| 栅格预览 | 预览图像与其元信息 |

三项设计要点:

- **字段统计是元数据模式下唯一的全量扫描**,是大数据集的性能关键点,采用**双引擎**(见下);
- **栅格预览的语义规则**(波段选择、拉伸、透明通道与空值处理)与 GDAL 模块共享同一份
  定义(§7.9 双引擎关系),两侧各自实现,以共享用例锁定一致性;
- **读取不得写盘**:栅格读取要计算统计量,而 GDAL 默认会把算出的统计量以 `.aux.xml` 写在
  **用户数据旁边**,只读打开也照写(落盘发生在关闭数据集时)。因此三个读取脚本的子进程环境
  统一带 `GDAL_PAM_ENABLED=NO`。这是 §7.6「产物归属」那条约束在本模块的落实——**该约束原本
  只有 GDAL 模块在守**,读取脚本一直在往用户目录里留文件。
  ⚠️ **只加在读取上**:算法执行必须保留 PAM,某些输出格式自身存不下坐标系,靠 `.aux.xml` 保存,
  在执行侧关掉是在毁产出而不是护目录。

**字段统计的双引擎**

| 引擎 | 适用 | 机制 |
|---|---|---|
| 批量列式 | 数据源与运行时都支持列式批量读取,且不需要几何普查 | 按列成批取属性,在数值层面聚合。相对逐要素遍历有**数量级**的优势 |
| 逐要素遍历 | 前者不可用,或本次需要几何普查 | 单次遍历,显式跳过几何解析——几何是要素物化的主要成本,而统计从不读它 |

三条约束:

- **两条路径的结果必须逐字一致**:全表精确,不抽样。产物中记录本次实际走了哪条,使性能异常
  可归因;
- **高基数字段设收敛上限**:超限后不仅停止计数,还要**丢弃已累积的中间结果**——这类字段在扫描
  结束后本就会被判定为"取值全唯一、无统计价值",提前释放把无界的内存增长换成同一个结论;
- **批量路径异常时必须先释放其读取句柄再回退**。未释放的批量句柄会破坏同一数据源上的后续
  顺序读取,使回退路径本身失败。

**构建链**:Python 脚本无法被 TypeScript 直接导入,且产品以单文件形式分发,磁盘上不存在
脚本文件。因此构建期将脚本序列化为模块常量,运行时物化到应用缓存目录后执行。生成物纳入
版本控制,使裸检出无需额外步骤即可运行;构建前自动刷新。

两条移植时校准过的量:矢量读取脚本以内联形式传递时已占用 Windows 命令行长度上限的约四分之三,
因此数据读取脚本走**物化执行**(脚本文件 + 引导改写),不走内联;栅格预览脚本在标准输出上
回传编码后的图像,其汇总上限须按预览尺寸上界**显式给足**——超限的表现是标记行被截断,呈现为
一个难以归因的"无标记"失败,而非大声的越限错误。

## 5. GEE 模块

### 5.1 职责与子模块

**职责**:管理 Google Earth Engine 的可用性判定,并执行遥感计算脚本。

**服务对象**:R3 云端遥感计算。

| 子模块 | 内容 | 设计 |
|---|---|---|
| lifecycle | 状态槽归属;三类事实的合成与提交;各事实来源的订阅与触发 | §5.7 |
| setup | 本地环境链的探测:解释器、依赖包、凭据、项目 | §5.3 |
| runtime-check | 远端授权校验 | §5.5 |
| executor | 脚本执行与环境注入 | §5.9 |
| pylib | 随执行注入的 Python 运行时库 | §5.10 |

**内部依赖**:`lifecycle → setup`、`lifecycle → runtime-check → executor`;网络事实由
lifecycle 从 Net 读取(§8.3)。三个事实来源互不可见。

**复杂度所在**。与 QGIS 相反,GEE 的环境定位是简单的——用户提供一个解释器路径,存在即可
用。它的难点在两处:**多个相互独立的事实如何合成**(本地环境、网络可达性、远端授权,
三者变化节奏与失败原因都不同),以及**如何引导用户完成配置与登录**(§5.11)。网络部分
由 Net 承担(§3.3),GEE 只读取结论。

### 5.2 配置输入

| 字段 | 内容 |
|---|---|
| `python` | 装有 GEE 客户端库的解释器路径 |
| `project` | 绑定了 Earth Engine 的云项目标识 |

两个字段都必需,但**分别检查、位置不同**:解释器决定脚本能否运行,项目标识决定运行后能否
获得授权。它们在依赖链上处于两端,合并为一种"配置不完整"状态会使指导失去针对性。

### 5.3 setup:依赖链探测

一次子进程调用完成全部本地检查,**按依赖序短路**:

| 序 | 检查 | 方式 |
|---|---|---|
| 1 | 解释器存在 | 文件存在性判定,不启子进程 |
| 2 | 依赖包齐备 | 逐个导入依赖清单中的包,收集缺失项 |
| 3 | 凭据存在 | 检查凭据文件是否存在 |
| 4 | 项目标识已配置 | 读取配置 |

四项设计要点:

**依赖清单是单一真相源。** 运行所需的不止 GEE 客户端库:运行时库(§5.10)用到影像下载库、
其瓦片下载的传递依赖、以及本地矢量读取库。只探测客户端库会让环境报告"就绪",随后在脚本
运行到一半时失败。清单同时驱动探测脚本与安装指导,新增一项自动贯通两处。

**凭据只查存在,不验有效性。** 有效性属于远端事实(§5.5)。在本地探测中验证会让网络波动
污染本地状态;而客户端库的静默认证接口语义暧昧(不抛异常、可能空转),会把"没有凭据"
误报为已有。

**探测过程完全离线。** 不注入网络路径、不注入项目标识——本地环境的结论不因网络不通而改变。

**依赖清单以数据形式嵌入脚本**,而非拼接为导入语句。包名中的特殊字符因此永远无法破坏
脚本结构。

**setup 状态集合**

| # | 状态 | 类型 | 含义 |
|---|---|---|---|
| 1 | `unconfigured` | 终态 | 未配置解释器 |
| 2 | `config-error` | 终态 | 配置文件不可解析(携带出错位置);§8.1 强制的成员,与"未配置"是两个事实 |
| 3 | `python-missing` | 终态 | 配置的解释器不存在 |
| 4 | `checking` | **中间态** | 探测子进程运行中 |
| 5 | `packages-missing` | 终态 | 依赖包缺失,**携带缺失清单** |
| 6 | `credentials-missing` | 终态 | 包齐备但机器上无凭据 |
| 7 | `project-missing` | 终态 | 前项均齐但未配置项目标识 |
| 8 | `probe-timeout` | 终态 | 探测超时 |
| 9 | `probe-failed` | 终态 | 探测异常,携带原始错误 |
| 10 | `ready` | 终态 | 本地环境完备 |

### 5.4 network:消费 Net

GEE 向 Net 注册目标端点,读取其连通性结论(§8.3 网络消费契约)。状态四值:

| 状态 | 类型 | 含义 |
|---|---|---|
| `idle` | 静默态 | 未订阅——setup 未就绪时不监视 |
| `checking` | **中间态** | 订阅后的首次探测中 |
| `reachable` | 终态 | 当前路径可达,携带路径标识 |
| `unreachable` | 终态 | 当前路径不通 |

### 5.5 runtime:远端授权校验

执行一次真实初始化并取回一个最小结果,一次验证三件本地无法回答的事:凭据仍然有效、项目
已绑定服务、接口已启用。

| 项 | 设计 |
|---|---|
| 触发 | **缓存未命中时惰性求值**,而非由事件驱动——见下 |
| 退避 | 失败后一段时间内不重试,避免反复触发远端 |
| 归因 | 从错误消息识别:接口未启用 / 权限不足 / 凭据失效 / 项目无效 / 未知;**原始消息逐字保留** |
| 有效性绑定 | 校验结果按**网络路径标识**缓存;标识不同才重取 |

#### 为什么是惰性求值,不是事件触发

本层是整个系统中**唯一带凭据、会进入远端配额与滥用检测视野**的调用,而且它要起一个解释器、
导入客户端库,单次成本以秒计。因此它的频率必须由"事实会不会变"决定,不能由"我们什么时候
方便查"决定。

**网络恢复不改变授权是否有效。** 凭据不会因为链路闪断而过期,项目绑定也不会。变的是我们能
不能去查,不是被查的那件事。把"网络转为可达"当作触发条件,等于让一次链路抖动换来一次带凭据
的远端调用——而 Net 是秒级判定的,抖动十次就是十次。

因此改为:**结果按路由标识缓存,需要时才填充**(状态合成、脚本执行前)。命中即用,不产生
任何调用。

**失效的条件是路由标识"确实不同",而不是"发生过变化"。** 掉线又回来、落回同一个出口,不使
结论失效:凭据与项目的绑定不因连通性抖动而改变,只有出口真的换了,旧结论才不再适用。把状态
跳变当作失效,等于每次链路抖动都换来一次带凭据的调用。

**缓存的代价,与堵它的办法。** 凭据可以被吊销、接口可以被关闭,而这些都不改变路由标识——
缓存因此可能长期停留在"有效"上。不为此增设周期性复查:那等于把刚省下的调用又花回去,而且
花在一件极少发生的事上。

改由**真实使用来兜底**:脚本执行时若被远端以授权类原因拒绝,**该结论立即作废并按归因更新
本层状态**。这一条不与 §8.3 冲突——§8.3 约束的是消费者不得反向影响 **Net** 的连通性判定,
而这里是本模块用自己的证据更新自己的状态,且那份证据比任何探针都更直接:它就是用户实际
经历的那次调用。

于是形成一个零成本的闭环:**不主动去问,但每一次真实使用都是一次回答。**

**runtime 状态集合**

| # | 状态 | 类型 | 含义 |
|---|---|---|---|
| 1 | `unknown` | 静默态 | 未校验,或先决条件变化后已作废 |
| 2 | `checking` | **中间态** | 校验进行中 |
| 3 | `valid` | 终态 | 授权链完整可用 |
| 4 | `failed` | 终态 | 被远端拒绝,携带归因与原始消息 |

### 5.6 三层合成

对外结论由三层事实按优先级短路合成:

```
setup ≠ ready                        → 呈现 setup 状态      (本地问题优先)
setup = ready, network ≠ reachable   → 呈现 network 状态    (网络问题次之)
setup = ready, network = reachable   → 呈现 runtime 状态    (最后是远端问题)
```

这个优先级本身即设计:**本地未配好则不谈网络,网络不通则不谈授权**。它保证任何时刻用户
只面对一个问题,也保证归因不会张冠李戴——网络不通时报"凭据无效"会把用户引向完全错误的
修复方向。

合成是纯函数:三层事实为输入,对外结论为输出,不持有自身状态。新增第四类事实时,合成函数
多读一个入参即可,无需重排既有状态集合。

### 5.7 跨层迁移

| 起点 | 事件 | 效果 |
|---|---|---|
| setup 任意 | 配置的 `gee` 块变更 / 应用启动 | setup → `checking` |
| setup 任意 | 工具重试且处于自愈态(§5.8)| setup → `checking`(带去抖)|
| setup → `ready` | — | 向 Net 注册目标并订阅;network `idle` → `checking` |
| setup 离开 `ready` | — | 退订;network → `idle`;runtime → `unknown` |
| network → `reachable` | — | **不触发校验**。若该路由标识已有缓存结论,直接沿用;否则在下一次需要时才求值(§5.5)|
| network → `unreachable` | — | runtime → `unknown`,**不尝试校验** |
| network 路径标识**变为另一个** | — | runtime → `unknown`(出口确实换了,旧校验不再成立)|
| network 掉线后回到**同一标识** | — | 沿用原结论,**不重取**——凭据与项目绑定不因连通性变化而变 |
| runtime `checking` | 校验通过 / 被拒 | → `valid` / `failed`,失败后进入退避 |
| 任意中间态 | 先决条件再次变化 | 旧结果作废丢弃(§3.4 提交协议的代际令牌)|

**lifecycle 编排**:持有状态槽并作为唯一写者;订阅配置变更与 Net 变更;按上表驱动三层
事实的获取与作废;每层结果落定即提交,不等待其余层。

### 5.8 自愈重探

`credentials-missing`、`packages-missing`、`python-missing`、`probe-timeout`、`probe-failed`
五个 setup 状态的成因**在系统的视野之外**:用户可能刚在终端安装了依赖包或完成了认证,
而这些动作不触碰配置文件,文件监控无从感知。

因此把**工具重试**当作用户发出的"请重新检查"信号:命中这五态时强制重探一次,并加去抖以
防连续重试造成探测风暴。

`unconfigured` 与 `project-missing` 不在此列:它们只能通过修改配置解决,而配置变更已由
Config 模块的监控覆盖,重复触发是冗余。

### 5.9 执行与注入

**两种模式**:内联脚本用于快速查询;脚本文件用于多步流程、需要迭代调试或值得为用户保留的
工作。

**注入内容**

| 项 | 作用 |
|---|---|
| 网络路由 | 取自 Net 的**子进程环境注入形态**(§3.3),在进程启动时施加,该次执行的全部远端访问共用它。含本机地址的直连例外——脚本的本地回调与本地服务不得经过代理 |
| 项目标识 | 供运行时库自动取用,Agent 无需在每个脚本中硬编码 |
| 运行时库搜索路径 | 前置库目录,使脚本可直接导入 |
| 故障处理器开关 | 原生扩展发生段错误时输出底层调用栈。脚本由 Agent 生成,无法为其插入代码,以环境开关达到等效 |
| 编码设置 | 非英语语言环境下的输出不产生乱码 |

**心跳契约**(GEE 特有,最关键的一条约定):执行采用**空闲超时**,而运行时库提供心跳工具。
长时操作必须以心跳包裹,否则将被判定为静默而终止。这是**脚本与执行器之间的正式约定**,
必须在工具提示词中明确写出——它不是建议,而是脚本能够完成的前提。

**输出与终止**:执行过程逐块回调;每条终止路径都保留已产生的输出并附带耗时;耗时从脚本
真正启动开始计量,不含权限确认等待。

### 5.10 运行时库

随每次执行注入的 Python 库,为 Agent 生成的脚本提供受控接口。它的价值在于**把易错的底层
细节收敛成正确的默认行为**——Agent 写出的脚本无需处理这些细节,也无从写错。

| 接口 | 消除的问题 |
|---|---|
| 初始化 | 单次初始化;失败时给出唯一可操作的指导。**脚本内不尝试浏览器授权**——服务进程无法驱动浏览器 |
| 加载研究区 | 只接受**单要素**文件(多要素直接拒绝,消除"合并还是取第一个"的歧义);自主重投影到地理坐标系,不信任第三方库对无坐标系文件的假设;**拒绝空几何与自交几何**——远端会静默接受脏数据,失败出现在很远的下游且形态诡异 |
| 覆盖度检查 | 分母以常量影像固定到研究区范围。否则影像未覆盖整个研究区时,部分覆盖会被静默计为完全覆盖 |
| 下载影像 | 先写临时文件再原子移动,不留半成品;不自动创建目录、不自动补全扩展名——路径笔误必须暴露而非被掩盖 |
| 导出到云端 | 打印任务标识(脚本被终止后任务仍在远端继续);**仅在状态变化时输出**,并以心跳维持活性,避免长任务刷出大量重复状态 |
| 心跳 | 三种形态:纯计时、按产物大小报告进度、捕获第三方进度输出并转为干净的进度行 |

### 5.11 指导结构

引导用户完成配置与登录是 GEE 模块的主要复杂度所在。本节确定其**结构**;面向 Agent 与用户
的具体文案在工具层落地阶段确定(§8.6)。

**分步推进模型**。setup 是一条依赖链,指导以"当前第 N 步 / 共 4 步"的形式呈现:用户在任一
时刻只面对一件待办事项,而非一张并列的问题清单。这与 §5.3 的短路探测同构——探测在哪里
停下,指导就从哪里开始。

**行动归属三分**。每个状态明确标注由谁执行:

| 归属 | 状态 | 说明 |
|---|---|---|
| Agent 可独立完成 | `unconfigured`、`python-missing`、`packages-missing` | 定位或创建解释器环境、写入配置、安装依赖包 |
| Agent 引导、用户执行 | `credentials-missing` | Agent 给出可复制的认证命令,并**等待用户确认完成**后再继续 |
| 仅用户可提供 | `project-missing` | 只有用户知道自己的项目标识 |

**三条硬边界**

1. **不在应用内发起浏览器授权**。服务进程无法驱动浏览器,交由用户在终端完成是唯一可靠
   路径,也是生命周期复杂度最低的路径;
2. **不臆造项目标识**。它是用户账户下的真实资源,猜测会导致远端拒绝且难以归因;
3. **网络类故障明确排除本地修复动作**。此时本地环境完整,唯一障碍在网络;指导必须阻止
   Agent 重装依赖、改写配置或重新认证——那些动作不仅无效,还会破坏已就绪的环境。

**安装指导的两条纪律**

- **以配置的解释器调用包管理器**,不推断用户使用的环境管理工具:该工具未必在可执行路径中,
  配置的解释器也未必属于当前激活的环境;
- **逐包安装**。单包安装耗时可达数分钟,合并执行会让用户面对一个长时间无反馈的过程,
  分开执行则每一包的进展都可见。

**认证命令的定位**:认证工具随客户端库安装,其位置由解释器所在环境的布局决定,需要从
解释器路径推导而非假定固定位置。

## 6. OSM 模块

### 6.1 职责与子模块

**职责**:从公共 OpenStreetMap 服务检索与下载地理数据,产出规范化的矢量成果。

**服务对象**:R4 数据获取。

| 子模块 | 内容 | 设计 |
|---|---|---|
| client | 端点选择、失败转移、限速与响应护栏 | §6.3 |
| http | 请求传输:代理套用、超时、响应大小护栏 | §6.3 |
| query | 查询构建 | §6.5 |
| search | 双引擎检索:并行询问、结果合并与排序 | §6.8 |
| convert | 结果转换与字段规范化 | §6.6 |
| geometry | 空间范围解析与几何归一 | §6.4 |
| output | 成果落盘 | §6.7 |

**依赖**:Net(仅代理告知)。不使用子进程——网络访问在进程内完成。

### 6.2 结构定位:唯一没有环境的能力模块

| | QGIS / GEE / GDAL | OSM |
|---|---|---|
| 配置项 | 有 | 无 |
| 环境探测 | 有 | 无 |
| 状态槽与指示灯 | 有 | 无 |
| 就绪门禁 | 有 | 无 |
| 可靠性归属 | 环境层——一次判定,长期有效 | **调用内**——每次调用自行解决 |

**不设状态灯是有意的**。状态面服务于"用户可以修的事";OSM 没有配置、没有本地依赖,一个
红灯只能表达"公共服务此刻不顺",既不可操作也无从修复。它的失败在调用结果中如实呈现即可。

**执行契约为请求-响应,不承诺实时展示**。OSM 的调用方是子代理,结果一次性返回后由子代理
汇报;这条判断至今成立——**界面不需要为 OSM 做实时展示,也不承诺做**。

**但下载保留一个最小的逐单元上报接口**(2026-08-16 定):`downloadFeatures` 与
`downloadObjects` 各接受一个可选的 `onProgress(settled, total)`,内核每了结一个范围 / 一个对象
调一次。这是**给前端阶段的预留物**,与 §12 挂起的那几项同类——接口先在,消费方(界面)还不存在,
真要展示时不必再动内核契约。**不做复杂实时视图这条没有变**,变的只是"内核连接口都不给"。

⚠️ `settled` 不是 `extentsDone`:前者数**已了结的**(含失败),回答"还要多久";后者数**答复了的**,
回答"拿到了什么"。两个词刻意分开,混用会让一个大量超时的下载**看起来卡在 0/5**。

### 6.3 客户端可靠性层

公共服务的不稳定是常态而非异常:单个后端可能病态数小时;各端点对不同用户网络的可达性
差异巨大;快速连续请求会被限流。可靠性因此是本模块的核心资产。

**端点池**只收录**全球全量**实例。区域受限实例会静默返回不完整结果——这比明确报错更危险。
清单为内置常量,不作为配置项:自建实例属于高级用法,不值得为其增加配置面。

**端点顺序固定分梯队,不做测量**。第一梯队是官方实例(含其两个具名后端),第二梯队才是第三方
镜像,且只有官方梯队真正失败后才会被使用。分梯队的依据是这些服务**是什么**,而不是它们在谁的
机器上跑得快:官方实例是项目自己背书的参考部署;镜像是他人捐赠的机器,可能滞后、可能由陈旧的
星球文件重建、也可能悄悄只提供区域数据——它正确时与官方无异(所以优先用它毫无收益),它错误时
调用方无从察觉。

这条**取代了按实测延迟排序**。测量意味着每个新进程在问任何人之前先去探测全部镜像:成本由每个
用户承担,而且是朝着捐赠服务器发一串握手,只为了决定不用它们。更根本的是它测错了东西——握手
衡量的是**路**,而决定能否拿到答案的是服务器**肯不肯干活**,后者只有真实请求能揭示。镜像的定位
就是备胎,那就按备胎来用。

**Net 对本模块只做一件事:告诉它这台机器有没有代理。** 有则整个模块的请求都套上,没有则直连。
这是关于**机器**的事实而非关于某台服务器的:这些都是公网普通主机,一个需要代理才能访问其一的
网络,访问其余的同样需要。判定由 Net 完成且经过真实 CONNECT 握手验证(声明的环境变量可能指向
早已停跑的代理,常见端口上的东西也可能只是个开发服务器),代价是几次回环连接,毫秒级。整次调用
在所有端点上全败时才会重新询问——那是代理可能刚启动、停止或改动的唯一时刻。

**调用期的四项机制**由 OSM 自行掌握——它们处理的是服务层面的问题,超出 Net 的认知范围:

| 机制 | 设计 |
|---|---|
| 粘性端点 | 从上次成功的端点开始。官方实例领跑新进程,但一旦它被证明不可用,每次调用都重付它的超时是调用方能感知到的浪费 |
| 逐调用失败转移 | HTTP 错误、非结构化响应体、超时均触发转移。繁忙服务器会以正常状态码返回错误页面,因此响应体的可解析性也是转移判据 |
| 轮间退避 | 遍历完全部端点为一轮。**只重试一轮**——端点池本身就是冗余,走到第二轮意味着整池刚刚全败,再问同一批服务器只在故障以秒计时才有意义,而公共实例的病态以分钟到小时计;更多轮次只会用"连得上但不应答"端点的完整预算,把同一个结论推迟数分钟 |
| 请求间节流 | 各服务维持独立的最小请求间隔时钟 |

**第四种失败:响应成功但携带软失败标记。** 服务端在查询超时等情形下会返回**正常状态码、结构
合法**的响应,并在其中附一个标记说明结果不完整。这不触发端点转移(数据仍然可用),但该次调用
必须计入不完整,并**带回服务端原话**——"超时了"与"这查询太宽跑不动"要求调用方做相反的事。
**只检查状态码与可解析性会把它当作完全成功**——这正是最危险的失败形态。

**服务健康只能由失败转移承担**。一个路径通畅但正在拒绝服务的端点,任何路径测量都看不出来,
只有第一次真实请求的失败能触发转移。

**流式字节护栏**:公共服务以分块方式传输,**响应头中不含长度**,只检查响应头等于没有检查。
必须边接收边计数,超过上限即中断——失控的查询不能拖垮整个进程。超限错误直接告知调用方
将请求拆分为更小的范围。

### 6.4 空间范围契约

范围以**带类型前缀的单一字符串**表达,四种形态:行政区标识、边界框、圆形范围、本地边界
文件。前缀显式,消除形态之间的歧义。

**超集契约**是本模块最重要的数据正确性规则:

> 对边界的任何空间化简,其结果必须是原边界的**超集**。

理由不对称:多下载的部分可以事后精确裁剪,**少下载的部分则永远无从发现**。边界附近的要素
静默丢失,是数据获取工具最坏的失败模式——使用者不会知道自己少了什么。

实现为三级降级:

| 情形 | 处理 | 性质 |
|---|---|---|
| 顶点数在服务端预算内 | 原样传递 | 精确 |
| 超出预算 | 退化为**凸包** | 近似,数学上保证为超集 |
| 凸包仍超预算 | 退化为边界框 | 近似,超集 |

**不使用常规的线简化算法**:这类算法会向内切割边界,在边界附近造成真实的数据丢失。凸包
虽然多包含区域,但偏离方向是安全的。

另两条:**任何非精确路径都要标记**——标记之后由**内核自己**把超集裁回边界(`osm/intersect.ts`),
在写盘与统计之前完成,所以报告里的数字描述的就是磁盘上的东西。裁剪一度是工具层的活,靠 QGIS 做;
那让一个没有环境依赖的能力凭空依赖了一个环境,而且报告引用的是裁剪之前的计数。标记本身仍然要留,
因为**混合 extent 的调用里,来自其他 extent 的要素合法地落在边界之外**;**多部分边界的每个外环都
进入查询**,而非只取面积最大的那个——研究区由多个分离部分构成是常见情形。

### 6.5 查询构建

| 项 | 设计 |
|---|---|
| 名称匹配 | 非锚定子串匹配——官方名称常带校区、分店等后缀 |
| 字面转义 | 名称中的正则元字符必须转义,否则会破坏查询结构或造成静默失配 |
| 大小写折叠 | **仅对含拉丁字母的模式启用**。中日韩文字无大小写之分,开启只是让服务端多付代价 |
| 类型配额 | 每种要素类型各自设上限,且**关系类型优先输出**——否则在广域名称检索中,噪音会在任何一个关系出现之前耗尽全局配额 |
| 已知限制 | 部分派生查询形态在公共服务上已不再受支持;命中时**明确拒绝并说明**,而非静默返回空集 |

### 6.6 转换与字段契约

**逐元素隔离转换**。每个元素独立转换,单个元素的装配失败只影响它自己。整批转换存在一种
已被确认的静默丢失模式:一个装配失败的关系会连带吞掉其成员要素。整批形式**仅在只针对
单个对象时使用**。

**大型关系的装配校验**。以装配所得的顶点数与原始节点数作合理性比对,明显偏低即判定为可疑
并拒绝——静默的部分边界比失败更糟,使用者会把残缺边界当作完整边界继续分析。

**字段契约**:要素属性与标签是同一个字段集。

| 层 | 内容 |
|---|---|
| 核心列(恒有)| 标识、类型、名称、类别 |
| 类别 | 由分类键推导为单一"键=值"字符串,避免与通用的类型字段冲突 |
| 保留 | 核心列 + 查询涉及的标签键 + 调用方点名的键 |
| 丢弃 | 其余标签,但**按键计数上报**,使调用方知道丢弃了什么并可按需重取。⚠️ 当前实现把键列表截到 30 个且不说明还有多少,调用方因此无从知道列表被截过——待界面阶段一并修 |
| 无损模式 | 通配请求时,全部标签以紧凑形式保留在单独一列 |

一处细节:转换库会将服务端的元数据混入属性。这些不是标签,须排除在字段集之外。

### 6.7 落盘契约

| 规则 | 理由 |
|---|---|
| **按几何族分文件**,绝不写入混合几何 | 混合几何文件是下游的硬隐患:GIS 软件按族处理、格式转换会失败、调用方也会困惑 |
| 同名时**编号而非覆盖**,并检查同族兄弟是否已被占用 | 撤销够不到地理数据(§10.1 #6),不覆盖是唯一防线。此条曾写作"重跑时清理陈旧的兄弟文件",清理已被编号取代 |
| 坐标系统一 | 与数据面一致,调用方无需判断 |
| 失败时保留**已获得的部分结果**并标记 | 多范围下载中,部分成功远比全部丢弃有用 |

### 6.8 四类能力与工作流

| 能力 | 输入 | 输出 |
|---|---|---|
| 检索 | 地名或要素名 | 候选清单,含标识、类型、位置 |
| 侦察 | 范围 + 标签组合 | 数量统计,或某标签键的取值分布 |
| 按标识下载 | 一组标识 | 行政边界等命名实体 |
| 按范围下载 | 范围 + 标签组合 | 该范围内的类别数据 |

四者构成一条工作流:**检索定位 → 侦察算账 → 下载**。侦察环节的价值在于下载前先知道数据
量级——公共服务对超量查询的反应是超时或截断,而非明确报错。

按标识下载采用**批量查询并内联几何**的方式获取,而非逐对象抓取后跨元素拼接:后者在大型
关系上会静默产生残缺边界。

#### 检索是双引擎

检索并行询问两类服务,合并结果后统一排序:

| 引擎 | 擅长 |
|---|---|
| 地理编码服务 | 模糊匹配:词序颠倒、缺少后缀、带地址上下文的输入 |
| 要素查询服务 | 对官方名称做字面匹配:能命中校区、括号后缀等变体,并展开成员名称不同的组合关系 |

两者的召回集差异很大,**任一单独使用都会漏**。合并后的排序需要体现四类信号:被两个引擎共同
命中(最强的置信信号)、服务给出的重要度、要素类型(面状实体优先于线、点),以及对同名交通
站点的**降权**——地名检索中它们几乎总是噪音,却常在数量上压倒真正的目标。

检索另有若干条降级路径:类别筛选导致零结果时去掉筛选重试并在客户端补过滤;命中组合关系时
展开其成员;候选中没有面状实体时,用地理编码服务返回的规范名反查要素服务。每一条都是**尽力
而为**,失败不影响主结果。

#### 几何归一化

下载支持两种几何形态:**原样**与**代表点**。后者把每个要素塌缩为一个点,并在属性中记录其原始
几何类型,使转换可追溯。

这不是一个便利选项,而是一条正确性规则:**"纯点兴趣点数据"的正确做法是全类型收集再归一化,
而不是只请求点类型要素**。现实中大量设施是以面的形式测绘的,只取点类型会静默丢掉它们——而且
往往丢掉的是多数。

## 7. GDAL 模块

### 7.1 职责与子模块

**职责**:为前端预览生产矢量与栅格数据。它是四个能力模块中唯一直接服务人机交互的模块,
其产物的生产速度直接构成用户体验。

**服务对象**:R1 的前端侧预览。

| 子模块 | 内容 | 设计 |
|---|---|---|
| env | 工具链发现、双轨可用性判定、子进程环境组装 | §7.3 |
| inspector | 元信息提取与坐标系解析 | §7.4、§7.5 |
| vector | 矢量数据生产:重投影、分页 | §7.4 |
| raster | 栅格预览生产:重投影、降采样、着色、编码 | §7.5 |
| cache | 产物缓存与生命周期 | §7.6 |
| access | 外部路径的边界判定 | §7.8 |

### 7.2 核心矛盾与应对

用户在文件树中点击一个数据文件,期待像打开图片一样立即看到内容。但地理数据与图片相差
数个数量级:一景遥感影像可达上万像素见方,一个矢量图层可含数十万要素,且都不在网页地图
可直接使用的坐标系中。

**数据规模与交互期待之间的落差,是本模块全部设计的出发点。** 四条应对策略构成模块骨架:

| 策略 | 手段 |
|---|---|
| 分离轻重 | 元信息与重载荷分两次生产,前端先渲染骨架再填充内容 |
| 预先降维 | 服务端完成重投影与降采样,前端拿到的即是可直接使用的产物 |
| 复用成果 | 产物落缓存,同一文件再次打开即时返回 |
| 收敛并发 | 同一产物的并发请求合并为一次生产 |

### 7.3 状态与门禁

探测为纯文件存在性检查,毫秒级完成、不启子进程,因此**没有中间态**。

状态按**双轨**判定:栅格轨与矢量轨依赖的工具集不相交。

| # | 状态 | 含义 | 端点反应 |
|---|---|---|---|
| 1 | `unconfigured` | 未配置 | 全部预览端点返回未配置错误 |
| 2 | `config-error` | 配置文件不可解析(携带出错位置)| 同上,指明是文件语法错误而非未配置 |
| 3 | `dir-missing` | 配置的目录不存在 | 同上,指明路径错误 |
| 4 | `unusable` | 目录存在但两轨均不齐(携带缺失清单)| 同上,指明安装不完整 |
| 5 | `raster-only` | 仅栅格轨齐备 | 栅格预览正常;矢量端点单独返回能力缺失 |
| 6 | `vector-only` | 仅矢量轨齐备 | 反之 |
| 7 | `ready` | 两轨齐备 | 全部可用 |

第 2 项是 §8.1 强制的成员,**且不可与第 1 项互换**:用户确实配了,只是文件读不了,而"未配置"
的指导会让他去做一件已经做过的事。

**门禁按轨施加**,这与 QGIS 的统一门禁(§4.9)相反,原因在于两者的事实结构不同:

| | QGIS | GDAL |
|---|---|---|
| 门禁粒度 | 统一 | 按轨 |
| 依据 | 三类能力共享同一个环境,环境的可用性是同一个事实 | 两轨依赖不相交,一轨缺失不影响另一轨 |

**状态迁移**只有一条:配置变更或应用启动触发重探,落入七态之一。无中间态、无定时轮询、
无自愈——可用性只取决于本机文件,而文件变化由配置监控覆盖。

数据面失败不影响 Agent 的地理能力(§7.9),只影响前端预览。

#### 子进程环境组装

发现工具链只解决"能不能启动",还要解决"启动后能不能工作"。工具链的资源文件与依赖库的定位
方式**按平台分野**:

| 平台 | 做法 |
|---|---|
| macOS | **不注入任何变量**。该平台的安装形态依靠编译期记录的搜索路径自行定位依赖与资源 |
| Windows | **必须显式注入**。安装器把资源文件放在安装内的约定位置,但不做任何全局注册 |

Windows 侧需要注入四类:

| 类别 | 说明 |
|---|---|
| 投影数据目录 | **两个变量名同时写入**(不同版本读取不同名称)。取值须在若干候选中选出**确实含有投影数据库文件**的那个,而非第一个存在的目录 |
| 数据资源目录 | 同构的候选选择 |
| 可执行搜索路径 | 前置工具目录,使同级依赖库在加载时可解析 |
| 文件名编码 | 强制以 UTF-8 解释文件名,否则非拉丁字符路径在库内部打开失败——即便进程层面已正确传入 |

候选集须覆盖该平台上并存的几种安装布局。**缺少这一层,任何涉及投影的操作都会失败于"找不到
投影数据库",而失败点距离真正的成因很远。**

**工具链来源的一条平台约束**:macOS 上应使用独立安装的工具链,不使用随桌面 GIS 分发的那一
份——后者的版本通常明显滞后,其图像编码器存在已知缺陷,会使单波段预览的色彩通道塌缩为色带
最低档,产出一张看似正常实则完全错误的图。Windows 上随桌面 GIS 分发的版本是当前版本,可以
直接使用。该约束进入未配置状态的指导信息。

### 7.4 矢量管线

**两阶段生产**

| 阶段 | 产物 | 手段 | 成本 |
|---|---|---|---|
| 元信息 | 要素总数、几何类型、字段名、坐标系 | 只读文件头的摘要查询 | 廉价,不解析要素 |
| 内容 | 目标坐标系下的完整数据 | 转换并重投影 | 与文件规模成正比 |

元信息阶段设一条回退:摘要查询失败时,退回完整转换并从产物中提取元信息,同时将内容一并
落盘——避免下一阶段重复同一份工作。

**统一重投影到网页地图坐标系**。前端不执行任何投影运算,这是数据面对前端的核心承诺,也是
前端能够保持简单的前提。

**分页三级回退**

```
内存中已解析的要素  →  磁盘上的完整产物(解析后入内存)  →  引擎直查(带偏移与限量)
```

第三级的价值在于:文件极大、完整产物尚未生成时,用户仍可翻页浏览属性,不必等待整份转换。

**几何类型的准确性是硬契约**。前端据此选择渲染方式——纯点数据走高性能路径,其余走通用
路径——报告错误会导致渲染方式选错。

**内容阶段需要服务端护栏**。完整产物随文件规模线性增长,而它是一次性整体返回的。要素数量
超出阈值时应直接拒绝并说明,由调用方改用分页。把这条约束留给前端自觉是不够的:数据面是
公开端点,任何调用方都能触发,而一次超量响应足以压垮渲染进程。

### 7.5 栅格管线

**两阶段生产**

| 阶段 | 产物 | 关键判定 |
|---|---|---|
| 元信息 | 尺寸、波段数、坐标系、范围、各波段统计量 | **地理参考来自哪里**(§7.9):仿射变换 / 控制点 / RPC / 地理定位数组 / 仅坐标系 / 无。判定与工具面共用同一个函数,五处皆空(`none`)才是普通图像,不进入预览管线 |
| 预览 | 图像 + 其地理范围 | 见下 |

元信息查询有**两个不可省的开关**,它们各自堵住一个坑:

| 开关 | 作用 |
|---|---|
| 近似统计 | 拉伸需要各波段的最小/最大/均值/标准差。**精确统计要遍历全图**;近似统计改为抽样,实测无论文件多大都在 0.1 秒量级,而拉伸对精度并不敏感 |
| 禁用持久化辅助信息 | 工具链默认会把算出的统计量**写成附属文件放在源数据旁**。这与概览是同一类问题(§12),必须显式关闭,否则一次只读的元信息查询就变成了对用户数据目录的写入 |

**预览生产四步**

| 步 | 动作 | 要点 |
|---|---|---|
| 1 | 波段选择 | 按序判定:透明通道识别 → 显式色彩标注 → 波段描述命名 → 按波段数回退 |
| 2 | 重投影与降采样 | 转为网页地图坐标系,施加双上限约束,并**生成透明通道**以承载空值区域。**源文件自带概览时自动采用**(遥感产品通常自带),提速可观且不花任何代价 |
| 3 | 拉伸与着色 | 多波段:三通道各自线性拉伸;**单波段**:灰度拉伸后套用色带,并与透明通道重新合成 |
| 4 | 编码 | 编码为前端可直接使用的图像格式 |

**内核不生成概览。** 源文件已有则用,没有则直接按全分辨率重投影。

这一步曾经存在过,它的经历值得完整记下来,因为**结论与直觉相反**:

1. 它作为性能优化被引入,依据是"重投影要遍历全分辨率像素并逐像素做坐标运算,是首帧的主要
   成本";
2. 后被安全审计判为红线问题——它对**源文件**执行写入,使一次只读的预览请求变成状态变更
   (§7.6);
3. 审计给出两条出路:改在缓存目录的描述文件上生成,或取消该优化;
4. 实测选了第二条。

**为什么第一条不该选:** 生成概览的代价是把源数据**完整读一遍**——正是重投影本来就要做的
那一遍。它换来的只是把"逐像素坐标运算"替换为"块平均",而实测这两者代价相当。于是概览路径
的总成本恒 ≥ 直连路径,与降采样倍数无关:倍数增大只让后续那次小重投影趋近于零,而那一次
全读是常数。

实测覆盖七种文件形态(Float32/Int16/UInt16、LZW/DEFLATE/未压缩、分块式/条带式、自带概览
/无概览)与七个降采样倍数(1.26× 至 30×),**无一例外**,两条曲线从不相交。

**还有一层更根本的理由:预览产物本身有缓存。** 同一文件第二次打开直接命中缓存,不会再有
第二次重投影——那笔预建成本永远没有摊销的机会。这是它与 GIS 桌面软件的关键差异:后者反复
在同一份数据上缩放漫游,概览能摊销无数次。

三条约束:

- **双上限降采样**:最长边与总像素数各设上限,**只缩不放**。任一上限触发即在产物元信息中
  标记"已降采样",前端据此告知用户当前并非全分辨率;
- **透明通道必须贯穿到底**:空值区域应当透明,而非被着色为有效数据。单波段路径尤其需要
  注意——着色环节会丢弃透明通道,必须显式重新合成;
- **中间产物使用描述文件而非像素拷贝**,且只存在于该文件的缓存目录内,不产生额外的数据
  搬运。

### 7.6 缓存与产物归属

**缓存键**:文件路径 + 大小 + 修改时间 + 环境配置指纹。由多个文件构成的数据格式,其附属
文件的大小与修改时间一并计入——任一附属文件变化都应使缓存失效。环境配置指纹计入键内,
使更换工具链版本后的旧产物自动失效。

**生命周期**:全部产物在**应用启动时整体清空**。两条理由:

1. 缓存不随使用无限增长,无需容量核算与淘汰逻辑,也不会积累历史键值;
2. 每次启动都从冷状态开始,使实测反映**真实用户的首次体验**。保留缓存会让重复测试跑在
   热状态上,首屏耗时、进度呈现、中间态是否可见等问题将不再可复现。

**并发合并**:同一产物的并发请求合并为一次生产,请求方共享同一次结果。

**内存层**:已解析的矢量要素单独缓存,避免同一文件被反复解析;按数量上限与最近最少使用
淘汰。

**产物归属:全部生成物写入应用缓存目录,不写入用户的数据目录。**

这条约束的分量来自它的反面:数据面的预览端点是**只读 GET**,而工具链的若干默认行为会往源
数据旁写附属文件(概览、统计量)。一旦发生,一次读取就变成了状态变更——它会无声地改动用户
的数据目录与版本库工作树,并且与路径逃逸叠加时可以波及项目之外。

因此本模块**不对源文件执行任何写操作**,也不依赖工具链的默认落点。若将来确有中间产物必须
生成,做法是在缓存目录内建立一个指向源数据的描述文件,对该描述文件操作——产物随之落在缓存
内。此路径已验证可行,当前没有消费者。

**这条约束同样约束工具面的读取**(§4.13),两侧各自以自己的方式关掉 PAM:数据面在每次
命令行调用上加 `--config GDAL_PAM_ENABLED NO`,工具面在读取脚本的子进程环境里设同名变量。
`GDAL_PAM_PROXY_DIR` 不是替代方案——它对**用户有写权限的位置无效**,而那正是用户数据所在。

### 7.7 HTTP 契约

| 端点 | 请求 | 响应 |
|---|---|---|
| `GET /geo/vector/meta` | `path` | `{source, feature_count, geometry_types[], projection, properties[]}` |
| `GET /geo/vector` | `path` | `{content}` — 目标坐标系下的矢量数据 |
| `GET /geo/vector/page` | `path, offset, limit` | `{features[], total, offset, limit}` |
| `GET /geo/raster/meta` | `path` | `{georeference, projection, width, height, band_count}` —— `georeference` 是**种类**(§7.9 列全),不是布尔 |
| `GET /geo/raster/image` | `path` | 二进制图像,预览元信息随响应头传递 |

两项设计:

**图像走二进制而非内嵌编码**。预览图像可达数兆,内嵌进结构化响应需经文本编码(体积增加
约三分之一),且两端各需一次额外转换。预览元信息(地理范围、所选波段、是否降采样、尺寸)
随响应头传递,前端一次请求即同时取得图像与其地理定位。

**错误必须结构化**:路径越界、文件不存在、格式不支持、工具链失败各有其标识。数据面直接
服务界面,区分这些情形是界面能做出正确反应的前提。

### 7.8 安全边界

所有路径参数**必须落在工作区范围内**,越界即拒绝。数据面是唯一接受外部路径输入的出口面,
这条检查是它的必要条件。

**字符串层面的包含判断不够**,这是旧版审计判定的红线之一:工作区内的符号链接可以指向机器上
任何位置,路径名全程在界内,而字节来自界外。因此**边界、目标文件、以及多文件格式的每个附属
文件都要先解析到真实路径,再判边界**——只判被点名的那一个,等于允许属性表来自任意位置。

两条相关约定:

- **"越界"与"不存在"是两个不同的事实**,不可互相顶替。把越界报成找不到文件,会让调用方去
  找一个并不存在的拼写错误;
- **路径检查先于环境门禁**。一个本就不该被允许的请求,不应该从回答里得知这台机器有没有装
  工具链。

### 7.9 双引擎关系

R1 的两个消费场景走**完全独立的两条管线**:

| | 工具预览(§4.13)| 数据面预览(本章)|
|---|---|---|
| 环境 | QGIS 的 Python | GDAL 命令行 |
| 消费者 | 模型 | 前端 |
| 输出 | 图像附件 | 图像 + 地理范围 |
| 坐标系 | 原生像素空间 | 网页地图坐标系 |
| 缓存 | 无 | 有 |

**两者不共用任何依赖**:只安装 QGIS 的用户,Agent 能力完整;只配置 GDAL 的用户,前端预览
完整。二者共享三条语义规则——波段选择、拉伸、透明与空值处理——**各自实现**。

**其中两条以共享用例在两侧分别锁定**(`test/geo/raster-rules.test.ts`):波段选择与拉伸都是
纯函数,测试把 Python 侧的两个函数**从脚本源码里原样抽出来**、喂一个假的 GDAL 执行,再和
TypeScript 侧回答同一份用例。所以答的是**上线跑的那份代码**,不是它的副本;production 一行
未动,锁整个住在 `test/` 里。每条用例同时比对**钉住的期望值**与**另一侧的答案**——只比期望
值,两边一起改会蒙混过关;只比彼此,两边会一起漂走。

⚠️ **第三条锁不住,且不假装锁得住**:透明与空值处理不是纯函数——Python 侧是 numpy 逐像素造
掩膜,TypeScript 侧是拼一段 VRT XML 交给 GDAL。同一个意图的两种表达,没有可比的输入输出,要
比就得真跑 GDAL。**这一条仍然只能靠评审**,而它恰恰是「nodata 必须靠 alpha=0 透明、不能靠
RGB 哨兵值」那条铁律所在。

预览尺寸不在共享之列:两侧的上限是**有意不同**的(界面要能放大看,模型不需要),各自持有
自己的常量。

**地理参考判定不在这三条之列,它只有一份。** 判定不需要 GDAL,只需要五个事实(仿射变换、
坐标系是否存在、控制点数、有无 RPC、有无地理定位数组),而两条管线都能把事实**报上来**——
Python 脚本放进自己的 JSON,`gdalinfo` 经 inspector 解析。所以规则留在 `geo/georeference.ts`
一处,两侧共用。两份实现靠测试拉平,仍会在测试没覆盖到的地方漂;一份实现漂不了。

**判据偏向放行**:五处证据但凡有一处便是地理数据,五处皆空才是普通图像。反向判错的代价是
拒掉用户未正射的原始影像(它们正是"无变换 + 有 RPC/控制点"),而那不会报错——与 §6.4 对
超集的取舍同一个道理。

**一条规则也治不了的差异**:两条管线用的可能不是同一个 GDAL——工具面是 QGIS 自带的,数据面
是独立发现的命令行工具链,同一台机器上版本可以不同,驱动能力与边角行为随之不同。出现
"同一文件两侧显示略有出入"时,先对版本,再怀疑规则。

## 8. 横切契约

契约是模块之间的正式接口。契约的变更即接口的变更。

### 8.1 状态契约

各能力模块的环境状态遵循统一形式:

- **判别联合**:以状态标识区分,附带字段随状态变化;
- **每个状态集合都含 `config-error` 成员**:§3.1 规定配置文件不可解析时全部块进入错误态,
  该事实必须在每个模块的状态里如实可见,并携带出错位置;
- **中间态显式存在**:探测、构建、校验过程在状态集合中有对应成员;
- **诊断随状态携带**:失败状态携带定位问题所需的结构化信息;
- **表现形式由模块自定**:状态到视觉呈现的映射属于模块的领域判断。

### 8.2 执行契约

工具在不同状态下调用能力模块时的统一行为:

| 状态档位 | 行为 |
|---|---|
| 中间态 | 等待其落定(带上限),落定后按结果继续 |
| 未就绪 | 返回结构化环境错误,携带状态标识与指导信息 |
| 就绪 | 执行,并将已验证的环境对象传递至执行入口 |

### 8.3 网络消费契约

**无论消费到哪一层,有四件事永远不归消费者**:决定何时探测与多久复验、实现探测方式、判断
某次失败是否属于网络问题、设定判定阈值与恢复策略。网络状态是消费者的输入,不是它的计算
对象;消费者执行期遇到的失败经各自的结果通道返回,**不反向影响 Net 的判定**——Net 的结论只
建立在它自己的验证之上。

消费的**深度**则分两档,而决定用哪一档的不是模块的偏好,是**它有没有状态槽**:

| 档 | 消费者做什么 | 谁在用 | 为什么是这一档 |
|---|---|---|---|
| 完整 | 注册目标、订阅连通性、按路径标识失效自身缓存 | GEE(§5.4) | 它有状态槽,要向用户显示"网络不通",连通性是它对外事实的一部分 |
| 仅路由 | 只问"这台机器有没有代理" | OSM(§6.3) | 它**没有状态槽**(§6.2),没有任何地方需要显示连通性;而它自带端点梯队与失败转移,单次请求的成败由它自己处置 |

**这两档不是历史包袱,是同一条判据的两个结果**:模块若要把连通性呈现给用户,就必须消费 Net
的判定,否则它显示的是自己猜的;模块若不呈现,再去订阅一份它不使用的结论,只是让两处状态有
机会漂移。

### 8.4 超时策略

超时不是一个统一的值,而是一族策略。选用哪一档,由一个判据决定:**谁控制输出的节奏**。

| 输出节奏的控制者 | 策略 | 适用 |
|---|---|---|
| **内核**——脚本由我们编写,行为完全已知 | **固定总时限** | 环境探针、启动器导出、目录导出、依赖探测、远端校验、命令行调用 |
| **第三方**——被调用的实现自行决定是否产生输出,我们无法插手 | **空闲时限,值由调用方给定** | 算法执行(§4.12)|
| **调用方**——脚本由调用方生成,它有能力主动产生输出 | **固定空闲时限 + 心跳契约** | 脚本执行(§5.9)|

中间一档的要害在于:被调用的实现可能整段沉默,而沉默时长与任务规模相关。内核无从预估,
只有发起调用的一方了解本次任务的性质,因此时限必须由它给定。

第三档之所以能固定时限,是因为脚本由调用方生成——它可以在长时操作外包裹心跳。契约由此从
"内核猜一个足够大的值"转移为"调用方保证产生输出",后者可靠得多。

**结算兜底与上述三档正交**(§3.2):它不判断任务是否正常,只保证调用必然返回。

#### 呈现语义可以简化,但只能向宽松偏离

面向调用方的参数语义不必是实现的精确描述,但必须满足一条约束:

> **实现的行为必须比呈现的语义更宽容,绝不更严格。**

这条约束区分了有益的简化与埋下的陷阱:

| 关系 | 后果 |
|---|---|
| 呈现严格、实现宽松 | 调用方按呈现推理,得到的只会是意外的成功 |
| 呈现宽松、实现严格 | 调用方按呈现推理,会撞上无法解释的失败 |

**算法执行的时限参数是这条约束的实例**:它以"总时长"呈现,实际是空闲时限。如实呈现反而
有害——调用方若知道这是"最长无输出时间",会推理"健康的任务应频繁产生输出"而给出较小的值,
从而杀死本就整段沉默的正常算法;而"总时长"的框架天然使其给出宽裕的值,那正是空闲时限
需要的。两种情形下实现都比呈现宽松:会报告进度的算法可运行超过该时长,沉默的算法获得的
额度与调用方预期一致。

### 8.5 消息通道

| 消息类别 | 通道 | 语义 |
|---|---|---|
| 环境状态 | 宿主事件通道 + 快照端点 | 整体替换,变化时发布 |
| 执行过程 | 宿主工具通道 | 流式增量,绑定单次调用 |
| 预览数据 | HTTP 端点 | 请求-响应 |
| 运行日志 | 宿主日志体系 | 排障用途 |

### 8.6 诊断与指导契约

失败状态携带两类信息,消费者不同:

| 类别 | 消费者 | 内容 |
|---|---|---|
| 结构化诊断 | 用户界面 | 定位问题所需的事实:路径、版本、检查项结果、原始错误 |
| 指导信息 | Agent 与用户 | 当前状态下的下一步动作,精确到单一步骤 |

指导信息的具体形态在工具层落地阶段与工具提示词一并确定。

## 9. 对外接口

### 9.1 工具面

以门面 API 形式提供给工具层:状态快照,以及各能力模块的**校验**与**执行**入口(QGIS 另有
算法检索,GDAL 另有预览生产)。

一条跨模块的硬性形态:**校验返回已验证的环境对象,执行入口接收该对象**,而非各自查询状态。
这消除了判定通过到进程启动之间配置被修改的时间窗口(§4.9)。

**第二条硬性形态:执行的两路输出分开。** 流式回调只透出脚本自己的输出(前端实时渲染),
环境头与终止横幅只进返回值(Agent 归因用)。内核交出的是**结构化事实**而非拼好的文本——
合流后前端只能靠字符串匹配把它剥回去,而脚本打印的内容随时可能撞上那个匹配。

### 9.2 状态面

三个环境状态事件经宿主事件通道广播,配套一个快照端点供客户端接入时获取全貌。事件载荷
即状态对象本身。

**订阅与快照之间存在顺序契约:必须先建立订阅,再取快照。** 反过来会留下一个窗口——在"快照
已读"与"订阅已建立"之间落定的状态变化,两条路径都收不到,客户端会停在过期状态且无从察觉。
状态面由两个独立调用组成,这个顺序因而是消费者的责任,须在契约中写明。

同一理由下,**每次重连都要重新取快照**:断连期间错过的变化只能靠快照补齐。

### 9.3 数据面

预览数据经 HTTP 端点提供,包含矢量元信息、矢量内容、矢量分页、栅格元信息、栅格图像五类
资源,以及状态快照。完整契约在 GDAL 模块的详细设计中确定。

## 10. 宿主集成

### 10.1 注入点

| # | 位置 | 内容 |
|---|---|---|
| 1 | 事件清单 | 注册三个环境状态事件 |
| 2 | HTTP API 聚合 | 数据面 API 并入根 API |
| 3 | 服务路由层 | 数据面处理器并入根路由层 |
| 4 | 服务图 | 挂载 GeoKernel 全局节点(单节点,聚合各子模块) |
| 5 | **文件分类学** | GIS 文件扩展名与附属文件的共享定义 |
| 6 | **项目快照排除** | 地理数据不进快照仓库 |
| 7 | **文件监视忽略** | 地理格式的事务与锁文件不触发监视 |
| 8 | **通用内容端点** | 尺寸上限 |
| 8b | **关停信号** | 服务进程的终止信号处理中调用同步清扫 |
| 9 | 工具注册表 | 注册地理工具,并定义其权限分组 |
| 10 | 文件读取工具 | 地理数据文件的读取引导 |
| 11 | 会话压缩模板 | 地理上下文保留项 |

第 5–8 项容易被漏掉,因为它们不在 GeoKernel 内部,却是它能正常工作的前提:

| 项 | 不做的后果 |
|---|---|
| 文件分类学 | 后三项各自维护一份扩展名清单,必然漂移。它同时是三个消费者的共同依赖,**但每个消费者只能使用其中特定的几类**——无条件生效的排除规则不能使用那些同时被非 GIS 场景占用的泛化后缀,否则会误伤用户的普通文件 |
| 项目快照排除 | 遥感影像与矢量数据进入快照仓库,体积失控 |
| 文件监视忽略 | 地理数据格式的事务日志、锁文件、自动保存文件持续变动,使监视器不断触发 |
| 通用内容端点 | 该端点无上限地整份读取任意文件;一次对大文件的重复请求即可耗尽渲染进程内存 |
| 关停信号 | 桌面壳关闭服务进程时,正在运行的地理进程被孤儿化并继续占用资源,而用户已看不到它们(§3.2 进程走失)。**桌面壳一侧同样要杀进程树而非只杀服务进程本身** |

第 9 项的权限分组是**能力隔离的唯一实现处**:工具对所有 Agent 无条件在册,靠分组规则决定谁
可见。该处的改动面极小(一处解析逻辑的接入),也因此极易在宿主升级中被覆盖——绊线测试必须
覆盖它。

其余部分为纯新增文件,与宿主内核无冲突面。每个注入点配套绊线测试,验证其在宿主内核升级
后依然存在。

### 10.2 生命周期

GeoKernel 以全局节点形式挂载,每个服务进程构建一次,与工作目录无关。启动探测以后台任务
形式发起,不阻塞服务启动。

### 10.3 运行时约束

全部代码使用 Node 标准 API,确保在 Electron sidecar 与命令行两种运行时下行为一致。

### 10.4 构建链

Python 脚本经构建期序列化为模块常量,运行时物化到临时位置执行。生成物纳入版本控制,
构建前自动刷新。

## 11. 移交契约

内核提供能力,不提供呈现。以下是旧版工具层中**不能静默消失**的职责(对照审计产出,§8.6 的
具体化)——内核交出去,工具层必须接住。本节是**契约的正本**;这些职责由谁承担、放在哪里,
见 TOOLS.md;各部分的实现现状见 OVERVIEW.md §7。

标 ⚠️ 的条目,是实现过程中发现契约本身需要修正的地方。

- 环境头快照:入口取一次、门禁检查后重取一次,前缀于每条**返回**,**绝不进流式回调**
  (§9.1 第二条硬性形态);就绪档的渲染数据源是状态面 `ready` 携带的解释器/版本/轨道事实;
- 参数 JSON 解析失败的归因文案("QGIS 未被调用,这是工具调用格式错误"+ 可用示例);
- 中间态的"等待落定(带上限)"(§8.2)——门禁现在即时返回中间态,工具层不等则冷启动首调用观感回退;
- 五种终止路径的横幅(含崩溃横幅的系统崩溃报告器解释)、耗时页脚、`drainIncomplete`/`truncated` 的呈现。⚠️ **只对执行类工具成立**:ReadGeoData 没有 spawn 的五种结束方式,它只渲染 `abort`,其余归 `error_code`——套用五种会造出一个不存在的区分;
- 空闲时限参数以"总时长"语义呈现(§8.4 的有意偏离);
- 结构化错误提取(`GeoOutput.structuredError`)接在非零退出的输出上;
- 毫秒级预检提示(`precheck`)与脚本内警告的合并呈现;运行脚本已不再内嵌工具名指引,指引由工具层补;
- 文档深链按 §4.11 存档的规则推导;
- 权限申请、执行 cwd 取实例目录、流式 metadata 的 3 万字符截断。⚠️ 清单原先点名的 `geo_processing` / `geo_read` 是**旧版键名**;新版用四个扁平键 `geodata` / `qgis` / `osm` / `gee`(TOOLS.md §4);
- 状态面快照缺"算法计数"一类聚合。⚠️ **"前端按目录查询接口现取"做不到**:目录查询没有 HTTP 出口,`catalog.groups()` 是进程内服务。要补,只有两条路——加一个端点,或让快照携带计数;
- **相近候选提示需自行接线**:目录的模糊查询与预检的"你是不是想找"两端形状兼容,但内核不替
  工具层串起来——不接则未知算法只剩运行脚本内嵌的兜底提示;
- **算法元数据要随门禁一并取走**:环境对象是快照移交,目录不是——它是活引用,新一轮配置变更
  会清空它。过了门禁再去查目录,可能查到空;
- **超长参数需检长**:参数经命令行传递,Windows 有总长上限。内联大几何或长表格的参数集可以
  撞线,而撞线的表现是无法归因的启动失败。⚠️ 实现检的是**入参串本身**而非拼装后的命令行,
  以 24 000 对 32 767 的固定余量近似——命令行里还有引导脚本与算法 id,余量是留给它们的。

GEE 另有三条,前两条**不接线则内核的契约不成立**:

- **执行失败后必须回报授权类拒绝**(`reject`)。内核提供入口,但没有任何东西会自己调用它——
  不接,§5.5 那个"不主动去问、每次真实使用都是一次回答"的闭环就只存在于文档里,缓存会长期
  停在过期的结论上。接线处是判定远端拒绝之后,而非捕获异常之时;
- **心跳契约必须写进工具提示词**。执行采用空闲超时,长操作不以心跳包裹就会被判静默而终止。
  §5.9 把它定为脚本能够完成的前提而非建议:提示词不写,Agent 就会持续写出注定被终止的脚本。
  提示词里的那个秒数**不能是自己写的常数**——它必须由绊线钉在 `IDLE_FLOOR_SECONDS` 上,
  否则内核调一次下限,提示词就开始教 Agent 写注定超时的脚本;
- 分步指导与行动归属(§5.11)在旧版是一组文案函数,不能随内核替换而消失。

还有一条横跨全部能力:

- **凡有凭据可能露出的出口,都必须过 `NetRedact`**。它是为状态事件、诊断包、日志这三处准备
  的。内核自身不泄漏并不靠它:`routeId` 按构造就不含凭据,QGIS 诊断的环境视图按白名单过滤
  (代理变量不在其中),GEE 的环境对象按 §9.1 不出内核——**所以这三处出口一旦建起来,防线就
  整个落在调用方手里**,而在此之前它是一个没人调用的函数,不会因为不被使用而报警。
  ⚠️ 有过一次实证,值得记在这里:`net/discovery.ts` 曾经走"取来再擦干净"那条路,而脱敏依赖
  URL 解析,密码里带一个 `/` 就原样漏出。改法不是把脱敏写得更严,是**不再取那一串**——从解析
  出的字段拼一个标识。⟹ **能不取用就不取用,胜过取用后再擦**;脱敏留给确实躲不开原值的出口。

OSM 一条:

- **检索的耗时量级要写进工具描述**。名称检索是全球范围的非锚定匹配,服务端要扫过整个星球的
  名称索引。**典型是几秒;而一个不应答的端点要等满 90 秒才转移下一个**,池有十个、最多两轮,
  所以一次糟糕的运行会到分钟级。这个数字必须写明——否则 Agent 会把正常等待判为卡死并重试,
  而重试只是从头再付一次同样的代价。

GDAL 与数据面四条,消费者是**界面**而非 Agent:

- **两条预览管线不可混用**(§7.9)。工具侧的数据读取走 QGIS 的 Python,产出原生像素空间的
  灰度 PNG 给模型;数据面走 GDAL,产出网页地图坐标系的彩色 WebP 给用户。接错的表现不是报错,
  是模型拿到一张被色带渲染过的图去读数值,或用户看到一张灰度图;
- **矢量交付上限必须两端一致**。服务端拒绝超过 `MAX_INLINE_FEATURES` 的整份交付,该值取自
  界面自己的渲染上限。两边不一致时,要么界面收到它已决定不画的数据,要么服务端拒绝了界面
  本可以画的数据——两种都不会报错;
- **栅格图像的地理定位在响应头里,不在响应体**。界面须读 `x-preview-meta`(base64 JSON),
  并且该头已由服务端列入 `access-control-expose-headers`——少了后者,浏览器会对脚本隐藏它,
  表现为图像正常但落不到地图上;
- **`notice` 字段是界面的分支依据**,不是文案。通用内容端点对超限栅格返回 `oversized-raster`,
  意思是"改用地图模式"(即数据面的栅格图像端点)而非"这个文件有问题";对其余超限文件返回
  `oversized`。响应体里的英文句子是给裸 API 消费者的兜底,界面应据 `notice` 渲染本地化提示。

## 12. 取舍记录

本节不引入新内容,只把散在各章的**主动放弃**集中列出。

代码能反推出"做了什么",反推不出"不做什么"。一旦理由丢失,后来者必然会把它加回来。集中
列出的目的不在查阅方便——散在各章也读得到——而在于给这些决定一个统一的形态:**让"这是一个
决定"本身可见**,使任何人要动其中一条时,先撞上它是决定,而不是一段可优化的实现。

| 决定 | 理由 | 出处 |
|---|---|---|
| 配置只要一个位置提示,不要求精确形态 | 所有形态都能推导出同一结果;多一个字段就多一处可以填错的地方 | §4.2 |
| **不生成栅格概览**(自带则用) | 生成概览要把源数据完整读一遍——正是重投影本来就要做的那一遍;它省下的只有逐像素坐标运算,而实测该项与块平均代价相当。此优化从不为正,且预览产物本身有缓存,没有第二次重投影可供摊销 | §7.5 |
| **不读取操作系统的代理设置** | 知名端口层已覆盖同一批用户,额外覆盖面窄,而代价是一套平台相关的读取与失效逻辑 | §3.3 |
| 仅 SOCKS 形态的代理声明直接跳过 | 消费端缺少可选依赖时会抛异常,反而破坏本来直连正常的用户 | §3.3 |
| **进程内路由不采用 HTTP 客户端库的调度器** | 那需要一个在目标运行时下不可解析的依赖,与"只用标准 API"直接冲突;代价是消费者经标准库而非 `fetch` 发起请求 | §3.3 |
| **不为远端授权设周期性复查** | 它是唯一带凭据、且单次成本以秒计的调用,而它验证的事实极少变化;代价是缓存可能长期停留在"有效"上,由真实使用的失败兜底 | §5.5 |
| **网络恢复不触发远端授权校验** | 连通性变化不改变凭据与项目绑定;按事件触发会让一次链路抖动换来一次带凭据调用,而连通性是秒级判定的 | §5.5、§5.7 |
| 终止流程的五项参数不暴露给调用方 | 它们描述流程本身的正确性,与任务性质无关;暴露只增加概念,改善不了任何决策 | §3.2 |
| **强制杀死后的孤儿进程不做补救** | 前三层防线已覆盖全部正常路径;补救手段(脚本轮询父进程 / 进程标识落盘)要在每个脚本或每次启动长期维持正确,而这一行的后果有界——一个终会跑完的进程,不损坏数据也不累积 | §3.2 |
| QGIS 三类能力共用单一就绪门禁 | 环境的可用性是同一个事实,一个环境只该有一份指导。**代价有两层**:通常只是数据读取要**等**算法目录构建完成;而在算法框架初始化失败的安装上,读取元数据这件本不需要 processing 的事被**永久**拒绝 | §4.9 |
| QGIS 失败态不自动重探(不同于 GEE) | 这里的重探是"探针 + 目录重建"的复合动作,期间三类能力全部停摆;而可修复的缝隙只剩"重装到相同路径"一种 | §4.8 |
| 算法目录不含第三方插件算法 | 当前范围 | §4.11 |
| 算法目录不设磁盘缓存 | 免去缓存目录、版本键与失效规则,并消除"同版本号的不同安装读到彼此缓存" | §4.11 |
| 参数预检不阻断执行 | 元数据的不完整会变成用户不能执行 | §4.12 |
| **输出编号只对目录型输出让步,不为任何算法让步** | 少数算法自带决定已存在文件命运的参数(如 `OVERWRITE`、`ACTION_ON_EXISTING_FILE`),看上去该把目标交还给它们——往已有的 GeoPackage 里追加一个图层时,"目标已存在"正是这次调用的目的。仍然编号,因为**两种失败不等量**:编号一次真正的追加,新数据写在原件旁边,原件完好、结果可人工合并;放行一次覆盖,数据落在检查点够不着的地方(§10.1 #6),没有任何东西能还原它。⟹ 二者无法可靠区分时,取可恢复的那一边。代价由输出报告承担:它明说这是新文件、不是对原文件的追加,工具描述则给出真要追加时的做法——先读出来,把原件移开,再写合并后的结果 | §4.12 |
| OSM 不设状态槽与指示灯 | 它没有用户可修的东西,一个红灯既不可操作也无从修复 | §6.2 |
| OSM 不提供流式输出 | 调用方是子代理,不存在需要用户实时观看的执行过程 | §6.2 |
| 端点清单不作为配置项 | 自建实例属于高级用法,不值得为它增加配置面 | §6.3 |
| 空间化简不使用常规线简化算法 | 这类算法会向内切割边界,在边界附近造成真实的数据丢失 | §6.4 |
| macOS 不注入任何工具链变量 | 该平台的安装形态依靠编译期记录的搜索路径自行定位 | §7.3 |
| **配置变更检测不设轮询兜底** | 旧版以 1 秒哈希轮询 + 每次工具调用同步复查兜住监听失效;新版只监听。代价由两处补偿:数据面的显式重读入口(设置界面与用户的逃生口),以及监听建立失败时的日志告警 | §3.1 |
| **Windows 手工轨不再组装 GRASS 环境** | 目录只导出三个官方提供者,GRASS 算法根本不进目录,为其组装环境是死代码;代价是若将来纳入 GRASS 提供者,需同时恢复其 PATH/PYTHONPATH 三项注入 | §4.5、§4.11 |
| **深度搜索不追随符号链接目录** | 它是"接住未知布局"的安全网,而没有任何已知布局把标准库藏在链接之后;为一种想象中的形态放宽搜索,换来的是每次搜索都要防环 | §4.4 |
| **解释器主目录农场按名共享单槽,不按安装隔离** | 同名解释器的两套安装并存且来回切换才会互相改写链接,而本进程内换配置必先弃用旧环境;按安装隔离要引入一层哈希目录并自负清理 | §4.4 |
| **剥离 BOM 时不区分数据内部的同码点** | 该字符出现在属性值里本身即是脏数据;要区分就得逐行判断位置,而它保护的是"Windows 控制台编码翻转"这一真实故障 | §4.13 |
| **启动崩溃判定不细分崩溃发生的阶段** | 无标记即判启动崩溃,会让"中途原生崩溃"也触发一次标准库深搜;代价有界(一次至多两千目录的扫描,不改变结论),而细分需要探针多发一行哨兵并在两处保持同步 | §4.6 |

另有一条不属于放弃,而是**有意的偏离**:算法执行的时限参数以"总时长"呈现,实际是空闲时限。
这类简化允许存在,但只能向宽松方向偏离——判据见 §8.4。
