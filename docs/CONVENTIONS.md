# 开发规范

本文档规定在这个仓库里怎么写代码、怎么修改上游代码、怎么测试、怎么写文档与提交。两个上游的导入与升级在 `UPSTREAM.md`,构建与运行在 `DEVELOPMENT.md`。

## 1. 总则

- 文档用中文;代码、注释、提交信息用英文。
- 代码要读起来像所在那棵树里已有的代码:`kernel/` 照 OpenCode 的写法,`desktop/` 照 OpenChamber 的写法。写法越接近上游,合并上游时冲突越少。
- 只格式化自有文件(上游没有的文件)。上游文件即使不合格式也不动。
- 规则从简。新增规则或检查之前,先确认现有的覆盖不了。

## 2. 代码风格

### 2.1 `kernel/`

OpenCode 的完整风格指南在它仓库根目录的开发指南里(不在本仓库中)。要点:

- 逻辑放在一个函数里,除非能复用或组合;不为只用一次的逻辑抽函数。分支多的函数,主体写主要流程,细节放到下方、以真实概念命名的小函数里。
- 用 `const`,以三元表达式或提前返回代替重新赋值;只用一次的值直接内联。
- 不用 `else`,用提前返回。
- 能推断的类型不标注;不用 `any`;`filter` 用类型守卫保住推断。
- 尽量不用 `try`/`catch`。
- 导入不起别名,不用 `import *`,不在类型位置写 `import("…")`。启动路径上的重模块用动态导入。
- 少解构,用点号访问。
- 外部输入只在边界校验一次,之后传递有类型的值。
- Effect:先把服务绑定到变量再调用方法;同步逻辑不包成 Effect;解析不可信的 JSON 用 Effect 的 Schema。
- 优先用 Bun 的 API,如 `Bun.file()`。

格式用 prettier(无分号、双引号、行宽 120,配置在 `kernel/package.json`),执行 `kernel/node_modules/.bin/prettier`,不用 `bunx prettier`,后者会拉取别的版本。类型检查在包目录执行 `bun run typecheck`,整棵树执行 `bun turbo typecheck`。

### 2.2 `desktop/`

- 格式以就近文件为准:单引号,有分号。
- 改一个模块之前,先读离它最近的 `DOCUMENTATION.md`。
- 界面调用 OpenCode 只经 `@opencode/client`;入口与桥接层保持薄,逻辑放进各自的模块。
- 请求失败不能当成空结果处理。
- 安全与正确性在运行时逻辑里保证,不只靠界面隐藏。

检查在 `desktop/` 执行 `bun run type-check`、`bun run lint` 与 `bun run lint:anti-slop`。

### 2.3 `scripts/`

shell 脚本用 POSIX sh(`#!/bin/sh`),要能在 macOS 自带的 sh 上运行。

### 2.4 注释

- 只为不明显的约束和出人意料的行为写注释:一句短从句,写在会被改错的那一行旁边。
- 理由、历史、测量数据写进文档,不写进代码。
- 注释描述代码,不描述进度。
- 不用 emoji,不用粗体。
- 测试里的注释只说明它防的是哪种失败。

## 3. 修改上游代码

### 3.1 先判归属

```bash
git cat-file -e kernel-upstream:<kernel/ 下的路径>
git cat-file -e chamber-upstream:<desktop/ 下的路径>
```

命中的是上游文件,修改它就是打补丁,要守这一节的规则。上游文件不做格式化、重构或顺手清理。

### 3.2 定制阶梯

配置 → 环境变量 → 插件 → 外挂进程 → 界面 → 源码补丁。能用前一级做到的,不用后一级。用到源码补丁时,要说得出前几级为什么做不到。

### 3.3 上游的缺陷不修

对照原味分支确认是上游本来就有的问题,就等上游自己修,随下一次合并得到修复。替上游修,等于在上游改动最频繁的地方堆自己的补丁,每次合并都要重新解冲突。

以下三种不属于上游缺陷,需要修改:GeoCode 自己引入的问题;按产品边界关闭的入口;上游按设计工作、但那个设计对地理用户不成立的地方。

### 3.4 补丁的写法

对上游的全部改动以 git 为准:

```bash
git diff --name-status kernel-upstream main:kernel      # A 自有文件,M 改过的上游文件,D 删掉的上游文件
git diff --name-status chamber-upstream main:desktop
```

合并与审阅都依据这份清单,不依据标记;还没提交的改动用 `scripts/patch-surface.sh <kernel|desktop>` 查看。

修改上游代码时,在修改处加注释标记,说明这处修改在做什么。标记用所在文件的注释语法:单行写 `GeoCode: <说明>`;多行的修改以 `--- GeoCode: <说明> ---` 开始,以 `--- /GeoCode ---` 结束,后者表示「上游代码从这里继续」。

带不了注释的文件(JSON、`.txt` 提示词、图片、翻译字典、锁文件),以及加了标记反而添乱的地方,可以不加,改在提交信息里说明。

屏蔽上游代码时,原来的行必须逐字节不变:整段包进块注释,或在前面提前返回。不要逐行加行注释:在 git 看来那是改了每一行,上游再改这些行就会冲突。

指向上游代码时写符号名,不写行号。行号会随合并漂移,而漂移了也没有任何提示。

## 4. 测试与检查

- 只测 GeoCode 自己的改动。上游的测试不跑,也不为了让它们通过而修改:有意改变的上游行为正是其中一批测试断言的内容,改它们只会增加合并冲突。
- 补丁在合并后是否还在、是否仍然正确,由合并前后的对账与审阅来回答(见 `UPSTREAM.md` 的升级步骤):清单取自 git,逐项读合并后的文件核实。不为每处补丁写专门的检查脚本。
- 机械检查有两项:`vendor.sh` 的文件集对账与写入检测。
- 测试只写在审阅看不出来的运行时行为上。配不配逐处权衡:值得配的,是会被静默破坏(例如跨文件的副本)或破坏后果严重(损坏用户数据、写入别的产品的目录)的地方;改动很小、审阅时一眼能看出的不配。断言后果,不断言措辞。
- 写一条检查,先证明它会失败:撤掉它保护的改动,确认它变红。
- 上游测试文件里新加的用例,名称以 `GeoCode: ` 开头,可以用 `bun test <文件> -t "GeoCode:"` 单独运行。
- 凡是「写入配置、期望某个服务读到」的改动,追到读取方,在运行时确认。

写入检测:`scripts/foreign-writes.sh` 在操作前后各运行一次(`before`、`after`),检查 OpenCode、OpenChamber 与 Claude 的目录有没有被写入。可能写盘的操作都要套上它;影响运行时路径的改动,还要在它的监视下跑一次真实会话。它只看写入,不看读取。

改完代码后,用 `node scripts/dead-code.mjs <文件…>` 检查动过的文件里有没有失去用途的函数与导入。它也会报出上游本来就有的死代码,所以只作参考。

## 5. 文档

| 文档 | 内容 |
|---|---|
| `README.md` | 对外的项目简介 |
| `docs/DESIGN.md` | 设计大纲:定位、基础、原则、待定问题与路线 |
| `docs/CONVENTIONS.md` | 怎么写代码、改上游、测试与检查、写文档、提交 |
| `docs/UPSTREAM.md` | 两个上游怎么导入与升级 |
| `docs/DEVELOPMENT.md` | 怎么安装、构建、运行、打包与检查 |
| `docs/DESKTOP.md` | 桌面应用:进程组成、内核的托管与打包、对外边界、本机访问控制 |

各部分的设计文档(内核、地理内核、壳等)在开始做那一部分时建立。

- 一个事实只写在一处,别处引用它。
- 改代码时,同一批改动里更新受影响的文档。
- 只写仍然成立的内容:决定、理由、约束、操作方法。开发过程、历史、进度与日期不写,它们在 git 历史里。
- 先写判断依据(定位、边界、约束、验收标准),实现细节等做出来以后再写。
- 只留关键、必要的内容与大纲,不写成流水账。说明与理由写成段落,并列的规则、步骤与清单才列条目。
- 用陈述句写规则与事实,不用「我们」「你」这类人称代词;需要区分归属时,写 GeoCode、上游等名称。
- 标点:`,` `:` `;` `(` `)` 用半角,`。` `、` 用全角,引号用「」。不用 emoji 与粗体。
- 指向代码写文件路径与符号名,不写行号。

## 6. 提交

- 提交信息的格式是 `type(scope): summary`,类型取 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`chore`、`revert`;需要时后接一两句英文说明。不带 AI 署名。
- 分支名不超过三个词,用连字符分隔,不带类型前缀。
- 提交前完整审阅 diff。一批改动分成几次提交时,每一次都要单独验证。
- 会随安装包分发的作者、版权、发布者信息,不自动填写真实姓名与邮箱。
