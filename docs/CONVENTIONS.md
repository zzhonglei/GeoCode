# 开发规范

本文档规定在这个仓库里怎么写代码、怎么修改上游代码、怎么测试、怎么写文档与提交。两个上游的导入与升级在 `UPSTREAM.md`,构建与运行在 `DEVELOPMENT.md`。

## 1. 总则

- 文档用中文;代码、注释、提交信息用英文。
- 代码要读起来像所在那棵树里已有的代码:`kernel/` 照 OpenCode 的写法,`desktop/` 照 OpenChamber 的写法。写法越接近上游,合并上游时冲突越少。
- 只格式化自有文件(上游没有的文件)。上游文件即使不合格式也不动。
- 规则从简。新增规则或检查之前,先确认现有的覆盖不了。
- 设计与代码都不做防御性的东西:不为少见的情况加参数、提示与检查。
- 代码按 macOS 与 Windows 都会运行来写,开发中测不了 Windows 时也一样。

## 2. 代码风格

### 2.1 `kernel/`

OpenCode 的完整风格指南在它仓库根目录的开发指南里(不在本仓库中)。要点:

- 逻辑放在一个函数里,除非能复用或组合;不为只用一次的逻辑抽函数。分支多的函数,主体写主要流程,细节放到下方、以真实概念命名的小函数里。
- 用 `const`,以三元表达式或提前返回代替重新赋值;只用一次的值直接内联。
- 不用 `else`,用提前返回。
- 能推断的类型不标注;不用 `any`;`filter` 用类型守卫保住推断。
- 尽量不用 `try`/`catch`。
- 导入不起别名,不用 `import *`,不在类型位置写 `import("…")`。启动路径上的重模块用动态导入。
- 少解构,用点号访问。
- 外部输入只在边界校验一次,之后传递有类型的值。
- Effect:先把服务绑定到变量再调用方法;同步逻辑不包成 Effect;解析不可信的 JSON 用 Effect 的 Schema。
- 优先用 Bun 的 API,如 `Bun.file()`。

格式用 prettier(无分号、双引号、行宽 120,配置在 `kernel/package.json`),执行 `kernel/node_modules/.bin/prettier`,不用 `bunx prettier`,后者会拉取别的版本。类型检查在包目录执行 `bun run typecheck`,整棵树执行 `bun turbo typecheck`。

### 2.2 `desktop/`

- 格式以就近文件为准:单引号,有分号。
- 改一个模块之前,先读离它最近的 `DOCUMENTATION.md`。
- 界面调用 OpenCode 只经 `@opencode/client`;入口与桥接层保持薄,逻辑放进各自的模块。
- 请求失败不能当成空结果处理。
- 安全与正确性在运行时逻辑里保证,不只靠界面隐藏。

检查在 `desktop/` 执行 `bun run type-check` 与 `bun run lint`,再在仓库根目录执行 `node scripts/own-anti-slop.mjs`。壳服务端与主进程的 JS 不在类型检查与 lint 的范围里,只由 anti-slop 与测试把关。

上游另有一套 anti-slop 规则(`bun run lint:anti-slop`),专挑 AI 生成代码的常见毛病。上游自己的代码也没有完全遵守这套规则,而上游文件不做顺手清理(见第 3.1 节),所以只查 GeoCode 自己的文件,即原味分支上没有的那些,还没加入 git 的也算。对上游文件打的补丁不查,交给提交前的审阅。有的规则和本项目的需要相冲突,确实要保留的违规写进脚本的例外清单,注明原因与处数。

### 2.3 `geoengine/`

GeoEngine 是 GeoCode 自己的代码,用 TypeScript 与 Effect 编写,写法照 `kernel/`(第 2.1 节),只有「优先用 Bun 的 API」一条不适用。格式用它自己目录下的 prettier,配置与内核相同。

它在 Electron 的辅助进程里以 Node 运行,所以 `src/` 只用 Node 的 API,不用 Bun 的;Bun 只用来安装依赖与打包,只有 `script/` 下的构建脚本能用 Bun 的 API,也只有它的类型检查带着 Bun 的类型。相对导入写 `.ts` 扩展名,只用能直接擦除的类型语法,测试因此由 Node 直接运行。

检查在 `geoengine/` 执行 `bun run typecheck` 与 `bun run test`。

`geoengine/python/` 是 GEE 脚本导入的 Python 包 `geocode`,在用户配置的 Python 里运行,所以只用标准库、GeoCode 要求装好的包(earthengine-api、geedim、geopandas)与它们带来的依赖(如 shapely、pyproj、rasterio)。写法照 PEP 8,行宽 120。交给 GeoAgent 的名字列在包的 `__all__` 里,其余模块以下划线开头,不写进工具说明。它由 GeoEngine 的测试经替身的 earthengine-api 运行检查,真实的 Earth Engine 在改动后另做冒烟。

### 2.4 `scripts/`

shell 脚本用 POSIX sh(`#!/bin/sh`),要能在 macOS 自带的 sh 上运行。

### 2.5 注释

- 只为不明显的约束和出人意料的行为写注释:一句短从句,写在会被改错的那一行旁边,说明它为什么这样写。
- 一次改动的经过与测量数据写进提交信息,影响整个部分的设计理由写进文档(第 5 节)。
- 注释描述代码,不描述进度与历史。
- 不用 emoji,不用粗体。
- 测试里的注释只说明它防的是哪种失败。

## 3. 修改上游代码

### 3.1 先判归属

```bash
git cat-file -e kernel-upstream:<kernel/ 下的路径>
git cat-file -e chamber-upstream:<desktop/ 下的路径>
```

命中的是上游文件,修改它就是打补丁,要守这一节的规则。上游文件不做格式化、重构或顺手清理。

### 3.2 定制阶梯

配置 → 环境变量 → 插件 → 外挂进程 → 界面 → 源码补丁。能用前一级做到的,不用后一级。用到源码补丁时,要说得出前几级为什么做不到。

### 3.3 上游的缺陷不修

对照原味分支确认是上游本来就有的问题,就等上游自己修,随下一次合并得到修复。替上游修,等于在上游改动最频繁的地方堆自己的补丁,每次合并都要重新解冲突。

以下三种不属于上游缺陷,需要修改:GeoCode 自己引入的问题;按产品边界关闭的入口;上游按设计工作、但那个设计对地理用户不成立的地方。

### 3.4 补丁的写法

对上游的全部改动以 git 为准:

```bash
git diff --name-status kernel-upstream main:kernel      # A 自有文件,M 改过的上游文件,D 删掉的上游文件
git diff --name-status chamber-upstream main:desktop
```

合并与审阅都依据这份清单,不依据标记;还没提交的改动用 `scripts/patch-surface.sh <kernel|desktop>` 查看,还没加入 git 的新文件不在其中。

修改上游代码时,在修改处加注释标记,说明这处修改在做什么。标记用所在文件的注释语法:单行写 `GeoCode: <说明>`;多行的修改以 `--- GeoCode: <说明> ---` 开始,以 `--- /GeoCode ---` 结束,后者表示「上游代码从这里继续」。

带不了注释的文件(JSON、`.txt` 提示词、图片、翻译字典、锁文件),以及加了标记反而添乱的地方,可以不加,改在提交信息里说明。

屏蔽上游代码时,原来的行必须逐字节不变:整段包进块注释,或在前面提前返回。不要逐行加行注释:在 git 看来那是改了每一行,上游再改这些行就会冲突。

GeoCode 只有桌面应用一种形式,补丁不判断运行方式。提前返回之后的上游代码里,TypeScript 不再沿用前面的类型收窄,可能报类型错误,这时把后面的上游代码也包进块注释;包住之后没人用的导入与变量 lint 会报,各自再包一次,与仍在用的名字同在一行的,在上面加 `eslint-disable-next-line @typescript-eslint/no-unused-vars`。界面上要藏起的一段 JSX,包进 `desktop/packages/ui/src/geocode/Closed.tsx` 的 `Closed`:它什么都不渲染,包住的上游行不变,里面用到的变量也仍有引用。

补丁调用的自有模块与它们的测试,放在所在包的 `geocode/` 目录里,与上游文件分开,补丁本身只留调用的那一两行。`kernel/` 的测试是例外:内核的测试配置与夹具只认包的 `test/` 目录,GeoCode 的测试放在那里,文件名以 `geocode-` 开头或放进 `test/geocode/`。GeoCode 自己的功能模块放在哪里,做那一部分时按它的设计决定。

指向上游代码时写符号名,不写行号。行号会随合并漂移,而漂移了也没有任何提示。

## 4. 测试与检查

- 只测 GeoCode 自己的改动。上游的测试不作为检查运行,也不为了让它们通过而修改:有意改变的上游行为正是其中一批测试断言的内容,改它们只会增加合并冲突。
- 补丁在合并后是否还在、是否仍然正确,由合并前后的对账与审阅来回答(见 `UPSTREAM.md` 的升级步骤):合并之前读上游在两个版本之间对这些文件的改动,合并之后逐项读合并后的文件核实,清单都取自 git。不为每处补丁写专门的检查脚本。
- 补丁的机械检查有两项:`vendor.sh` 的文件集对账与写入检测。
- 测试只写在审阅看不出来的运行时行为上。配不配逐处权衡:值得配的,是会被静默破坏(例如跨文件的副本)或破坏后果严重(损坏用户数据、写入别的产品的目录)的地方;改动很小、审阅时一眼能看出的不配,一条路径已被别的测试覆盖的也不再加。界面的外观与交互不写测试,在应用里实际操作查看。断言后果,不断言措辞。交给模型与用户的文字(工具的返回、出错的说明、界面上的文字)靠撰写时认真设计、交维护者审阅定稿来保证,不写测试守护:它们都在 GeoCode 自己的文件里,改动都出现在 diff 中。
- 写一条检查,先证明它会失败:撤掉它保护的改动,确认它变红。
- 上游测试文件里新加的用例,名称以 `GeoCode: ` 开头,可以在包目录用 `bun run test <文件> -t "GeoCode:"` 单独运行。
- 凡是「写入配置、期望某个服务读到」的改动,追到读取方,在运行时确认。

可能写盘的操作,前后都要运行写入检测(用法见 `DEVELOPMENT.md` 第 8 节);影响运行时路径的改动,还要在它的监视下跑一次真实会话。它只看写入,不看读取。

改完代码后,用 `node scripts/dead-code.mjs <文件…>` 检查动过的文件里有没有失去用途的函数与导入。它只看单个文件,导出给别处用的也会报出,上游本来就有的死代码也在其中,所以只作参考。

## 5. 文档

文档是外人了解 GeoCode 的窗口,也是后续开发的依据。它只写读者需要的关键内容,不求全,不把代码再写一遍。

### 5.1 信息放在哪里

一条信息只放在一处,按谁读它、它成立多久决定:

| 信息 | 位置 |
|---|---|
| 一个部分是什么、为什么这样设计、守什么约束 | `docs/` 里这一部分的设计文档 |
| 写代码、文档、测试与提交的规则 | 本文档 |
| 构建、运行与升级上游的步骤 | `DEVELOPMENT.md`、`UPSTREAM.md` |
| AI 助手怎样与维护者协作 | `AGENTS.md` |
| 一行代码为什么这样写 | 那一行的注释(第 2.5 节) |
| 一次改动的经过与测量数据 | 提交信息 |
| 实现的样子:文件、函数、参数与界面的细节 | 代码本身 |
| 对上游的逐项改造 | `git diff` 列出(第 3.4 节) |
| 进度、日期、讨论经过、没有采纳的提议、谁做的决定 | 仓库的文档里不写 |

### 5.2 文档的种类

- 入口与总纲:`README.md` 讲 GeoCode 是什么、由什么组成、文档在哪;`DESIGN.md` 讲定位、原则与路线。
- 规范与操作:本文档、`DEVELOPMENT.md`、`UPSTREAM.md`。
- 设计:每个部分一篇,开始做那一部分时建立,加进 `README.md` 的清单。大体按定位、原理与结构、边界与约束、验收、待定组织。原理写到读者能理解它、改动时不会改坏为止;验收只写结果,不写检查的步骤;待定只列会影响设计的问题。
- 参考:`PATHS.md` 这类供查阅的清单,用途就是完整列出。

### 5.3 写什么

- 每句话都要经得起一问:后来的开发者没有它,会不会做错。不会就不写。
- 只写仍然成立的内容:决定、理由、约束、操作方法。
- 「不做什么」只在合理的后来者自然会去做、做了又会出问题时才写,写成约束并附理由。
- 文档里的决定都是 GeoCode 的决定,不写由谁、在哪天决定。
- 一个事实只写在一处,别处引用它。
- 设计文档在实现之前写判断依据(定位、边界、约束、验收);做出来之后补上原理,细节留在代码里。
- 改代码时,同一批改动里更新受影响的文档。

### 5.4 写法

- 说明与理由写成段落,并列的规则、步骤与清单才列条目。句子要短,一句说一件事。
- 用陈述句写规则与事实,不用「我们」「你」这类人称代词;需要区分归属时,写 GeoCode、上游等名称。
- 标点:`,` `:` `;` `(` `)` 用半角,`。` `、` 用全角,引号用「」。不用 emoji 与粗体。
- 指向代码写文件路径与符号名,不写行号。

## 6. 提交

- 提交信息的格式是 `type(scope): summary`,类型取 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`chore`、`revert`;需要时后接一两句英文说明。不带 AI 署名。
- 分支名不超过三个词,用连字符分隔,不带类型前缀。
- 提交前完整审阅 diff。一批改动分成几次提交时,每一次都要单独验证。
- 会随安装包分发的作者、版权、发布者信息,不自动填写真实姓名与邮箱。
