# 地理引擎

GeoEngine(地理引擎)是 GeoCode 自己的组件,为整个应用提供地理数据相关的能力。本文档说明它的定位、在应用中的位置、结构、边界、约束与验收。各能力域共用一套框架,逐个接入,各自的设计做到那一个时补进本文档;仍未决定的问题列在第 9 节。

## 1. 定位

GeoEngine 做两件事:管理用户电脑上的地理执行环境,执行地理任务。能力域按 QGIS、Google Earth Engine、OpenStreetMap、GDAL 的顺序接入。

管理环境指发现、验证与诊断:GeoEngine 在常见的安装位置找到用户装好的 QGIS、Python 等软件,列给用户在设置里选择,找不到时由用户指定位置,用哪一套总是由用户决定,GeoEngine 不替用户选;它验证这些软件能否真正运行,把缺什么、出了什么问题整理成提示信息交给 GeoAgent。GeoEngine 不安装软件,也不改动用户已有的环境;怎样补齐由 GeoAgent 决定,它引导用户安装,或经内核的权限规则执行命令去处理;各能力域的提示写明它能自己做什么、哪些只能请用户做。QGIS、Google Earth Engine、GDAL 与 Python 的环境各有各的发现与验证方式,在做到对应的能力域时决定。

地理任务与 agent 平常的工作不同:一次空间分析或遥感计算可能运行几分钟甚至更久,占用大量内存,调用的外部程序也可能卡住或崩溃。所以地理能力不放进内核,也不放进壳服务端,而是单独成为一个进程:任务出了问题,不会拖垮界面、壳服务端与内核。

## 2. 在应用中的位置

```
Electron 主进程
 ├─ 壳服务端
 │    └─ 子进程:内核
 ├─ 辅助进程:GeoEngine
 │    └─ 任务子进程:QGIS、Python 等外部程序
 └─ 界面(渲染进程)
```

GeoEngine 由主进程启动与管理,随应用启动、随应用退出,启动时检查各能力域的执行环境。主进程在并入登录 shell 的环境之后启动它,与内核同时启动,不耽误窗口出现;它在限定的时间里报告启动完成,之前到达的请求先挂着。它与内核一样是应用的私有组件,只为这个应用服务。外部程序失败、卡住或崩溃,都只是一次任务失败,结果返回给 GeoAgent;GeoEngine 自己起不来或异常退出,说明应用本身出了问题,所以不自动重新拉起,也不提供重试,应用显示出错页(见 `DESKTOP.md` 第 6 节),恢复的办法只有重启应用。正在执行的任务以失败结束,不自动重试,因为执行到一半的任务未必能安全地重跑。

GeoEngine 不监听任何端口,只与主进程通信:agent 调用的地理工具与界面都经壳服务端转达到它,本机的其他程序连不到它,能到达它的请求都先经过壳服务端的访问控制(见 `DESKTOP.md` 第 4 节)。

GeoEngine 运行在 Electron 的辅助进程里,不单独构建可执行文件,所以在进程列表里显示为 GeoCode 的辅助进程(macOS 上是「GeoCode Helper」)。它启动的外部程序显示各自的名字。

## 3. 结构

GeoEngine 分两层。基础设施层提供与地理领域无关的机制:环境配置(读写 `machine.json`,在它变动时通知受影响的能力模块)、进程执行(启动外部程序、交付输出、超时与中断、结束整棵进程树)、状态记账(各能力域的环境状态的存储、发布与快照)。访问外网不设 GeoEngine 自己的出口,跟随用户自己的网络配置(第 8.5 节)。能力层在其上实现各个能力域。能力模块之间互不依赖,共同需要的机制下沉到基础设施层。

GeoEngine 对外有三个出口,都经主进程:

- 工具:内核里的地理工具经壳服务端把任务交给 GeoEngine,执行中回报进度,结束时返回结果;环境没有就绪时,GeoAgent 得到下一步的提示,诊断记入内核的日志。
- 状态:各能力域的环境状态,注册时与每次变化时整体推送给主进程;界面从主进程一次取全并接收变化,据此显示环境是否就绪。
- 数据:界面要显示的预览数据,经壳服务端的接口按请求取得。

代码在仓库根目录的 `geoengine/`,与 `kernel/`、`desktop/` 并列,用 TypeScript 与 Effect 编写,打包时编进应用。GEE 脚本导入的 Python 包 `geocode` 在 `geoengine/python/`,是普通的 `.py` 文件。应用把 GeoEngine 放在自己的归档里,Python 读不到其中的文件,所以构建时把包的各个文件原样编进 GeoEngine,运行时随请求交给 Python,由运行脚本按文件导入;报错的 traceback 照常写出包里的文件名与行号。

### 3.1 与主进程的通道

GeoEngine 与主进程之间只有一条消息通道,上面走五类消息:请求与应答、进度、中断、状态推送、生命周期的通知。

每个请求带一个编号,应答按编号对应,内容是结果或结构化的错误;长任务在应答之前按同一编号回报进度。中断按编号叫停一个任务:GeoEngine 结束它的整棵进程树,仍然给出应答,标明已中断,并带上已经产生的输出,因为这时已有的输出正是调用方最需要的。生命周期的通知包括 GeoEngine 启动完成、退出前的清扫与清扫完毕,以及每个任务进程的登记与注销,主进程据此在 GeoEngine 崩溃时结束它留下的任务。任务进程一退出就注销,不等它的输出读完:退出后的进程号可能已被别的进程复用。

通道本身不设超时,任务运行多久由 GeoEngine 按任务的性质判断,或交给调用方(如执行算法,第 7.4 节);只有退出前的清扫有时限,超时就直接退出,应用不能因此退不出去。GeoEngine 崩溃时,主进程把未完成的请求以错误结束。各能力域的最新状态由主进程统一接收并保存。收到的消息在接收的一端校验一次,预览这类二进制数据随消息直接转移,不另做编码。

外部的两条链路接在这条通道上。地理工具向壳服务端发出的请求不设超时、带着中断信号,壳服务端以流式应答逐段转回进度,工具调用被取消时请求断开,壳服务端把它转成一条中断。接收工具请求的是壳服务端里 GeoCode 自己的接口,它只确认来电的是这个应用自己的内核,不做权限判断:到达它的任务已经过内核的权限规则(见第 4 节)。界面的快照与数据经壳服务端的接口取得,状态的变化经壳服务端已有的推送通道送达。

### 3.2 环境配置

环境信息都记在 `machine.json` 里:各外部软件的位置与所需的标识。它与内核的 `geocode.json` 放在同一个配置目录(见 `PATHS.md`),但不合成一个文件:`geocode.json` 在加载时读取,`machine.json` 保存即生效;它记的全是本机的绝对路径,换一台电脑就不再成立。

文件是一个 JSON 对象,每个能力域一块,块里记什么在做到那个能力域时决定。块是变化的单位:某一块变了,只重新检查那个能力域;是否变化按解析后的值比较,调整格式与键的顺序不算变化。不认识的键忽略,一块写错只影响这一块。文件不支持注释:GeoEngine 也写这个文件,写回时注释留不住。

用户在设置里的选择由 GeoEngine 写进文件,发现的结果不写进文件;写入先写临时文件再改名,文件不会停在写了一半的状态。用户手改与 GeoAgent 改同样生效:GeoEngine 监听配置目录,文件变动后重读;监听可能失效,所以用户要求重新检查时也先重读文件。文件被改得无法解析时,各能力域都进入配置错误的状态,带着出错的位置,GeoEngine 不覆盖它,以免抹掉用户手写的内容。

### 3.3 环境状态

每个能力域有一份环境状态,取值是以状态标识区分的几种状态之一,每次整体替换,没有变化就不推送。检查中这类中间态也是正式的状态;每个能力域的状态都包含未配置与配置错误,其余由能力域自己定义。旧一轮检查的结果不会覆盖新一轮的。

失败的状态带两类信息,给不同的读者。给界面的是诊断,即定位问题所需的事实:路径、版本、各检查项的结果、原始错误。界面只显示错误本身,简短的状态名与诊断,不给用户附建议,免得复杂;它们是日志式的信息,一律用英文,不随界面语言切换。给 GeoAgent 的是提示,即下一步该做什么,由能力模块自己生成;不同的错误给出不同的提示,具体内容写在各能力域里。

界面在标题栏为每个有状态的能力域显示一个指示灯,颜色按状态归类:就绪为绿色,检查中为黄色,未配置与设置还没走完的为灰色(GEE 的未登录与缺项目,见第 8.9 节),其余的失败为红色。未配置不是故障,刚装好应用、还没有配置的用户不该看到红灯。点开指示灯,显示状态与诊断,诊断可以整份复制;给 GeoAgent 的提示不显示。界面不显示 `machine.json` 的位置:环境在设置里配置,也可以交给 GeoAgent,用户不需要去找这个文件。界面打开时先读一次快照,之后接收变化,推送通道断线重连后再读一次;晚到的快照不会盖掉已经收到的变化。

设置里的「地理环境」一页集中管理各能力域的环境,与指示灯读同一份状态。页面先是各能力域的列表,一行一个,一眼看到各自的状态,点进去是这个能力域的详情;加一个能力域只是多一行。详情里列出在这台电脑上找到的安装与各自的版本,用户点选一套即写入配置并重新检查,也可以指定别处的安装;另有重新检查,软件原地重装或升级之后不必重启应用。列出安装只读安装包自带的信息,不启动软件,完整的验证只对选中的那一套做。

地理工具执行之前先看环境:还在检查中,就等它落定,等待有上限;没有就绪,就不执行,把提示返回给 GeoAgent;就绪才执行。没有就绪的状态在环境改变后才会变,有的改变不经过配置文件(如原地重装),各能力域决定工具调用时要不要先再检查一次。

## 4. 边界

GeoEngine 只负责执行任务与管理执行环境。agent、工具的定义与权限都在内核:地理工具是内核的内置工具,与 OpenCode 自带的工具一样,由内核的权限规则决定执行前是否询问用户;每个地理工具的权限各不相同,写在各能力域里(QGIS 见第 7.5 节)。到达 GeoEngine 的任务都已经过这一关,GeoEngine 自己不做权限判断。

界面要显示的地理状态与数据(执行环境是否就绪、数据的预览)同样经壳服务端从 GeoEngine 取得,界面不直接与它通信。

## 5. 约束

- 不开端口。GeoEngine 与外界的全部通信经过主进程;以后加任何通道,都不能让本机的其他程序直接连到它。
- 任务要能长时间运行。执行中要能回报进度、能被用户中断;从内核到 GeoEngine 的整条链路上,不能有比任务更短的超时。
- 管好进程的生命周期。GeoEngine 随应用退出,但它启动的外部程序不会自动跟着退出,要由 GeoEngine 负责结束:任务被中断时,应用正常退出时(主进程先等 GeoEngine 清扫完再退出),结束的都是整棵进程树。GeoEngine 自己崩溃时无法清扫,由仍在运行的主进程结束它留下的任务。整个应用被强制结束、崩溃或断电时,进程内无从清理,留下的任务会自己跑完,不做补救:它不损坏数据、也不会累积,而补救要在每个脚本或每次启动里长期维持正确。Windows 没有进程组,也没有可以先礼后兵的信号:任务在运行时,按进程树强制结束;任务退出之后,它留下的子进程不再结束,因为退出后的进程号可能已被别的进程复用,按进程号结束整棵树会误伤。内核执行命令时也是这样处理的。
- 输出按 UTF-8 读取。Windows 上的命令行程序默认用系统的本地代码页输出(如简体中文系统的 GBK、繁体中文系统的 Big5),能力模块启动外部程序时要让它以 UTF-8 输出,否则中文的报错与路径会变成乱码。
- 用户环境与内核相同。GeoEngine 拿到的环境是登录 shell 的变量按 `DESKTOP.md` 第 5 节清理之后的那一份,用户装在 conda 或系统里的 QGIS、GDAL、Python 能被找到。应用为壳与内核写入的同前缀变量也不交给它,地理任务看不到它们。
- GeoEngine 自己写的文件只放在 GeoCode 自己的目录里(见 `PATHS.md`),新增的目录在实现时补进 `PATHS.md`。外部软件运行时写它自己的配置与缓存(如 QGIS 在用户目录下的配置与缓存),照它的默认位置,不归 GeoCode 管。
- macOS 与 Windows 同等对待,两个平台的安装布局与路径规则都要覆盖。
- 对内核与壳的上游代码,只改接入所需的几处(见 `CONVENTIONS.md` 第 3 节)。

## 6. 验收

框架的验收如下,各能力域的验收做到时补充。

- 应用正常退出之后,没有残留的 GeoEngine 进程与任务子进程(Windows 上任务自己退出后留下的除外,见第 5 节);应用被强制结束之后,GeoEngine 随之结束。
- GeoEngine 崩溃或被结束时,主进程不受影响;它留下的任务子进程被结束,正在执行的任务以失败结束,应用显示出错页并给出原因,重启应用后恢复正常。
- 运行期间,GeoEngine 没有监听任何端口。唯一的例外是 GEE 的登录(第 8.3 节):登录进行时,它启动的 Python 在本机回环地址上监听一个端口,等浏览器带回授权码,登录结束即关闭。本机的其他程序可以借这个端口提前结束登录,但带回伪造的授权码无用:换取凭据要用只有这个 Python 持有的校验码。
- 一个运行超过十分钟的任务能完整跑完,期间进度持续回报;中途中断时任务停止,它启动的外部程序随之结束。
- 写入检测干净,GeoEngine 自己写的文件都落在 `PATHS.md` 列出的位置。

## 7. QGIS

QGIS 能力域让 GeoEngine 在用户安装的 QGIS 里执行空间处理算法。执行载体只有 QGIS 自带的 Python:算法、PyQGIS 脚本与数据读取都要在这个解释器里运行,只用它就只需维护一套环境组装与一套验证;`qgis_process` 同在这个安装里,不另外支持。范围是 QGIS 内置的算法,第三方插件提供的算法不在其中。

### 7.1 支持的安装

支持 QGIS 官方的安装包:macOS 上的应用包,Windows 上的独立安装包与 OSGeo4W,目标是两个平台上的大多数版本。conda、Homebrew 等其他来源的 QGIS 不支持。两个平台的安装布局与环境组装方式完全不同,各自单独实现。GeoCode 不按版本号判断一套 QGIS 能不能用:能不能运行由检查与执行说明,遇到的问题原样交给 GeoAgent。不同版本运行时会出各种意想不到的问题,只能在两个平台上逐个版本验证、逐个解决。

macOS 上已经实现的是 3.44、4.x 的应用包布局:解释器在应用包的可执行目录里,旁边有官方的 `python` 启动脚本。更早的版本还没有验证;找不到这个启动脚本时报告为找不到 QGIS 的 Python,不去猜测它的结构。应用包的路径里不能有空格:官方的 `python` 启动脚本没有给路径加引号,路径带空格时它自己就启动不了解释器;这是 QGIS 打包的问题,GeoCode 不绕开它,这样的安装检查时报告为出错,原始输出里有原因。

Windows 上的独立安装包是用 OSGeo4W 的组件包打成的,装好后的布局与 OSGeo4W 相同:一套 QGIS 是根目录下的 `apps\<名字>` 与它的启动脚本 `bin\python-<名字>.bat`,名字以 `qgis` 开头(如 `qgis`、`qgis-ltr`),不写死名单。独立安装包的根目录里只有一套,OSGeo4W 的一个根目录里可以并存几套。现在的实现依据当前 OSGeo4W 上 3.44 与 4.2 的组件包和独立安装包的打包脚本,还没有在 Windows 上运行过;2021 年以前的旧布局还没有核对。

### 7.2 配置与环境组装

`machine.json` 的 `qgis` 块记一个路径,GeoEngine 用的就是它指向的那一套 QGIS。macOS 上路径指向应用包,落在应用包内部时取它所在的应用包。Windows 上路径可以是根目录、启动脚本或其中任何位置,从它往上找到 QGIS 的根目录,即 `bin` 里有启动脚本、或 `apps` 下有以 `qgis` 开头的文件夹的那一层。路径指明了哪一套就用那一套,即落在 `apps\<名字>` 里、是它的启动脚本,或是桌面快捷方式启动的 `<名字>-bin.exe`;指明的那一套不在根目录里时报告为不是 QGIS,不换成另一套。路径没有指明时,根目录里只有一套能启动的就用它,有几套时报告为一个文件夹里有多套,列出能启动的各套,由用户或 GeoAgent 指定。路径不分大小写,正反斜杠都认,记下的是硬盘上的写法,同一套 QGIS 不会因为写法不同被当成两套。

列给用户选的安装按应用的身份找,不按名字:应用包可以被改名或放在别处。macOS 上取 `/Applications` 与 `~/Applications` 下的应用包,再加上 Spotlight 按包标识找到的,包标识以 `org.qgis.` 开头的都算,版本取自应用包的信息文件。`/Volumes` 下的不列出,即磁盘映像与外接磁盘上的:推出之后它就不存在了,要用时仍可以手动指定;废纸篓里的也不列出。找不到 Python 启动脚本的照样列出、可以选,选了由检查说明问题。

Windows 上没有按身份找遍全盘的办法,取每块固定硬盘上安装程序放 QGIS 的位置:`Program Files\QGIS*`,根目录下的 `OSGeo4W*` 与 `QGIS*`,加上 `ProgramFiles` 与 `ProgramW6432` 指向的文件夹;不少人把软件装在 C 盘以外。固定硬盘由 PowerShell 列出,断开的网络驱动器一查就会卡住;列不出时只查系统盘。一个根目录里的每一套各列一项,版本取自根目录里安装程序记下的组件清单;缺了启动脚本的照样列出、可以选,选了由检查说明问题。注册表不查:独立安装包只留下卸载信息,不记安装位置,文件关联只记最后装的那一套。装在别处的由用户在设置里指定,或由 GeoAgent 去找。

环境采用 QGIS 自己的答案:macOS 上以官方的 `python` 启动脚本运行解释器,只叠加 GeoCode 的场景需要、而 QGIS 不会替它设置的几项。投影与 GDAL 的数据目录要显式给出:官方脚本只设了 Python 的位置,缺了它们 GDAL 找不到投影数据库,坐标变换静默失败。从登录 shell 继承来的 `PYTHONPATH` 要清空:它常由 conda 这类工具设置,会把另一个 Python 的包排到 QGIS 自带的包前面,让 QGIS 的 Python 连 numpy 都导入不了;从访达打开的 QGIS 本来就看不到它。

Windows 上每次都经那一套的 `python-<名字>.bat` 运行,环境全由它组装:先把 `PATH` 换成只有 QGIS 与系统的目录,清空 `PYTHONPATH`,再设好 Qt、GDAL、PROJ 与 Python 的 UTF-8 模式;GDAL 与 QGIS 的 Python 包按 `PATH` 自己登记 DLL 目录。GeoCode 不自己组装,也不留环境的快照:Qt、GDAL 与各个依赖的位置随版本变,Qt6 的变量只在用 Qt6 的启动脚本里设,自己组装就要跟着每个版本追,漏一项就是 Qt 找不到或 DLL 加载失败。叠加的只有 Python 输出的编码与关掉 Qt 的日志。

脚本连同请求经标准输入交给 QGIS 的 Python,不放在命令行上:Windows 上的官方启动脚本要经命令解释器运行,命令行里的引号、`%`、`^`、`&`、`!` 会被它改写,多行内容会被截断,长度也有上限,路径与参数里的这些字符就到不了 Python。两个平台用同一种传法。

QGIS 启动时在系统的临时目录建几个文件夹与文件,只在它自己收尾时删掉,所以启动了 QGIS 的脚本送出结果之后走 QGIS 的收尾再退出;被中断的任务来不及收尾,留下这一次的。结果在收尾之前已经送出,GeoEngine 按结果判断,收尾即使出错也不改变结论。

### 7.3 验证与状态

验证由一段探针脚本在组装好的环境里完成,依次检查 GDAL 能否导入、能否完成一次真实的坐标变换、QGIS 核心能否导入、处理框架能否初始化,前一步失败就不再往下查。坐标变换单独成一步,因为投影库在数据库缺失时照样能导入,要到真正变换时才失败。

状态除了各能力域共有的未配置与配置错误,还有平台不支持、路径不存在、不是 QGIS、一个文件夹里有多套、找不到 QGIS 的 Python、检查中、探针各步骤的失败、探针超时或崩溃,以及就绪。检查在 GeoEngine 启动时、`qgis` 块变化时与用户要求重新检查时进行,被中途停下(如应用退出)的检查不改变状态。检查看 QGIS 得出的失败(路径不存在、不是 QGIS、一个文件夹里有多套、找不到 QGIS 的 Python、探针各步骤的失败、探针超时或崩溃)在工具调用时再检查一次:在原处重装 QGIS 不改动配置文件,否则要重启应用才看得到;QGIS 就绪时调用不检查,同时到达的调用共用一次检查。未配置与配置错误时,工具调用先重读配置文件:GeoAgent 得到的提示说文件一保存就生效,而调用可能紧跟在写入之后、早于监听的反应。失败的状态带上诊断(配置的路径、用的是哪一套与它的版本、检查运行的启动脚本、探针的原始输出;一个文件夹里有多套时,另列这个文件夹与其中能启动的各套)。探针某一步失败时,诊断另附 Python 实际拿到的几项环境变量:QGIS 的前缀、Python 的位置、Qt 的插件目录与前缀、`PATH`,在 Windows 上都由启动脚本设置,用户贴回诊断就看得出是哪一项不对、用的是哪一套。只附这几项,其余环境变量可能带着密钥;这几项也只进用户看的诊断,不进给 GeoAgent 的提示,提示会发给模型的服务商,而 `PATH` 里有用户自己的文件夹名。

环境没有就绪时,三个工具都把 GeoEngine 给的提示原样交给 GeoAgent。设置页是用户自己配置的路,GeoAgent 走另一条:提示不提设置页,而是给它自己动手所需的一切,配置文件的绝对路径与写法、在本机找 QGIS 的位置与命令,找到多套时问用户用哪一套;能不能用由检查判断,提示不按版本替它筛选。写好之后调用 `qgisdoc` 验证;都在 GeoEngine 运行时写出,路径不会写错。QGIS 坏了时另给检查运行的启动脚本与输出的最后 20 行,请用户重装或改用另一套;一个文件夹里有多套时列出各套,请 GeoAgent 问用户用哪一套。提示要 GeoAgent 不安装 QGIS、不写包装脚本、不自己运行 QGIS 的 Python 试探:安装由用户决定,后两件前两版里它都做过,只会添乱。

### 7.4 执行算法

每次执行算法是一个独立的任务进程:在就绪的环境里由运行脚本承载,算法标识与参数随请求传入,执行中按处理框架报告的进度逐个百分点回报,中断时结束整棵进程树,结束时返回结果与输出。任务进程的当前目录是会话目录。

无界面运行时没有 QGIS 项目,项目带来的默认值随之缺失,其中影响结果的是测量用的椭球。椭球为空时,按椭球测量的算法(字段计算器的 `$area`、线长求和、距离矩阵等)在图层的坐标上按平面量:经纬度数据得到以度为单位的数,或按赤道的比例换成米而不论纬度,北纬 60° 的面积因此大一倍,且不报错;投影到 Web 墨卡托的数据同样失真。桌面版的项目按椭球测量,所以运行脚本一律设 WGS 84 椭球,各地常用坐标系的椭球与它的差别可以忽略。

算法要运行多久无从预估,GeoEngine 不计时,由调用方决定何时中止。`qgisrun` 由模型给出 `timeout`(默认 60 秒,至少 10 秒),内核按连续多少秒没有新进度计算,到时中止任务:对模型说成时长,执行时按空闲计,持续报告进度的算法不会被误杀。QGIS 启动时什么也不报告,冷启动要十几秒,所以这个时限从算法开始执行算起,在那之前至少等两分钟。调用 GDAL 命令行的算法在无界面运行时直到结束才有输出,对它们这个时限就是整个运行时间,所以工具说明要求模型在大数据上给足。

`qgisrun` 把请求原样交给 QGIS,GeoCode 自己判断出的事实写进答复,供模型判断。只有判断确定、执行又只会白跑或悄悄得出错误的结果时,才在执行前拦下,而且都在询问之前,不让用户批准一个注定执行不了的请求。取值与必填参数由 QGIS 检查:它在算法开始前就报错,说得清楚,而导出的元数据表达不了全部约束,GeoCode 不重复这一层。拦下的有:

- 算法不在目录里(第 7.7 节):区分被剔除的与不存在的,后者给出相近的候选。
- 参数名不属于这个算法:QGIS 会忽略它而改用默认值。只差大小写的,答复指出正确的写法。
- 输入的一个图层混合了点、线、面中的两类以上,几何集合也算一类:无界面运行时 QGIS 不拆分这样的图层,图层的类型取第一个要素的,算法也不按实际内容拒绝,产出的数据是错的。答复说明在路径后加 `|geometrytype=MultiPoint`(或 `MultiLineString`、`MultiPolygon`)取其中一类;写单的类型也能取到同类的单、多两种,但图层声明为单的,与内容不符。
- 输出写成 `TEMPORARY_OUTPUT`、`memory:` 或 `/vsimem/`:矢量结果成为内存图层,`/vsimem/` 是 GDAL 的内存文件,都随任务进程消失;栅格结果留在系统的临时目录里,无人清理。
- 坐标系类参数的值 QGIS 读不出坐标系:QGIS 不报错,当作没给照常运行,重投影矢量时输出没有坐标系、坐标不变,重投影栅格时 GDAL 命令里不带目标坐标系。最常见的是不带 `PROJ:` 前缀的 PROJ 字符串,写法本身正确也读不出。答复列出 QGIS 自己对这类参数写的可接受写法,GeoCode 不另写规范。

算法、参数名与临时输出只对照目录与参数,不启动任何程序。混合几何要看数据才知道,所以只在输入是不声明单一几何类型的矢量图层、路径后又没有选定几何类型时,才由 QGIS 自带的 Python 只用 GDAL 清点要素的类型,不启动 QGIS 本身,数据旁边不留下任何东西;GDAL 读不通的数据当作不知道,照常执行,由 QGIS 说明问题,清点本身没有答复时才不执行。坐标系只有 QGIS 读得准,所以坐标系类参数填了值时,启动 QGIS 用算法读取这类参数的同一个函数判断,在任务进程同样的当前目录里,图层的路径也照样读出;这要多花启动 QGIS 的一两秒,只限这样的执行。检查本身出错时照常放行,由执行说明问题。两项检查同时进行。没填的可选输出 QGIS 不产出,不必检查。

参数里的路径按参数的类型认出:只有输入类(矢量、栅格、图层、多图层、文件、网格)与输出类参数的值可能是路径,字符串、表达式、坐标系等参数的值一律不当路径。这些参数的值除去不是文件的写法都是路径。不是文件的有 `TEMPORARY_OUTPUT`、`/vsi` 开头的 GDAL 虚拟路径,以及数据源的写法:QGIS 把冒号之前的部分当作数据源的类型(`postgis:`、`spatialite:`、`memory:` 等),GDAL 也有 `PG:` 这样的写法,所以 `|` 之前有冒号、冒号前至少两个字符的值都不当路径,网址也在其中;只有 `ogr:` 写法指向文件,只取 `dbname` 里的文件。`|` 之后是 QGIS 的选项。认出的路径交给内核解析,规则与 `read`、`write` 相同。坐标系与范围参数也接受文件路径,GDAL 的附加参数与创建选项是自由文本,多个图层组成的复合参数把路径嵌在结构里,这些都不解析,原样交给 QGIS,其中的相对路径由任务进程的当前目录同样落在会话目录。

QGIS 遇到已有的输出文件时直接覆盖,不报错:写到含多个图层的 GeoPackage 时整份文件被替换,输出就是输入时数据被清空。地理数据没有撤销,所以输出撞名时另起名字,在文件名后加 `_1`、`_2`,取最小的空号。Shapefile 的任一附属文件存在都算占用;判断不分大小写,因为 macOS 与 Windows 的文件系统不分;文件夹输出不编号,已有的文件夹本就是它的目标;以 `ogr:` 写法往已有的 GeoPackage 里加表时,表名不重复照常执行,重复则给表名编号。判断的是 QGIS 实际会写的名字:矢量输出的扩展名不在 QGIS 认得的格式里(或者没有扩展名)时,QGIS 在后面加上 `.gpkg`,检查前先照样加上;`ogr:` 写法的表名写在 `dbname` 前后都算,不写表名时 QGIS 用文件名作表名,替换同名的表,所以照文件名检查,要编号时补上表名;写法里的引号按 QGIS 的规则转义,路径里有引号也不会截断。编号在检查时定下,询问与执行的都是编号后的路径;答复不另外说明改了名,结尾列出的输出位置带着编号,模型看得出来;定下的名字到这次执行结束前不给别的执行,执行多久都一样,同时检查的两次执行不会写到同一个名字,检查过而没有执行的(如用户拒绝)一小时后放开。

答复逐段累加:开头是执行前定下的事实(QGIS 的版本、算法、按默认值运行的参数与取值),接着按收到的顺序附上 QGIS 运行中的信息、警告、报错与 GDAL 的命令行和输出,最后写怎样结束:成功时列出每个输出实际写到的路径,失败时补上 QGIS 报错点名的参数的说明,超时时写连续多久没有进度,失败、超时与崩溃都列出可能不完整的输出。调用 GDAL 命令行的算法,命令以错误码退出时 QGIS 只报告这个错误码,算法照常以完成结束;GeoEngine 收到这个报告就把执行当作失败,一个算法里任何一条命令出错都算。`gdal:ogrinfojson` 不把它的命令报告给处理框架,出错时仍以完成结束。无论怎样结束,前面的内容都保留,不另做省略。答复只陈述事实,下一步由模型判断,用户在对话里看得到同样的内容。用户在对话里停止执行时,内核直接中断工具,答复不会送到模型。

中段的内容有两个来源,都按来源与时间转达,不看文字:QGIS 处理框架的反馈按它标的级别;任务进程自己写到标准输出与标准错误的行原样转达,不分级别,PROJ 与 GDAL 直接打印的报错与警告就在这里,QGIS 的反馈里没有它们(坐标系读不出时,唯一的迹象是 PROJ 与 GDAL 打印的报错)。按时间分界:从算法开始执行起的行属于这次执行,一直转达到进程结束;之前是 QGIS 启动时的输出,只留作诊断。标准错误与标准输出之间不保证先后,所以开始的标记在两条上各发一次,各按自己的算,结果之后才到的行也算。Qt 自己的诊断(如查找字体用了多久)用 Qt 的日志开关在来源处关掉,Qt 5 与 Qt 6 在各个平台上是同一个开关,只关 Qt 内部的类别,QGIS、GDAL 与 PROJ 的消息不受影响。

### 7.5 工具与权限

QGIS 能力域给 agent 三个工具。它们是内核的内置工具,与 OpenCode 自带的工具同样注册、同样询问,直接列在模型的工具清单上,不收进 Code Mode。名字照自带工具的写法:全小写,不用下划线(下划线是命名空间的标记),也不以 `geocode` 开头,以免与壳的 `geocode_web` 等工具混淆。

| 工具 | 做什么 | 权限参照的自带工具 |
|---|---|---|
| `readgeodata` | 读一份地理数据:坐标系、范围、字段、统计与要素,栅格可以出预览图 | `read` |
| `qgisdoc` | 查本机 QGIS 的算法目录:分组、算法、帮助与搜索 | `grep`、`glob` |
| `qgisrun` | 执行一个 QGIS 算法 | 按整个工具询问,另查输出的位置与少数算法 |

权限的逻辑与自带工具一致,设置里的工具权限管理它们,与管理自带工具相同;「始终允许」同样由内核按项目保存。`readgeodata` 把数据内容交给模型,所以照 `read` 询问:工作区以外的文件先问能否访问项目外的目录,再按读取的规则判断,读取的规则同时管着这两个工具。一份数据常要分几次读(图层、翻页、预览),所以同一会话里每份数据只按规则检查一次,同时发出的调用共用这一次检查;放行之后直到内核重启都不再复查,拒绝不记住。`qgisdoc` 只读应用自己掌握的信息,与 `grep`、`glob` 一样每次检查、默认放行。

`qgisrun` 按整个工具询问,不按算法逐个设权限:QGIS 的算法有数百种,逐个授权既不合理,也容易在少数算法上出意外。它的输入不检查,读数据的是 QGIS,数据内容不经过模型;要守住的是写到哪里,以及少数后果不可逆的算法。输出按算法的参数定义认出:QGIS 的输出类参数同属一类(`QgsProcessingDestinationParameter`),不必为每个算法写规则。几乎每个算法的输出都能写进数据库或网络服务,数据库里同名的表被直接替换,不报错,这也不经过项目内外的判断,所以输出不是文件的执行与名单上的算法一样询问。后果不可逆的算法列成一份名单:清空要素、往已有的栅格里烧值、改写坐标系、执行 SQL、写入数据库、把文件上传到网址或 GPS 设备。名单只求挡住主要的危险,漏掉少数可以接受;同样直接改动输入的建索引、建金字塔这类可以撤回,不在名单上。

规则按算法标识求值,写到哪里都一样,所以按算法写的规则(如拒绝 `gdal:*`)在输出写到项目外时照样成立。规则是询问时每次执行都问;规则是允许时,只在输出落在会话目录与项目之外、输出不是文件、或算法在名单上时问。这些在规则允许时也问,否则用户放行这个工具之后名单就形同虚设:内核按规则求值之后,GeoCode 再看一次,这样的执行除非名单上的算法、项目外的目录与写入的数据库各自有过「始终允许」,仍然询问;对整个工具的「始终允许」不算在内。OpenChamber 的全部接受模式一律放行。一次执行至多一张卡片,要问的几件事合在一起;「始终允许」把其中的算法、目录与数据库分别按项目记住,数据库按连接里的服务、主机、端口与库名认,同一个库的各张表算一处,认不出库的按输出的写法本身,卡片上只写「始终允许」,不列算法标识与目录的通配写法。权限只决定问不问,不自己拦下执行,所以执行分三步:GeoEngine 先认出参数里的文件,内核解析后交回,GeoEngine 再检查数据、定下输出,不执行任何东西;内核据此询问;得到允许后,GeoEngine 按检查过的参数执行。

### 7.6 读取数据

`readgeodata` 读 GDAL 打得开的一切数据。事实由 QGIS 自带的 Python 只用 GDAL 与 numpy 取出,不启动 QGIS 本身;给模型的文字由 GeoEngine 写。文件有多个图层而没有指定时,照 QGIS 的列法列出矢量、栅格与纯属性表,由模型选一个再读,QGIS 存在 GeoPackage 里的样式表与工程表不列。读取不在数据旁边留下任何东西:不写统计缓存 `.aux.xml`,不给 GML 写 `.gfs`,GeoPackage 在 WAL 模式下也不留 `-wal` 与 `-shm`。坐标系声称是经纬度而坐标超出经纬度的范围时,坐标系报告为未知,不给面积与长度。

矢量给出几何类型、坐标系、范围、每个字段的统计与可以翻页的样本要素,几何类型照 QGIS 的叫法。不声明单一几何类型的图层(常见于 GeoJSON)逐个要素清点,几何混合时按点、线、面分开统计与取样,因为不同几何的要素往往连字段都不同。字段的统计先说多少个要素有值,再按类型给常见值、取值范围或均值;样本里的数字照写入时的样子,不带 GDAL 转换出的浮点尾巴,超长的整数也不失真。Shapefile 的编码先看文件的声明;没有声明时,能完整解成 UTF-8 就是 UTF-8,否则在 GB18030、CP950 与 Windows-1252 之间识别,对应 GeoCode 面向的中国大陆、台湾与英文世界;`.cpg` 声明 UTF-8 而文字不是时,同样识别。识别不对时由模型指定编码重读。

栅格给出尺寸、坐标系、地理参照、像元大小与每个波段的统计。统计从全部像元精确算出,不用文件里缓存的近似值,近似统计可能差得很远。取值不多或带色表、类别名的整数波段按分类数据给出每个值的占比。经纬度的像元大小同时换算成米。没有地理参照的图片答以不是地理数据。

预览图与描述分开读,模型多数时候只读描述。图片的长边缩到 2000 像素以内;拉伸照 QGIS 的默认,每个波段取第 2 到第 98 百分位;模型选一个波段以灰度显示,或三个波段合成彩色,不选时照文件标明的红绿蓝,没有标明就显示第 1 个波段;分类数据逐值上色并附图例;无数据处透明,没有有效像元时不给图。进一步的缩小、压缩与不支持图片的模型,交给内核处理图片的既有做法。

答复按内核给工具结果的上限裁剪,不让内核从中截断:依次少列常见值、样本、字段与波段,字段与波段说明省略了多少。`encoding` 用在 Shapefile 以外、`bands` 没有配 `preview` 时,答复说明没有使用。读取不设总时限,只按空闲时间计算,脚本读大文件时定时回报。

### 7.7 查阅算法

`qgisdoc` 的内容全部来自本机 QGIS 自己的算法定义,不靠 GeoCode 手写:各版本的算法与参数不同,手写的说明与示例总会在某个版本上出错。目录只含 native、qgis、gdal 三个提供方,并剔除 QGIS 标为不能在独立工具中运行的算法,它们要用 QGIS 的界面或打开的项目,`qgis_process` 同样不列它们;GeoCode 另剔除 `native:openurl`,它用系统默认的程序打开文件或网址,GeoAgent 用不着,也不该借它启动别的程序。目录与 `qgisrun` 共用这一份剔除。设置样式、改图层名这类只作用于打开的项目的算法,QGIS 没有标出,在 GeoCode 里能运行而没有效果,不另剔除。目录在第一次查询时导出,换一套 QGIS 后重新导出。四个动作:`groups` 列出分组,`algorithms` 列出一个分组里的算法,`help` 读一个算法的文档,`search` 按英文词搜索(目录是英文的,模型读英文也更准)。算法的写法可以有出入,大小写、空格与标点都不影响查找,但不猜:一个名字对应多个算法时,列出全部候选让模型选。算法文档以 `qgis_process help` 为底稿,这是 QGIS 为命令行写的帮助,只补上它没写而调用需要的三样:能否多选、字段与波段等属于哪个图层、高级参数;删去或改正在 GeoEngine 的运行方式下会失败的写法;QGIS 没给说明的就不写。每份有内容的答复开头带 QGIS 的版本,文档末尾给出对应版本的官方手册里这个算法那一节的链接(手册网站没有这个版本时转到最接近的版本),提示有疑问时用 `webfetch` 去读。

官方手册一个分组一页,大的有上百 KB,超过内核给工具结果的上限,模型只能看到开头一段;所以 GeoCode 让 `webfetch` 读 QGIS 官方手册(`docs.qgis.org`)时像浏览器跳到锚点一样,链接带锚点就只返回那一节;不带锚点或找不到这一节时只返回正文,不含网站的导航与页脚,找不到时另加说明。别的网站照 OpenCode 原样返回。

### 7.8 界面

界面沿用 OpenChamber 显示自带工具的方式,对话里的工具行、询问卡片与设置里的工具权限都用同一套组件(`qgisdoc` 与 `readgeodata` 的工具行除外,见下)。GeoCode 只补上自己的内容:彩色的图标(QGIS 的标志;`readgeodata` 在对话里用地球,它的询问卡片与设置里的规则就是读取的),随界面语言切换的标题,以及 QGIS 工具自己的卡片正文。算法的名称与描述取 QGIS 自带的翻译,随界面语言,与用户自己的中文版 QGIS 叫法一致,没有翻译的显示英文;界面不显示算法标识。

`qgisrun` 由模型写一句这一步的用途,与 `subagent` 的 `description` 相同,显示在对话与询问卡片上;没写也照常执行。它的询问卡片在上游权限面板的框架里逐行排列:标题行写明请求执行 QGIS 算法与算法的名称,其下是请求原因(模型写的用途)、算法用途(QGIS 的描述)、需要时的警示(项目外写入的目录,写入数据库或其他不是文件的位置,名单上的算法可能影响现有的数据),再是输入、参数、输出各一行,项目外与不是文件的输出用警示色,放不下的省略。输出写到项目外时也用这张卡片,不用上游访问外部目录的卡片,让用户看到是哪个算法要在那里写文件。

对话里 `qgisrun` 的一行是标志与用途,运行中再加「正在执行」与算法的名称、百分比与计时:QGIS 自身的算法逐步报告进度,调用 GDAL 命令行的算法在无界面运行时直到结束才有输出,所以计时始终在,百分比有才显示,不做估算出来的进度条。计时从得到允许、开始执行时算起,等待用户回答的时间不算在内,没有执行的调用不显示用时。结束后只留标志、用途与用时,失败、超时、崩溃与用户停止时用途变成错误色。展开后是给模型的答复的节选,保持英文,省去环境头(QGIS 的版本与算法标识),从执行前的检查信息开始;每条信息占一行,放不下的省略,运行中跟着新的信息滚动;逐个要素报告的算法信息可能成千上万,界面只拿最近的 500 条,答复里仍是全部。信息按 QGIS 标的级别显示,警告与报错用警示色、错误色加图标,不靠匹配文字,任务进程自己写的行与 GDAL 的输出同样显示;结尾是一行带符号与颜色的文字,成功时是绿色的输出路径,失败、超时、崩溃是红色的说明。用户停止时内核直接中断工具,停止的说明只在界面上显示。

`qgisdoc` 与 `readgeodata` 只是查阅,对话里不逐次列出:同一个工具相邻的调用合成一行,中间隔着文字、思考、别的工具等任何显示出来的内容才分开,跨步也照样合并。出错的调用不另外显示,由 GeoAgent 告诉用户。`readgeodata` 的一行是地球、「正在读取地理数据」或「已读取地理数据」与读了几个文件,展开后逐个列出读过的文件与图层,没读成的也算在内;预览图只给模型,不在对话里显示。`qgisdoc` 的一行只有 QGIS 的标志与「正在阅读 QGIS 文档」或「已阅读 QGIS 文档」,不能展开:模型可能还会接着读时(这一行仍在本轮末尾、本轮还在进行)显示前者,并在右侧逐个显示最近一次读的分组、算法或搜索词;读完之后不列读了什么。

`webfetch` 读 QGIS 官方手册时,展开它的卡片看到的是手册网页本身,缩小显示并停在链接所指的那一节;网页加载不了(没有网络、出错或超时)时仍显示 `webfetch` 返回的文字。别的网站的卡片照 OpenChamber 原样。

### 7.9 验收

- 配置指向 3.44 与 4.x 的官方应用包后,状态变为就绪;内置算法在两个版本上都能执行,含中文的路径与属性正确无误,路径里的引号、反斜杠与 `%`、`^`、`&`、`!` 原样到达 QGIS。
- Windows 上配置指向独立安装包或 OSGeo4W 里 3.44 与 4.x 的任一套后,状态变为就绪,内置算法能执行,含中文与 `%`、`^`、`&`、`!` 的路径正确无误;路径写成根目录、`bin`、启动脚本或桌面快捷方式启动的程序都认得出,写在一个装了多套的 OSGeo4W 根目录时报告为一个文件夹里有多套,并列出各套。
- 执行中进度持续回报;中断后任务进程与它启动的程序都结束。检查环境、列出算法、检查坐标系与执行算法,无论成败,都不在系统的临时目录留下 QGIS 启动时建的文件。
- 路径不存在、不是 QGIS、找不到 QGIS 的 Python、缺少投影数据,各自报告为对应的状态,并带有诊断;本机找到的每一套 QGIS 都列在设置里、都可以选,Windows 上包括装在 C 盘以外的,一个 OSGeo4W 里的每一套各列一项。探针某一步失败时,诊断里有 QGIS 的前缀等几项环境变量,给 GeoAgent 的提示里没有。
- 界面的 QGIS 指示灯随状态变化:改动 `qgis` 块后先变为检查中,再落到新的状态;打开新窗口或推送断线重连后,显示的仍是当前状态。
- 设置里列出本机安装的每一套 QGIS 与版本,包括改过名的;选中一套后,设置页与指示灯一起先变为检查中,再落到新的状态。原地替换 QGIS 之后,重新检查得到新的结果。
- 没有配置 QGIS 时,GeoAgent 照三个工具中任何一个的提示,自己找到 QGIS、写好配置并用 `qgisdoc` 确认就绪,找到多套时先问用户;QGIS 坏了时,用户在原处重装之后,GeoAgent 再调用一次工具就看到就绪,不用重启应用。
- `qgisdoc` 在 3.44 与 4.x 上都能列出分组、算法与文档,文档里标出能否多选与所属图层;被剔除的算法答以不可用,不说成不存在;有歧义的名字给出候选。文档末尾的链接经 `webfetch` 打开,得到的是对应版本手册里这个算法那一节。
- `readgeodata` 在 3.44 与 4.x 上读不声明编码的中文 Shapefile、混合几何的 GeoJSON、含栅格表的 WAL 模式 GeoPackage、带近似统计缓存的分类 GeoTIFF 与没有 `.xsd` 的 GML,文字与统计正确,读取前后目录里的文件逐字节不变;别的程序开着的多栅格 GeoPackage,读到的是 `-wal` 里最新的内容。
- 三个工具在设置的工具权限里都有对应的规则(`readgeodata` 归读取),把规则设为询问或拒绝,行为与自带工具相同(`readgeodata` 对同一会话里已放行的数据不再复查)。
- 规则允许 `qgisrun` 时,输出写在会话目录或项目里就直接执行,写到外面、写进数据库或算法在名单上时弹出一张卡片;规则为询问时每次一张;一次执行不出现第二张;按算法写的规则(如拒绝 `gdal:*`)在输出写到项目外时照样拒绝。两个版本的全部内置算法,输出参数都能认出,其余参数都不被当作输出。
- 按椭球测量的算法在经纬度与 Web 墨卡托的数据上量出的面积与距离,与 WGS 84 椭球上的值一致。
- 写错的参数名、混合几何的输入、`TEMPORARY_OUTPUT`、`memory:` 与 `/vsimem/` 输出、QGIS 读不出的坐标系在询问之前被拦下;PROJ 与 GDAL 在执行中直接打印的报错出现在答复与工具行里,QGIS 启动时的输出与 Qt 的诊断不出现;输出撞名时写到 `_1`,含多个图层的 GeoPackage 与输入本身不被覆盖;相对路径与 `read`、`write` 落在同一处。
- 调用 GDAL 命令行的算法,命令出错退出时 `qgisrun` 以失败结束,工具行显示失败;命令正常结束的照旧以成功结束。
- 在对话里停止 `qgisrun`,任务进程随之结束;运行中显示计时,QGIS 自身的算法同时显示百分比;QGIS 冷启动时,给最短的 `timeout` 也不被误判为超时。

## 8. Google Earth Engine

GEE 能力域让 GeoAgent 用 Google Earth Engine 做遥感计算:GeoAgent 写 Python 脚本,GeoEngine 在用户自己的 Python 里运行它,计算在 Earth Engine 的服务器上完成,结果以脚本的打印、下载到本地的影像或导出到 Google Drive 的任务交回。

与 QGIS 相反,GEE 的环境定位简单,只是一个解释器的路径;难的是本地环境、登录与项目、能否连上 Earth Engine 三类事实各自会出问题,而且出问题时该做的事各不相同。

### 8.1 执行环境

执行载体是用户自己的 Python,conda、venv 或系统的都可以,要装有三个包:earthengine-api 是 Earth Engine 的客户端,geedim 把影像分块下载成本地的 GeoTIFF,geopandas 读取本地的研究区边界。三个都是就绪的必要条件:配置时一次装齐,脚本不会跑到一半才发现缺包。geemap 不用:它的下载只是转调 geedim 已经废弃的旧接口,自己又带着 Jupyter 组件、绘图库等二十个直接依赖。GeoCode 不按版本号判断能不能用,能不能运行由检查说明。

GeoEngine 不安装软件,也不改动用户的环境(第 1 节)。缺包时,GeoAgent 在用户同意后用这个 Python 的 pip 安装;conda 环境用 conda-forge 安装,不与 pip 混装,因为 geedim 依赖的 rasterio 与 geopandas 读文件的库各自带着一份 GDAL。

### 8.2 配置与发现

`machine.json` 的 `gee` 块记两项:`python` 是解释器的路径,`project` 是开通了 Earth Engine 的 Google Cloud 项目 ID。项目每次都显式交给 Earth Engine 的初始化:用本机回调的方式登录后,凭据里不带项目,不给就无法初始化。项目 ID 只有用户自己知道,在设置里填写,或由 GeoAgent 问用户,不猜。设置只接受由英文字母、数字与连字符组成的 ID(一些旧项目带的点与冒号也接受),因为它要放进发给 Google 的请求头,混进的中文标点会让检查在发出请求前就出错;是否真有这个项目,由 Earth Engine 判断。

用哪个 Python 由用户决定。设置里列出在这台电脑上找到的、装了 earthengine-api 的 Python,用户点选一个即写入配置并重新检查,也可以指定别处的;列出时只看包的目录,不启动 Python。找的位置是 conda 自己记下的环境清单与 conda 的常见安装目录、pyenv 的各个版本、virtualenvwrapper 的环境、Homebrew、python.org 与 macOS 自带的 Python;后三者也看用户自己的 site-packages,用 `pip install --user` 装的包在那里。其余的虚拟环境位置不定,由用户在「其他位置…」里选它所在的文件夹,或者含有 `.venv`、`venv` 的项目文件夹,GeoEngine 在里面找解释器。选的是文件夹而不是解释器:macOS 的文件对话框会解析链接,虚拟环境的解释器是指向原 Python 的链接,解析后就离开了这个环境。每个 Python 显示环境名、Python 与 earthengine-api 的版本,缺 geedim 或 geopandas 的照样列出,标明缺什么。两项分开写,先填项目也可以:没有 Python 时仍是未配置,状态里带着已填的项目,好让设置页显示它。

### 8.3 登录

Earth Engine 用 Google 账号登录。凭据由 earthengine-api 写在它自己的位置,与用户在别处运行的 GEE 脚本共用一份,GeoCode 不另存。登录与 QGIS 的配置一样有两条路:设置里的登录按钮,由 GeoEngine 用配置的 Python 以本机回调的方式登录,界面打开系统浏览器,用户授权后凭据写好、随即重新检查;或由 GeoAgent 在对话里运行这个 Python 环境的 `earthengine authenticate`,效果相同。账号与授权都由用户在浏览器里完成。

设置里的登录用 earthengine-api 自己的本机回调流程,换成任意空闲的端口,因为它默认的端口可能被占用。GeoEngine 先报告要打开的地址,由界面用系统浏览器打开,浏览器没打开时也可以复制这个地址。用户在浏览器里拒绝,登录立即以失败结束,带着拒绝的原因,浏览器里也显示一句说明;earthengine-api 自己的流程这时会转去读终端输入的授权码而出错,浏览器里什么也不显示,所以由 GeoEngine 接管回调,其他请求(如浏览器要网页图标)照常回答、继续等。用户关掉页面而不回来,登录等到用户取消或 10 分钟后结束。同一时间只有一次登录,新开始的一次结束之前的那一次。关掉设置不会结束等待中的登录。

### 8.4 验证与状态

检查分两段。本地一段依次查解释器在不在、三个包能否导入、有没有凭据、有没有项目 ID,前一步不通就不往下查,也不联网。装了却导入失败与没装分开报告:前者重装同一个包解决不了。有没有凭据只看文件:earthengine-api 自己的凭据,没有时它退而使用 Google Cloud 的应用默认凭据,两者有一份就算已登录。本地齐了再做远端一段:先单独刷新一次凭据,再以配置的项目初始化,并算一个最小的结果,一次确认网络通、凭据有效、项目存在且开通了 Earth Engine、接口已启用。凭据单独刷新,是因为 earthengine-api 把刷新被拒说成没有凭据。远端的失败按异常类型与 HTTP 状态区分连不上与被拒绝,服务器自己出错或过载算连不上;被拒绝再按服务器给的原因分为凭据失效、项目不存在、没有项目的权限、接口未启用与其他,不靠匹配报错的文字,服务器的原话照附。项目没有注册 Earth Engine 时,服务器的回答里没有可以辨认的原因,归入其他,提示里给出注册的地址。

状态除了各能力域共有的未配置与配置错误,还有解释器不存在、缺包、包损坏、未登录、缺项目、检查中、连不上、被拒绝、检查超时或出错,以及就绪。检查在 GeoEngine 启动时、`gee` 块变化时、用户要求重新检查时与登录完成时进行。装包、登录、打开代理都不经过配置文件,所以看环境得出的失败在工具调用时再检查一次,与 QGIS 相同(第 7.3 节);远端一段只算一个数,用的配额可以忽略,不为它缓存结论。

环境没有就绪时,`geerun` 把 GeoEngine 给的提示交给 GeoAgent,写明它自己能做的与只能请用户做的:找 Python 与写配置、装包、发起登录,GeoAgent 都可以在用户同意后去做;项目 ID 只能问用户;连不上时,本地的环境是好的,提示只说网络有问题,要它不去重装、改配置或重新登录。安装与登录的命令按配置的 Python 给出:conda 环境用它自己的 conda 从 conda-forge 安装,登录用这个环境的 `earthengine` 命令,固定以本机回调的方式,否则装有 Google Cloud CLI 时它会改走那条路。就绪之后,运行时初始化失败或 Python 启动不了,说明环境变了(凭据被撤销、Python 被删),GeoEngine 随即重新检查,这次调用就拿到新状态的提示。

### 8.5 网络

Earth Engine 在有的地区要经代理访问。GeoCode 不探测代理,也不提供代理设置,跟随用户自己的配置:GEE 的 Python 认代理环境变量,用户在 shell 配置里设的随登录 shell 的环境到达 GeoEngine(第 5 节);没有设时,Python 自己读 macOS 的系统代理与 Windows 注册表里的代理;代理软件的 TUN 模式本来就对所有程序透明。连不上时,状态报告为连不上,附原始错误。

### 8.6 执行脚本

`geerun` 执行一段 Python 脚本,内联的代码或一个 `.py` 文件,任务进程的当前目录是会话目录。运行脚本先以配置的项目初始化 Earth Engine,再执行 GeoAgent 的脚本,脚本直接使用 `ee`。

运行时限按空闲计,不设总时长。GEE 的筛选与计算只在本地搭出计算图,真正的等待都在向服务器要结果的那一刻(取值、下载、提交导出),而这些请求都经同一个网络库发出。运行脚本守在这个出口上,有请求在等服务器回应就替脚本报活,所以服务器算得再久,脚本也不会因为没有输出被中止,GeoAgent 不必为此做任何事。一个请求等了太久不再算活着,卡死的请求因此仍会被中止。脚本既没有输出、也没有在等服务器,持续一段时间才中止。用户随时可以在对话里停止;已经提交的导出任务在服务器上照常运行。

运行中的信息分两路。等待 Earth Engine 的计时与导出的进度由 GeoCode 产生,只在对话的工具行实时显示,不交给模型;模型的答复里是脚本自己的打印与报错,以及 GeoCode 的函数打印的结局(如导出了哪个资产、等了多久)。GEE 脚本把结果交给模型的唯一途径是打印,所以打印全部交给模型,过长时在工具结果的上限之内只留结尾:失败的脚本,报错与运行的结局都在结尾。

脚本可以导入 GeoCode 的 Python 包 `geocode`,其中存取任务资产的函数见第 8.7 节;把容易写错的细节收成正确默认行为的处理函数尚待设计(第 9 节)。

### 8.7 任务与资产

GEE 的工作常要好几天、跨几个对话,耗时的结果要留在云端接着用:人自己用 Earth Engine,也是把中间结果存成资产再往下做。GeoCode 在配置的 Cloud 项目下用一个文件夹 `projects/<项目>/assets/GeoCode/` 收纳它产生的资产,其中每个文件夹是一个任务,任务的资产都在里面。用户在 Code Editor 的资产面板里一眼看得出哪些是 GeoCode 建的、每个任务里有什么。GeoCode 只管理这个文件夹,不碰项目里的其他资产,也不碰用户的其他 Cloud 项目。

每次调用 `geerun` 都要给出这一步的用途、一个任务与一段脚本,缺一项或多给都直接报错,说明怎样改,不另设别的调用方式:`task` 在已有的任务里继续,`new_task` 新建一个,脚本是内联的代码或 `.py` 文件。任务名就是文件夹名,由 GeoAgent 取,工具说明要它写出用途与日期(如 `taipei-ndvi-20261008`)。GeoCode 不改动名字,只检查它由字母、数字、`_` 与 `-` 组成,至多 30 个字符。Earth Engine 自己允许 100 个字符,但进行中的导出只在它的描述里写着目标,GeoCode 把「任务:资产:指纹」写在那里,描述至多 100 个字符,所以任务名与资产名各限 30 个。新建时同名的任务已经存在,或这个对话已经建过同名的任务,就拒绝,提示在那个任务里继续或换个名字。很多任务只做查询与统计,结果打印出来或下载到本地,并不产生资产,所以执行时不创建任何东西:任务的文件夹在第一次存资产时才建,`GeoCode` 文件夹不存在时一并建出;导出在提交时被拒或等待中失败,而这次新建的文件夹仍是空的,就删掉它。不等的导出在脚本结束后才失败,或运行在等待中被停止,文件夹可能留空,下一次运行的开头会报告失败的导出。还没有文件夹的任务只在建它的对话里存在:内核按对话记下这个对话建过的任务名,存在内核自己的数据库里(插件的键值存储),重启应用后仍在,对话删除后留下的几个名字无害,不另清理。继续一个任务,要么它在 `GeoCode` 里有文件夹(存过资产,哪个对话都能继续),要么这个对话建过它;都不是就拒绝,脚本不执行,并列出最近更新的任务。写错的名字因此不会被当成一个新任务。任务没有对应的本地目录,记录也不写进项目:脚本仍是内联的代码或 `.py` 文件,当前目录仍是会话目录。

GeoAgent 每次拿到的答复由两部分组成:开头是 GeoCode 在执行脚本之前、同一次运行里读出的任务空间,其后是脚本的打印与报错。空间写明这个任务是新建还是继续、已有的资产(类型、波段、保存时间、标题与说明)、进行中的导出与资产上次保存之后失败的导出,以及最近更新的另外三个任务与其他任务的总数。GeoAgent 不必另查就知道手头有什么、哪些还在导出、可以跨任务取用哪些;更早的任务由用户提起。读这些只用 Earth Engine 的元数据,不做计算,不耗用户的计算配额。平常一个任务的资产与说明不过十几 KB;过长的说明截短,空间至多占答复上限的一半,超出时只省略末尾的资产行,其余留给脚本的打印。空间里只有任务与资产的名字,不写它们在 Earth Engine 里的完整路径:GeoAgent 按名字经 GeoCode 的函数存取,完整路径只用于用户给出的 `GeoCode` 以外的资产。

脚本经 GeoCode 的模块存取资产(`import geocode as gc`),交给 GeoAgent 的只有两个函数,任务与资产的名字已在答复的开头,不另设函数去查。`gc.save` 把影像或表格存进本任务,写上 `title` 与 `description`,用户在 Code Editor 的资产详情里看得到;另记所属的任务、保存时间与内容的指纹,换了对话的 GeoAgent 读这些就知道每个资产是什么。指纹由计算图、网格,以及计算图读取的 `GeoCode` 资产各自的更新时间算出;公开数据集不算在内,它们几乎每天入库新影像,算进来的话,早已完成的合成也会显得变了。文件夹不能带属性,所以说明都在资产上。GEE 的计算图在导出之前从没被完整算过,导出就是第一次把它算出来,要排队,也要时间。`gc.save` 默认等导出完成,再返回从资产读出的数据:不等的话,下游的每个请求都会从源数据把上游再算一遍,与导出重复,等待只花时间,不花配额。同名而指纹相同的资产直接沿用,不再导出,脚本重跑时这一行几乎不花什么;内容变了就替换旧的,并打印一句警告;同一个资产已有导出在进行时,内容相同就等它,不同就取消它。存完就结束的最终结果可以不等。`gc.load` 按名字读:「资产」是本任务的,「任务/资产」是其他任务的,`projects/` 开头的是用户给的完整路径。`GeoCode` 以外的资产由用户告诉 GeoAgent 完整的路径,GeoAgent 不去浏览。GeoCode 的函数只往本任务的文件夹里写资产;GeoAgent 不主动删除任务与资产:删除在云端,不可逆,只在用户明确要求时做。

存中间结果是用第一次运行的时间换之后每次的速度与配额:导出走批处理,要排队,又比在线计算慢,第一次运行因此更慢;之后的运行直接读算好的像元,不再重算上游。所以工具说明要 GeoAgent 先探索、不存,合成经检查确认无误、下游还要反复用到时再存一次,通常就在合成之后,用户要留下的结果也存;一次性的查看、便宜的步骤、只要粗略或局部结果的下游与还在调整的步骤不存;在线计算超时或超出内存时,先存上游再往下算。GeoCode 不做结果缓存:引用资产的请求只写路径,资产被替换以后同样的请求会拿到旧的结果,不报错,只是结果错。`gc.save` 判断内容变没变时也会遇到同样的事,所以指纹里算进了读取的 `GeoCode` 资产的更新时间。

### 8.8 工具与权限

GEE 能力域给 agent 一个工具 `geerun`,与 QGIS 的工具同样是内核的内置工具,名字照自带工具的写法。它执行的是任意 Python,能读写文件、访问网络,风险与 `shell` 相同,所以权限照 `shell` 处理,设置的工具权限里单独有一行。默认问不问也与 `shell` 相同:agent 本来就能经 `shell` 执行任何 Python,只问 `geerun` 守不住什么,GEE 的工作又要反复执行小段脚本,每次询问徒增打扰。两者并不相连:GeoCode 改动 GeoAgent 对 `shell` 的默认规则时(与内核的装配一起),对 `geerun` 同样改动;用户自己给 `shell` 设的规则不管 `geerun`,它在设置里有自己的一行。规则只按整个工具,「始终允许」也按整个工具记住:脚本每次不同,按内容或文件记住没有意义。询问之前先查环境是否就绪、项目里的脚本文件在不在,不让用户批准一个注定执行不了的请求;项目外的文件等用户允许了它的目录再看。任务也是一样:参数齐不齐、名字合不合规、这个对话是否建过同名的任务,询问之前就查;云端是否已有同名的任务、要继续的任务在不在,执行时才查。与 `qgisrun` 一样,模型写一句这一步的用途,显示在对话与询问卡片上。脚本文件在项目外时,先出现的是访问外部目录的询问,与 `qgisrun` 不同,不合进同一张卡片:要两张卡片接连出现,得用户把规则改成询问,且脚本文件在项目外,很少见。

### 8.9 界面

标题栏在 QGIS 旁边多一个 GEE 的指示灯,图标是 Earth Engine 的标志,颜色归类与 QGIS 相同(第 3.3 节),只是未登录与缺项目也归入灰色:它们和未配置一样是设置还没走完,不是故障。被拒绝时,指示灯直接显示服务器给的原因(如接口未启用),浮层里的错误是服务器的原话。「地理环境」页多一行 Google Earth Engine,就绪时显示项目与版本。详情按配置的先后分三步:Python 环境、Google 账号、Cloud 项目,每步带编号与完成标记;失败落在哪一步,那一步标红,网络类的失败不归任何一步,只显示在页头下的错误里。Python 一步列出找到的 Python 与「其他位置…」;账号一步在未登录与登录失效时显示醒目的登录按钮,已登录时只是一个不起眼的重新登录;项目一步是输入框与保存,旁边是到 Code Editor 的链接。页头有重新检查。详情页的标题下不放只在某些状态才有的一行(QGIS 的详情页也是),免得状态一变整页跟着跳动;就绪时的版本在列表页与指示灯里看。对话里 `geerun` 一次调用一行:标志、用途与任务,运行中加计时、「正在等待 Earth Engine」与导出的进度,展开后是脚本的输出。

询问卡片的标题行是 Earth Engine 的标志与「请求执行 Earth Engine 脚本」,其下是请求原因,再是脚本的前四行,其余只写省略了几行:脚本常常很长,在卡片上看全文不现实。执行文件时只写文件的路径,不显示内容:询问之后文件仍可能被改动。卡片不加警示:任意的 Python 靠扫描认不准,认不准的警示反而让人以为安全。

### 8.10 验收

- 配置指向装齐三个包的 Python、填好项目并登录之后,状态变为就绪;macOS 与 Windows 都是。
- 解释器不存在、缺包、包损坏、未登录、缺项目、连不上、凭据失效、项目不存在、没有项目的权限、接口未启用,各自报告为对应的状态,带有诊断;项目没有注册时报告为被拒绝,附服务器的原话与注册的地址;在终端里装包或登录之后,GeoAgent 再调用一次 `geerun` 就看到新的状态,不用重启应用。
- 设置里能登录:打开系统浏览器,授权后状态变为就绪;在浏览器里拒绝,登录立即以失败结束;关掉页面,可以在设置里取消,否则 10 分钟后结束。GeoAgent 在对话里登录同样可行。
- 设置里列出本机装了 earthengine-api 的 Python;选中一个后,设置页与指示灯一起先变为检查中,再落到新的状态。
- 没有配置时,GeoAgent 照提示自己找到 Python、装包、写好配置,登录与项目 ID 请用户完成,最后确认就绪。
- 用代理环境变量、macOS 的系统代理或 TUN 模式访问 Earth Engine 都能就绪;断网时报告连不上,而不是凭据或项目的问题。
- 一次运行超过十分钟的计算或下载能完整跑完,期间没有任何打印也不被中止;既没有输出、也没有在等服务器的脚本在空闲时限后被中止;用户停止时任务进程随之结束。
- 等待的计时与导出的进度出现在工具行,不出现在给模型的答复里;脚本的打印与报错完整地交给模型。
- 含中文的路径与打印正确无误。
- 调用缺了用途、任务或脚本,或者多给,都直接报错并说明怎样改;同名的任务已在或这个对话建过时新建被拒绝;继续一个既没有文件夹、也不是这个对话建的任务被拒绝,并列出最近的任务;对话里建过、没存资产的任务,重启应用后仍能继续;名字不合规则时拒绝。只查询、不存资产的任务在用户的 GEE 里不留任何东西;第一次存资产时 `GeoCode` 与任务的文件夹自动建出,导出在提交时被拒,或等待中的导出失败,都不留空文件夹。
- 答复开头写明任务、它的资产与说明、进行中与失败的导出、最近更新的另外三个任务,不耗计算配额,`GeoCode` 以外的资产不出现在其中;资产再多,答复也不超过内核的上限,脚本的报错仍在结尾。
- 存进任务的资产在 Code Editor 里看得到标题与说明;同样的内容重跑不再导出,内容变了就替换,读取的 `GeoCode` 资产被替换过也算内容变了;换一个对话指明同一个任务,GeoAgent 读到之前的资产并接着用。
